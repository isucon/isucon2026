# DB構成と既存4台の役割の比較

独立DBとレプリケーションの優劣は、まだ確定していない。地域内で読める構成を維持しながら、まず更新が複製より先行する量を抑えて比較する。その結果でも画像の転送が支配的なら、画像とメタデータの分割を次の候補とする。

新しいAWSリソースは作成せず、秘密情報は既存VM間へscpで共有する。Asiaのdb1も役割を固定せず、アプリ処理や画像配信を担う候補に含める。ルーターの遅延・帯域制限と地域の判定は維持する。

## 計測から分かったこと

| 実行 | 構成・変更 | 結果 |
| --- | --- | ---: |
| [13:04 UTC](results/20261027T130427Z-team10/result.json) | 欧州・米州に物理レプリカを配置し、更新SQLはAsiaへ送る | 8,742 PASS |
| [14:03 UTC](results/20261027T140308Z-team10/result.json) | 更新HTTPをAsiaのワーカーへ転送し、SQLの地域間往復を減らす | 45,790 PASS |
| [16:50 UTC](results/20261027T165020Z-team10/result.json) | 通知・権限判定などの改善後、行ロックを解放してから応答時に両レプリカの反映を待つ | 50,018 PASS |
| [17:10 UTC](results/20261027T171057Z-team10/result.json) | 画像保存時のTOAST圧縮試行を省く | 38,237 PASS |

各行には途中のアプリ改善も含まれるため、この表だけでDB方式の差を切り分けることはできない。最高点の版と最新の版も異なる。

17:10 UTCの走行では、プライマリの平均CPU使用率は約44%、Asiaアプリは約20%だった。一方、欧州レプリカの未反映WALは最大198MiB、応答前の同期反映待ちは最大約9.9秒になった。画像の圧縮試行を省くとCPU負荷は下がったが、更新を複製へ渡す速度との差が大きくなった。CPUの削減だけではスコアは上がらなかった。

## 候補

| 案 | 期待する効果 | 比較で確認すること |
| --- | --- | --- |
| 現在の物理レプリカを保ち、更新量と応答前の確認を調整 | 地域内の読み取りと既存のトランザクションを維持し、WALの滞留を抑える | 更新要求の待ち時間、未反映WAL、投稿期間の開始遅延、スコア。実行枠を狭めすぎると投稿を待たせる |
| 地域ごとに独立したDBへ分割 | 自地域の投稿やセッションの書き込みを地域内で完了できる可能性がある | ユーザー名の一意性、地域変更、友達・ブロック、他地域のフィード、初期化をどう整合させるか。遠隔参照が増えるAPIもある |
| 画像のDBとメタデータのDBを分割 | メタデータのレプリカへJPEG本体を送る必要を減らす。db1を画像保存・配信とアプリ処理に使い、app1をメタデータDBにする配置も可能 | キャッシュにない画像とZIP出力の地域間転送、画像と参照の公開順序、初期化、途中失敗時の復旧。画像は引き続きPostgreSQLに保存する |
| db1へ更新ワーカーを移す、またはapp1とDBの役割を入れ替える | 既存4台のCPU・I/O負荷を再配分できる | 同じAsia内での移動だけでは地域間の複製量は減らない。計測時のdb1は6,000 IOPS、app1は3,000 IOPSであり、単純な入れ替えが有利とは限らない |

独立DBを試す場合は、最初に読み書きの担当を表で確定し、ローカル環境で更新・削除・地域変更・初期化の結合テストを通す。切り替え時は更新を止め、データの一致を確認してから新しい書き込み先を有効にする。失敗時に最新データを失わず戻す手順も用意する。

成功した更新の直後に結果が見えること、全地域で整合した初期状態へ戻ること、初期の履歴・画像を維持することは、[アプリケーションマニュアル](../docs/application-manual.md#データの反映)と[競技マニュアル](../docs/manual.md)に合わせる。古い設計検討資料の「地域内だけのread-your-writes」を根拠に、現行の反映要件を緩めない。

独立DBへの移行とdb1の役割変更は、まだ実施していない。まず現在の構成で残る待ち時間を計測し、その結果に基づいて比較対象を選ぶ。
