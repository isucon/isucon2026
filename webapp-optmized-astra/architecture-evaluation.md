# DB構成と既存4台の役割の比較

独立DBとレプリケーションの優劣は、まだ確定していない。更新量の制御、検索、画像探索、キャッシュを改善した後、新規投稿の画像だけを独立したDBに保存する版を比較する。既存の画像とメタデータは現在の物理レプリケーション構成に残す。

新しいAWSリソースは作成せず、秘密情報は既存VM間へscpで共有する。Asiaのdb1も役割を固定せず、アプリ処理や画像配信を担う候補に含める。ルーターの遅延・帯域制限と地域の判定は維持する。

## 候補

| 案 | 期待する効果 | 比較で確認すること |
| --- | --- | --- |
| 現在の物理レプリカを保ち、更新量と応答前の確認を調整 | 地域内の読み取りと既存のトランザクションを維持し、WALの滞留を抑える | 更新要求の待ち時間、未反映WAL、投稿期間の開始遅延、スコア。実行枠を狭めすぎると投稿を待たせる |
| 地域ごとに独立したDBへ分割 | 自地域の投稿やセッションの書き込みを地域内で完了できる可能性がある | ユーザー名の一意性、地域変更、友達・ブロック、他地域のフィード、初期化をどう整合させるか。遠隔参照が増えるAPIもある |
| 画像のDBとメタデータのDBを分割 | メタデータのレプリカへJPEG本体を送る必要を減らす。db1を画像保存・配信とアプリ処理に使い、app1をメタデータDBにする配置も可能 | キャッシュにない画像とZIP出力の地域間転送、画像と参照の公開順序、初期化、途中失敗時の復旧。画像は引き続きPostgreSQLに保存する |
| db1へ更新ワーカーを移す、またはapp1とDBの役割を入れ替える | 既存4台のCPU・I/O負荷を再配分できる | 同じAsia内での移動だけでは地域間の複製量は減らない。計測時のdb1は6,000 IOPS、app1は3,000 IOPSであり、単純な入れ替えが有利とは限らない |

独立DBを試す場合は、最初に読み書きの担当を表で確定し、ローカル環境で更新・削除・地域変更・初期化の結合テストを通す。切り替え時は更新を止め、データの一致を確認してから新しい書き込み先を有効にする。失敗時に最新データを失わず戻す手順も用意する。

成功した更新の直後に結果が見えること、全地域で整合した初期状態へ戻ること、初期の履歴・画像を維持することは、[アプリケーションマニュアル](../docs/application-manual.md#データの反映)と[競技マニュアル](../docs/manual.md)に合わせる。古い設計検討資料の「地域内だけのread-your-writes」を根拠に、現行の反映要件を緩めない。

db1の役割変更はまだ実施していない。画像DBの試作では、空きメモリ約3GiB、空きディスク約33GiBを確認したAsiaアプリVMを使う。db1は既存のメタデータと履歴画像を維持し、欧州・米州のレプリカも継続する。

## 独立した画像DBの比較手順

`imageStore.enabled`で画像DBへの接続、`imageStore.writesEnabled`で新規投稿画像の保存先を切り替える。既存のAsiaアプリVMにPostgreSQL 16の`astra-assets`クラスタをポート5433で作成する。元の`16/main`は変更しない。AWSリソースは作成せず、接続情報は既存の非公開`env.sh`を使う。構成はPulumiのruntime出力とSSH/SCPの適用スクリプトで管理する。

画像のバイト列を独立DBへ永続化してから、メタデータ側の同じトランザクションで投稿・画像行・保存先参照を公開する。メタデータの公開に失敗した画像は外部から参照できない。画像DBのアプリ用権限はSELECTとINSERTだけで、保存済みバイト列は変更しない。プロフィール画像とリアルモジの画像は、まず従来の保存先を維持する。

画像取得時の現在の利用者状態、鍵、削除状態の確認は維持する。キャッシュにない新規投稿画像は、既存の帯域・遅延制限を通って画像DBから取得する。ZIP出力では取得を最大8件並行させ、SQLの順序と画像内容を保つ。初期化では公開参照を削除し、画像DBの孤立行は残す。公開中の書き込みと削除が競合しないよう、孤立行の削除はベンチ停止中に書き込みを止めた状態でのみ行う。比較中は空きディスクを確認する。

適用は画像DB起動、参照列追加、読み取り対応アプリの配備、新規書き込み有効化の順で行う。まず`writesEnabled=false`で従来保存先のベンチを取り、同じコードとseedで`true`の結果を比較する。切り戻しでは新規書き込みだけを無効にし、既存の公開参照がある間は画像DBへの接続を維持する。対応前の古いバイナリへ戻す場合は、先に初期化するか、外部保存のバイト列を元のDBへ戻す必要がある。

ローカルでは独立したPostgreSQLクラスタと物理レプリカを使い、公開前の不可視性、公開途中の失敗によるロールバック、重複投稿、画像削除・鍵変更、レプリカからの参照、ZIPの内容、初期化後の参照削除を検証した。実機でどちらが高得点になるかは、比較結果が出るまで未確定である。
