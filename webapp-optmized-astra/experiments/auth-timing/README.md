# 登録・ログインの待ち時間の計測

反復ベンチで登録・ログインのタイムアウトが発生したため、authTimingEnabledで一時的な診断を有効にする。250ms以上のPOST /api/auth/registerとPOST /api/auth/loginだけ、受付枠の待ち時間、next.runの処理時間、レプリカ反映待ちを記録する。next.runには本文取得、IP制限などのmiddleware、SQL処理を含む。HTTPの到着前や応答の転送時間は含まない。

診断の項目は時刻、register/login、HTTPステータス、3段階の所要時間だけ。ユーザー名、鍵、トークン、本文は記録しない。auth-timing-stats.pyもこれらの項目だけをVMから取得する。通常のログレベルと失敗ログイン監視は変えず、調査後はフラグで無効にする。

計測用の変更であり、スコア向上の変更とは扱わない。実機ベンチと読み取り専用のpg_stat_activityサンプルを照合して原因を絞る。

初回の計測ベンチは188,002点・PASS。250ms以上の登録・ログインを3,889件採取した。Asiaの通常アプリでは、遅い登録868件の中央値が受付892ms、処理74ms、複製待ち178ms。遅いログイン2,452件は受付1,134ms、処理85ms、複製待ち170msだった。writerの遅い登録166件は受付118ms、処理14ms、複製待ち143msで、通常アプリ側の受付待ちが特に大きい。これらは250ms以上の要求だけの統計で、全要求の中央値ではない。

DBの180秒サンプルには初期化も含む。初期化のVACUUMを除く長いSQLは約0.4秒で、受付待ちの数秒とは差がある。小さな書き込み128枠を関係更新などと共有しているため、次は登録・ログインに独立した受付枠を設け、一般更新・画像・管理操作の既存枠と分けて比較する。レプリカ反映を待つ条件は維持する。

受付枠の分離2案は全体スコアを改善せず、元の共有128枠へ戻した。診断フラグはfalseへ戻している。処理段階の計測と採取ツールは、必要な場合に再度有効化できる。
