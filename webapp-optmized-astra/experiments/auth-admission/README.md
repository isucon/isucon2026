# 登録・ログインの受付枠を独立させる候補

認証の計測で、Asiaの遅い登録の受付待ち中央値892ms、ログイン1,134msを確認した。小さい一般更新128枠を登録・ログインと関係更新などが共有しているため、登録・ログインに独立した128枠を設ける。

対象はPOST /api/auth/registerとPOST /api/auth/loginで、本文サイズが判明していて64KiB以下の場合だけ。大きい本文やサイズ不明の本文は既存の重み付き枠を使う。画像64枠、一般更新128枠、管理更新4枠、SQL接続16、レプリカ確認8枠は維持する。認証の枠も応答前のレプリカ反映が完了するまで保持する。

受付待ちの改善がSQL接続待ちや他のAPIの遅延へ移る可能性があるため、同じ診断を有効にして実機比較する。診断用ログは調査後に無効にする。

認証128・一般128の実機比較は166,616点・PASSで、計測あり対照188,002点を下回った。全要求のAsia登録中央値は560→360ms、p90は2,003→850msへ短縮したが、投稿中央値は1,352→2,942msへ延びた。遅い認証だけの統計では、Asia登録の受付中央値892→185ms、処理74→198ms、複製待ち178→136ms。ログインは受付1,134→0ms、処理85→163msだった。受付待ちは減ったが処理側の待ちが増えており、追加した同時実行枠が他処理を圧迫した可能性がある。

次は小さい更新の合計枠数を元の128に戻し、認証64・一般64へ分ける。登録・ログインの取り分を確保しつつ、DBへ進む要求数を増やさない比較とする。
