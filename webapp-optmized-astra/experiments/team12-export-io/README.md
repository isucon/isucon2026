## ZIP直接出力

完成ZIP全体をVecへ書いてから応答する方式を、zip 9.1.1のnew_streamでHTTP本文へ送る方式へ変更する。64KiBのチャンクを最大2個キューに保持し、受信側が遅ければZIP生成も待つ。切断すると書き込みを終了する。ZIP生成・出力中も既存の同時実行2枠を保持する。

Go版と同様、SQLと画像読み取りは成功応答を始める前に完了させる。画像が欠けている場合は従来どおり500を返す。画像全体を準備するメモリは残るため、プロセス全体が一定メモリになる変更ではない。画像の順序・バイト列・posts.json・URL署名・公開状態の判定は維持する。

単体テスト4件が成功。ZIPの内容、空の履歴、遅い受信側、切断、SQLの区画検索を確認した。実PostgreSQLを使う独立画像ストアの統合テストも成功し、画像欠落時にZIPを200で返さないこと、削除・鍵変更・地域別保存を確認した。既存のフィードテストでClippyのsort_by警告が出たため、同じ降順のsort_by_keyへ置き換えた。

## 所有者順パックとまとめ読み

既存のpack参照を使って初期画像を所有者・画像ID・時刻順に書き直す`--repack`を追加した。画像のバイト列は再エンコードしない。既存の移行手順で全書き込み元を停止し、3地域の新しいファイルと参照一覧のハッシュが一致してから、主DBで参照を一括更新する。元の参照・所有者・行の版が一致しなければ更新全体を取り消す。旧ファイルが残っている間は`--restore-layout ARCHIVE_ID`で元の参照へ戻せる。

ZIPのSQLは先に読み終え、その時点で認められた画像参照だけをまとめて読む。同じパックを1回開き、オフセット順に並べて、隙間64KiB以内・合計16MiB以内の範囲を結合する。大きい単独画像は既存の32MiB上限内で個別に読む。返却順は元の投稿順を維持し、共有バッファのスライスで本文の再コピーを避ける。地域別ファイルや旧画像DBへのフォールバックは同時実行8件のまま残す。

まとめ読みの単体テストは順序・重複・隙間・別パック・切り詰め・欠損を確認。実DBの移行テストは所有者順への配置変更、同一本文、元データ変更時の公開拒否、繰り返し公開の拒否、元の参照への復帰を確認した。実DBの画像API・ZIP統合テストも成功した。

配置替えは小さい区画で公開・読み取り・復帰を確認してから進める。参照されない旧パックは、既存の停止・参照検査付きGCで回収する。配置替えとまとめ読みの初回は183,352点PASS。

## Team 12での配置替えと再起動確認

小区画30画像で配置替えと元の参照への復帰を確認した後、全25区画を所有者順へ移行した。初期画像1,826,950枚・14,054,519,155バイトは移行前と一致し、SQL内の画像本体はゼロ。全区画で3地域のファイル全体と参照一覧のハッシュが一致した。区画ごとの移行前後で計375画像をHTTP取得し、本文とJPEG形式が一致した。検証記録は区画ごとにコミット・Pushした。

旧パックは参照検査付きGCで回収済み。GC後、3地域のアプリ・画像DB・Nginxを再起動し、計18画像の本文とJPEG形式、実行バイナリ、設定、メタデータレプリカを確認した。旧パックの回収後は元の物理配置への復帰はできないが、ZIP出力のみの旧バイナリでも新しいパック参照を読める。

配置の確認として、初期ユーザーID順の50人から取得した5,929投稿画像を調べた。同一所有者・同一パック内で64KiB以内に隣接する箇所は5,304。このサンプルの最大範囲は864,751バイトで16MiB上限内のため、未キャッシュ画像を個別に読む5,929範囲を625範囲へ結合できる。これは参照配置から求めた範囲数であり、実測I/O回数やスコアの改善率ではない。冒頭の3,900画像とは抽出条件が異なる。

[全体照合](../../results/owner-layout-complete-team12/coverage.json)と[再起動検証](../../results/owner-layout-complete-team12/restart-validation.txt)を保存した。配置替え後の初回は183,352点PASS。無再起動の反復で確認する。
