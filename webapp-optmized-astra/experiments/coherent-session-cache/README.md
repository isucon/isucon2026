# リージョン間で無効化を確認する認証キャッシュ

Go optimizedのhotStateは、ユーザー・セッション・関係・投稿などを各リージョンに保持し、更新を応答前に配布する。Rust側の履歴SQL改善だけではこの差を埋められないため、まず読み取りリクエストの認証を共有DBプールから切り離す候補を検証する。

GET/HEADの有効なセッションだけを最大8,192件保持する。書き込みの認証とキャッシュミスは毎回SQLで確認する。認証情報はDBで照合した値だけを保存し、未知・無効なトークンはキャッシュしない。SQL開始前から5秒の期限を持ち、ヒット時には延長しない。

ログインによるセッション置換、ログアウト、退会、ユーザー更新、初期化では、コミット後のWAL位置と無効化対象を既存3アプリの内部HTTP経路へ通知する。各受信側はそのWAL位置まで自分のDBが再生したことを確認してから無効化する。通常のnative write fenceと通知を並行させ、両方の完了まで応答を返さない。内部エンドポイントは既知VMのソケットIPと、既存DBパスワードから導出した共有トークンで認証する。秘密値は設定ファイル・ログ・リポジトリへ追加しない。

キャッシュには世代番号を持たせ、無効化前に始まったSQLが後から古い結果を挿入することを防ぐ。通知失敗時は成功応答にせず、レプリカ反映の完了後さらに5秒待ち、届かなかった相手でも古いキャッシュが失効してから503を返す。停止・再起動でキャッシュが消えること自体は正しさに影響しない。初期化では全キャッシュを無効化する。

WAL位置の取得と受信側の再生確認にはそれぞれ最大2接続の専用プールを使う。認証用キャッシュを失効させる処理が、認証の接続待ちの後ろで止まることを避ける。新しいAWSリソースは作らず、runtimeのsessionCacheEnabledをPulumiと配備スクリプトで管理する。falseへ戻すと従来の毎回認証SQLと履歴への接続引き継ぎに戻る。SQLスキーマ変更はない。

検証は実DBを使う5テスト。1接続のプールを占有した状態でもキャッシュされたGETが成功し、POSTはSQL接続を要求すること、無効化・地域変更・退会の反映、期限の非延長、古いSQL結果の挿入拒否、内部経路の認証を確認した。実レプリカの再生停止中は無効化が完了せず、再開後に完了する。3つのHTTP受信先のうち1つを遅延させ、書き込み応答が全ACKを待つことも検証した。通知先停止時の503と期限切れ待ちも確認した。既存の履歴接続・ログインテスト、ライブラリテスト、Clippyも成功している。

測定前の通常設定は176,708点、再起動なし反復169,952点（ともにPASS）。本候補の総合性能は実機測定で判断する。10秒ごとにヒット数・ミス数・無効化数・エントリー数だけを記録し、ユーザーID・トークン・本文は記録しない。

初回35854c6、20261030T075453Z-team12は160,884点でPASS。総合改善は確認できなかった。ヒット・ミス・無効化の累計をinitial-counters.jsonに保存。全体世代の変更で無関係なユーザーのSQL結果も挿入を拒否しており、負荷時にキャッシュへ入らない問題を改善する。

次の候補では、挿入を拒否する世代番号をユーザーごとに管理する。無関係なユーザーの更新は待機中のSQL結果を破棄しない。本人の無効化と初期化は従来どおり古い結果を拒否する。世代管理は最大65,536ユーザーに制限し、上限時は全体を無効化して安全にリセットする。期限や配信方式は変更しない。対象本人・別ユーザー・初期化の遅延挿入テストと実DBの5テストが成功。初回の最終ヒット率はAsia 29.5%、Europe 42.0%、America 72.6%だった。
