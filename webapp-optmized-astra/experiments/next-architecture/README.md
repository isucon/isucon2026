# 残る差と、レプリケーション・独立DB・Asia DB VMの役割

2026-10-30時点の判断。Team 12では今回の利用者別export画像配置が200,330点PASS、同構成の再起動なし反復は188,075点。Go optimizedの既存約30〜33万点は別チーム・別時刻の記録で、配備SHAと全条件が一致する対照測定ではない。差が解消したとは判断していない。初期exportメタデータとの最新比較は測定中で、結果はowner-export-layout/に追記する。

## 今回わかったこと

- 画像本体をSQLへ戻す必要はない。既存ファイルのまま、初期投稿61.9万画像を利用者順に並べることで、全対象のまとめ読みを64,309範囲から5,000範囲へ減らした。実機のAsia読み取り量も63.3→37.6 MB/sとなった。ただし総合点の安定した増加はまだ確認できていない。
- 単一画像とexportを同じ新配置へ送る候補は189,772点で撤回した。配置変更にはOSキャッシュと読み取り方の相互作用があり、連続配置だけで全APIが速くなるとは限らない。
- 認証キャッシュ、短い読み取り用の接続分離、通常フィードのUS転送、Nginx応答バッファ無効は一部の遅延を改善しても総合点を上げなかった。US転送ではUS平均CPUが30.8→40.7%となり、推薦を含むフィードの遅延が増えた。
- 現行Rustは初期履歴や画像メタデータを保持しても、現在のユーザー状態・世代・変更記録をSQLで確認する。Go optimizedはhotstate/history_storeを組み合わせ、より多くの読み取りをアプリ内で完了させる。次の大きな改善には、このSQL依存を減らす変更と、その整合性検証が必要。

## 現行レプリケーションを残す案

当面の候補は、共有primaryと物理レプリカを維持したまま、ユーザー状態・画像の有効性・初期履歴の変更をアプリ内へ反映する範囲を広げること。永続化・再起動・初期化の基盤を維持できる。既存のprimary authorityにより、Asia利用者のログイン・ログアウトは既に地域間反映待ちを省いている。

アプリのキャッシュはTTLだけで成立させず、API応答前に関係するノードが変更を適用したことを確認する必要がある。ログアウト、鍵・表示名・地域変更、退会、投稿削除、コメント、リアクション、ブロック、初期化を対象にし、応答後の他地域読み取りもテストする。今回のAsia認証キャッシュの世代番号と無効化ACKのテストは、この検証の一部として再利用できる。ただし、そのキャッシュ単独での総合改善はなかった。

## 地域ごとに独立したDBを置く案

既存VM内で論理DBを分ける構成は、新規AWSリソースなしでも検討できる。地域内の書き込み・読み取りを分担できる可能性がある一方、友人関係・ブロック・地域移動・退会など複数所有者にまたがる状態について、正本の所在と更新完了の条件をアプリが管理する必要がある。

比較するなら、最初は利用者の不変な所属を決め、地域移動でも正本を移さず、他地域が必要とする状態だけを配信する方式を小さく実装する。複数DBへの更新の途中失敗、再送、初期化、再起動を含めて整合性テストを先に作り、現行の物理レプリケーションと同じTeam 12・同じベンチで比較する。現段階で独立DBの方が速いとは判断しない。PostgreSQLからMySQLへの変更だけで、アプリのSQL回数や地域間の確認が減る根拠も得ていない。

## Asia DB VMを別用途に使う案

DB専用の役割は固定条件ではない。ただし現状の主DBは代表走行で平均約67%の2 CPUを使い、Asiaアプリも約64%を使っている。両者を同じ2 CPU VMへ単純にまとめる案は、現在の負荷実績では余裕がない。主DBを海外へ移す案も、Asiaの認証・更新に地域間通信を追加するため、そのまま採用しない。

読み取りのSQL依存を減らした後なら、このVMを画像配信・export生成・アプリの処理分担に使う余地がある。現在このVMの空き容量は約44 GiBあり、検証済みの利用者別パック約10 GBの置き場にはなる。ただし配信の追加ホップ、DBとのCPU・I/O競合、同時実行数を測る必要がある。既存archive-peerの単一画像読み取りをそのまま戻すのではなく、今回の利用者別連続範囲をまとめて転送する候補を別途測定する。

いずれも、既存Team 12 VMだけを使用する。秘密値はSCPで配布し、新規AWSリソースやSecrets Managerは使わない。実機設定はPulumi astraと配備・照合手順へ反映し、測定していない構成を最終配置として残さない。
