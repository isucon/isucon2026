# 友達の友達フィードの実行計画

検索改善後はフィードのCPU負荷が目立った。友達109人の実データでは、generic planが
友達の友達を136人と推定したが、実際は1,610人だった。3つの投稿期間で投稿の索引を
4,830回引き、約26msかかっていた。候補集合が128人を超える場合だけ、投稿期間の行へ
ハッシュによる所属判定を適用する案を比較する。少人数では従来の索引探索を残す。

候補数の判定と両分岐は単一SQLの同じスナップショットで行う。分岐は排他的であり、
各投稿期間から権限判定済みの上位51件だけを取得して、全体の順序で51件に絞る。
公開状態、ブロック、投稿済み条件、ページ送りの意味は変えない。

最初のgeneric plan比較では、友達109人のケースが31.4msから8.2msへ短縮した。
この測定中はAsiaレプリカの準備も進んでいたため、負荷のない状態で再比較した。
再比較時のデータでは最大の友達数が29人で、3.20msから3.58msへ微増した。
友達0〜1人のケースも約0.2ms増える。準備直後のplanning時間は約1.4ms増えるため、
prepared statementのキャッシュを維持する。実機スコアは未測定で、採用は未決定。

`first-measurement.txt`と`after-backup-measurements.json`に結果を保存した。
固定したSQLを既存の実データで再比較するには、ベンチ停止中に以下を実行する。
読み取り専用トランザクションと5秒の制限を使い、データは変更しない。

```sh
python3 webapp-optmized-astra/experiments/feed-window-plan/compare.py
```

`feed_query_test`は独立した従来ロジックと、全フィードの権限・ページ送りを比較する。
候補ではgeneric planを強制し、128人を超える関係集合と複数ページ、関係の削除後に
少人数へ戻るケースを追加した。テストとClippyが成功した。
