# 発行済みURLの署名を検証でも再利用する

従来も、署名検証は事前計算ファイルとHMAC計算結果のキャッシュを利用していた。今回、発行済みURLのキャッシュにも32バイトの署名値を保持し、現在の所有者の鍵・画像ID・リクエストの有効期限が一致すれば、その値を定数時間比較する経路を追加した。計算結果のキャッシュから追い出された後でも、発行済みURLが残っていればHMACを再計算しない。

一致するキャッシュがない場合は、従来どおり事前計算ファイル・計算結果キャッシュ・HMAC計算の順に処理する。URLが更新されて期限が変わった後も、以前の有効なURLはこの経路で検証できる。画像の公開状態・現在の鍵・有効期限はHTTPハンドラーで毎回確認し、キャッシュには閲覧可否の判定を保存しない。

キャッシュの件数上限と期限更新の規則は変えない。署名値の追加は1件32バイトで、設定上限262,144件に対して値の合計は最大8MiB。AWSリソースやruntime設定の追加はない。

基準は所有者順配置＋まとめ読み版の183,352点・171,580点（両方PASS、seed 1）。今回の変更は未測定。

署名キャッシュ単体テスト4件、署名・画像キャッシュ・独立画像ストアのテスト6件が成功。計算結果キャッシュを追い出した状態で発行済み署名を再利用できること、改変・別の鍵・別画像・別期限の拒否、更新前URLへのフォールバックを確認した。実PostgreSQLの画像APIテストでは、発行済みURLを使って鍵変更と削除後の拒否を確認した。Clippy全ターゲットは警告なし。
