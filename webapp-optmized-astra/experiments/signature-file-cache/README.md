# 既存画像の署名ファイルキャッシュ

発行済みURLキャッシュを262,144件に増やしても、Asiaでは初回の署名計算が約9万回残った。既存DBの全画像と所有者の現在の鍵から署名を事前計算し、初回アクセスでも再利用する候補。ベンチの固定応答や既知IDは使わない。

`cargo build --release --bin cache-signatures` で生成ツールをビルドする。既存VMで非公開envを読み込み、`cache-signatures OUTPUT` を実行する。出力は生成開始から24時間の期限、現在の鍵、画像UUID、通常の1000回HMAC署名を含む。秘密情報として0600で扱い、SCPでローカルの無視対象 `var/astra/signatures.bin` に保存する。キャッシュ本体はコミットしない。

`signatureFileCacheEnabled` と `signatureFileCachePath` をruntime.jsonで管理し、Pulumiには参照とSHA256だけを記録する。通常の `apply.sh application` が既存3アプリVMへ0600で転送し、アプリを再起動する。アプリは約147MBのファイルを起動時に読む。Asiaの書き込み専用プロセスでは無効にしてメモリ重複を避ける。

現在の鍵と正規形の画像IDが一致し、残り期限が60秒を超える場合だけURL発行に再利用する。返したURLをメモリに保存するときもファイルの元の期限を引き継ぐ。鍵変更・新規画像・期限切れは従来の計算に戻る。画像取得時の権限・現在の鍵・期限チェックは継続し、署名検証も同一入力のみ再利用する。時計巻き戻り専用の処理はない。

切り戻しはruntimeのフラグをfalseにして通常配備する。期限切れでもアプリは通常計算で動作する。再生成時は新しい出力ファイルを指定し、運用中のファイルへ追記しない。

ローカル検証: 実DB・2レプリカを使った既存テスト一式、キーと画像IDの照合、以前の期限を保つURLキャッシュ境界、Clippyを実施。実機のスコアはこれから測定する。
