# 通常のユーザー検索を1 SQLにまとめる

従来は認証後にBEGIN、候補取得、ユーザー取得、COMMITの4往復が必要だった。通常ページは候補64件をMATERIALIZED CTEで絞り、同じSQLのスナップショットで現在のユーザー行を返す。全件の大きなプロフィール行をソートすることを避けるため、候補制限後に主キーで行を取得する。

既存のUnicode正規化をRustで再確認する。51件以上一致するか候補が尽きた場合は、その結果からページを返す。古い索引や更新中の候補により64件の中に十分な一致がない場合は、従来のREPEATABLE READでページ検索をやり直す。表示名・状態・両方向ブロック・カーソル・51件目によるhasMore判定は維持する。地域やDB接続先は変えない。

実DBのsearch_query_testは、正規化前の多数の候補、索引作成後、Unicode、特殊文字、NUL、ページ送り、表示名とID変更、退会、ブロック、索引のDELETE/TRUNCATE、派生索引の不整合、更新失敗時のロールバックを独立した全件走査と比較し、成功した。Clippy全ターゲットも成功。
