## ディスク枯渇からの復旧と比較の制約

対照版の配備時にAsiaのディスク使用率が100%となり、tarの書き込みが失敗した。配備途中の状態ではベンチを開始していない。初期化はSQL参照を戻すが、外部ファイルは別途GCするため、反復走行の未参照画像が蓄積していた。

Asiaのアプリ2プロセスを停止し、Goのビルドキャッシュを一時的にメモリ上の非公開ディレクトリへ退避して、実行ファイルを復旧した。isurealとarchive-imagesのハッシュをローカルの配布物と照合した後、既存apply.sh image-gcを実行した。全アプリ停止・公開参照の取得・全保存先の確認を経て未参照ファイルを削除し、全アプリが起動した。Goビルドキャッシュは元の場所へ戻した。公開中の初期パックや画像ファイルは保持した。

回収量とGC後の容量はstorage-recovery.jsonに保存した。GC後はAsia 18.8GiB、EU 14.8GiB、US 14.9GiBが空いた。過去の反復低下すべてが容量不足によるものとは確認できていない。また、GC前後ではディスク状態とプロセス状態が変わるため、得点差をコードだけの効果とは扱わない。

配備はextract-release.shで全体を一時ディレクトリへ展開してからファイルを置き換える。展開や実行属性確認が失敗しても既存実行ファイルは変わらない。展開前の容量確認も追加した。正常更新、不完全なアーカイブ、展開後の不正な実行属性の3テストが成功した。benchmark.shは開始前に既存4VMの残量を確認し、アプリ4GiB・主DB2GiB未満ならECSタスクを開始しない。値は各走行のexperiment.jsonへ保存する。容量不足時にGCを暗黙に実行しないため、「再起動なし」の比較を勝手に変えない。
