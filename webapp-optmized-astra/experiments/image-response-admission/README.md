# 画像の本文処理と複製待ちの枠を分ける

元の実装は画像処理後も重み付き64枠をレプリカ反映まで保持しており、Asiaの遅い投稿で受付待ち中央値1.68秒を確認した。本文処理が終わった時点で重み付き枠を返し、現在の採用構成では画像要求全体を別の64枠で応答完了まで制限する。本文処理の枠数は64を維持し、反映待ちの小さな応答と次の画像処理を重ねる。

対象は投稿・RealMoji・プロフィール画像の書き込み。一般更新128枠と管理更新4枠は従来どおり応答完了まで保持する。画像ファイルとSQLは永続化し、応答前にEU・US両方のレプリカ反映を確認する。

レプリカを停止した実DBテストで、16MiBの画像要求を2件処理しても応答が返らないこと、256件で後続処理が止まること、反映再開後に全応答が成功し両レプリカの値が一致することを確認した。実DBを使うreleaseテスト52件が成功し、性能測定用1件は除外した。

計測ありの実機ベンチは177,680点・PASS。対照180,913点よりスコアは低く、改善とは判断しない。一方、Asiaの250ms以上の投稿では受付中央値1,684→230ms、p90 2,779→962msへ短縮した。全投稿の応答中央値は1,901→952ms、p90は3,496→4,654msで、長い要求は悪化した。成功投稿の画像保存中央値は10.05ms、SQLは54.50ms。本文処理と複製待ちを重ねる効果は出たが、全体スコアへの寄与は診断なしの反復で確認する。Clippyも成功。

診断無効の通常構成は171,801点・PASS。Asiaの投稿中央値695ms、p90 4,838msで、中央値は短いがスコア改善はない。再起動なしの反復は負荷ユーザー準備の登録タイムアウトで0点・FAILとなり、負荷段階へ進まなかった。同じ種類の失敗は旧構成にもあるため、この変更との因果は断定しない。

次は画像要求全体の上限を64件へ下げ、処理と反映待ちを重ねる動作を保ちながら集中を抑える。本文サイズに応じた64枠は維持する。

64件上限でも、本文処理の先行・上限での停止・応答前の両レプリカ反映を確かめる実DBテストが成功した。

64件上限は185,395点・184,915点でともにPASS。Asiaの投稿中央値は506ms・538ms、p90は4,029ms・4,222msだった。256件上限の通常走行171,801点より高く、反復でも同程度だったため64件上限を維持する。以前の最高195,259点は更新していない。診断は無効。次の構成比較に使えるよう、この版の配布物とruntimeを保存した。

GCと3地域のアプリ・画像DB・Nginxの再起動後も18画像の内容・JPEG型が一致した。実行設定、配布物、全レプリカ反映を確認し、Asiaの空き容量は8.7GiBへ回復した。
