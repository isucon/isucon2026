# 不正ログイン検知を維持した操作ログ削減

NginxアクセスログとアプリのGETログは停止済みだが、成功した更新の操作ログはinfoで出力していた。180,392点の走行の負荷開始から66秒間では、Asiaの通常アプリと書き込み専用アプリが計31,666行・3,810,869バイトの操作ログを出した。失敗ログインまたは5xxは31行・3,739バイトだった。EU・USの更新はAsiaへ転送されるため、同じ期間の操作ログはAsiaに集まった。

ログレベルをerrorへ上げる候補を比較する。失敗ログイン401は診断用ログレベルの条件から分離し、従来と同じJSONとIP・usernameの検証、即時の1行書き込みを必ず維持する。既存guardとその判定条件は変えない。5xxと既存の内部エラーログも残す。成功した更新や読み取りの操作ログを省く。

runtimeのapplicationLogLevelとPulumiの検証条件、管理配備スクリプトへ反映する。旧アプリへ戻す場合は、ログレベルもinfoへ戻して配備し、失敗ログインの監視を保つ。実機スコアは未測定。

releaseモードの操作ログテスト2件が成功した。error設定でも、失敗ログインのIPと有効なusername、無効なusernameの除外、5xxの出力が従来どおりであることを検証した。成功した更新とGETは出力しない。Pulumiの型検査と配備シェルの構文検査も成功した。

実機の初回は190,094点でPASSし、最高点を更新した。直前の通知SQL版は172,478点と183,498点。ログ削減版の負荷開始から66秒間の操作ログは31行・3,739バイトで、すべて失敗ログインだった。不正ログイン検知を含むベンチの判定を通過した。GC・全地域のアプリとNginx・画像DBの再起動後、18画像の本文とContent-Type、稼働設定、複製反映の一致も確認した。単発最高点を効果の確定値とはせず、反復する。
