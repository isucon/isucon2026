# 初期投稿の画像メタデータ

直近の197,417点構成では、主DBが平均約1,300 read IOPSを使っていた。画像本体・署名のキャッシュは既にあるが、画像の有効性を確認するSQLが画像表と投稿表を参照している。初期投稿の画像だけ、起動時のメタデータと既存の変更記録を組み合わせて返す候補を試す。

起動時のREPEATABLE READで、各地域の初期ユーザーの初期投稿に紐付く画像ID、所有者、作成時刻、形式、既存ファイル参照を読む。画像の所有者と投稿者が一致し、初期化で消えない時刻の画像に限定する。同じIDが複数行・複数投稿に現れる場合、SQL内の画像、参照不整合、UUID以外のIDは従来SQLへ戻す。画像本体を追加のストアに移す変更はない。

毎回のSQLは現在の所有者のactive状態と鍵、初期履歴の世代、astra_initial_export_dirtyを同じスナップショットで確認する。021-initial-export.sqlの既存トリガーが初期投稿・画像の変更を所有者単位で記録し、020/021のTRUNCATE検知が世代を更新する。変更後は通常の画像SQLへ戻り、プロフィールやリアクションなど別の有効な参照も通常どおり判定する。dirty記録は初期化で消さない。ロールバック時はキャッシュの適用可能性も戻る。

鍵変更・退会はキャッシュに保存せず毎回のユーザー取得へ反映する。署名と期限の検証、ファイル読み取り、バイトキャッシュは既存処理を共有する。バイト再利用は同じimmutable assetを条件とする。メタデータの設定はPulumi astra、配備環境、実プロセス照合へ反映する。新しいAWSリソースや秘密値は作らない。

結合テストは実DBとJPEGファイルを使い、既存ハンドラーとステータス・形式・全バイトを比較する。対象外の重複・SQL内画像・新しい画像、署名・期限、鍵変更、退会、投稿の削除・所有者・画像ID変更、画像の形式・所有者・参照・時刻変更、直接パーティション操作、初期化、ロールバックを確認する。コミット後の画像差し替えと、投稿削除後もプロフィール参照が残る場合も比較する。

基準は197,417点PASS、US推薦32接続、セッション受付16枠・DB8接続、短い読み取りと履歴専用は0。主DB推薦4接続の183,523点候補は撤回済み。今回の画像メタデータキャッシュは実機未測定。
