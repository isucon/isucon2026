# 月をまたぐ利用者別の画像配置

検索の1 SQL化169,733点とAsia限定認証キャッシュ193,650点を撤回し、199,704点の読み取り構成へ戻した。次は、既存の月別画像パックから初期投稿の画像だけを利用者順に並べた追加ファイルを作る。画像のSQL参照・公開範囲・署名・期限は変更しない。

既存のpackキー全体（元ファイル、位置、長さ）をキーに、追加ファイル内の同一バイト列へ対応付ける。対応表にない画像は従来ファイルを読む。エクスポートのまとめ読みだけで使い、通常の単一画像取得は維持する。対応表はソート済み52バイトレコードで、起動時にSHA-256・並び順・重複・範囲・ファイルサイズを検証する。元画像は削除しない。

prepare-owner-archives.pyは既存3アプリVMだけで配置を作る。benchmarkと共通ロックを取り、既存Team 12ベンチがないことを確認する。現在SQLに参照されている初期投稿画像の一覧を非公開ファイルへ取得し、SCPで配布する。各VMは元ファイルからコピーし、入力バイト列のSHA-256と書き込み後のファイル全体のSHA-256を比較する。3台の出力ハッシュ・サイズ・対応表が完全一致した後だけ有効化する。元ファイルとSQLは変更せず、追加先は既存GCの対象外の/var/lib/astra-owner-images。作成時は4 GiB以上の余裕を残す。

ファイルは利用者境界で約2 GiBごとに分ける。利用者の画像を連続して読み、既存の最大16 MiBのまとめ読み上限を維持する。実行設定はPulumi astraとsystemd配布・照合へ反映する。有効化前のスコアは未測定。

Pythonでコピー全バイト・利用者単位の連続配置・索引レコード・再検証・破損拒否を確認。Rustで新旧ファイルが混在する取得、順序、重複、長さ違い、索引ハッシュ・並び・重複・切れたファイルの拒否を確認。Clippy全ターゲット、TypeScriptチェックも成功。

選択した初期投稿画像は618,901件、5,000所有者、10,019,479,849バイト。既存read_manyの64 KiB隙間・16 MiB範囲上限で全対象を所有者ごとにまとめると、現行は64,309範囲・13,112,762,074バイト、新配置は5,000範囲・10,019,479,849バイトになる。最大所有者は5,877,793バイトで、1範囲に収まる。これは全選択キーからの配置計算であり、実機のキャッシュヒット・後続削除・ベンチ選択率を含むIOPS測定ではない。ranges.jsonに集計を保存する。
