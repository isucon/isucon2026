# 通知配送SQLの実行計画

負荷後半のDBサンプリングでは、通常SQLの中で通知配送の問い合わせが目立った。1回512人の現在状態を確認するSQLから、旧通知の地域横断ソートを除く。最後に全候補から最初の通知を選んでいるため、途中の同じ選別は不要だった。旧通知がない期間は、ユーザーごとの旧通知検索も実行しない。

現在のユーザー情報はID索引で調べる。LATERALとOFFSET 0により、512人分の確認でusers全体を走査する計画を避ける。ユーザーの有効性・現在の地域・鍵、投稿期間の未終了、接続後の通知であることは同一SQLスナップショットで引き続き確認する。

ローカルの専用スキーマで30,000人・512購読者を使い、新旧通知の混在、全期間が新方式の場合、配送候補の有無、custom/generic両計画を比較した。全返却行が一致した。

ベンチ終了後のTeam 10 db1でも、READ ONLYと5秒のstatement_timeoutを指定して比較した。512購読者のgeneric計画は、候補なしで3.893msから2.143ms、候補ありで4.855msから3.221msだった。custom計画は5.630msから2.165ms、6.527msから3.202msだった。各3反復の最終値。実データでも全返却行が一致した。出力にはSQL条件・ユーザーID・鍵を残さず、実行計画のノード種類・時間・行数・バッファ数だけを保存した。

これは無負荷時のクエリ単体比較であり、スコア改善とは区別する。ベンチで測定する前に、地域移動・退会・期間終了・初期化・複製遅延を含む既存の結合テストを実行する。

再実行はリポジトリルートから`python3 webapp-optmized-astra/experiments/notification-query/compare-local.py`。実機比較はベンチが停止し、直前の成功走行でAsiaに512人以上の有効な通知対象がいる状態で`compare-live.py`を使う。既存Team 10 db1へ読み取り専用で接続する。

releaseモードのRust全テストは50件成功、0件失敗、性能測定用1件を除外。実プライマリ・2台のレプリカ・独立画像DB・地域画像DBを使った既存の結合テストを通過した。
