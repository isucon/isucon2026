# 投稿期間ごとの通知保存候補

投稿期間を開く処理は、対象地域で有効な全ユーザーの通知行をINSERTする。現行の通知ID・ユーザー・期間の索引更新を減らすため、同じ通知IDと対象者を投稿期間ごとの不変配列として保存する候補を比較する。作成時刻、対象者の確定時点、通知ID、現在のアカウント・地域・接続時刻の判定は維持する。

専用ローカルスキーマで5,000人を比較した。1人1行は48.253〜53.810ms、1期間1行は10.722〜11.253msだった。EXPLAINのINSERTノードのWALは2,773,380バイトから426,921バイト、表と索引のサイズは1,990,656バイトから483,328バイトになった。展開後の全通知IDと対象者が一致することも確認した。合成データ・単一ローカルDBの予備試験であり、地域間の複製時間と実機スコアは未測定。

実装する場合は、投稿期間と通知配列を同じトランザクションで確定する。既存の地域別対象者ロックと応答前の複製確認を維持する。アプリは現在開いている期間の不変配列を読み込み、通知対象の検索に再利用する。配送時には単一SQLスナップショット内で、現在のユーザー状態、地域、キーの有効性、期間の未終了、接続時刻以降の通知であることを検証する。候補が複数あれば作成時刻とID順の先頭を選ぶ。

初期データと従来の通知行も読み取り対象に残す。新方式への書き込みは設定で切り替え、無効に戻した後も既存配列を読める状態を保つ。初期化は追加表も同一トランザクションで消去する。新しい期間IDと連動してキャッシュを入れ替え、途中の地域移動・退会・終了・初期化で古い通知を送らないことを検証する。地域レプリカの反映を停止する既存テストも維持する。

追加表`astra_notification_batches`と、旧行・配列の両方を読む通知ポーラーを実装した。開いている期間の配列だけを保持し、配送候補をSQLへ渡して現在状態を再確認する。`notificationBatchWritesEnabled`は既定でfalse。まず`apply.sh upgrade`で追加表と読み取り対応を全台へ配備し、旧方式で対照走行を行う。その後trueにして`apply.sh application`で新規通知の保存先を切り替える。切り戻しはfalseへ戻し、対応済みの読み取り処理を保つ。

旧バイナリへ戻す場合は、全アプリを止め、配列の全通知を従来表へ展開してから切り替える必要がある。初期化だけで戻す場合は、対応済みアプリによる初期化が完了し、追加表が空であることを確認してから旧バイナリへ戻す。

通知作成の結合テストは両方式で対象者・UUID・競合・途中失敗の取り消し・地域別ロックを検証する。読み取りテストは旧方式との混在・時刻とIDの順序・接続時刻・キャッシュ後の地域移動と退会・期間終了・初期化・再起動を検証する。反映を停止したレプリカのテストも両方式で成功した。全Rustテスト、Clippy、Pulumiの型検査、配備用シェルとPythonの構文検査が成功した。

全体テストで、先行する初期化VACUUM追加後のSQLxテストハーネスが複数SQLを一括送信し、VACUUMを暗黙のトランザクションへ入れる問題を検出した。テストは同じ接続でCOMMIT後の保守文を個別に送り、psqlで動く実配備と同じ実行単位へ修正した。

## 実機比較

同一バイナリの旧書き込み対照は185,418点。新方式は169,421点、GC・アプリ再起動後174,707点、続けて再起動しない反復187,187点でPASSした。間の再実行は準備時の登録タイムアウトでFAIL。20件中18件が開始から約0.3秒以内に201を返し、アプリのERRORはなく、ルーター入口のリクエストエラーが1件あった。原因は未確定。初期化後の準備失敗では再起動検証用の各地域2画像が揃わず、その検証はGCの前に中止された。公開参照を検証する通常のGCを行ってから再計測した。

新方式の3成功走行にはスコアの幅があり、旧方式より安定して高いとはまだいえない。一方、約32,800件の新規通知を18行・約1.9MBへ集約し、従来表の新規通知は0件だった。最後の走行ではdb1の平均送信量が対照の90.2Mbpsから61.1Mbpsになった。ただし要求数も異なるため、全差分を通知方式だけの効果とはしない。新方式を有効のまま次のI/O改善と比較する。
