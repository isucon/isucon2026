# Asiaの読み取り分散案

既存のAsiaアプリVMへ3個目のメタデータレプリカを置き、db1の読み取りCPU負荷を分ける候補。
初期画像をファイルへ移した後のメタデータDBは約3.4GBで、GC後のAsia空き容量は約13.7GiBだった。
AWSリソースは追加しない。元の`/var/lib/postgresql/16/main`は保持し、ベースバックアップは`16/astra`へ保存する。

`asiaReplicaEnabled`でレプリカを準備し、`asiaReplicaReads`で読み取り先を切り替える。
切り戻しは後者をfalseにしてアプリを再配備する。レプリカのデータや公開画像は削除しない。
準備時は全DB容量に6GiBを加えた空きを要求する。複製用の秘密情報は従来の非公開envをscpで共有する。

更新成功前の反映待ちは従来の欧州・米州2台を維持する。
Asiaの追加レプリカは非同期なので、Asiaの各読み取りは要求到着後のプライマリのWAL位置を取得し、
ローカルでその位置まで反映されたことを確認する。複数の要求は同じ確認にまとめる。
確認に失敗した場合は503を返す。SSEの後続ポーリングにも同じ確認を行う。
アプリ起動時にも、同期反映の対象外のレプリカを確認なしで読む設定を拒否する。

移行時のWAL追従と古い行の回収待ちは、追加レプリカも含む全台を対象にする。
アーカイブのファイルは従来どおり3地域に保持する。

これは独立DBへの分割とは異なる比較。ユーザー名、地域変更、友達・ブロックなどの整合性は
単一プライマリで管理したまま、既存VM間のCPU配分を変更する。
スコア、db1とAsiaのCPU、I/O、メモリ、反映待ち時間を比較して採否を決める。
候補段階では両フラグをfalseにしてあり、実機スコアは未測定。

## 検索・フィードに限定する候補

全読み取り分散は141,182点でPASSしたが、Asia側の画像メタデータ・ZIP取得のI/O待ちが増えた。
`asiaReplicaReadScope=feed_search`では、検索とフィードだけをローカルレプリカへ送る。
画像、ZIP、ユーザー詳細、通知などはプライマリを使い、更新も従来どおりプライマリへ送る。
反映確認はレプリカを読む2経路に付け、認証より先に実行する。IP制限の確認はプライマリで行う。

ローカルの物理レプリカを一時停止する結合テストで、検索・フィードの待機、通常のユーザー詳細の
最新値取得、ログアウト後のセッション無効化を確認した。実機用の反映確認ツールも、
検索を待たせながらユーザー詳細が最新値を返すことを検証する。トークンはVM上のメモリだけで扱う。
