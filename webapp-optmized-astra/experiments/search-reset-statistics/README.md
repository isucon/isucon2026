# 初期化後の検索補助テーブル統計

診断20261030T111549Z-team12の主DBでは、待ちイベントのないクライアント接続237サンプル中130が検索SQLだった。500ms間隔の占有観測で、CPU時間ではない。

reset.sqlはastra_search_dirtyをTRUNCATEして初期ユーザーを挿入する。続くRustの正規化再構築が全行を削除するが、ANALYZEはastra_user_searchだけだった。空のdirty集合についてreltuples=-1のままとなり、検索プランナが多数の候補を想定する。

ローカル6,000ユーザーで同じ手順を再現した。自動vacuumは実験スキーマのdirtyテーブルだけ無効にし、初期化直後の状態を固定した。修正前は実数0に対して3,672行を見積もり、users全件をHash Joinしていた。dirtyのANALYZE後は候補を2件と見積もり、usersの主キー参照に変わった。3回の中央値はPlanning 0.991→0.992ms、Execution 2.146→0.978ms。実機性能の予測値ではない。

initialize_handlerで正規化完了後に両方の表をANALYZEする。検索結果、検索SQL、ページ送り、変更の反映は変えない。通常走行181,990点のセッション受付分離を含む候補へ追加する。実機は未測定。

compare.pyは既存のローカルastra-local-assetsコンテナ内に固有スキーマを作り、終了時に削除する。実機のデータ・設定は変更しない。measurements.jsonに全実行計画を保存した。
