# 投稿処理の段階別計測

postTimingEnabledで一時的な診断を有効にする。250ms以上のPOST /api/postsについて、受付待ち、next.runの処理、レプリカ反映待ちをslow_postとして記録する。投稿ハンドラーが正常に完了した場合は、入力・JPEG検証、画像保存、SQL、応答作成の所要時間をpost_workとして記録する。本文取得・multipart解析・sessionなどはハンドラーに入る前なので、post_workには含まれない。SQLには接続取得待ちも含む。

EU・USで準備した画像はwriterへ参照を渡すため、writer側の画像保存時間にはその地域でのファイル保存を含まない。stored=1で区別する。本文、画像ID、ユーザーID、認証情報は記録しない。診断のない通常スコアとは分けて評価し、調査後は無効にする。

計測版は180,913点・PASS。Asia通常アプリの成功投稿2,777件では、画像保存の中央値9.53ms・p90 12.98ms、SQLの中央値45.67ms・p90 136.68msだった。250ms以上の投稿2,025件では、受付待ちの中央値1,684ms・p90 2,779ms、ハンドラー197ms・305ms、複製待ち133ms・191msだった。統計の母集団が異なるため段階別中央値を合計して全体時間とはしない。

次は本文処理用の重み付き64枠をハンドラー完了後に返し、複製待ちを含む画像要求は別の256枠で制限する。画像本体を保持しない応答待ちが、次の画像の処理開始を止めないようにする。SQLとファイルの永続化、成功応答前の両レプリカ反映は維持する。
