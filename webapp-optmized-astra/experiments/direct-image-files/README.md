# 新規画像ファイルの名前を付ける処理を減らす候補

従来は一時ファイルへ書き込み・fsyncし、最終名へのhard link、一時名のunlink、ディレクトリのfsyncを行っていた。候補ではO_EXCL相当のcreate_newで最終名のファイルを作り、書き込み・ファイルfsync・ディレクトリfsyncが完了してから保存キーを返す。公開用SQLはその後に更新するため、公開画像から書きかけのファイルを参照することはない。内部ファイル配信は既存4VMだけに許可している。

既存のIDは上書きしない。新しいファイルを作れた場合だけ失敗時の削除を有効にし、書き込みや永続化に失敗したら自分が作った未公開ファイルを除去する。SQLの公開に失敗した後の孤立ファイルは従来どおりGCで回収する。成功後の保存形式と読み取り処理は同じなので、旧バイナリでも読み取れる。

狙いは画像ごとの名前追加・削除と、それに伴うファイルシステムのメタデータ更新を減らすこと。永続化の待ち時間と実機スコアを比較する。候補段階で実機未適用。

実PostgreSQLとレプリカを使うreleaseテスト52件が成功し、性能測定用1件は除外した。既存テストで同じIDへの同時書き込みが一方だけ成功すること、既存ファイルを上書きしないこと、新しいFileStoreインスタンスからの読み取り、SQL公開失敗時に画像メタデータが増えないこと、画像API・ZIP・再初期化を検証した。
