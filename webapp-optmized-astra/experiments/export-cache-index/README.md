# ZIP用画像キャッシュの所有者索引

従来のZIPエクスポートは、画像キャッシュ全体をロックして最大16,384件から所有者が一致する画像を探していた。画像の保存・所有者情報の更新・置換・追い出しに合わせて所有者別のID索引を更新し、エクスポート時には対象者の画像だけを取り出す。空になった所有者の索引も削除する。本文はBytesの参照を保持し、コピーしない。

索引は権限の判定には使わない。エクスポートのSQLは従来どおり所有者・投稿の公開状態・画像の版と時刻を確認する。画像GETも現在の鍵・期限・可視性を確認する。キャッシュの上限、CLOCK方式の追い出し、エクスポート中の本文保持は維持する。追加索引のID数はキャッシュの件数以内に収まる。

## ローカル比較

releaseビルドで16,384画像・1,024所有者のキャッシュから2,000回取り出した。全走査と索引で本文集合が一致することを確認した。

| 試行 | 全走査 | 所有者索引 |
|---|---:|---:|
| 1 | 168.364ms | 8.138ms |
| 2 | 151.093ms | 7.604ms |
| 3 | 118.868ms | 5.138ms |

これはSQL・ZIP生成・HTTPを含まない局所計測。1回あたりの削減は数十µsであり、実機スコアの改善は未確認。AWS再認証後、他の候補と混ぜずに配備・比較する。直近の実機スコアは176,830点・174,401点PASSで、この変更の測定値ではない。

再現コマンド:

```sh
cargo test --release --locked --lib compare_export_owner_index -- --ignored --nocapture
```

所有者が不明な画像の登録、版不一致の更新拒否、所有者変更、画像置換、容量超過による追い出し、取り出し済み本文の保持を単体テストで確認した。既存の画像キャッシュ容量テストも成功。

実PostgreSQLを使う画像キャッシュAPIテストと独立画像ストアの統合テストが成功した。後者はZIP、画像の変更、削除、初期化、ファイル保存、地域別保存も検証する。releaseのClippy全ターゲットも警告なし。
