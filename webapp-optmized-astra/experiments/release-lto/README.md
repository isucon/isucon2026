# Releaseビルドの最適化候補

アプリのreleaseビルドをThinLTOとcodegen-units=1で比較する。API、DB構成、CPU命令セットの指定は変えない。panicの巻き戻しは維持し、既存のリクエスト例外処理を保つ。

候補のビルドとreleaseモードのテストは別のtargetディレクトリで行う。実機のベンチ中に配布物を置き換えない。実機スコアが出るまでは改善と扱わない。

releaseビルドと全結合テストが成功した。50件成功、性能測定用1件は既定どおり無視。実PostgreSQLのプライマリ・2台のレプリカ・独立画像DB・地域画像DBを使い、通知の新旧保存方式と反映待ちも検証した。

実機への適用前の対照は176,344点でPASS。Nginxバッファ有効、通知バッチ有効、SQL接続枠16、画像キャッシュ512MiBの構成を維持して比較する。

初回は178,621点でPASS。対照176,344点との差は小さく、反復する。負荷後半から60秒のDB診断では121サンプルを採取した。COMMITのIPC待ちが816接続サンプルで最多、通常SQLでは通知配送がCPU待ち75接続サンプルだった。採取には負荷終了後の時間も含むため、負荷全体の平均とは扱わない。

同じバイナリでの反復は180,392点でPASSした。2回とも直前の対照176,344点を上回るが、これまでの実測の変動幅内なので、薄いLTOだけで大幅に改善したとは判断しない。機能テストを通過しており、このビルド設定を保って次のSQL改善を比較する。
