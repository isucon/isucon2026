# おすすめフィードの共通集計と上限付きJOINの比較

eeb69dcの対照版では共通集計も外し、f9aeafc9のSQLに戻している。以下は各候補の評価記録。

最終候補4279a28は、友達の友達の集合と共通の友人の人数を同じ集計結果から求める。以前は同じ2段階の関係を2回走査していた。加点Cの計算には従来の集合全体のJOINとGROUP BYを使う。候補の閲覧条件、反応した有効な友人の集計、得点と時刻とIDによるページ送りは同じSQLスナップショットで評価する。

途中のb53f0973ではmin(C,30)の性質を利用して、著者ごとの正の加算項を30件まで読む案も試した。正の整数30件なら必ず合計30以上になり、30件未満なら全項が残るため、結果は正しい。ただし実行計画は著者ごとに共通の友人一覧を再走査する形になり、候補が多いと遅くなったため撤回した。

実DBの独立した参照実装との比較テストは、途中案・最終候補とも成功。全4種類のフィード、密なグラフと疎なグラフ、50件を超えるページ送り、同時刻、ブロック・友人変更・ユーザー削除、リアクション重複・置換・削除、30点上限を確認した。Clippy全ターゲットも警告なし。

公式ベンチのない時間に、Team 12主DBで関係計算を切り出した読み取り専用EXPLAIN ANALYZEを各3回行った。候補選択は直前の負荷試験で作られた投稿の著者。閲覧条件やページ送りを省いた診断SQLであり、API全体の測定ではない。候補選択の全表走査の時間も含む。

最初は全ユーザーの中で友人関係の多い1人を選び、候補は7著者・39投稿だった。

小さい候補集合の改善だけで上限付きJOINを採用できないことが分かった。JSONB案も従来の集合JOINより速い結果ではないため採用しない。共通集計だけを残す。計画はold-plans.json、bounded-plans.jsonとactive-*.jsonに保存し、ユーザーUUIDを伏せた。compare_plans.pyは最初の2案を現時点のデータで再測定するスクリプトで、配備・ベンチと同じ操作ロック、読み取り専用トランザクション、15秒のstatement_timeoutを使う。
