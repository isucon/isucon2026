# ファイル保存後のアップロード実行枠

画像本体をメタデータDBの複製から分離した後も、更新ワーカーの画像用実行枠は64スロット（1スロット256KiB）だった。Asiaは画像本体を受け取り、EU・USは地域内で保存した参照を送るため、Asiaの投稿は同じ待ち列の複数スロットを使う。

128スロットへ増やし、待ち時間とメモリ・I/O負荷を実機で比較する。小さな更新128件と管理更新4件の別枠、ファイル保存の同時実行16件、応答前のレプリカ反映確認8件は維持する。スコアの反復結果が出るまでは改善と断定しない。

実機の128スロットは[168,825点](../../results/20261028T141246Z-team10/result.json)、[172,721点](../../results/20261028T141650Z-team10/result.json)でPASS。64スロットの173,249点・183,359点を上回らず、64へ戻した。最終日のゲート通過人数は128で1,048人・1,154人、64の直前走行は1,569人だった。初回128のベンチ側CPU負荷も他走行より高く、差を実行枠の効果だけとは断定しない。DBの採取ではIPC待機中のCOMMITが最多で、最大観測待機は0.549秒だった。
