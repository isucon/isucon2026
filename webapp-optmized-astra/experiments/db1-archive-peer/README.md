# db1を初期画像の読み取りにも使う候補

アプリ改善後、Asiaの負荷中のディスク読み取りは約16〜22MB/s、db1は約9〜13MB/sだった。db1は6,000 IOPS・200MiB/s、AsiaアプリVMは3,000 IOPS・125MiB/sの既存ボリュームを使う。db1の空きディスクは約44GBで、初期画像の25パック・約14GBを追加配置できる。DBの役割は残し、余力を画像の範囲読み取りにも使えるか比較する。

候補のアプリは、Asiaの初期画像パックだけをdb1の非公開HTTPで読む。画像の現在の所有者・鍵・公開状態の確認は既存のSQLとアプリに残す。新規画像の地域別ファイル保存、EU・USのローカルパック、メタデータの複製は維持する。元のパックは3地域に保持し、読み取り先を設定で戻せるようにする。

HTTPクライアントは要求した範囲に対する206応答、Content-Rangeの開始・終了・全体サイズ、受け取ったバイト数を検証する。環境設定から使える宛先は既存db1の192.168.148.10:8082に限定する。既定ではローカル読み取りを維持する。releaseテストで正しい範囲の一致と、不正・不足・過剰・範囲外応答の拒否を確認した。

管理配備とコピー手順を追加した。Pulumi runtimeへ配信準備と読み取り切替を別々に記録し、既存4VMのprivate Nginxだけを使う。パックは元の3地域のものを保持したままdb1へコピーし、全パックのサイズ・SHA-256・永続化を確認してから読み取りを有効にする。設定・HTTP範囲応答・再起動後の公開画像本文も照合する。新しいAWSリソースは作らない。

実機比較は未実施。共有バッファは512MiBに戻して比較を終えた。続いて配信準備だけの対照、Asia読み取り切替を反復する。DB側のI/Oとメモリを圧迫したり、HTTPの追加往復で不利になったりする可能性もあるため、採用はスコアと負荷を確認して決める。

ローカル検証では実PostgreSQLを使うreleaseテスト52件が成功し、性能計測用1件は既定どおり除外した。追加のAPI経由テストは、ローカルにないパックのHTTP取得、画像本文、ZIP本文、キャッシュ後の鍵変更・ユーザー削除・投稿削除を確認した。コピー補助処理の5テストも成功し、SHA不一致・途中切断・既存内容不一致・不正な範囲応答を拒否した。Python構文、Bash構文、PulumiのTypeScript型検査も成功した。

配備はarchivePeer.enabled=true、readsEnabled=falseで始め、`archive-peer.py copy`で25パック・14,054,519,155バイトをdb1へ複製する。全内容のSHA-256を照合し、ファイル・ディレクトリをfsyncしてからコピーを公開する。通常の再検証は確定済みのサイズ・権限・マニフェストと各パック先頭・中央・末尾のHTTP範囲を照合する。readsEnabled=trueの配備には、この検証が先に成功する必要がある。切り戻し時はアプリをローカル読み取りに戻してからdb1の配信設定を無効化する。

実機の準備配備とコピーは完了した。25パックすべてで全内容のSHA-256が一致し、14,054,519,155バイトを永続化した。3地域のアプリ・画像DB・Nginxに加えてdb1のNginxも再起動し、公開画像18件の本文とContent-Type、db1の75範囲を再照合した。Pulumi出力と実機設定・配布物ハッシュも一致している。読み取りはまだローカルのままで、切替前の対照を測定する。
