# 最適化版 Go Web アプリケーション

`webapp/go` をコピーした独立した実装です。元のアプリと、作成中の `bench/` は変更していません。ベンチマークへの依存やスコアに合わせた分岐はありません。

## 起動

リポジトリのルートで、既存の開発環境に override を適用します。

```sh
docker compose -f compose.yaml -f webapp-optimized/compose.yaml up --build -d
```

最適化版のアプリイメージとSQLを使用します。DBの作り方と初期化は元のアプリと同じです。DBを作るときに、最適化版の `sql/001-schema.sql`、初期データの `002-seed.sql`、`sql/003-initial-snapshot.sql` を1回だけ流します。DBのボリュームが空なら、上のコマンドで最適化版のスキーマのDBができます。

元のアプリで作ったDBが残っている場合や、`SCALE=large` のデータを使う場合は、リポジトリのルートでDBを作り直してください。

```sh
make datagen-load WEBAPP=webapp-optimized  # SCALE=large も指定できます
```

`/api/initialize` は `sql/reset.sql` で負荷走行で変わった分だけを戻し、`ANALYZE` で統計を更新したあと、各リージョンのアプリが持つ状態を読み直します。最適化版のスキーマにはDB関数があり、元のアプリの `001-schema.sql` ではテーブルを消せません。元のアプリに戻すときは `docker compose down -v` でDBのボリュームを消して作り直してください。

直接実行する場合:

```sh
cd webapp-optimized/go
make
# ISUREAL_DB_* と ISUREAL_REGION は元のアプリと共通
./isureal
```

作業ディレクトリを `webapp-optimized/go` にすることで、初期化時に `../sql/init.sh` が使われます。DBは事前に `sql/` の `001-schema.sql`、`002-seed.sql`、`003-initial-snapshot.sql` をこの順に流して作ってください。`sql/002-seed.sql` は元の生成データへのシンボリックリンクです。データがない場合はリポジトリのルートで `make datagen` を実行してください。`reset.sql` は `session_replication_role` を変えるため、スーパーユーザーで接続する必要があります。

`sql/003-initial-snapshot.sql` と `sql/reset.sql` は元のアプリと同じ内容のコピーです。元のアプリのテーブル構成が変わったら、こちらも合わせて更新してください。

## 2026-10-27 の変更（新しいベンチ向け）

team 11（Large データ、各サーバー 2 vCPU / 3.8 GiB）で新しいベンチを走らせながら入れた変更です。計測の記録は
作問チームの調査メモにあります。グランプリ（全地域同時の投稿期間）を即時に開く変更（管理者操作の専用プール、
期間行の `FOR KEY SHARE`、通知行の追記型の主キー）は、2,300 人の一斉投稿で db1 が飽和しエクスポートが
15 秒を超えて失格になったため、いったん戻してあります。

- 投稿期間を開く処理: `LOCK TABLE users` をやめ、開いている期間の部分一意索引で直列化します。通知行
  （asia は 1 期間あたり約 5,000 行）はユーザー順にバックグラウンドで書き、初期化の前に書き終わるまで待ちます。
- 通知（SSE）: DB のポーリングをやめ、投稿期間を開いた事象（通知対象のユーザー ID を含む）を各地域の
  hot state へ配り、購読者へその場で渡します。通知 ID は期間 ID とユーザー ID から決定的に作ります。
- hot state から返す読み取りを増やしました: 現在の投稿期間、自分の今日の投稿、投稿の詳細（開いている
  期間のもの）、プロフィール、自分の情報、ユーザー検索（正規化済みの名前を持ち、(username, id) 順）。
  状態が答えられないときは従来の SQL に戻ります。
- 画像: 走行中に上がった画像は受け取った app の `ISUREAL_IMAGE_DIR/run/<id>` に置き、DB の行は
  メタデータと空の本体です。取得はメモリ → 自分のディスク → 他地域の app（`/internal/images/:id`）→ DB
  （初期データ）の順です。初期化はディレクトリを rename して裏で消します。
- エクスポート: 投稿を先に読み、画像は (id, 投稿時刻) の配列で 64 枚ずつ 4 本まで並列に読みます
  （画像の `created_at` は投稿時刻なので月のパーティションに絞れます）。
- ログイン失敗のアクションログを出し、`isureal-guard` が不正な IP を BAN できるようにしました。
- `postgresql/isucon.conf`（shared_buffers 512MB など）と VM 用の `deploy/nginx.conf` を追加し、
  初期化の `ANALYZE` は走行で書き換わる小さな表に限ります。
  `ISUREAL_PPROF=127.0.0.1:6060` で pprof を開けます。
- 同期スタンバイ用の `ReadDB` 設定は外しました。

環境変数: `ISUREAL_PEERS`（他地域の app）、`ISUREAL_DB_MAX_CONNS`（asia 32、海外 96 を使用）、
`ISUREAL_IMAGE_DIR`、`ISUREAL_HOT_STATE=off`（テスト用、DB から読む）。

## 2026-10-28 の変更（v3）

team 11 の seed 1 で 171,674 点から 297,384 点になった変更です。最終の ebf9988 で seed 1〜5 は
286,597 / 282,547 / 292,912 / 283,403 / 287,817 点（すべて pass、走行ごとの揺れは ±4% ほど）。

- 初期データの画像（約 183 万枚、14 GB）を app のディスクに置きます。`isureal pack-images` が DB から読み、

  起動時に索引を読み、初期データの境界が DB と違えば使いません。エクスポートは 1 人の画像を連続した 1 回の
  読み取りで返し、画像の取得は所有者がわかるので `image_objects` を引かずに生存だけを DB で確かめます。
  1 台で作ったファイルを他の app へ写してもかまいません（中身は初期データだけで決まります）。
- 初期データの Memories を app のメモリから返します（履歴ストア）。地域の利用者の投稿・コメント・RealMoji を
  起動時に読み、ポインタを持たない配列にしています。利用者の名前や画像、退会は hot state から合わせます。
  走行中にコメント・RealMoji・編集・削除で触られた初期データの投稿は、書き込みが応答する前に全地域へ印を配り、
  その投稿を含むページは DB から読みます。初期データの外の投稿期間を含む期間も DB から読みます。
- 画像 URL の有効期限の刻みを 6 時間にしました（期限は現在より後で 24 時間以内）。履歴ストアの投稿と RealMoji の
  画像の署名を裏で先に計算し、応答の URL と画像取得の検証の両方で使います。署名は現在と次の刻みの 2 つを持ち、
  次の刻みの分は CPU の 5% ほどでゆっくり計算します（刻みの境目は UTC 0・6・12・18 時、日本時間の 9 時を含む）。
- 履歴ストアの画像は、投稿が走行中に触られていなければ読み込み時と同じく有効なので、持ち主（RealMoji なら
  投稿者も）が有効かを hot state で確かめるだけで返します。エクスポートの zip は応答へ直接書き出します。
- hot state のセッションは本拠地の利用者の分だけを信用し、他地域の利用者は DB で確かめます。そのため
  ログインとログアウトは本拠地の app にだけ同期で反映し、他地域へは非同期で送ります。
- friends と friends-of-friends のフィードは対象の人の投稿だけを集めて並べます。コメントと RealMoji の一覧は、
  開いている投稿期間の投稿なら閲覧の可否を hot state で決め、DB からは一覧だけを読みます。
- friends-of-friends のおすすめ順の点数は hot state で計算します。共通の友達の数と 3 歩の道の数は友達関係から、
  反応した友達の数は、開いている投稿期間の投稿に付いた有効な RealMoji とコメントを hot state に持って数えます。
  そのため、それらの投稿へのコメントと RealMoji の作成・削除も、ほかの書き込みと同じく全 app に同期で送ります。
- nginx を外し、app が 80 番を直接受けます（`ISUREAL_PUBLIC_LISTEN=:80`、フロントエンドは
  `ISUREAL_PUBLIC_DIR`）。80 番を開くための systemd の drop-in が `deploy/isureal-go.service.d/public.conf` です。

team 11 で使った環境変数の追加分: `ISUREAL_PUBLIC_LISTEN=:80`、`ISUREAL_PUBLIC_DIR=/home/isucon/webapp/public`、
`GOMEMLIMIT=1500MiB`、`GOGC=50`（パックのページキャッシュを残す）。履歴ストアと署名の計算は起動後に
app1 で約 2 分半かかるので、計測はジャーナルに `history signatures` が出てから始めます。

この状態での律速は app ではありません。5 日目の終盤にルーターの CPU が 100% になり、グランプリは HAProxy から
app への転送が共有する 1 Gbps の上りで決まります（約 2,400 人の写真が同時に流れて多くが締め切りに間に合わない）。
試して効かなかったもの: 投稿の本体を先着順に読む枠（接続ごとの帯域の取り合いに負け、asia が時間切れになる）、
JSON の gzip（ルーターの送信は 6% 減ったが点は変わらない）、エクスポートの同時数の制限、DB 接続数の増加。

計測の注意: ベンチの Fargate タスク（4 vCPU）はこの水準のアプリでは CPU が平均 50〜60%、p95 で 80〜90% に達し、
遅いホストに当たると 100% に張り付いて 19〜20 万点に落ちます（report.txt の bench 行で見分けられる）。また前の走行の
直後に始めると、最初の要求（/api/initialize）がルーターに届かず 60 秒で時間切れになったり、接続に数秒かかる要求が
出たりするので、走行の間は 2 分以上空けています。ベンチのタスクのメモリ（8 GB）も 6〜7 GB まで使い、グランプリ中に
OOM で落ちて結果が出ない走行が 1 回ありました。

## 変更内容

- 画像署名のHMAC 1,000回反復では、ハッシュオブジェクトと出力バッファを再利用します。さらに鍵・画像ID・有効期限の完全一致をキーに、署名計算結果を最大8,192件のLRUに保持します。反復回数・署名値・有効期限は元と同じです。署名だけの純粋関数キャッシュなので、初期化や別VMでの更新による無効化通知は不要です。この署名キャッシュは閲覧許可をキャッシュしません。
- プロフィールと自分の現在投稿の取得は、認証を除くSQLをそれぞれ3回から1回に統合しました。書き込みは下記のDB関数に統合し、ロック・検証・更新・結果取得をまとめています。
- 投稿・プロフィール画像・RealMojiの画像は、元と同じくJPEGであることと縦横の上限（投稿は4096、プロフィール画像とRealMojiは512）を確認します。元のアプリは画像全体を読んでからデコードします。最適化版はJPEGのヘッダーだけを読んで寸法を確かめ、不正な画像は残りを読む前に拒否します。ヘッダーより後ろのデータが壊れたJPEGは受け付けます。
- IPアドレスのBANは元と同じく、すべてのAPIで `X-Client-IP`（なければ接続元）を `ip_bans` と照合し、BAN中なら `403 {"error":"ip_banned"}` を返します。元のアプリは、前回の読み込みから200ms以上たっていればリクエストの処理中に一覧を読み直します。最適化版は起動時と200msごとにバックグラウンドで読み直し、リクエストではメモリ上の一覧だけを見ます。そのため海外リージョンでも、BANの確認でDBの往復を待つリクエストはありません。追加したBANが効くまでの遅れは元と同じく最大200ms程度で、DBが遠い場合は1往復分延びます。`/api/initialize` を受けたアプリはその場で読み直します。リージョン間の内部通信（`/internal/`）はBANの対象外です。

- フィードの閲覧条件・公開範囲・ブロック・フォローをSQLで判定し、ページの候補を最大51件に制限しました。認証を除くDB問い合わせは1回です。カーソルの有無でSQLを分け、次ページでは複合インデックスを使える比較条件にしています。
- 単一投稿の取得・投稿者情報・認可を1回のSQLに統合しました。友人の友人全体をアプリへ転送せず、閲覧者と投稿者の友人関係、投稿済み判定、ブロックをDBで確認します。コメント・RealMojiの一覧はDB関数 `opt_access` の認可と一覧取得を1回のSQLに統合しました。書き込み時は引き続きトランザクション内で再確認します。
- Memoriesは投稿・投稿者・コメント・RealMojiを1回のSQLにまとめました。相関サブクエリで退会・削除・置換を除外してから投稿ごとに最大50件を取得し、コメントの昇順、RealMojiの降順を維持しています。
- 投稿時の投稿期間ロックを `FOR SHARE` に変更しました。ユーザー行の排他ロックで同一ユーザーの重複投稿を防ぎつつ、別ユーザーの投稿を並行処理します。期間終了の更新とは引き続き排他になります。
- ログインセッション・管理者セッション・コメント・RealMojiの作成は `INSERT ... RETURNING` で挿入後の再取得を省きます。
- ユーザー検索はブロックをSQLで除外し、行を順次読み取ります。UnicodeのNFC正規化とcase foldingは元のGo実装を維持しています。プロフィールの友人判定も対象ユーザーに限定しました。
- ZIPエクスポートは画像を順次読み取り、全画像のスライスと完成ZIPを同時に保持する状態を解消しました。
- 認証、投稿、画像参照、友人関係、コメント、RealMoji、通知などの検索・ページング用インデックスを追加しました。画像参照のインデックスは、プロフィール画像削除時の外部キー確認にも使える構成です。元の制約は変更していません。
- DB接続はアプリプロセスごとに最大32、アイドル32に設定しました。3プロセスならアプリ用に最大96接続を使用します。固定のSELECT列リストも再利用します。

エクスポートの読み取りでは、セッション認証と同じSQLで取得したユーザー情報をそのリクエスト内だけで再利用します。別のリクエストでは必ずDBを読み直します。書き込み処理にはこの再利用を適用せず、従来どおりロック取得後に確認します。通知はアプリプロセス内のSSE購読者をまとめ、ユーザーの退会・地域変更の確認と通知の取得を1回のSQLで行います。

### 画像配信

画像本体はアプリプロセスごとに最大64MiB・4,096件のLRUに保持します。上限はキャッシュが保持する画像本体の合計であり、処理中のレスポンスなどを含むプロセス全体のメモリ上限ではありません。上限より大きな画像はキャッシュしません。

DBには `image_objects.content_version` を追加しています。INSERT時に新しいUUIDを付与し、UPDATE時はDBトリガーで必ず更新するため、別VMからの更新や初期化後の同じID・作成日時の再利用も判別できます。公開状態・所有者の鍵・画像の版番号・メディアタイプを毎回1回のSQLで取得し、版番号が一致した場合は画像本体をDBから転送しません。キャッシュミス時も同じSQL内で画像本体を取得します。キャッシュヒットでも署名・期限・削除・退会・差し替えの確認を省略しません。

この変更には、最適化版のスキーマで作ったDBが必要です（「起動」を参照）。形式が正しくても署名が不正なリクエストは、キャッシュミス時に画像本体を取得してから拒否する場合があります。これはDB往復を1回にまとめるためのコストで、返却するHTTPステータスや画像のアクセス条件は変えていません。

最適化途中の実装とのDB呼び出し回数の比較（通常の成功リクエスト、認証込み。SQLバッチは1回と数えます。変更前は画像・単一投稿の追加最適化より前の状態）:

| API | 変更前 | 変更後 |
| --- | ---: | ---: |
| `GET /api/me` | 2 | 1 |
| `GET /api/me/export` | 3 | 1 |
| `GET /api/posts/:postId` | 3 | 1 |
| `GET /api/posts/:postId/comments` | 4 | 1 |
| `GET /api/posts/:postId/realmojis` | 4 | 1 |
| `GET /api/images/:imageId` | 2 | 1 |

通知のポーリングは接続ごとの実行から、プロセス内の購読者をまとめた500ms間隔の実行に変更しました。購読者が増えても1巡のSQL実行は1回です（SQL内の対象ユーザー・通知の検索量は購読者数に比例します）。接続開始時の認証とDB時刻取得は1バッチで行い、その後の共有ポーリングとは分けています。

接続ごとのDB時刻より後に作られた通知のうち、期間が終了していない最初の1件を `created_at, id` 順で返します。退会・地域変更・署名鍵の不正を毎回DBで確認し、対象の接続を終了します。通知や認可結果はキャッシュしません。購読者がゼロになるとポーリングを停止し、実行中のSQLもキャンセルします。遅いSSEクライアントへの送信は各HTTPハンドラーが担当し、他の購読者のポーリングを止めません。

認可・セッション・画像の削除状態はDBで確認します。プロセス間キャッシュの同期や失効待ちは追加していません。画像本体は引き続きDBに保存します。

### 海外リージョンのDB往復削減

通常の書き込みを `sql/001-schema.sql` の `optimized_write` にまとめました。登録・ログインは1回、認証が必要な書き込みは認証SQL＋更新SQLを1バッチで送り、1回のDB呼び出しで完了します。投稿、コメント、RealMoji、プロフィール・画像、友人申請、フォロー、ブロック、ログアウト・退会が対象です。管理者APIは対象外です。

更新関数の呼び出し全体が1トランザクションです。ユーザー行のロック順序、投稿期間の共有ロック、認可、制約、失敗時のロールバックを維持します。更新結果が不明な通信障害で二重更新を起こさないよう、書き込みの独自リトライは追加していません。投稿作成の時刻はDB側の `clock_timestamp()` で取得します。

Memories・コメント・RealMoji一覧も、認証と本処理を1バッチで呼び出します。pgxは `default_query_exec_mode=exec` に設定し、初回実行時のDescribe用の往復も省きます。パラメーターは引き続きバインドします。このモードはテキスト形式を使うため、画像転送時のbytea表現には帯域コストがあります。

認証バッチ化より前に行った、DBへのTCP通信に片道200ms、往復400msの遅延を入れた独立した検証結果（秒、p99）:

| リージョン | 同時利用者 | 読み取り・変更前 | 読み取り・変更後 | 書き込み・変更前 | 書き込み・変更後 |
| --- | ---: | ---: | ---: | ---: | ---: |
| europe | 8 | 1.618 | 0.810 | 5.238 | 0.817 |
| america | 8 | 1.614 | 0.814 | 4.846 | 0.817 |
| europe | 16 | 未測定 | 0.813 | 未測定 | 0.818 |
| america | 16 | 未測定 | 0.819 | 未測定 | 0.819 |

変更前は今回の海外向け変更を入れる直前の最適化版です。各リージョンを別々に測定し、最初の1巡はウォームアップとして集計から除外しました。8人ではリージョンごとに読み取り96件・書き込み128件、16人では192件・256件です。変更後は集計対象の全リクエストが読み取り1秒・書き込み3秒以内でした。

これは `overseas_latency_test.go` の独立した負荷で、作成中のベンチマークには依存しません。実際のDB通信に遅延を入れ、HTTPハンドラーはプロセス内で実行します。現行ルーターの地域間遅延200msは往復の予算なので、この検証の往復400msはそれより厳しい遅延です。ただし画像サイズ、データ量、帯域制限、VMのCPU制限、競合の分布、ルーター経由のHTTP通信は本番負荷を再現しておらず、ISUCONスコアや昇格の実測ではありません。

認証バッチ化後の追加測定（同じ往復400ms・16人同時、秒、p99）:

| リージョン | 読み取り・バッチ化前 | 読み取り・バッチ化後 | 書き込み・バッチ化前 | 書き込み・バッチ化後 |
| --- | ---: | ---: | ---: | ---: |
| europe | 0.813 | 0.411 | 0.818 | 0.415 |
| america | 0.819 | 0.416 | 0.819 | 0.413 |

各地域の読み取り192件・書き込み256件を集計しました。この測定は通知SSEや実サイズの画像転送を含みません。スコアの測定ではありません。

#### 認証と本処理のバッチ化

一般ユーザーのAPIでは `BatchSessionMiddleware` と `pgx-auth` ドライバーを使います。ヘッダーからトークンハッシュを作り、最初のDB問い合わせ時に `optimized_auth` と本処理SQLをPostgreSQL拡張プロトコルの1バッチで送ります。SQL文は2つですが通信は1往復で、2文全体が暗黙のトランザクションになります。管理者APIは従来の認証方式を維持しています。

`optimized_auth` は有効セッション・アクティブユーザー・必要な地域を毎回確認します。認証失敗は後続SQLの実行を止めます。認証したユーザーIDをトランザクション内だけ有効な設定へ格納し、本処理はそのIDを使います。ユーザー入力は引き続きバインドし、接続再利用時に認証結果は残しません。書き込み側の行ロックと再確認も維持します。

入力不正で本処理SQLへ到達しない場合は認証だけを実行し、従来と同じく401や地域不一致の403を入力エラーより優先します。書き込みはバッチのコミット完了まで確認してから結果を返し、送信後の通信エラーで更新を独自に再試行しません。読み取りは行を順次処理するため、検索やZIPエクスポートで全画像を追加バッファへ保持しません。

バッチ用ミドルウェアは、成功レスポンスの前に必ずDB問い合わせを行うハンドラー専用です。DBを使わずに成功を返す汎用ハンドラーには従来の `SessionMiddleware` を使用してください。スキーマに `optimized_auth` が追加されたため、最適化版のスキーマで作ったDBが必要です。

再現には専用DBとPython 3を使います。以下はDBを `127.0.0.1:25432` に用意した例です。テストは指定DBのテーブルを再作成します。

```sh
# 別ターミナルで起動。25433から25432へ片道200msを加える
python3 webapp-optimized/tools/db_latency_proxy.py

# テスト専用DB overseas_test を事前に作成して実行
ISUREAL_SESSION_TEST_DSN='postgres://postgres@127.0.0.1:25432/overseas_test?sslmode=disable&default_query_exec_mode=exec' \
ISUREAL_LATENCY_TEST_DSN='postgres://postgres@127.0.0.1:25433/overseas_test?sslmode=disable&default_query_exec_mode=exec' \
ISUREAL_LATENCY_ENFORCE=1 ISUREAL_LATENCY_USERS=16 \
  go -C webapp-optimized/go test -run '^TestOverseasLatency$' -v -count=1 -timeout=10m
```

`ISUREAL_LATENCY_USERS` の既定値は8です。遅延テストは `ISUREAL_LATENCY_TEST_DSN` がない通常のテスト実行ではスキップされます。

## 検証

専用のPostgreSQL 16に対して、コピーした既存の結合テストと追加テストを実行できます。指定したDBは各テストでテーブルを再作成するため、テスト専用DBを指定してください。

```sh
cd webapp-optimized/go
ISUREAL_SESSION_TEST_DSN='postgres://USER:PASSWORD@HOST:PORT/TEST_DB?sslmode=disable&default_query_exec_mode=exec' \
  go test -race ./... -count=1
go vet ./...
go build ./cmd/isureal
```

通知の追加テストでは、64接続を含む一括取得のSQL回数、接続時刻の違い、同時刻の通知順序、他ユーザー・終了済み期間の除外、退会・地域変更、購読者ゼロからの再開を確認します。

追加テストは、元の友人グラフ展開をテスト内に保持し、地域・期間・公開範囲・ブロック・フォロー・退会・削除の組み合わせについて、フィードと単一投稿認可の結果を照合します。投稿期間の共有ロック下で投稿が進むことと、期間終了の更新が待機することも確認します。既存テストが同一ユーザーの競合投稿、ログイン失効、画像署名、ページング、Memories、ZIPなどを検証します。

DB呼び出し回数はpgxのQuery/Batchトレーサーを用いた結合テストで確認しています（1バッチ内のSQL文数とは区別します）。認証バッチでは未認証・地域不一致・不正入力の優先順位、空の検索結果、接続再利用時のユーザー分離、コミット時の遅延制約トリガー失敗によるロールバックも検証します。書き込みの回数、同時更新、DBトリガーによる途中失敗時のロールバックも検証します。海外向け変更後にPostgreSQL 16で既存・追加テスト全体の `go test -race ./...`、`go vet`、ビルドを確認しました。画像では独立した2つのアプリのキャッシュを維持したまま、別アプリ相当のDB更新、鍵変更、削除・退会、空画像、スキーマ初期化とID再利用を検証しています。キャッシュヒット時にDBから画像本体が返らないことと、容量・件数制限、並行利用も確認します。

署名の追加テストでは元の1,000回反復実装との照合、鍵の長さ・画像ID・有効期限の境界値、キャッシュの容量制限と退避、返却バッファの独立性、並行アクセスを検証しています。

署名単体の独立した測定（Go 1.26.5 / linux amd64、同一マシンで各3回、中央値）:

| 処理 | 時間/回 | 割り当てバイト/回 | 割り当て回数/回 |
| --- | ---: | ---: | ---: |
| 元の1,000回反復 | 365.9µs | 約512KB | 6,002 |
| オブジェクト再利用・キャッシュなし | 113.0µs | 832B | 11 |
| 同一入力のキャッシュヒット | 0.052µs | 32B | 1 |

キャッシュ未使用でもこの測定では約3.2倍です。キャッシュの実際の効果はヒット率に依存し、この値はアプリ全体の速度倍率やISUCONスコアではありません。測定用コードは一時ファイルとして実行・削除し、作成中のベンチマークには依存していません。

画像の検証は、JPEGのヘッダーだけで寸法の上限超過と非JPEGを拒否し、残りを読まないことを `TestReadJPEG` で確認します。IPのBANは元のアプリのテストを移し、読み直しの間隔を待ってから確認するように変えています。内部通信がBANされないことも確認します。

通常の生成済み初期データ（Small、確認時点ではユーザー1,000件・投稿9,909件）を最適化版のスキーマで入れたDBで、`sql/init.sh`（差分の巻き戻しと統計更新、約0.9秒）を確認しました。`/api/initialize` のあとに、登録したユーザー・アップロードした画像・ログインセッションが消えることも確認しています。

## 残る負荷源

今回の海外向け変更後のISUCONスコアは未計測です。検索はUnicodeの厳密な挙動を維持するため、非一致が多い場合は引き続き多数のユーザーを走査します。友人グラフが密なフィード、初回の大量通知作成、画像転送量も負荷源です。ZIP本体は元と同様にレスポンス送信前にメモリへ構築します。追加インデックスにはディスク容量と書き込みコストがあるため、完成したベンチマークと実際のリソース条件での調整余地があります。
