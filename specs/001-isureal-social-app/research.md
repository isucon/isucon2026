# Phase 0 Research: ISUReal Social Application

## 1. サーバー構成

- **Decision**: 最新安定版Go 1.26.5の単一コードベースからAPIとワーカーの2バイナリを作り、
  Echo v5 (`github.com/labstack/echo/v5`)とpgxを使う。
- **Rationale**: Go公式リリース履歴で2026-07-07公開の1.26.5が現時点の最新安定版であり、
  Echo公式ドキュメントではv5がCurrent、Go 1.25以上を要件としているため、この組み合わせは互換性を満たす。
  Echoのルーティング、入力バインド、ミドルウェア拡張点と明示的SQLにより、認可・競合・クエリを追跡しやすく、
  将来の競技仕様でもHTTP処理とデータアクセス境界を個別に差し替えやすい。
- **Alternatives considered**: chiは軽量だが、プロジェクト方針としてEchoを採用するため不採用。
  Echo v4はLTS保守版であり、新規実装では現行のv5を優先する。Node.jsのみの構成は可能だが、
  CPU負荷のあるJPEG再エンコードと並行処理を一つの実装言語にまとめる利点を優先した。

## 2. Webクライアント

- **Decision**: React + TypeScript + ViteのSPAとService Workerを採用し、対応対象を最新安定版デスクトップChromeに限定する。
- **Rationale**: 投稿・フィード・関係・通知・Memoriesの状態を画面単位で分離でき、Push API、通知クリック、
  キーボード操作をPlaywrightでE2E検証できる。OpenAPIから生成した型でAPIドリフトを防げる。
- **Alternatives considered**: サーバーサイドテンプレートはService Workerと複雑な画面状態の共有が冗長になる。
  Next.jsのSSRは本仕様にSEO要件がなく、実行面を増やすため採用しない。

## 3. 永続化と整合性

- **Decision**: PostgreSQLを正本とし、外部キー、CHECK、複合UNIQUE、行ロック、条件付き更新で不変条件を守る。
- **Rationale**: 同一投稿期間の投稿、関係ペア、単一セッション、通知、冪等性などの競合をアプリ内ロックに
  依存せず守れる。キーセットページングの複合索引と、ワーカーの`SKIP LOCKED`取得も一つのDBで扱える。
- **Alternatives considered**: インメモリロックは複数プロセス/再起動で破れる。イベントソーシングは監査性が高いが、
  初期実装の複雑性が要件規模に対して過大。MySQLでも実装可能だが、条件付き制約と競合テストの明瞭さを優先した。

## 4. 画像保存とメタデータ除去

- **Decision**: 受信バイト数を先に制限し、APIプロセスから分離した一回限りのサニタイザプロセスでJPEGを
  デコード後、画素を新しいJPEGへ再エンコードする。APIは同時実行枠を制限し、子プロセスへ設定可能な
  メモリ、CPU、処理時間上限を適用する。枠不足、資源上限到達、異常終了、タイムアウトは503へ変換する。
  出力は所有ユーザーを名前空間に含む不変ローカルファイルへ保存し、SHA-256を完全性確認用メタデータとして
  DBへ記録する。異なるユーザー間では同一内容でも物理ファイルを共有しない。
- **Rationale**: EXIFその他の入力セグメントをコピーせず、配信対象をサニタイズ済み出力だけにできる。
  所有者単位の名前空間によりアカウント完全削除の対象が明確になり、DB確定前の一時ファイルも公開しない。
  サニタイザの障害をAPIから隔離することで、展開寸法を固定的な受理上限にせず、資源枯渇時もAPIを継続できる。
- **Alternatives considered**: 元JPEGからAPPセグメントだけ除く方式は未知メタデータの取りこぼしがある。
  ユーザー横断の内容アドレス共有は重複を減らせるが、完全削除時の所有権と削除順序を複雑にする。
  DB `bytea`は原子性が単純だが、大きな画像でDB I/Oを強く結合する。外部S3は初期ローカル競技環境に不要。
- **Constraint resolution**: 仕様どおり画素数・縦横寸法では拒否しない。展開時の資源上限は寸法判定へ
  変換せず、隔離プロセスの運用境界として管理する。障害時は一時ファイルと子プロセスを回収し、DB行や
  公開ファイルを残さない。通常の受理テストと、503・API生存・再試行を確認する障害注入テストを分離する。

## 5. 認証・セッション・SecretKey

- **Decision**: ユーザー作成時にSecretKeyを発行して登録応答で返し、クライアントは端末のIndexedDBへ保存して画面に表示する。ログインはユーザー名とSecretKeyを送信する。256-bitランダムBearerセッショントークンのハッシュ保存、ユーザーごとに
  有効セッション最大1件、管理者は別テーブル/別認証ミドルウェアとする。トークンは`Authorization: Bearer`
  だけで受理し、Cookie、URL、form bodyからは受理しない。Webクライアントのユーザートークンは同一Originの
  IndexedDBへ永続化し、ログアウト、セッション置換、アカウント削除時に削除する。SPA/API/認可画像は同一Originとし、
  CORSを許可せず、ブラウザが送る`Origin`と`Sec-Fetch-Site`を完全一致または`same-origin`として検証する。
  APIと認可画像は常に`no-store`とし、SPAにはself限定CSP、frame禁止、referrer抑止、cameraのself限定を適用する。
- **Rationale**: 平文資格情報を保存せず、一般ユーザー資格情報による管理API利用を構造的に防ぐ。
  新規ログイン時はユーザー行をロックして旧セッションとPush購読を同一トランザクションで無効化する。
  Cookieへ自動付与される認証情報を使わないためCSRF依存を作らず、Origin検証を多層防御として適用できる。
  IndexedDBはブラウザ終了後も有効とする仕様を満たしつつ、URL・DOM・ログへのトークン露出を避けられる。
- **Alternatives considered**: 自己完結JWTは即時の単一セッション無効化に失効管理が別途必要。
  Basic認証の常用は毎回資格情報の照合が必要で、セッション要件にも合わない。
  CookieセッションはOpenAPIのBearer契約と異なり、CSRF tokenやCookie属性を含む別の公開契約が必要になる。

## 6. 認可とフィード

- **Decision**: `VisibilityPolicy`を単一ドメインサービスとして、ブロック、活動状態、投稿期間、投稿済みゲート、
  直接友達、距離2、公開範囲、フォローを取得経路に依存せず評価する。
- **Rationale**: フィード、投稿詳細、交流、Memoriesで判定がずれることを防ぐ。距離2フィードは直接友達を除外し、
  コメントは直接友達または公開、RealMojiは距離2も許すという差を明示できる。
- **Alternatives considered**: 各SQL/ハンドラーへの認可埋め込みは公開範囲変更やブロック競合で漏えいしやすい。
  非正規化した可視投稿一覧は初期正解実装には不要で、将来の競技仕様が整合性検証付きで導入できる。

## 7. 投稿期間と通知スケジューリング

- **Decision**: 全時刻をUTC instantで保存し、PostingWindow作成時に地域固定オフセットと地域日を確定する。
  DB時刻を基準に、ワーカーが期限到来ScheduleをロックしてPostingWindow・通知を一意に作る。
- **Rationale**: 夏時間やサーバーローカル時刻の影響を排除し、同地域の次Window開始時にだけ前Windowを終了できる。
  `(region, local_date)`と`(recipient, posting_window)`の一意制約が再試行時の重複を防ぐ。
- **Alternatives considered**: cronのみでは管理者による取消/変更、実行後未設定、再起動時の取りこぼしを扱いにくい。
  地域日終了でWindowを閉じる方式は仕様に反する。

## 8. Web Pushの部分失敗

- **Decision**: アプリ内Notification確定後、その通知IDを論理Push通知IDとするPushAttemptを別ジョブとして
  送信し、一時失敗は初回後最大3回、恒久失敗は購読を無効化する。全試行で同じ論理通知IDを送信し、
  Service WorkerはそのIDを通知タグとして同じ表示へ収束させる。購読識別子と通知IDを送信時にも照合する。
- **Rationale**: 外部配信失敗でPostingWindowやアプリ内通知をロールバックせず、古い端末への再送を防げる。
- **Alternatives considered**: DBトランザクション中の同期Pushは外部障害でロックを長時間保持し、部分失敗の再試行も曖昧になる。

## 9. 冪等性

- **Decision**: 読み取り専用操作と内部ワーカーを除く全状態変更HTTP操作へ`Idempotency-Key`を必須化する。
  認証済み操作は`(principal_type, principal_id)`、未認証の自己登録・一般/管理者ログインは
  `(auth_kind, normalized_username)`をcaller scopeとし、`(caller_scope, operation, key, generation)`を一意にする。
  正規化要求ハッシュ、状態、確定応答、確定時刻を保存する。503では状態を`retryable`へ戻して応答を確定せず、
  同じキーの再実行を許可する。最初の503以外の結果確定から24時間経過後は新generationを割り当てる。
- **Rationale**: 同じ要求には同じ結果、異なる内容には409を返し、処理中の並行再送も一件へ直列化できる。
  応答確定とドメイン変更を同一トランザクションで記録する。
- **Alternatives considered**: リクエストIDだけのUNIQUEは24時間後再利用を表現できない。キャッシュのみでは再起動で保証が消える。
  認証操作だけを例外にするとログインの並行再送でセッションを複数回置換し得るため採用しない。

## 10. ページングと検索正規化

- **Decision**: すべて50件のキーセットページングとし、ソート値+IDをバージョン付き・HMAC署名済み
  Base64URLカーソルへ格納する。表示名検索キーはNFC後Unicode Default Case Foldingした値を保存する。
- **Rationale**: 同時追加時の重複を避け、カーソル改ざんや異なる一覧への転用を拒否できる。
  ユーザー名はASCII lowercaseを別列に保存して一意制約を張る。
- **Alternatives considered**: offsetは同時挿入/更新で重複や欠落が起きる。DBロケール依存比較は環境差が出る。

## 11. アカウント削除

- **Decision**: 削除要求時に`deletion_pending`へ遷移し、セッション/購読を無効化して全通常クエリから除外する。
  30日未満の正しいログインだけが復旧する。期限以後の全アクセスは復旧不能として扱い、期限到来ワーカーまたは
  期限後の同名登録/ログイン処理がユーザー行をロックし、関連DB行とアカウント専用画像を同期的に削除してから
  ユーザー名を解放する。稼働中は期限から60秒以内に物理削除を完了する。
- **Rationale**: 猶予中の関係を凍結し、復旧時に元の状態を再開できる。期限以後のログイン競合はロック下で
  完全削除を優先する。共有内容アドレス画像を避けてアカウント単位の削除対象を明確にし、DB削除だけ先に
  確定して画像が残る状態を作らない。
- **Alternatives considered**: 即時cascade削除は30日復旧を満たさない。匿名化だけでは完全削除とユーザー名再利用を満たさない。

## 12. マイグレーション方式

- **Decision**: 本番相当スキーマ変更はforward-onlyとし、各migrationを単一トランザクションで適用する。
  開発/競技初期化は全スキーマを削除して既知状態へ再構築するresetコマンドで行う。
- **Rationale**: down migrationが安全でないデータ変換を形式的に逆変換せず、競技初期化の再現性はresetで保証できる。
- **Alternatives considered**: 全migrationへdown SQLを要求する方式は、不可逆なデータ変換で誤った復旧保証を与える。

## 13. 競技要件との責務分離

- **Decision**: 本フィーチャーは正しい基準実装、テスト、初期化可能なスキーマ、Clock/Push/Repository境界までを作る。
  負荷モデル、採点、意図的ボトルネック、課題台帳、較正、配布監査は別feature specificationでのみ決める。
- **Rationale**: `spec.md`がアプリ仕様を正本とし、競技要素による機能要件の上書きを禁止している。
  Constitutionの正しさと情報分離を守りつつ、未確定の性能条件を本計画へ混入させない。
- **Alternatives considered**: この計画で仮のボトルネックやスコア帯を定義すると、根拠のない難易度と
  非公開情報が公開アプリ設計へ混ざるため不採用。

## Resolution Summary

Technical Contextの全項目を上記判断で確定した。未解決の`NEEDS CLARIFICATION`はない。
性能数値は不明なのではなく、仕様により別競技フィーチャーの責務として明示的に対象外である。
