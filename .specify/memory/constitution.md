# ISUCON 2026 Constitution

## Core Principles

### I. 公開仕様の正しさを不変条件にする
アプリ基準実装、ベンチマーカー、負荷生成、整合性検査、および想定解は、参照する版が固定された
同一の公開仕様とデータ不変条件に従わなければならない（MUST）。性能を意図的に低下させる実装で
あっても、機能、認証・認可、応答、永続化、および並行実行時の整合性を壊してはならない
（MUST NOT）。各競技シナリオには正常系、境界値、異常系、および競合を含む自動テストを用意し、
最適化前後へ同じ判定を適用しなければならない（MUST）。スコア向上は正しさの欠落を正当化しない。

### II. 仕様を段階的に固定する
ISUCON作問では、アプリの公開機能とデータ不変条件を定める「アプリ基準仕様」を先に完成させ、
その後に「競技仕様」で負荷モデル、採点、意図的ボトルネック、想定解、競技環境、および配布条件を
確定してよい（MUST）。アプリ基準仕様は未確定のスコア帯や負荷条件を推測してはならず
（MUST NOT）、対象外の競技事項と後続仕様への引渡条件を明記しなければならない（MUST）。
競技仕様は参照するアプリ基準仕様・契約・マイグレーション・テストの版を固定し、公開機能、認証・
認可、プライバシー、およびデータ不変条件を上書きまたは緩和してはならない（MUST NOT）。

### III. ボトルネックを設計資産として分離する
意図的な性能問題は、競技仕様の段階で、機能要件から分離された交換可能な実装点として設計しなければ
ならない（MUST）。各問題には識別子、配置箇所、原因、発現条件、観測可能な症状、想定する改善、
期待スコア帯、および無効化または強度調整の方法を非公開の作問資料に記録しなければならない（MUST）。
N+1、索引不足、過剰ポーリング、直列処理、重複計算等を複数箇所へ不可分に埋め込んではならない
（MUST NOT）。アプリ基準実装は、通常のコード境界、データアクセス層、設定値、または差し替え可能な
アルゴリズムを用意するが、競技仕様が確定する前に意図的な遅さを導入してはならない（MUST NOT）。

### IV. 解法・ベンチマーク・スコアを再現可能に較正する
競技仕様で採用した各ボトルネックは、初期実装、単独で解消した状態、複数を段階的に解消した状態、
および想定上位解のベンチマークで検証しなければならない（MUST）。ベンチマーカーは負荷条件、
初期データ、時間進行、乱数、タイムアウト、検査、採点式、および実行環境を明示的に管理し、同一条件で
結果を再現できなければならない（MUST）。試し解きで複数の妥当な改善経路、段階的な課題顕在化、
スコア分散、フレーク率、および主要資源の飽和を確認する。これらは競技設計開始後には必須だが、
アプリ基準仕様の作成時点で未確定であること自体を品質ゲート違反として扱ってはならない（MUST NOT）。

### V. 競技に必要な品質境界を明示する
意図した性能問題以外は、各仕様段階で宣言した品質境界を満たさなければならない（MUST）。認証・認可、
入力検証、データ整合性、エラー処理、秘密情報の非開示、および仕様判定に必要な診断可能性は延期しては
ならない（MUST NOT）。一方、本番サービス固有のレート制限、WAF、可用性目標、障害対応、監査制度、
ログ・メトリクス・トレースの保存基盤と保持期間、保存時暗号化の鍵管理等は、競技の正しさ・公平性・
診断可能性に不要なら、責任をデプロイ環境または後続仕様へ明示して対象外にできる（MAY）。対象外事項を
暗黙の未確定事項として残してはならない（MUST NOT）。単体、契約、統合、E2E、マイグレーション、
競合、および必要なベンチマーカーテストを仕様段階とリスクに応じてCIで再現可能に実行する。

## 仕様段階と責務境界

1. **アプリ基準仕様**: 利用シナリオ、公開契約、データ不変条件、認証・認可、プライバシー、入力境界、
   構造化ログ等の必須診断情報、テスト、および競技事項を含む対象外を定義する（MUST）。性能数値、
   スコア、負荷、非公開課題台帳は未定義でよい。正しい基準実装と自動テストを先に完成させる。
2. **競技仕様**: 参照するアプリ基準仕様の版、競技環境、負荷・採点、初期データ、時間・乱数、
   ボトルネック台帳、想定解、較正条件、診断信号、および配布境界を定義する（MUST）。
3. **競技配布**: 正しい基準実装とテスト → ベンチマーカー → ボトルネック導入 → 単独・累積較正 →
   試し解き → 配布物監査、の順序を完了して初めて実施できる（MUST）。この順序は複数の連結された
   feature specificationとtasks.mdをまたいでよい。
4. 各仕様は自身の段階を明記し、その段階で必須のゲートだけを評価する（MUST）。後続段階へ明示的に
   引き渡した事項は例外ではない。現在段階で必須のゲートを外す場合だけ、例外手続きを使用する。

## 作問・性能設計上の制約

- 公開仕様と競技者向け初期実装は、特定の想定解や内部のボトルネック一覧を漏らしてはならない（MUST NOT）。
- 初期化処理は、スキーマ、索引、初期データ、および当該段階で定義済みの設定を毎回既知の状態へ
  戻さなければならない（MUST）。
- ボトルネック同士の依存関係と顕在化順序を記録し、一つの修正で無関係な課題が偶発的に消滅する場合は、
  意図と難易度への影響をレビューしなければならない（MUST）。
- キャッシュ、非正規化、バルク化、並列化、ポーリング変更等の想定解について、古いデータ、二重処理、
  競合、再起動、および部分障害時の正しさを検証しなければならない（MUST）。
- ベンチマーカー、初期実装、想定解、試し解き結果、および配布パッケージには追跡可能な版を付け、
  組み合わせの互換性を記録しなければならない（MUST）。

## 開発ワークフローと品質ゲート

1. 計画は仕様段階を宣言し、現在段階の公開契約、正しさ、テスト、初期化、情報分離、および後続段階への
   引渡条件をConstitution Checkで示さなければならない（MUST）。競技仕様の計画では、これらに加えて
   ボトルネック挿入点、課題台帳、ベンチマーク再現条件、較正、および想定解検証を示す（MUST）。
2. タスクは現在段階に必要な成果物を依存順で示す（MUST）。アプリ基準仕様では正しい実装とテスト、
   初期化、版固定、競技仕様への引渡しまでを対象とする。競技仕様以降ではベンチマーカー、ボトルネック、
   較正、試し解き、配布監査を前項の順序で対象とする。
3. 各性能課題の変更では、機能テスト、初期スコア、解消後スコア、分散、資源指標、および他課題への
   影響を同一条件で記録しなければならない（MUST）。
4. 競技配布前に、競技者と同等の情報・時間・環境による試し解き、クリーン環境でのセットアップ、
   初期化の反復、長時間負荷、秘密情報検査、および配布物の再現ビルドを通過しなければならない（MUST）。
5. 現在段階で必須の品質ゲートの例外は、理由、具体的な責任者、期限、難易度と公平性への影響、および
   解消計画を記録した場合に限り認める。

## Governance

本Constitutionは、リポジトリ内の他の開発慣行およびテンプレートに優先する。改定案は、変更内容、
理由、影響を受ける成果物、競技難易度・公平性・情報管理への影響、および移行方法を文書化し、レビューで
承認された後に適用しなければならない（MUST）。改定時は依存テンプレートと実行時ガイダンスを同じ変更で
同期する。

バージョンはセマンティックバージョニングに従う。原則またはガバナンスの削除・互換性のない再定義は
MAJOR、新しい原則・セクションまたは実質的な義務の追加はMINOR、意味を変えない明確化はPATCHとする。
すべての仕様、計画、タスク、およびレビューは適用中のバージョンと自身の仕様段階への準拠を確認しなければ
ならない（MUST）。期限切れの例外を残してはならない（MUST NOT）。
