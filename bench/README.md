# ISUReal ベンチマーカー

`webapp/go` の `/api` に対して、初期化 → 事前検証 → 負荷走行を実行する。
結果 JSON を標準出力、進捗を標準エラー出力へ出す。

## シナリオ

### 設定

ISUReal はアジアで流行っている BeReal 風の写真共有サービスである。初期データのユーザーは 99% がアジアにいて、
1 年分の投稿と画像（約 16 GB）が溜まっている。サーバーは asia、europe、america に 1 台ずつあり、DB は asia にしかない。
海外のサーバーから DB へは往復 100 ms かかる。負荷走行は 60 秒で、9 秒を 1 日として各地域が 5 日を過ごし、
最後の 9 秒は全地域が同時に投稿するグランプリになる。

### 走行の前

ベンチはまず、前回の走行で増えたデータを消して初期状態に戻す。次に 1 人のユーザーで、登録やログインなどの
基本機能を確かめる。続いて無作為に選んだ数人について、過去の Memories、友達の一覧、エクスポートが初期データと
一致するかを確かめ、並行して負荷をかけるユーザーを用意する。この準備は 45 秒以内に終わらなければならない。

最初のユーザーは、asia が 8 人とインフルエンサー 2 人、europe と america が 4 人とインフルエンサー 1 人ずつで、
友達関係は同じ地域の中だけにある。さらに初期データのユーザーが地域ごとに 8 人までログインして加わる。

### ユーザーの種類

- インフルエンサー（認定公開アカウント）: 毎日 public に投稿し、普通のユーザーにフォローされる。
- 普通のユーザー: 毎日 1 回投稿する（投稿しないと他人の投稿を見られない）。投稿のあとの過ごし方で 4 種類に分かれる。
  投稿だけして終わる人が 4 割、フィードと写真を眺める人が 3 割、RealMoji を送る人とコメントを書く人が 1.5 割ずついる。
  ときどき友達を探して申請し、届いた申請に答え、プロフィールや写真を変え、フォローやブロックをする。
- 初期データのユーザー: 昔からいる人。普通のユーザーと同じく投稿し、ときどき自分の過去の履歴を見返す。
- 思い出を見返す人: しばらくぶりに戻ってきて、昔の Memories を月や日付で見返し、ときどき全データをエクスポートする。
  1 年分の履歴から無作為に選ぶので、最近のデータだけをメモリに置く実装では遅くなる。
- 不正な利用者: 走行の途中に現れ、ログインの失敗を繰り返したり、壊れた画像を送ったりする。

### 1 日の流れ

各地域では 9 秒ごとに新しい 1 日が始まり、地域の全員に「今日の写真を投稿しよう」という通知が届く。1 日の始まりは
asia（0 秒）、europe（3 秒）、america（6 秒）の順にずれる。通知を受けたユーザーは少し間を置いて（中央値 1 秒）
写真を投稿し、友達のフィードを読む。その日のうちにここまで終われば「ゲート通過」になる。

1 日が始まるとき、前の日に RealMoji を最も多く受けた人を、管理者が認定公開アカウントにする。

### ユーザーの増え方

地域で 1 日が始まるとき、前の日の失敗率が 1% 以下なら新しい人が来る。前の日にゲートを通過できた人は、通過が
速いほど多くの友達を誘う。通知がすぐ届いていたら投稿を始めたはずの時刻から友達のフィードを読み終えるまでが
0.25 秒以内なら 2 人、1 秒で 1.5 人、2 秒以上なら 0 人で、その間は直線で減る。通知が遅れればその分も待たせたことに
なる。通過できなかった人は 1 人ずつ思いとどまらせ、BAN された人も通過できなかった人に数える（値は暫定で、スコアと
増え方を見ながら調整する）。全員がすぐに通過すれば、1 日で 3 倍になる。アプリが詰まり始めると通過が遅くなるので、
詰まりきる前に増え方が鈍る。失敗の多かった日の翌日は誰も来ない。新しい人の 7 割は友達に誘われて来て、既存のユーザーに友達申請を送る。asia の人は 8 割が
asia の人に、海外の人は 8 割が asia の人に申請する。残りの 3 割はインフルエンサーをフォローする。

アプリが遅いと、その日のうちに投稿を終えられない人が増え、翌日に来る人が減る。海外のサーバーは DB まで遠いので、
何も工夫しなければ海外の人は 1 日のうちに投稿を終えられず、海外は育たない。

### グランプリ

最後の 9 秒（51 秒から）は、全地域が同時に 1 日を始めるグランプリになる。この日は新しい人は来ず、今いる人が
全地域で一斉に投稿する。この日のゲート通過は、通常のゲート通過の 2 倍の点になる。

### 得点

ユーザーの行動ごとに、アプリにかかる手間に見合った点を足す（重みは「結果と検証範囲」）。減点はない。

### 失格になる場合

次のどれかが起きると、その走行は失格になり、スコアは 0 になる。

- 見えてはいけない投稿（ブロックした人や友達でない人の投稿など）がフィードに出る。
- 削除から 5 秒を過ぎた投稿の画像を返す。
- 過去の履歴やエクスポートが初期データと違う。
- 5 秒間のエラー率が 10% を超える。
- 事前検証で、地域外のサーバーからのアクセス、JPEG でない画像、寸法が上限を超える画像、署名の違う画像 URL、
  期限切れの画像 URL を拒否しない。

書き込みが成功を返したあとは、どの地域からもすぐにその結果が見えなければならない。海外にキャッシュを置く場合も、
この条件を守る必要がある。

普通のユーザーを BAN しても失格にはならない。BAN されたユーザーはサービスを使うのをやめ、ログに悪評として残り、
増え方では通過できなかった人に数え続ける。

### 走行の後

ベンチは無作為に選んだ 300 人について、投稿と友達関係が失われていないかを確かめる。

TCP接続には接続時に `SO_LINGER=0` を設定し、閉じるときはRSTを送る。通知購読のキャンセルや
ベンチ終了後に、RouterにFINのACKを待つ接続が残るのを防ぐ。keep-alive中は接続を使い回す。
負荷走行は通知購読の終了も待ち、走行終了時には管理者と負荷ユーザーの待機中の接続を閉じる。

## 使い方

```sh
# Compose を起動済みのリポジトリルートから実行
# 対象の共有 DB は initialize により初期化される
go -C bench run . -users 8 -duration 25s
```

| フラグ | 既定値 | 内容 |
|---|---|---|
| `-target` | `ISUXBENCH_TARGET`、なければ `http://app.127.0.0.1.nip.io:18090` | 接続先 |
| `-host` | 空 | HTTP Host の上書き（VM の IP に接続する場合など） |
| `-users` | `8` | asia の最初の負荷ユーザー数（海外はその 1/2、1 人以上）。初期データのユーザーも地域ごとに同じ人数までログインする |
| `-images` | `ISUXBENCH_IMAGES`、なければ空 | 投稿に使う写真のアーカイブ（zip のパスか http(s) の URL）。空なら小さな画像を生成して使う |
| `-seed` | `0` | 走行の乱数の種（0 なら無作為に選ぶ）。同じ種なら同じユーザー名、過ごし方、写真の順になる |
| `-evil` | `true` | 負荷走行で不正な利用者を動かすか |
| `-quick-share` | `0.111`（1/9） | 通過した人が 1.5 人を誘う、通過までの時間（1 日に対する割合）。誘う人数の折れ線全体がこの値に比例して伸び縮みする。較正用 |
| `-duration` | `60s` | 負荷走行の長さ。短くするのは開発用 |
| `-scale` | `small` | 対象の DB の初期データの規模（`small` か `large`）。`datagen -scale` と合わせる |
| `-timeout` | `190s` | 全体の上限。詳しくは「supervisor からの実行」を参照 |
| `-verify-rate` | `ISUXBENCH_VERIFY_RATE`、なければ `0.1` | 負荷走行で重い検証（フィードの欠落、画像 URL の署名、履歴の画像）を行う操作の割合（0 より大きく 1 以下）。詳しくは「検証の間引き」を参照 |
| `-cpuprofile` | 空 | 走行全体の CPU プロファイルを書き出すファイル（`go tool pprof` で読む） |
| `-memprofile` | 空 | 走行の終わりに、起動からの割り当てのプロファイルを書き出すファイル |

`GOGC` を指定しなければ、GC の目標を 400 にする（常駐ヒープが小さく、既定の 100 では負荷走行中の GC が多いため）。

1 回の走行で asia / europe / america の 3 リージョンを同時に扱う。各ユーザーは自分のリージョンに
ルーターが振り分ける国（asia は JP / KR / CN / AU、europe は GB / DE / FR、america は US / CA / MX）を
`X-Country-Code` に付けて送る。管理者は JP から送る。
VM 環境では `make vm-benchmark BENCH_ARGS='-users 2 -duration 25s'` でも実行できる。

## 実行内容

事前検証では、初期データの管理者 `admin` / `password1234` でログインする。
検証ユーザーは登録時の SecretKey でログインし、重複登録、誤った鍵、プロフィール、
投稿前の空フィード、地域外のサーバーからのアクセスの 403、JPEG でない画像と 513x513 の画像の 400（プロフィール画像）、
署名の違う画像 URL と期限切れの画像 URL の拒否、再ログインとログアウトによるセッション失効を確認する。

事前検証のあと、初期データのユーザーとしてログインし、アプリが初期データどおりの内容を返すことを
確かめる。期待値は bench がリポジトリ直下の `dataset` から計算する（seed を作った `datagen` と同じもの）。
対象は友達の最も多い通常ユーザー、各リージョンから無作為に選んだ通常ユーザー、無作為に選んだ認定公開アカウントで、
走行ごとに変わる。並行に確かめる。

- Memories: 履歴のある月から無作為に 2 か月を選び、最後のページまで読んで、投稿（キャプション、公開範囲、位置、投稿時刻と
  on-time）、RealMoji（新しい順、最大 50 件）、コメント（古い順、最大 50 件）を比べる。
- 友達の一覧: 最後のページまで読み、関係の ID、新しい順、相手のプロフィールを比べる。
- エクスポート: ZIP の `posts.json` が全投稿を古い順に並べ、各画像が一致することを確かめる。
- 画像: すべての画像 URL が持ち主のシークレットキーから計算した署名と一致し、期限内であることを
  確かめる。投稿と RealMoji の画像は中身も取得して比べる（1 人あたり同時に 6 件まで）。

1 つでも違えば fail とする。履歴は読むだけで書き込まない。初期データの投稿期間と日付が重ならないよう、
負荷走行の `localDate` は履歴の最終日の翌日以降から始める。

初期データの検証と並行して、負荷ユーザーを用意する（`scenario/prepare.go`）。asia に `-users` 人とインフルエンサー 2 人、
europe と america にその 1/2（1 人以上）とインフルエンサー 1 人ずつを登録し、初期データの cohort のユーザー（書き込んで
よいユーザー）にリージョンごとに `-users` 人までログインする。リージョンごとに登録ユーザーを 1 列に並べて隣どうしを
友達にし（2 つ先は友達の友達になる）、4 人ごとに 3 つ先のユーザーをブロックする。インフルエンサーを認定し、登録ユーザーは
同じリージョンのインフルエンサーを 1 人フォローする。関係はまず地域の中でできる。cohort のユーザーは初期データの関係を
そのまま持つ。初期データの検証と負荷ユーザーの準備は、合わせて 45 秒以内に終わらなければ fail とする。

負荷走行では、投稿期間を時間割どおりに開き、各ユーザーは独立したクローズドループで動く。

- 時間割（`scenario/timetable.go`）: 走行の長さの 9/60（60 秒なら 9 秒）を 1 日とし、asia 0 秒、europe 3 秒、
  america 6 秒から 5 日ずつ投稿期間を開く。51 秒からの 6 日目は全リージョンが同時に開くグランプリ。開く日付
  （`localDate`）はリージョンごとに初日（UTC の今日か、履歴の最終日の翌日の遅い方）から 1 日ずつ進める。
  サーバーの時計は操作しない。
- ユーザーは同時に 1 リクエストだけ送り、待ち時間を置かない。通知は別の接続で購読し続ける
  （ストリームが切れたら購読し直し、エラーにはしない）。
- ユーザーの過ごし方（`scenario/user.go`）: 名前から決まる。投稿だけ 40%、閲覧 30%、RealMoji 15%、コメント 15%。
  cohort のユーザーは初期データの活発さで決める。投稿のあとに 1 日に行う操作の回数は、閲覧の人が 20 回、RealMoji と
  コメントの人が 15 回、投稿だけの人が 0 回（認定公開アカウントは 10 回まで）で、使い切ったら次の通知まで何もしない。
  点になる回数は 1 日にフィード 20 回、画像 4 回、投稿の詳細と一覧 8 回ずつ、プロフィール 4 回、RealMoji と
  コメント 5 件ずつまで。通知は投稿期間ごとに 1 回だけ数える。
  1. 通知を受けたら、ユーザーと日ごとに決まる指数分布の待ち（中央値 1 日の 1/9、上限 1 日の 8/9）のあと、現在の
     投稿期間を確かめて投稿する。10% のユーザーは、待つ前に friends フィードを覗く（今日まだ投稿していないので、
     ほかの人の投稿が見えれば失格）。公開範囲は、認定公開アカウントは public、ほかは friends か friends_of_friends。
     応答の内容と画像の署名を確かめる。待っている間に次の通知が来たら、その日は諦める。
  2. friends フィードを読んで検証に通り、その日のうちに終わればゲート通過とする。
  3. 前回の投稿が Memories にあること、自分の今日の投稿（`/api/posts/me/current`）と画像を確かめる。一部は投稿を
     削除し（5%）、公開範囲を変える（10%）。削除した投稿の画像は、削除から 6 秒後にもう一度取得し、返れば失格。
  4. 次の通知まで、過ごし方に応じて、フィードを選んで読み（続きがあれば 50% で次のページ）、投稿を開き、画像を取得し、
     プロフィールを見て、RealMoji やコメントを送り、その一覧を読み、自分の分を消す。合間に、届いた友達申請に答え
     （8%）、友達を探して申請し、断り、取り消し、友達をやめ、一覧を読み（3%）、プロフィール、写真、キャプション、
     フォロー、ブロックを変える（2%）。cohort のユーザーは 2% で過去の履歴を読む。
- 退会: 5 日目に、各リージョンの登録ユーザーから 1 人（認定公開アカウントを除く）が退会する。
- 思い出を見返すユーザー（`scenario/history.go`）: 負荷ユーザーとは別に、各リージョンに負荷ユーザー 8 人につき 1 人置く。
  初期データの history のユーザーを無作為に選んでログインし、無作為に選んだ 1 か月（65%）か 1 日（20%）の Memories、
  エクスポート（8%）、画像の抜き取り検査（7%）を待ち時間なしで繰り返す。人も月も履歴全体から一様に選ぶので、
  古いデータも読まれる。違えば 1 件で失格とする。

### ユーザーの増え方

`scenario/growth.go`（`scenario.GrowthConfig`、値は暫定）。

- リージョンの 1 日が始まるとき、前日に始まった操作の失敗率（失敗数 /（操作数と 300 の大きい方））が 1% 以下なら、
  「前日に通過した人が誘う人数の合計 − 前日に通過できなかった人数 × 1」（切り上げ、0 以上）の新しいユーザーを、
  その日の最初の 40% に散らして登録する。誘う人数は通過までの時間で決まり、1 日の 1/36（60 秒の走行で 0.25 秒）
  以内なら 2 人、1/9（1 秒）で 1.5 人、2/9（2 秒）以上なら 0 人で、その間は直線で減る。通過までの時間は、通知が
  すぐ届いていたら投稿を始めたはずの時刻（投稿期間を開く要求を送った時刻 + 待ち）から friends フィードを読み終える
  までで、通知の遅れも含む。通過できなかった人数は、その日の始まりの人数（登録中の人と BAN された人を含む）から
  前日の通過数を引いたもの。失敗率が上回れば、その日は誰も来ない。間引いた検証の失敗は、打ち切りの判定と同じく
  割合の逆数の件数として数える。BAN による拒否と、思い出を見返すユーザーと不正な利用者の操作は数えない。
  グランプリの日には新しいユーザーは来ない。
- 投稿期間を開く要求は 1 日の 8/9 で打ち切る。結果がわからなければ、そのリージョンのユーザーとして今の投稿期間を
  次の日の始まりまで読み、開いていればその投稿期間で 1 日を続ける（開くのに時間がかかったことは物語に残す）。
- 新しいユーザーの 70% は友達に誘われて来る。既存の負荷ユーザーに友達申請を送り、相手は友達の数に応じて選ぶ。
  asia の人は 80% が asia の人に、海外の人は 80% が asia の人に申請する。残りは認定公開アカウントをフォローする。
  登録後は開いている投稿期間にそのまま投稿してから、ほかのユーザーと同じループに入る。
- 1 日が始まるとき、前日の投稿期間で RealMoji を 2 件以上受けた登録ユーザーのうち最も多い人を認定する。
- 結果 JSON の `days` に、リージョンと日ごとの人数、新しいユーザー数、ゲート通過数とその所要時間の p50 / p90、
  失敗率、前日の快適な通過数と通過できなかった人数を、`grandPrix` に
  グランプリのゲート通過数を、`story` に日ごとの出来事を出す。

### フィードの検証

bench は初期データの関係と、自分が行った書き込み（投稿、公開範囲の変更、削除、友達関係、ブロック、投稿期間の開始）を
`internal/model` に持ち、アプリの閲覧可否とフィードの規則を独立に実装して、見えるべき投稿を判定する。
書き込みは送信した時刻と応答を受けた時刻の区間付きで記録し、読み取りの区間と重なる書き込みや結果のわからない
書き込み（タイムアウト、5xx）は、反映されていてもいなくてもよいものとして扱う（判定は 真 / 偽 / 不明 の 3 値）。

- 見えてはいけない投稿や、bench の知らない投稿が返れば、1 件で失格とする。結果のわからない投稿作成が
  あるユーザーの投稿は、ID を知らなくても許す。
- 見えるべき投稿がページの範囲に無ければ、エラー（エラー率に数える）とする。
- 投稿時刻の新しい順に並んでいること、投稿の内容（投稿者、キャプション、公開範囲、投稿時刻、画像 URL の署名）を確かめる。
  同じ時刻の投稿の順は問わない。
- RealMoji とコメントの結果も同じ判定と比べる。送れるはずなのに拒否されたらエラー、送れないはずなのに受け付けられたら失格。
  画像の取得も、投稿が確実に残っていたのに 403 ならエラーとする。途中で状態が変わりうる操作の 403 は計測上も失敗に数えない。
  削除した投稿の画像は、削除から 5 秒までは返してよいが、それを過ぎても返したら失格とする。
- 書き込みが読み取りに反映されるまでの遅れは、`scenario.Config.Staleness`（既定 0 秒）まで許す。

検証のコストがユーザー数に比例して増えると、アプリが速くなってユーザーが増えるほど bench の CPU が先に尽き、
スコアが下がる。そのため、欠落の検査では開いている投稿期間の投稿を総当たりせず、friends と following は相手の投稿だけ、
friends-of-friends は友達の友達の投稿だけを索引から引く（public だけはすべての投稿が候補になる）。閲覧者が今日投稿したか
などの読み取りごとに決まる値は 1 回だけ求め、偽と決まった条件があればそれ以上求めない。画像 URL の署名
（HMAC 1000 回）は、鍵、画像、期限の組ごとに bench が計算した正しい値を控えて使い回す。

### 検証の間引き

それでも public フィードの欠落の検査は 1 回ごとに開いている投稿期間の全投稿を調べ、署名の検証や履歴の画像の比較も
重いので、負荷走行ではこれらを `-verify-rate`（既定 10%）の割合の操作だけで行う。

- 間引くのは、フィードの欠落と画像 URL の署名、`checkImage` の署名、履歴（Memories）の画像の署名と中身の比較。
  間引いた操作でも画像は取得する（負荷は変えない）。
- ゲート通過の friends フィードは毎回すべて検証する。返った投稿が見えてはいけないものでないか、並び順と内容、
  画像の中身、RealMoji とコメントの可否、履歴の投稿、RealMoji、コメントは常に確かめる。
- 間引いた検証で見つけた失敗は、割合の逆数（10% なら 10 件）としてエラー率に数える。ときどき誤る実装の
  エラー率の期待値は、すべてを検証したときと変わらない。
- 初期データの検証と走行後の確認は間引かない。

通知漏れ自体はエラーにしない（ゲートを通過できないのでスコアに表れる）が、受信内容の不整合と、開いていない
投稿期間の通知はエラーとする。一覧は `hasMore` と末尾の `postedAt` / `id` でページ送りする。

## HTTP クライアント

- すべてのエンドポイントで 503 を再試行する。ジッター付き指数バックオフ（基準 200ms、上限 2 秒、最大 4 回）で、`Retry-After` があれば上限 2 秒で丸めて従う。再試行を含めて 1 操作と数える。
- リダイレクトは追わない（ルーター以外の経路を通らないため）。3xx は期待外のステータスとしてエラーになる。
- 応答の JSON は `github.com/goccy/go-json` で読む。負荷走行で最も多く読むフィードは、bench が確かめて使う項目だけの型
  （`client.FeedPost`）で読み、投稿者のプロフィールや位置などは値を作らずに読み飛ばす。
- ユーザーごとに専用の接続（HTTP/1.1 の keep-alive）を持ち、他のユーザーとは共有しない。実際の端末と同じく、サーバーから見た接続数はユーザー数に比例する（通知ストリームの分は別に加わる）。
  待機中の接続は 1 人 8 本まで残し（履歴の画像を 6 本で並行に取るため）、次の操作で使い回す。
- 応答の本体は最後まで読んでから閉じ、接続を keep-alive で使い回す。通知のストリームも、通知を受けたあと応答の終わりまで
  読む（応答を終えない実装に備えて 1 秒で打ち切り、その接続は捨てる）。

## 結果と検証範囲

スコアは、ユーザーの行動ごとの点の合計である。点はアプリにかかる手間に見合うよう決める（`score.DefaultWeights`、
値は暫定）。ゲート通過（1 人のユーザーが 1 つの投稿期間で、投稿が受理され、そのあと friends フィードを取得でき、
その日のうちに終わったこと）は 10 点、グランプリのゲート通過は 20 点。エクスポートは 20 点、RealMoji は 5 点、
コメントとプロフィール画像と 1 か月の Memories は 3 点、画像の取得、検索、友達申請と承認、1 日の Memories、抜き取り検査は
2 点、そのほかの閲覧と操作は 1 点。閲覧の点は 1 人 1 日あたりの上限までしか足さない（上限は上記）。
減点はなく、エラーはスコアを変えない。可用性は次の打ち切り条件で、正しさは失格で扱う。

- 負荷走行は 5 秒の観測窓で操作を集計する。操作数が 20 以上の観測窓で、失敗（期待外のステータス、接続エラー、タイムアウト、再試行を使い切った 503、検証の失敗）が 10% を超えたら打ち切って fail とする。判定は全リージョン合算で、閉じた観測窓を 1 秒ごとに見る。
- 正しさの違反（Critical）は 1 件で fail とする。見えてはいけない投稿や存在しない投稿がフィードに返った場合と、送れないはずの RealMoji・コメントが受け付けられた場合が該当する。
- 負荷走行のあと、無作為に選んだ負荷ユーザー（300 人まで、同時に 64 人ずつ）について、自分の投稿（負荷走行で
  開いた投稿期間の分、Memories で読む）と友達の一覧を最後のページまで読み、受け付けられた書き込みと突き合わせる
  （走行後の整合性チェック、上限 15 秒）。
  受け付けられた投稿や友達関係が失われている、削除した投稿や友達でない人が残っている、bench の知らない投稿がある
  場合は fail とする。結果のわからない書き込み（走行の終わりに打ち切られたものを含む）は、どちらでもよい。
- 初期化・事前検証・ユーザー準備・投稿期間の開始・走行後の整合性チェックに失敗した場合も fail とする。
- 60秒走行は進行中のリクエストを期限でキャンセルし、キャンセルした操作は集計しない。
- 単独実行の終了コードは pass=0、fail=1、設定などの異常=2。
- supervisor 実行時は通常の fail も終了コード 0 とし、結果の `passed=false` で不合格を報告する。

結果 JSON の `pass`、`score`、`messages`（日本語）は参加者向け、`story`（日ごとの出来事）、`breakdown`（要素ごとの件数）、
`scores`（リージョンと日と要素ごとの件数と得点。日はリージョンの日で、始まる前は 0。bench-runner の report.py が日×地域と
要素×地域の表にする）、`openedWindows`（リージョンごとに開いた投稿期間の数）、`users`（リージョンごとの最終的な負荷ユーザー数）、`grandPrix`、
`days`（リージョンと日ごとの人数、通過、失敗率、得点 `points`）、`reputation`（BAN した正常なユーザーの数）、`seed`、`critical`、`errors`、`windows`（観測窓ごと・リージョンごとの
操作数、失敗数、タイムアウト数、503 を受けた数、読み取り p99 [ns]）、`routes`（リージョンとルートごとの操作数、失敗数、
所要時間の p50 / p90 / p99 / 最大 [ns]）は運営向けである。

未実装のもの: 地域外アクセスの拒否の検証、スコアと閾値の較正。

## supervisor からの実行

supervisor は [`../supervisor`](../supervisor/README.md) に同梱している。
`make -C supervisor docker-build`（リポジトリルート）で、ベンチを含むイメージをビルドできる。

`ISUXBENCH_REPORT_FD` が渡された場合、ポータルと共有する `BenchmarkResult` の protobuf を専用パイプへ送る。
起動時、各フェーズ（初期化、事前検証、初期データの検証、ユーザーの準備、負荷走行）の前、負荷走行中の観測窓
（5 秒）が閉じるたびに途中報告し、終了前に最終結果を送る。途中報告の `passed` は false とし、正常に完走した
最終報告だけを true にする。全体タイムアウトや SIGTERM による中断は失敗になる。パイプへの書き込みは 5 秒で
タイムアウトし、報告エラーは終了コード 2 とする。

```bash
# リポジトリルートからビルドする。生成 protobuf は ../portal を参照する。
go -C bench build -o /tmp/isureal-bench .

# 接続先と秘密値は systemd の EnvironmentFile 等で設定しておく。
# --target は supervisor がジョブから追加するため、ここでは指定しない。
ISUXPORTAL_SUPERVISOR_HARD_TIMEOUT=210 \
  /usr/local/bin/isuxportal-supervisor /tmp/isureal-bench --target-port 8080 --scale large
```

| 追加フラグ | 既定値 | 動作 |
|---|---|---|
| `-target-port` | `80` | ポートを含まない IP を `http://<IP>:<port>` に変換する際のポート。URL または明示ポート付きの対象には適用しない |
| `-timeout` | `190s` | 初期化から走行後の整合性チェックまでの全体上限。超えたら中断して失敗にする |
| `-only-post-validation` | `false` | 最終検証は未実装のため、対象へ接続せず失敗を報告して終了コード 1 で終了する |

`-target` の指定がなければ `ISUXBENCH_TARGET` を参照し、それもなければ開発環境の入口
（`http://app.127.0.0.1.nip.io:18090`）を使う。`ISUXBENCH_ALL_ADDRESSES` は使わない（3 リージョンへの振り分けは
ルーターが行う）。

全体上限の 190 秒は、初期化（上限 60 秒）、初期データの検証と負荷ユーザーの準備（上限 45 秒）、通知の購読（上限 5 秒）、
負荷走行（60 秒）、走行後の整合性チェック（上限 15 秒）の合計 185 秒に余裕を足したものである。初期化の上限は、走行で増えた大きな写真をリセットで
消すと 30 秒を超えることがあるため 60 秒にした（ルーターの上流タイムアウトも 60 秒）。supervisor のハードタイムアウト
（210 秒）は、ベンチの全体上限と報告処理の余裕を含めて長く設定する。

supervisor 実行時の stdout はシナリオの進行ログ（phase、初期ユーザー確認、投稿期間の開始、レベル上昇、バズ、最終検証の完了）と、`pass`、`score`、参加者向けの `messages` を含む JSON を出す。
ポータルの失敗理由には結果の `reason` を送り、初期化失敗やエラー率超過などの原因を参加者に表示する。
採点内訳や言語を含む詳細 JSON は運営向けの stderr に出す。
通常の不合格は終了コード 0 として、運営通知の対象となる実行障害と区別する。
設定不備や報告処理の異常、未実装の最終検証モードは非ゼロ終了のままとする。
単独実行時は従来どおり詳細 JSON を stdout に出し、不合格なら終了コード 1 とする。
減点はないので、`ScoreBreakdown` の素点（`raw`）はスコアと同じ値を送り、減点（`deduction`）は 0 とする。

最終検証モードの検証内容は未定義であり、この対応だけでは本番の最終検証を実施できない。初期化してから通常ベンチを
回す代替動作は行わない。残る supervisor 自体の修正と実行環境の準備は [結合要件](../docs/research/bench.md) を参照。

### 接続実装のテスト

```bash
go -C bench test -race ./...
go -C bench vet ./...
go -C bench build ./...
```

子プロセスへ実際に FD を引き継ぐテストで、protobuf の途中報告と確定、公開出力の制限、最終検証指定時に対象へ
接続しないことを確認する。フレーム長 65,535 / 65,536 バイトの境界、短い書き込み、不正 FD、書き込み失敗も検証する。

## 利用エージェントの調査

`POST /api/initialize` のレスポンスには、使用したエージェントを表す `agent`、実行ツールを表す `harness`、モデル名を表す `model` を文字列で含めます。
初期実装は `{"language":"go","agent":"human","harness":"manual","model":"brain"}` のように返します（`language` は実装言語によります）。
競技アプリをエージェントで最適化する際は、使用したエージェント名、ツール名、モデル名に書き換えてください。
手作業の場合は `human`、`manual`、`brain` のままにします。
`manual` はエージェント用ハーネスを使わず、人間が手作業で変更したことを表す値です。

`model` に複数のモデルを記録する場合は、`"model-a,model-b"` のようにカンマで区切ります。
`brain` は AI モデル未使用を表します。
未申告や不明の場合は空文字とし、`brain` と区別します。
申告文字列は分割や正規化をせず、最新値と履歴にそのまま保存します。

これらの申告項目は調査と集計のための自己申告値で、得点や合否の判定には使いません。
ベンチマーカーは項目の省略や空文字も受け付け、結果 JSON の `agent`、`harness`、`model` に記録します。
スーパーバイザー配下では運営向けの標準エラー出力にも記録し、`language` とともに `SurveyResponse` でポータルへ送ります。
ポータルは `survey_responses` にチームごとの最新値、`survey_response_history` にベンチ実行ごとの申告を保存します。
初期化前や初期化失敗時は申告を送らず、保存済みの値を維持します。
集計方法と履歴の扱いは [ポータルの利用言語とエージェントの調査](../portal/README.md#利用言語とエージェントの調査) を参照してください。
