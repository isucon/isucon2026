# ISUReal レビュー 参考資料: 提案した前提での想定チューニング手法

**レビュアー**: fujiwara
**日付**: 2026-09-05
**位置づけ**: `design-competition-environment.md`（要点）と同 `-appendix.md`（補助資料）の
参考資料。提案 P-101〜P-112 の前提（3 リージョンサーバー、東京の中央 DB、管理外ルーター、
リージョン間レイテンシ約 100 ms、リージョンごとの SLO、`client_region` ルール、同期移行）で、
参加者が取れる手法を実装に即して整理したもの。想定解法の妥当性確認とキャリブレーションの
材料であり、決定事項ではない。ファイル参照は 2026-09-05 時点のコードに対するもの。

## 0. 全体像

手法は 3 層に分かれる。後の層ほど点数の伸びしろが大きい設計になっている。

| 層 | 目的 | 動くもの | 頭打ちになる理由 |
|---|---|---|---|
| 1. 単一ホストのチューニング | 1 台の中で速くする | `asia` のスループット、on-time 比率 | 海外リクエストは毎回東京の DB へ 100 ms 往復するので、海外の SLO を満たせない |
| 2. リージョンをまたぐ往復を減らす | 海外リージョンの p99 を SLO 内に収める | 海外のレベル上昇、画像 GET | 投稿とファンアウトが東京のプライマリに集中し、海外の on-time 比率が伸びない |
| 3. リージョンで分ける | 投稿スパイクをリージョン内に閉じ込める | リージョンごとの on-time 比率、通知レイテンシ | リージョン間のやりとりと移行の正しさが難所 |

想定している順序は、層 1 で `asia` を立て直し、層 2 で海外の SLO を満たしてレベルを上げ、
層 3 でスパイクをリージョン内に閉じ込める、というもの。

## 1. 層 1: 単一ホストのチューニング

通常の ISUCON。初期実装には序盤に効く典型的なボトルネックがそろっている。

### 1.1 負荷で現れる並行性の不具合を直す

- 初期実装は並行性制御を持たない（P-112）。低負荷では動くが、負荷が上がると次が出る:
  相互にリアクションしたときのデッドロック、再送時の投稿の制約違反 500、同じ冪等性キーの
  並行送信の片方が 500、worker を複数にしたときの通知の二重処理と成功済み push の再送。
- 手法: 投稿と交流のトランザクションでユーザー行をソート順にロックする。冪等性は初期実装でも
  キーを先に INSERT するので二重確定はしないが、並行送信の片方が制約違反で落ちる。競合時は
  既存レコードの応答を待って返すようにする。worker の claim を `FOR UPDATE SKIP LOCKED` か
  `UPDATE ... RETURNING` にする。
- 注意: P-108 の「同じキーでの再送は同じ結果」「同一ウィンドウの重複投稿は 409」「成功済み
  push の再送なし」は検証される。特にリージョンごとに worker を分ける（3.1）前に claim を
  直さないと、分けた瞬間に落ちる。

### 1.2 セッション検索のキャッシュ

- 認証リクエストごとに `login_sessions JOIN users` を `token_hash` で 1 回引いている
  （`postgres/session.go:110`）。キャッシュはない。
- 手法: トークンハッシュからユーザーへの対応をプロセス内キャッシュに載せる。
- 注意: P-108 の「新しいログインが古いトークンを無効化する」チェックが入るので、ログイン時に
  古いトークンのキャッシュを確実に消す必要がある。複数ホストになると、無効化をホスト間で
  伝える仕組み（層 2 以降）が要る。
- トークンにはユーザー ID もリージョンも含まれないので、ルーターや nginx がトークンだけを
  見て振り分けることはできない。リージョンごとの振り分けは `client_region` ヘッダに依存する。

### 1.3 画像パイプライン

- アップロード: 画像ごとにサニタイザのサブプロセスを起動する（`internal/image/sanitizer.go`）。
  一時ディレクトリの作成、書き出し、exec、再デコード、SHA-256、rename を毎回行う
  （`image/store.go:58-121`）。サブプロセスは複数言語で提供するための意図的な設計で、
  同時実行の制限はアプリ側にはない（P-112）。
- GET: セッション認証のあと、投稿、RealMoji、プロフィールの順に認可を試し、最大 3 回 DB を
  引いてから配信する（`httpapi/images.go:41-62`、`service/posts.go:98-108`、
  `service/interactions.go:96-105`、`service/accounts.go:85`）。ETag や Last-Modified はなく、
  `Cache-Control: no-store` が全 API に付く（`httpapi/security.go:47-52`）。
- 手法: Go のプロセス内で JPEG を再デコード・再エンコードすればメタデータは落ちるので、
  サブプロセスをなくす（参加者の選択としては可）。サブプロセスを残すなら同時実行数を
  CPU 数に合わせて制限する。画像 ID から所有者と可視性を 1 発で引くテーブルかカラムを作り、
  3 段階の認可を 1 クエリにまとめる。配信は nginx に任せる（ただし認可が要るので、
  `X-Accel-Redirect` 等で認可後に nginx へ渡す形になる）。
- 注意: P-108 の画像検査は「メタデータがなく、寸法が一致し、画素が近似一致する」ことを見る。
  再エンコードせずメタデータのセグメントだけ取り除く実装は画素が完全一致するので、より軽い
  正当な手法である。バイト列の一致や再エンコードの決定性は要求されない。

### 1.4 通知ファンアウトのバルク化

- ウィンドウ開始時に、期限の来た予約を取り、開いているウィンドウを閉じ、新しいウィンドウを
  作り、リージョンの全アクティブユーザーを取って、ユーザーごとに `INSERT INTO notifications`
  と `INSERT INTO push_attempts ... SELECT` の 2 文を発行している
  （`postgres/notifications.go`）。P-112 の素朴版ではトランザクションで包まず、予約の取得も
  `SKIP LOCKED` なしになる。
- `users(region)` にインデックスがない。
- push の送信は `push-sender` を試行 1 件ごとに exec し（P-112）、しかも直列
  （`worker/push_delivery.go`）。exec ごとに fork と接続確立（Push モックは平文 HTTP なので
  TCP のみ）が発生するので、フォロワー通知（1.4a）で件数が増えると worker の支配的なコストに
  なる。
- 手法: 2 つの `INSERT ... SELECT` にまとめる。`users(region)` にインデックスを張る。
  `push-sender --help` を読むと stdin を閉じるまで行を処理し続けることが分かるので、閉じずに
  流し込み続ければ fork と接続確立のコストが消える（stdin の書き込みと stdout の読み取りを
  別スレッドにしないとパイプで詰まる）。1 プロセスは順次送信なので、並列化は複数プロセスを
  立てて行う。Web Push
  であることは明示されるので、自分の言語で送信を組み込んでもよい。投稿起点の通知（1.4a）も
  同じ worker を通るので、どちらかが詰まると両方の到達時間が伸びる。
- 効果: スパイク直後の on-time 比率と通知レイテンシに直接効く。P-102 のスコアで最も
  重い部分。

### 1.4a 認定アカウントの投稿起点の通知ファンアウト（P-111）

- 認定公開アカウントの投稿ごとに、フォロワー全員へ通知行と push 試行を作る。フォロワー数は
  新規ユーザーの登録直後のフォローでレベルとともに増えるので、1 投稿あたりの件数が走行中に
  伸びる。初期実装は投稿トランザクション内で 1 件ずつ INSERT する想定で、投稿スパイクの最中に
  発生する。
- 手法: `INSERT ... SELECT` で 1 文にする。投稿の応答からファンアウトを切り離し、worker か
  キューで非同期にする（通知到達時間の許容値内で）。push 送信の並列化（1.4 と同じ）。
  フォロワー一覧のキャッシュ。
- 注意: P-108 の 11 で「全リージョンのフォロワーに 1 件だけ届く」「ブロック中は届かない」が
  検証される。非同期化しても重複と漏れを出さないこと。

### 1.5 距離 2 の友人判定

- フィードは 1 クエリで N+1 はないが、候補行ごとに友人、友人の友人、フォローの 3 つの相関
  `EXISTS` を評価している（`postgres/posts.go:204-231`）。距離 2 は `friendships` の
  自己結合（208-211 行）。閲覧者が自分のウィンドウに投稿済みかも行ごとに `EXISTS` で
  見ている（216 行）。
- 手法: 閲覧者の友人集合と距離 2 の集合を先に求めて配列で渡す。閲覧者の投稿済みフラグは
  1 回だけ引く。友人集合はセッションキャッシュと一緒に持てる。
- 注意: P-108 でフィードと可視性がリージョンをまたぐユーザーで検証されるので、ブロックと
  可視性の扱いを崩さないこと。

### 1.6 定番の調整

- 認証は P-110 でサーバー発行キーと SHA-256 になるので、ログインと登録は数ミリ秒で終わり、
  ここに改善余地はない。
- pgx プールサイズの明示。現状は DSN に書かない限り pgx の既定値（CPU 数と 4 の大きい方）
  （`postgres/db.go:39-46`）。
- worker のポーリング間隔（既定 1 秒）とバッチサイズ（既定 50）の調整。
- nginx のアクセスログをリクエスト時間とヘッダ付きに直す。初期状態では意図的にデフォルト
  のままにしてある（P-104）。

### 1.7 この層の限界

`asia` のスループットしか伸びない。海外ユーザーが増えるレベルに入ると、リクエストごとに
東京の DB へ 100 ms の往復が乗り、読み取りの p99 が SLO（例: 50 ms）を超えて海外のレベルが
止まる。

現行実装（P-112 適用前）の海外ホストの DB 往復数は補助資料 P-104 の表のとおり（フィード 2、
投稿 1 件の取得 3、画像取得 3〜5、投稿作成 16、RealMoji 18、ログイン約 13）。往復数より効くの
は接続プールの占有で、投稿作成は冪等性トランザクションの開始から `COMMIT` まで 1 本の接続を
約 1.6 秒握るため、pgx 既定プール（CPU 数と 4 の大きい方）では海外ホストは毎秒 2〜3 件しか
投稿を通せない。CPU は遊んだままプール待ちで詰まる。P-112 適用後は投稿作成が 9 往復前後に
減る見込みだが、逐次の往復で約 1 秒かかる構造は同じで、実装を直した時点で測り直す。プールを
増やしても RTT は変わらず、`asia` の DB 側の接続数が 3 台分に膨らむ。往復数を減らす候補は、
冪等性の往復、応答用の再取得、認証の 1 往復（セッションキャッシュ）。

## 2. 層 2: リージョンをまたぐ往復を減らす

海外リージョンの p99 を下げるには、リクエスト処理中に東京へ行く回数をゼロか 1 回にする。

### 2.1 リージョンごとのリードレプリカ

- `europe` と `america` に PostgreSQL のストリーミングレプリカを立て、読み取りをローカルで
  捌く。書き込みは東京のプライマリに送る。
- 注意: P-109 の一貫性ルールは「リージョン内では read-your-writes」。自分の書き込み直後の
  読み取りはプライマリに向けるか、レプリカが該当 LSN に追いつくまで待つ必要がある。
  投稿直後のフィード取得はベンチの典型パターンなので、ここを外すと落ちる。

### 2.2 画像のローカリティ

- 初期実装は画像を DB の bytea に置く（P-104）ので、海外からの画像 GET は毎回東京に行く。
  画像は 1 リクエストあたりのバイト数が最も大きく、帯域上限（未決）が入れば最初に詰まる。
- 手法: アップロード時にローカルディスクへ書き、他リージョンへ非同期でコピーする。または
  URL にリージョンを埋め込み、所有リージョンのサーバーから配信させる。ルーターはユーザー
  ID を見られないので、URL に情報を載せるのがルータールールで振り分ける唯一の方法。
- 注意: 初期実装のホストは 3 台とも同じコードなので、ローカルディスクに書くとそのホストで
  しか配信できない。「どのホストから来ても配信できる」を保ったまま移す必要がある。

### 2.3 セッション、プロフィール、通知のリージョン内完結

- 認証、通知一覧、メモリー、ユーザー検索、プロフィールはリージョン内のレプリカやキャッシュ
  で完結させる。これらは読み取りが支配的で、更新はまれ。
- セッション無効化（1.2 の注意）は、ログインを受けたホストから他ホストへ伝える必要がある。
  中央 DB で世代番号を持ち、キャッシュヒット時に軽く照合する、などの手がある。

### 2.4 ルータールールの活用

- 初期状態は「リージョンから同一リージョンのサーバーへ」だけ（P-104）。
- 使い方の例:
  - 管理者 API と `/initialize` を `asia` に固定する。伝播の問題を減らせる。
  - 海外の負荷が小さい序盤は、すべてを `asia` に送る。層 1 だけで戦える時間を延ばす。
    データ所在地ポリシー上も適法で、マニュアルに明記される（補助資料 P-106）。
  - 画像 GET をパスプレフィックスで所有リージョンに向ける（2.2）。
  - 重み付き upstream で、あるリージョンの余力を隣に貸す。
- 制約: ルールは実行前にしか変えられず、実行中は固定（P-103）。実行ごとの構成を決めてから
  走らせる運用になる。

## 3. 層 3: リージョンで分ける

投稿スパイクは各リージョンで時間差で来る。投稿トランザクションと通知ファンアウトが東京の
プライマリに集中する限り、海外の on-time 比率は頭打ちになる。

### 3.1 書き込みのシャーディング

- ユーザー、投稿、ウィンドウ、通知をリージョンごとの DB に分け、worker もリージョンごとに
  動かす。投稿トランザクション（`postgres/posts.go:57`、`FOR UPDATE OF w`）とファンアウト
  （1.4）がリージョン内で完結する。
- 投稿起点の通知（1.4a）はリージョンをまたぐ。`asia` の認定アカウントの投稿を `europe` の
  フォロワーへ通知するには、投稿イベントを相手リージョンへ渡し、通知行と push はフォロワー
  のリージョンで作る形になる。リージョンごとの通知到達時間（P-108 の 11）がこの分割の動機。
- `client_region` ルール（P-106）により、あるユーザーのリクエストは必ずそのユーザーの
  リージョンのエッジから来る。どのサーバーで処理するかはルータールール次第で、ルールを
  「同一リージョンのサーバーへ」にしておけば処理ホストもリージョンで揃う。シャードキーは
  リージョンで自然に決まる。GDPR 由来のデータ
  所在地ポリシー（補助資料 §1.1.1）がこの分割を後押しする筋書き。

### 3.2 リージョン間のやりとり

- 他リージョンの友人の投稿、公開フィード、ブロック、友人リクエストはシャードをまたぐ。
- 手法:
  - 内部 API で相手リージョンに問い合わせる（同期。レイテンシが乗るがシンプル）。
  - フォロー・友人関係と投稿メタデータを非同期で相互レプリケーションする。
  - リージョン間は有界の陳腐化を許容し（P-109）、キャッシュで返す。
- 前提として、リージョン間の一貫性要件は緩い。非同期レプリケーションが現実的。ただし
  ブロックは「即座に見えなくなる」ことを期待されやすいので、陳腐化の許容量（未決）次第で
  同期にする必要がある。

### 3.3 同期移行（P-107）

- 中央 DB のまま（層 2 まで）なら `UPDATE users SET region` の 1 文で済む。
- シャーディングした場合の順序:
  1. ディレクトリ（ユーザーとリージョンの対応）を切り替え、旧リージョンへの新規リクエストを
     拒否し始める。
  2. 旧リージョンで処理中のリクエストをドレインする。
  3. 旧リージョンの履歴（メモリー、通知、リレーションシップ、プロフィール画像、コメントと
     RealMoji、セッション）を新リージョンへ移すか、遅延取得の仕組みを用意する。
  4. 200 を返す。
- ベンチは移行中に旧リージョンへ読み書きを浴びせる。拒否の検査対象は「移行の成功応答の
  受信後に開始したリクエスト」だけで、重なったリクエストは成功・拒否のどちらでもよい（P-107）。
  落ちやすい箇所は、旧リージョンで受理した書き込みの取りこぼし（1 と 2 の間）と、成功応答の
  受信後に開始した旧リージョンのリクエストが成功してしまうこと（ドレイン漏れ、キャッシュの
  残り）。移行操作の冪等リプレイは旧リージョンからでも同じ結果を返す必要がある。
- 冪等性キーもリージョンをまたいで同じ結果を返す必要がある。冪等性ストレージがシャード
  ローカルだと、移行後の再送で別の結果になる。

## 4. この前提で通りにくくなる手法

- **1 台にすべて載せるインメモリ実装。** `asia` の 1 台に全トラフィックを集めると、海外
  リージョンの読み取り p99 に 100 ms が必ず乗り、リージョンごとの SLO（P-109）を満たせず
  海外のレベルが上がらない。後のレベルほど海外ユーザーが多いので、上限が低い位置で止まる。
  SLO 以前に、エージェントは同時に 1 リクエストなので海外エージェントの毎秒イベント数が
  往復 100 ms で約 10 に頭打ちになり、リージョン内で返す実装（数 ms、毎秒数百）との差が
  海外エージェント数に比例して開く（補助資料 P-109）。序盤で最速なのは意図どおりで、
  海外比率が上がる後半で逆転するように較正する。
- **画像処理の省略。** メタデータの除去と画素の保持は検査（P-108 の 9）で検証されるので
  省けない。ただし再エンコードは要求されないので、メタデータのセグメントだけ取り除く軽い
  処理に置き換えるのは正当で、画像処理は CPU のレバーにならない。
- **ルーターを迂回する。** ベンチはルーター経由でしか来ない。クライアントとルーターの間に
  レイテンシを入れないのは、この制約をサーバーから計測できるようにするため（P-103）。
- **`client_region` チェックの削除。** 速くなるが、不一致リクエストの拒否プローブ（P-108）
  で落ちる。逆に、このチェックがあるおかげでシャーディング（3.1）が安全にできる。
- **セッション検証の省略。** キャッシュは可能だが、セッション置き換えのチェック（P-108）
  があるので、無効化を伝えない実装は落ちる。

## 5. キャリブレーションで確認したいこと

競技の主眼は上位の弁別である。層 1 は LLM エージェントが最も得意な作業で構成されているので、
層 1 だけで勝てる配点にしないこと、上位で頭打ちにならないことの 2 点を優先する。

- 層 1 だけで到達できるスコアの上限。LLM エージェントを 1 台に置いただけの条件で実測する。
  ラチェットのレベル表で、海外ユーザーが増え始めるレベルをこの上限のすぐ上に置けているか。
- 層 2 に到達した人間のチームのスコアが、層 1 の上限を明確に上回るか。
- 層 3 まで到達したチームが頭打ちにならないだけのレベル数と海外比率があるか。
- 層 2 のリードレプリカ構成が SLO を満たすか。レプリカの遅延と read-your-writes の両立が
  現実的な時間で実装できるか。
- 層 3 まで行ける参加者がいるか。いないなら移行イベントの頻度と配点を下げる。
- 画像 GET の帯域が層 2 以前に詰まらないか。帯域上限（未決）を入れる場合の値。
- on-time 締切 N の較正。5 秒で参考実装が基準レベルで on-time 95% 以上を保ち、単一サーバーが
  上位レベルで明確に下回るか。画像サイズと帯域上限を決めたあとに再較正する。
- `asia` 一極集中が「海外をリージョン内で返す」実装に逆転されるレベル。人間のチームが
  ステージ 1 に到達する点より下にあるか。
- P-102 の追加ユーザー供給（走行中の新規登録と初期データのユーザーの混合）で、レベルアップ
  時の登録コストがスパイク計測を汚さないか。新規登録ユーザーだけだと公開フィードに負荷が
  偏らないか。
- P-111 の投稿起点の通知が、上位レベルでスパイク中のファンアウトとして意味のある大きさに
  なるか。認定アカウントの人数とフォロー数で調整する。
