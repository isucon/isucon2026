# ISUReal ベンチマーカー仕様

現行のベンチマーカー（`bench/`）が何を行い、何を合格・失格とするかを定める。実行方法と結果 JSON の形式は
[README](README.md) を参照する。値に「暫定」とあるものは較正（§11）で見直す。

対象のアプリは現行の `webapp/go` の仕様とする。アプリの仕様が変われば本仕様も追従する。

## 1. 用語

| 用語 | 意味 |
|---|---|
| リージョン | asia / europe / america。ユーザーは 1 つのリージョンに属する |
| 国 | リクエストの `X-Country-Code`。ルーターは JP/KR/CN/AU を asia、GB/DE/FR を europe、US/CA/MX を america のサーバーへ振り分ける |
| 投稿期間 | リージョンごとに管理者が開く期間。同じリージョンで次の期間が開くと終わる。日付（`localDate`）はラベルで、サーバーの時計とは関係しない |
| ゲート | 閲覧者が、自分のリージョンで開いている投稿期間と同じ日付に投稿していなければ、他人の投稿は見えない |
| ゲート通過 | 1 人のユーザーが 1 つの投稿期間で、投稿が受理され、そのあと friends フィードを取得して検証に通ったこと |
| 負荷ユーザー | 負荷走行で動かすユーザー。bench が登録したユーザー（インフルエンサーを含む）、初期データの cohort のユーザー、走行中に来た新しいユーザー |
| 初期データ | リポジトリ直下の `dataset` が決定的に作るデータ。bench は同じ `dataset` から期待値を計算する |
| history / cohort | 初期データのユーザーの役割。history は bench が読むだけ、cohort は bench が書き込んでよい |
| 観測窓 | 負荷走行の開始から 5 秒ごとに区切った区間。打ち切りの判定に使う |
| 日 | リージョンの投稿期間 1 つ分。成長の判定はリージョンと日ごとに行う |

## 2. フェーズ

1 回の実行は次の順に進み、どこかで失敗したらその時点で fail とする。

1. 初期化（§3）
2. 事前検証（§4）
3. 初期データの検証（§5）
4. 負荷ユーザーの準備（§6、3 と並行に行い、合わせて 45 秒以内）
5. 負荷走行（§7、60 秒）
6. 走行後の整合性チェック（§9、負荷走行が失格でない場合だけ）

どのフェーズも、実行を中断されたら fail とする。

## 3. 初期化

- 管理者の国（JP）で `POST /api/initialize` を送り、60 秒以内に 200 と空でない `language` が返ること。参考実装のリセットは
  走行で増えた画像のパーティションを TRUNCATE するので 1 秒前後だが、参加者の実装に余裕を持たせて上限は 60 秒にし、
  ルーターの上流タイムアウトも 60 秒にしている。
- 初期化レスポンスの `agent`、`harness`、`model` は調査用の文字列として結果 JSON に記録する。省略や空文字を許容し、得点や合否には使用しない。`model` は複数モデル名をカンマで区切った文字列を保持する。AI モデル未使用の初期値は `brain`、未申告は空文字とする。
- 負荷走行で開く投稿期間の最初の日付は、UTC の今日と初期データの最終日の翌日の遅い方とする。

## 4. 事前検証

asia のユーザーを 1 人登録して、次をすべて確かめる。1 つでも違えば fail とする。

- 管理者（`admin` / `password1234`）としてログインできる。
- 登録で発行されたシークレットキーでログインでき、同じユーザー名での登録は 409、誤ったキーでのログインは 401 になる。
- プロフィールが登録した内容と一致する。
- 投稿前の public フィードが空で、今日の投稿（`GET /api/posts/me/current`）が 404 になる。
- 認定されていないユーザーの認定の取り消しが 409 になる。
- europe の国から `GET /api/me` を送ると 403 になる（地域外のサーバーからのアクセス）。
- プロフィール画像として、JPEG でないバイト列と 513x513 の JPEG は 400、写真から作った 256x256 の JPEG は受理される。
- 受理した画像を、署名の違う URL（別の鍵で署名）と期限切れの URL（正しい鍵で署名した過去の期限）で取得すると、
  403 か 404 になる。どの拒否も、省けばアプリが速くなるので確かめる。
- 再ログインで前のセッションが無効になり（401）、ログアウトしたセッションも無効になる。

## 5. 初期データの検証

初期データの有効な history のユーザーとしてログインし、並行に確かめる。対象は、友達の最も多い通常ユーザー（友達の
一覧にページ送りが要る）、各リージョンから無作為に選んだ通常ユーザー、無作為に選んだ認定公開アカウント（RealMoji と
コメントが多い）で、走行ごとに変わる。1 つでも違えば fail とする。履歴は読むだけで書き込まない。

- Memories: 履歴のある月から無作為に 2 か月を選び、最後のページまで読んで、投稿（ID、投稿期間、キャプション、公開範囲、位置、投稿時刻、
  on-time と遅延秒数、投稿者）と、RealMoji（置き換え・削除されていない、有効なユーザーの分を新しい順に最大 50 件）、
  コメント（削除されていない、有効なユーザーの分を古い順に最大 50 件）が初期データと一致する。
- 友達の一覧: 最後のページまで読み、有効な友達との関係が新しい順に並び、相手のプロフィールが一致する。
- エクスポート: ZIP の `posts.json` が削除されていない全投稿を古い順に並べ、各画像のバイト列が一致する。
- 画像: 画像 URL が画像の持ち主のシークレットキーで署名されていて（§8.4）、期限内である。投稿と RealMoji の
  画像は中身を取得して比べる（1 人あたり同時に 6 件まで）。

## 6. 負荷ユーザーの準備

- サービスはアジアで広まっていて、海外のユーザーはまだ少ない。asia に `-users`（既定 8）人とインフルエンサー 2 人、
  europe と america にその 1/2（1 人以上）とインフルエンサー 1 人ずつを登録する。国はリージョンの国を順に割り当てる。
  各ユーザーには、ほかのユーザーと重ならない公開 IP アドレスを決めて `X-Client-IP` に付ける。
- 登録と並行して、各リージョンの cohort のユーザーに、そのリージョンの最初の人数（`-users`）までログインし、負荷ユーザーに
  加える。cohort のユーザーは初期データの関係をそのまま持つ。
- リージョンごとに登録ユーザーを 1 列に並べ、隣どうしを友達にする（申請と承認）。同じユーザーが同時に 2 つの関係の
  作成に入らないよう、偶数番目の組、奇数番目の組、ブロック（4 人ごとに 3 つ先のユーザー）の順に作る。これと並行して、
  インフルエンサーを認定し、登録ユーザーは同じリージョンのインフルエンサーを 1 人フォローする。
- 初期データの検証（§5）と準備が合わせて 45 秒で終わらなければ、その時点の段階を示して fail とする。

## 7. 負荷走行

### 7.1 時間割

- 走行の長さの 9/60（60 秒なら 9 秒）を 1 日とする。asia は 0 秒、europe は 3 秒、america は 6 秒から 5 日ずつ投稿期間を
  開く（asia 0/9/18/27/36 秒、europe 3/12/21/30/39 秒、america 6/15/24/33/42 秒）。
- 51 秒（走行の長さの 51/60）からの 6 日目はグランプリで、全リージョンが同時に投稿期間を開く。新しいユーザーは来ない。
- 日付はリージョンごとに §3 の最初の日付から 1 日ずつ進める。
- 投稿期間を開く要求は 1 日の 8/9 で打ち切る。結果がわからない（タイムアウトや 5xx）ときは、そのリージョンの
  ユーザーとして今の投稿期間を次の日の始まりまで読み、開く日付の投稿期間が開いていればそれを使ってその日を続け、
  物語に残す。見つからなければエラーとして数え、開けたかは不明として扱って、次の予定の時刻に次の日付で開き直す。

### 7.2 ユーザーの過ごし方

各負荷ユーザーはクローズドループで動く。同時に 1 リクエストだけ送り、待ち時間を置かない。通知は別の接続で
購読し続け、ストリームが切れたら購読し直す（エラーにしない）。

ユーザーの過ごし方はユーザー名と走行の種から決まる。登録ユーザーと新しいユーザーは、投稿だけ 40%、閲覧 30%、
RealMoji 15%、コメント 15%。cohort のユーザーは初期データの活発さで決める（低い 3 割は投稿だけ、中ほどは閲覧、
高い人は RealMoji かコメント）。

過ごし方が投稿のあとに何をするかの種類を決めるのに対し、好みと癖（`scenario.persona`）がどれだけ・どのように
するかを決める。これもユーザー名と走行の種から決まる。

| 好みと癖 | 範囲 | 効くところ |
|---|---|---|
| 活動量 | 0.45〜1.55 倍 | 1 日の操作の回数（加点の上限は変えない） |
| 投稿する日の多さ | 85〜100%（cohort は 80% + 20% × 活発さ） | 投稿しない日は何もしない（休む） |
| 投稿の早さ | 0〜1 | 通知から投稿までの待ちを、日ごとの気分と半分ずつ混ぜる |
| 好きなフィード | 全体の重みを 0.3〜1.7 倍に揺らす | 読むフィードの選び方 |
| スクロール | 20〜80% | 続きのページも読む確率 |
| 投稿を開く / 画像を見る / プロフィールを見る | 10〜50% / 25〜75% / 5〜25% | 見えた投稿への行動 |
| 親しい人への偏り | 0〜3 | 見えた投稿から選ぶ重み exp(偏り × 組ごとの親しさ) |
| 好きな RealMoji と口癖のコメント 3 つ | 40〜90% で使う | RealMoji の種類、コメントの本文 |
| 公開範囲 | friends を選ぶ確率 20〜80% | 一般のユーザーの投稿 |
| 位置情報 | なし 65%、市区町村 25%、座標 10% の人（15% の日は気が変わる） | 投稿に付ける位置情報 |
| 交流と身づくろい | 0.5〜1.5 倍 | 友達申請や関係の整理、プロフィールなどを変える頻度 |
| 撮り直し | 30〜90% | 投稿を削除したあとにもう一度投稿する確率 |
| 登録時のプロフィール | 画像 30〜80%、自己紹介 20〜70% | 新しいユーザーが登録直後に設定する |
| 旅 | 8% の人が 15〜35% | 日を過ごし終えたあとで別のリージョンへ移る確率（登録ユーザーだけ） |
| アプリを閉じる | 15% の人が 40〜80% | 日を過ごし終えたあとでログアウトし、次の日に開き直してログインする確率 |

1. 通知を受けたら（同じ投稿期間の通知は 1 回だけ数える）、その日に投稿するかを決める。休む日は何もしない（初めての日、
   グランプリ、退会する日、認定公開アカウントは休まない）。投稿する日は、日の気分と投稿の早さの癖から決まる指数分布の
   待ち（中央値は 1 日の 1/9、上限は 1 日の 8/9）を置く。待つ間に次の通知が来たら、その日は投稿しない。10% のユーザーは待つ前に friends
   フィードを覗く。今日まだ投稿していないので、ほかの人の投稿は見えてはいけない（§8.1）。
2. 現在の投稿期間を読み、通知と同じなら投稿する。公開範囲は、認定公開アカウントは public、ほかは friends か
   friends_of_friends。写真はアーカイブから地域に合うものを選び、投稿ごとに中身を変える（§8.3）。位置情報は
   好みに合わせて付け、応答と突き合わせる（座標は小数 4 桁）。読んでから送るまでに次の投稿期間が開き、その日付に
   もう投稿していれば `409` が正しい（リージョンを移った人に起きる）。
3. friends フィードを読み、検証（§8.1）に通って、その日が終わる前に終わればゲート通過とする。
4. 前回の投稿が Memories にあることを確かめる（cohort のユーザーは前回の投稿の日付の Memories も読む）。
   自分の今日の投稿（`GET /api/posts/me/current`）と画像を確かめ、5% は投稿を削除し、10% は公開範囲を変える。
   削除した人の一部（撮り直しの好み）は同じ日付にもう一度だけ投稿し、その投稿でその日を続ける。
   削除した投稿の画像は、削除から 6 秒後に集計しないクライアントでもう一度取得し、返れば失格（§8.3）。
   公開範囲の変更が 403 になったときは、その間に投稿期間が閉じたかもしれなければ正しい拒否とし、確実に開いていた
   ときだけエラーとする。
5. その日の操作の回数（閲覧 20 回、RealMoji とコメント 15 回、投稿だけ 0 回。認定公開アカウントは 10 回まで）を使い切るか
   次の通知が来るまで、次から 1 つずつ選んで行う。
   - 8%: 届いた友達申請に答える（承認か、ときどき断る）。
   - 3%: 友達を探して（ユーザー検索）申請する、申請を取り消す、友達をやめる、フォローや友達の一覧を読む。
   - 2%: プロフィール（表示名、自己紹介、写真）、投稿のキャプション、フォロー、ブロックを変える。cohort のユーザーは
     プロフィールを変えない（履歴の検証と食い違うため）。
   - cohort のユーザーは 2% で過去の履歴を読む（§8.5）。
   - それ以外: フィード（friends 35%、friends-of-friends 25%、public 25%、following 15%）を読み、続きがあれば 50% で
     次のページも読む。見えた投稿を開き（30%）、画像を取得し（50%、1 日 4 回まで）、投稿者のプロフィールを見る（15%）。
     RealMoji の人は RealMoji を送り（1 日 5 件まで）、一覧を読み、ときどき自分の分を消す。コメントの人も同様。
- 投稿だけの人の半分は、ゲート通過のあと届いた友達申請に答える。
- 旅をする人は、その日の操作の回数を使い切ったあとで所属リージョンを変える（`PATCH /api/me` の `region`。グランプリの
  日とその前の日は移らない）。変えたあとは移った先の国から接続し、通知を購読し直し、移った先でまだ投稿していない日付の
  投稿期間が開いていれば通知を待たずに投稿する。モデルは閲覧者の所属リージョンを履歴で持ち、変えている最中の読み取りは
  どちらのリージョンでも正しいとする（ゲートの判定、§8.1）。投稿が今のものかは投稿者ではなく投稿の投稿期間で決まる。
  変える間は通知を購読しない。変更の応答が届かなければ同じ変更を 3 回まで送り直す。成功の応答だけが移った先を確かめ、
  拒否は最初の変更が拒否されたときだけ「変わっていない」とする。確かめられなかった人は以後使わず、走行後の整合性
  チェックでも確かめないが、BAN された人と同じく通過できなかった人に数え続ける（§7.4）。
- アプリを閉じる人は、日を過ごし終えたあとでログアウトし（`POST /api/auth/logout`）、通知を受けない。次の日が始まって
  いつもの投稿の待ちが過ぎたらログインし直し、開いている投稿期間に通知を待たずに投稿する（通過までの時間は開き直して
  から数える）。グランプリの日と、退会する人、認定公開アカウントは閉じない。
- 5 日目に、各リージョンの登録ユーザーから 1 人（認定公開アカウントを除く）が退会する。退会の応答が届かなかった
  人は、退会が済んだかもしれないので以後は使わず、走行後の整合性チェックでも確かめない。退会と重なった友達の解除や
  友達申請の 404 は正しい応答として扱い、送ってから応答までずっと相手が有効だったときだけ違反とする。
- 正常なユーザーが `403 ip_banned` を受けたら、そのユーザーは止まり、悪評としてログに残す（失格にも失敗にもしない）。
  BAN されたユーザーは、成長の判定では通過できなかった人に数え続ける（§7.4）。

### 7.3 思い出を見返すユーザー

負荷ユーザーとは別に、しばらくぶりに戻ってきて過去の Memories を見返すユーザーを、各リージョンに負荷ユーザー 8 人に
つき 1 人（切り上げ）置く。負荷ユーザーが増えると一緒に増やす。

- 初期データの有効な history のユーザー（負荷走行で書き込まない人）からそのリージョンの 1 人を無作為に選んでログインし、
  次を待ち時間なしで繰り返す。同じ人を同時に 2 か所で使わない。20% の確率でログアウトして別の人に代わる。
  - 65%: 履歴のある月から無作為に選んだ 1 か月の Memories を最後のページまで読み、§5 と同じく初期データと比べる。
  - 20%: 履歴のある日から無作為に選んだ 1 日の Memories を読んで比べる。
  - 8%: エクスポートを取得し、内容を初期データと比べる（画像は一部を選んで比べる）。
  - 7%: 画像の抜き取り検査（署名付き URL を bench が作り、画像の中身を比べる）。
- 人も月も履歴全体から一様に選ぶので、最近のデータだけをメモリに置く実装では古いデータの読み取りが遅くなる。
- このリクエストは打ち切りの判定に数え、成長の判定には数えない。エクスポートの API エラーは無視する（内容の違いは失格）。
- 初期データのユーザーとしてログインできない（401）、または履歴が初期データと違えば失格とする。

### 7.4 成長

- リージョンの 1 日が始まるとき、前日に始まった操作の失敗率（失敗数 /（操作数と 300 の大きい方））が 1% 以下なら、
  「前日に通過した人が誘う人数の合計 − 前日に通過できなかった人数 × 1」（切り上げ、0 以上）の新しいユーザーが来る。
  誘う人数は通過までの時間 t で決まる。t が 1 日の 1/36（60 秒の走行で 0.25 秒）以内なら 2 人、1/9（1 秒）で 1.5 人、
  2/9（2 秒）以上なら 0 人で、その間は直線で減る。t は、通知がすぐ届いていたら投稿を始めたはずの時刻（投稿期間を
  開く要求を送った時刻 + その人の待ち）から friends フィードを読み終えるまでで、通知の遅れも含む（参加中に来た新しい
  ユーザーは投稿を始めた時刻から）。通過できなかった人数は、その日の始まりの人数（前日に来て登録中の人、BAN された
  人、所属リージョンの変更を確かめられずに止めた人を含む）から、前日に通過した人と通過しなくてよかった人（自分で休んだ人、ほかのリージョンから移ってきた人）を
  引いたもの。前日のうちにほかのリージョンへ移った人は、どちらにも数えない。失敗率が上回れば、その日は誰も来ない。前日のゲート通過は、その日が
  終わる前に終わったものだけを数える。グランプリの日には新しいユーザーは来ない。
- 速く使えた人ほど多く誘い、使えなかった人は思いとどまらせる。全員がすぐに通過すれば 1 日に 3 倍になる。閉じたループの
  ユーザーは詰まると一斉に遅くなるので、通過できたかどうかだけでは詰まる直前まで何も表れず、翌日に人が押し寄せて全員が
  通過できなくなる（振動する）。通過までの時間を見ると、詰まり始めた段階で増え方が鈍る。誘う人数を時間の折れ線にして、
  速いアプリほど上限なく育つようにした（2.5 倍で頭打ちにすると、最上位の実装の人数がベンチの上限で揃った）。
- 数える操作は負荷ユーザーのもの。`403 ip_banned`、思い出を見返すユーザー、不正な利用者の操作は数えない。間引いた検証の
  失敗は、打ち切りの判定と同じく割合の逆数の件数として数える。
- 新しいユーザーは、その日の最初の 40% に均等に散らして登録する。70% は友達に誘われて来て、既存の負荷ユーザーに
  友達申請を送る。相手は友達の数に応じた重みで選び、asia の人は 80% が asia の人を、海外の人は 80% が asia の人を選ぶ。
  残りは最近認定された認定公開アカウントほど選ばれやすい重みでフォローする。登録後は開いている投稿期間に
  そのまま投稿してから §7.2 のループに入る。
- 1 日が始まるとき、前日の投稿期間で RealMoji を 2 件以上受けた登録ユーザー（退会する予定の人を除く）のうち、
  最も多い人を管理者が認定する。
- 結果 JSON の `days` に、リージョンと日ごとの開始時の人数、新しいユーザー数、ゲート通過数と通過時間の p50 / p90、
  操作数、失敗率、前日の 1 秒以内の通過数、誘った人数の合計、通過できなかった人数、休んだ人数（`rested`）、
  移ってきた人数（`arrived`）と移った人数（`departed`）を出す。

### 7.5 不正な利用者

`internal/evil` が動かす（`-evil=false` で止める）。走行の途中に現れ、決めた IP アドレスからログインの失敗を繰り返し、
しばらくすると検索と壊れた画像の投稿を混ぜる。`403 ip_banned` を受けたら止まる。不正な利用者のリクエストは、
得点にも、打ち切りと成長の判定にも数えない。

### 7.6 打ち切り

- 閉じた観測窓（全リージョン合算）で、操作が 20 件以上あり失敗の割合が 10% を超えたら、ただちに打ち切って fail とする。
  走行の終わりには最後の窓も判定する。
- 正しさの違反（§8）が 1 件でも記録されたら、ただちに打ち切って fail とする。
- 走行の終わりに処理中だったリクエストは打ち切り、計測にも検証にも含めない。

## 8. 検証

bench は初期データの関係と自分の書き込みを持ち、アプリの閲覧可否とフィードの規則を独立に実装して、読み取りの
結果を判定する。

- 書き込みは送信した時刻と応答を受けた時刻の区間付きで記録する。4xx は反映されていないもの、5xx・タイムアウト・
  通信エラーは結果がわからないもの（反映されたかもしれない）として扱う。
- ある読み取りから見て、応答を受けてから許容する遅れ（既定 0 秒）が経ったあとに送った読み取りには反映済み、
  読み取りの応答より後に送った書き込みは未反映、それ以外はどちらでもよいとする。
- 判定は 真 / 偽 / 不明 の 3 値で、不明な条件にかかわる結果はどちらでもよい。

### 8.1 フィード

閲覧者 V から投稿 P が見えるのは、次をすべて満たすとき（V が P の投稿者なら、P が削除されていなければ見える）。

- P が削除されておらず、P の投稿期間がまだ開いている。
- V が自分のリージョンの開いている投稿期間と同じ日付に、削除されていない投稿を持つ（ゲート）。
- V と P の投稿者がどちら向きにもブロック関係にない。
- P が public、または friends で V が投稿者の友達、または friends_of_friends で V が投稿者の友達か共通の友達を持つ。

フィードに出るのは、V 以外の投稿で見えるもののうち、public は公開範囲が public、following は V がフォローしている人、
friends は V の友達、friends-of-friends は友達ではなく共通の友達がいる人の投稿。

1 ページごとに次を確かめる。

| 事象 | 扱い |
|---|---|
| 見えてはいけない投稿が返った | 失格 |
| bench の知らない投稿が返った（その投稿者に結果のわからない投稿作成がない） | 失格 |
| ページの範囲（ページ送りの位置より古く、続きがあれば最後の投稿以降）にある見えるべき投稿が無い | エラー |
| 重複、投稿時刻の新しい順でない（同時刻の順は問わない）、ページ送りの位置より新しい投稿、続きがあるのに 50 件に満たない | エラー |
| 投稿者、キャプション、公開範囲（ありうる値のどれか）、投稿時刻が違う | エラー |
| 画像 URL の署名が違う（1 ページにつき 2 件を選んで確かめる） | エラー |

見えるべき投稿の欠落と画像 URL の署名は、ゲート通過の friends フィードでは毎回、ほかの読み取りでは §8.6 の割合で
選んだものだけ確かめる。

### 8.2 RealMoji とコメント

- 送る前に、RealMoji はその投稿が見えるか、コメントは見えていて投稿期間が開いていて public か投稿者の友達かを判定し、
  真のものだけに送る。
- 結果は送った区間での判定と比べる。受け付けられたのに判定が偽なら失格、403 で判定が真ならエラー、403 で判定が
  真でなければ正しい拒否とする。正しい拒否は計測上も失敗に数えない。

### 8.3 投稿と画像

- 投稿する写真は `-images` のアーカイブ（`manifest.json` 付きの zip、URL でもよい）から、ユーザーのリージョンを
  舞台にした写真を選ぶ（5% は珍しい写真）。キャプションは写真の題名。投稿ごとに JPEG の COM セグメントへ
  一意の文字列を挟み、さらにエントロピー符号化データの 256 バイトごとに 1 か所、AC 係数の付加ビットの最下位を
  反転する（付加ビットが 2 ビット以上の係数だけを選ぶので、係数は ±1 しか変わらず、ハフマン符号もデータの長さも
  変わらない）。同じ写真でも画素まで異なり、写真の中身や数 KB 単位のブロックで重複を除いても保存や転送を省けない。
  画素の変化は平均 0.01〜0.03、最大 4〜6（0〜255 の値で）で、目では区別できない。baseline でない JPEG は COM
  の印だけにする。RealMoji とプロフィールの画像は、写真から作った正方形の縮小を使う。
  アーカイブがなければ小さな画像を生成して使う。
- 投稿の応答の投稿者、公開範囲、キャプション、投稿期間（bench が開いた期間であること）を確かめる。
- 画像は署名を確かめて（§8.6 の割合で選んだときだけ）から取得し、SHA-256 が投稿したバイト列と一致することを
  確かめる。投稿が確実に残っていて投稿者も退会していないのに 403 か 404 ならエラーとする。削除から 5 秒を過ぎた
  投稿の画像を返したら失格とする。自分で削除した投稿の画像は、削除から 6 秒後に必ずもう一度取得して確かめる。

### 8.4 画像 URL の署名

画像 URL は `/api/images/{imageId}?exp={unix 秒}&sig={署名}` とし、署名は画像の持ち主の `sha256(シークレットキー)` を
鍵にして `"{exp}:{imageId}"` に HMAC-SHA256 を 1000 回重ねたもの（base64url、パディングなし）。`exp` は現在より後で
24 時間（と 1 分の余裕）以内であること。

### 8.5 履歴

cohort のユーザーと思い出を見返すユーザー（§7.3）が読む履歴（履歴のある月の Memories）は §5 と同じく初期データと
比べ、負荷走行で開いた投稿期間の投稿は除く。画像の署名は無作為に 8 件、中身は無作為に 4 枚取得して比べる（§5 の
初期データの検証ではすべて確かめる）。画像の署名と中身の比較は §8.6 の割合で選んだ読み取りだけで行い、選ばなかった
読み取りでも画像は取得する。履歴は変わらないので、違えば失格とする。

### 8.6 検証の間引き

bench の CPU がアプリより先に尽きないよう、負荷走行では重い検証（見えるべき投稿の欠落、画像 URL の署名、履歴の
画像の比較）を、操作ごとに確率 `-verify-rate`（既定 10%）で選んだものだけで行う。選んだ検証で見つけた失敗は、
割合の逆数の件数としてエラー率に数え、エラー率の期待値をすべて検証したときとそろえる。失格になる違反の判定
（見えてはいけない投稿など）は間引かない。初期データの検証と走行後の確認も間引かない。

## 9. 走行後の整合性チェック

負荷走行のあと、無作為に選んだ負荷ユーザー（300 人まで、止まったユーザーを除く）について、同時に 64 人ずつ（上限 15 秒）次を読み、受け付けられた
書き込みと突き合わせる。速いアプリほど負荷ユーザーが増えるので、全員を一斉に確かめると走行中の負荷と関係なく最後に
詰まる。書き込みの取りこぼしは系統的に起きるので、一部で見つかる。
違えば fail とする。結果のわからない書き込みはどちらでもよい。

- 負荷走行で開いた投稿期間の日付を含む月の Memories（その期間の投稿だけ）: 確実に残っている投稿がある、
  確実に削除された投稿がない、bench の知らない投稿がない（結果のわからない作成がなければ）、ほかの人の投稿がない。
- 友達の一覧: 有効なユーザーとの確実な友達関係がすべてあり、確実に友達でない人がいない。
