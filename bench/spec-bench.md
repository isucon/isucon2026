## 0. スコープと情報分離

### 0.1 本仕様が定義するもの

本仕様は ISUReal を ISUCON 2026 の競技課題として出題するためのベンチマーカーを定義する。
対象は次のとおりである。

- ベンチマーカーの実行モデル、フェーズ構成、入出力契約
- アプリ側に追加する競技運用エンドポイント（`POST /api/v1/initialize`）の契約
- 仮想時間モデルと投稿期間の駆動方式
- 事前整合性チェック・負荷走行・最終整合性チェックの検証項目
- Push 受信モックサーバの契約
- スコアリング構造と合否判定
- ベンチマーカー自身の品質保証

### 0.2 本仕様が定義しないもの

Constitution 2.0.0 の情報分離に従い、次は本仕様に含めない。

- 意図的ボトルネックの配置箇所・原因・強度・想定解（非公開課題台帳）
- スコア係数の確定値・合否しきい値の確定値
- 較正結果・試し解き結果
- 初期データセットの具体的な規模・分布（PRE-003 として別途定義する）

## 1. 用語

| 走行 | ベンチマーカーの 1 回の起動から終了までの全体 |
| 仮想時間 | ベンチマーカーがアプリへ注入する論理的な時刻。実時間とは独立に進行する |

| finalcheck | 最終整合性チェックフェーズ |
| スコアタグ | スコアカウンタに付与する操作種別の識別子 |
| 失格 | `pass: false`、スコア 0 で走行を終了すること |

## 2. ベンチマーカーの役割

ベンチマーカーは以下の 4 つの役割を同時に担う（MUST）。

| ID | 役割 | 責務 |
|---|---|---|
| ROLE-1 | 負荷生成 | 選手実装が処理できる限界まで負荷を出す。ベンチマーカー側の資源が先に飽和してはならない（MUST NOT） |
| ROLE-2 | E2E 検証 | 公開契約（`openapi.yaml`）とデータ不変条件（`spec.md` FR/SC）への適合を検査し、不正な高速化を検出する |
| ROLE-3 | スコア・診断出力 | 順位決定の根拠となるスコアと、選手・運営それぞれに向けた診断情報を出力する |
| ROLE-4 | 時間軸の駆動 | 仮想時間を管理し、管理者 API を通じて投稿期間を開始し、アプリの状態機械を進める |

## 3. 仮想時間モデル（D-002）

### 3.1 概要

ISUReal は投稿期間を管理者 API でしか開始できず、同一地域の同一カレンダー日には最大 1 件しか
開始できない（FR-003, FR-004）。実時間で数分の走行中に複数の投稿期間サイクルを実行するため、
ベンチマーカーは仮想時間をアプリへ注入する。

### 3.2 要件

- **VT-001**: アプリは `POST /api/v1/initialize` の応答で返す `base_time` を仮想時間の起点として使用しなければならない（MUST）。
  アプリ内部では `base_time` と実時間の差分をオフセットとして保持し、`time.Now()` に加算して仮想現在時刻を得る。
  初期化前は実時間で動作する。

- **VT-002**: アプリの全ての時刻判定（カレンダー日の計算、投稿期間の開始可否、冪等性キーの 24 時間 TTL、
  削除猶予 30 日の判定）は仮想現在時刻を基準にしなければならない（MUST）。

- **VT-003**: `POST /api/v1/initialize` は初期化完了時にレスポンスで `base_time` を返す（D-003）。
  `base_time` は既知のカレンダー日の 00:00:00 UTC であり、アプリはこの時刻を仮想時間の起点とする。
  これにより走行開始時の各地域のカレンダー日が確定的になる
  （Asia: 09:00 = 当日、Europe: 01:00 = 当日、America: 19:00 = 前日）。
  走行中のカレンダー日遷移には `POST /api/v1/virtual-time/advance` でオフセットを更新し、
  アプリの仮想時刻を動的に進める。

- **VT-004**: 仮想時間のオフセットにより、走行中に複数のカレンダー日を跨ぎ、
  各地域で複数回の投稿期間を開始できなければならない（MUST）。

- **VT-005**: 初期データに「過去の投稿期間で作成された投稿」を含め、
  Memories フィード（月別一覧）の検証と負荷に使用する（MUST）。

- **VT-006**: 仮想時間を使うことで、冪等性キーの 24 時間 TTL 境界（FR-026）と
  アカウント削除猶予 30 日（FR-031）の検証を走行内で実施できなければならない（MUST）。

### 3.3 走行中の時間進行パターン

1 回の走行における投稿期間の駆動は次の構造を持つ。

1. 初期化完了後、仮想時間を十分に未来へ進め、初期データの最終カレンダー日から新たなカレンダー日へ入る
2. 管理者エージェントが各地域の通知時刻を設定する
3. 通知ファンアウト → 投稿スパイク → フィード閲覧・交流の負荷サイクルを実行する
4. 仮想時間をさらに進め、次のカレンダー日へ移行する。前回期間は Memories へ遷移する
5. 手順 2〜4 を走行時間内で繰り返す

各サイクルで「通知 → 投稿 → 閲覧・交流 → 期間終了」の完全なライフサイクルを検証する。

### 3.4 仮想時間の注入 API（D-003）

走行中に仮想時間を進めるため、以下の競技運用エンドポイントを追加する。

| ID | 項目 | 内容 |
|---|---|---|
| VT-API-01 | メソッド・パス | `POST /api/v1/virtual-time/advance` |
| VT-API-02 | 認証 | 不要（初期化と同じ扱い） |
| VT-API-03 | リクエスト | `{"offset_seconds": <integer>}` 現在のオフセットに加算する秒数 |
| VT-API-04 | 成功応答 | `200 OK`、`{"current_time": "<RFC 3339>"}` 適用後の仮想現在時刻 |
| VT-API-05 | 制約 | ベンチマーカーは負荷走行中のサイクル間でのみ呼び出す（MUST）。投稿スパイク中に呼んではならない（MUST NOT） |
| VT-API-06 | 同期性 | ベンチマーカーはオフセット更新後に十分な待機を入れ、アプリの全プロセスがオフセットを反映するまで次のリクエストを送らない（D-006）。アプリ側の同期保証方式は選手の裁量とする |

## 4. アプリ側の追加契約

### 4.1 初期化エンドポイント（D-001）

#### 位置づけ

- 競技運用エンドポイントであり、アプリの機能要件・認証・認可・データ不変条件を上書きしない（MUST NOT）
- アプリ基準仕様（`spec.md` v1.0.5）には存在しない。本仕様の承認後に `openapi.yaml` と実装へ追加する
- 参考実装を提供する。選手は自由に差し替えてよいが、「毎回既知の状態へ戻す」責務を維持しなければならない（MUST）

#### 契約

| ID | 項目 | 内容 |
|---|---|---|
| INIT-01 | メソッド・パス | `POST /api/v1/initialize` |
| INIT-02 | 認証 | 不要（`security: []`）。初期化は全セッションを破棄するため、認証要求は自己矛盾する |
| INIT-03 | 冪等性キー | 不要。競技運用エンドポイントとして FR-026 の対象外とする |
| INIT-04 | 成功応答 | `200 OK`、`{"language": "<言語識別子>", "base_time": "<RFC 3339>"}` 仮想時間の起点（VT-003） |
| INIT-05 | 失敗応答 | `500`、`application/problem+json`（FR-027 準拠: `type`/`title`/`status`/`code`/`correlationId`） |
| INIT-06 | 同期性 | 応答時点で初期化が完了していること（MUST）。非同期初期化を禁止する |
| INIT-07 | リセット対象 | スキーマ・索引（マイグレーション適用済み状態）、競技用初期データセット（PRE-003）、画像ファイル領域、ログインセッション、Push 購読、冪等性レコード、通知・Push 試行記録、ワーカージョブ状態、全地域の通知スケジュールと投稿期間、仮想時間オフセット（初期化時に `base_time` を起点にリセット） |
| INIT-08 | リセット対象外 | 構造化ログ（FR-031, SC-011 に準拠） |
| INIT-09 | 応答ヘッダー | FR-044 の保護応答ヘッダーを適用する（`Cache-Control: no-store` 等） |
| INIT-10 | 実行時間上限 | 競技仕様で確定する（暫定 30 秒）。超過は失格 |
| INIT-11 | 並行実行 | ベンチマーカーは初期化中に他リクエストを送らない。アプリ側の相互排他保証は不要 |
| INIT-12 | 観測性 | 開始・完了・失敗を構造化ログへ記録する（MUST） |
| INIT-13 | 契約検査 | OpenAPI へ追加し、契約テストで成功・失敗の両応答を検証する（MUST） |

### 4.2 追加の前提条件

| ID | 前提条件 | 理由 |
|---|---|---|
| PRE-003 | 競技用初期データセットの定義と生成器 | 規模・分布・乱数シードを固定し、ベンチマーカーとアプリが同一ダンプを参照する |
| PRE-004 | 管理者資格情報 | 投稿期間の開始と認定公開状態の付与に必要。初期化後に既知の資格情報で管理者ログインできること（MUST） |
| PRE-005 | Push 購読エンドポイントの外部指定 | ベンチマーカーのモックサーバへ Push を送信させる。VAPID 鍵の設定方法と送信先ホストの許可範囲を明示する |
| PRE-006 | 画像処理の資源設定 | `ISUREAL_IMAGE_SANITIZER_*` の既定値を競技環境で固定する |
| PRE-007 | 仮想時間の注入境界 | `POST /api/v1/initialize` のレスポンス `base_time` と `POST /api/v1/virtual-time/advance` による時計の操作（§3.2 VT-001、§3.4） |
| PRE-008 | 静的ファイルの正本とハッシュ | SPA アセットの改変検出用ハッシュ一覧を配布時点で生成する |

## 5. 実行モデル

### 5.1 プロセスモデル

- **EXEC-001**: 1 起動 = 1 走行 = 1 プロセス。終了時にプロセスも終了する単発アプリケーションとする（MUST）。
  ポータル通信・強制停止・実行キューはスーパーバイザの責務とする。

- **EXEC-002**: 設定はコマンドライン引数と環境変数で与える（MUST）。設定ファイルを必須としない。
  スーパーバイザから与えられる対象アドレス、全ノードアドレス、結果報告用ファイルディスクリプタを環境変数から受け取る。

- **EXEC-003**: 標準出力を選手向け、標準エラー出力を運営向けとする（MUST）。
  panic のスタックトレースが選手へ露出してはならない（MUST NOT）。

- **EXEC-004**: 結果を機械可読 JSON（`pass`, `score`, `messages`, `language`, スコアタグ別内訳）として指定パスへ書き出す（MUST）。

- **EXEC-005**: 起動時にバージョン、全設定値、乱数シード、初期データセットバージョンを運営向けログへ出力する（MUST）。
  この出力で同一条件の再実行が可能な形式とする。

### 5.2 フェーズ構成

走行は以下の 4 フェーズで構成する（MUST）。前フェーズが失敗した場合、後続を実行せず失格とする（MUST）。

| 順序 | フェーズ | 概要 |
|---|---|---|
| 1 | 初期化 | `POST /api/v1/initialize` の呼び出しと内部モデルのロード |
| 2 | 事前整合性チェック（pretest） | 公開契約・データ不変条件への適合を短時間で検査 |
| 3 | 負荷走行（load） | 仮想時間を進めながら投稿期間サイクルを繰り返し、負荷を生成 |
| 4 | 最終整合性チェック（finalcheck） | 書き込み停止後の整合性検査 |

- **EXEC-006**: 各フェーズおよび全体に上限時間を設ける（MUST）。上限到達時は進行中リクエストを中断し結果を確定させる。
  全ての待機・ループは `context.Context` のキャンセルで中断できること（MUST）。

- **EXEC-007**: `--pretest-only` モードを持ち、pretest だけを短時間で実行できること（MUST）。
  参考実装の移植確認と CI で使用する。

## 6. 初期化フェーズ

- **INIT-F01**: `POST /api/v1/initialize` を呼び、INIT-10 の専用タイムアウトを適用する（MUST）。
  失敗またはタイムアウトは失格とする。`Idempotency-Key` を付けず、認証もしない。

- **INIT-F02**: 応答から言語識別子を取得し、結果 JSON と運営ログへ記録する（MUST）。
  応答が INIT-04 に適合しない場合は失格とする。

- **INIT-F03**: 初期データセット（PRE-003）をベンチマーカー内部モデルへロードする（MUST）。

- **INIT-F04**: 応答の `base_time` を取得し、ベンチマーカー内部の仮想時間管理に反映する（MUST）。
  走行時刻に依存する不確定性を排除する。

## 7. 事前整合性チェック（pretest）

pretest で検出した違反は原則として失格とする（MUST）。

### 7.1 データ整合性

- **PRE-T01**: 初期データの読み取り整合性を検査する（MUST）。
  フィード、プロフィール、Memories、関係一覧、通知一覧が初期データと一致すること。

### 7.2 主要導線

- **PRE-T02**: 正常系の主要導線を 1 周する（MUST）。
  自己登録 → ログイン → 管理者による投稿期間開始 → 未投稿状態でのフィード閲覧（投稿促進状態の確認、FR-012） → 投稿 → フィード閲覧 → RealMoji → コメント → キャプション編集（FR-006） → 通知開封。

### 7.3 境界値・異常系

- **PRE-T03**: 以下の境界値・異常系を検査する（MUST）。
  - 画像: JPEG 以外の拒否、容量上限超過の拒否、上限内で展開後が大きい画像の受理、EXIF 付き画像のメタデータ除去
  - 文字数: Unicode コードポイント基準の上限・下限、結合文字・複数コードポイント絵文字
  - パスワード: 許可文字範囲（U+0020〜U+007E）、前後空白の保持、8〜72 文字の境界
  - ユーザー名: 許可文字（ASCII 英数字・`_`・`.`・`-`）、大文字小文字無視の重複拒否
  - 位置情報: 範囲外・非有限の座標の拒否、種別と値の不一致の拒否
  - RealMoji: 固定 6 種以外の拒否、投稿者自身による RealMoji の拒否、投稿者自身のコメントの許可
  - 公開範囲変更: 公開範囲を狭めた後に範囲外ユーザーから閲覧・交流できないこと（FR-013）
  - キャプション編集: 投稿者本人のみ・現在期間中のみ編集可能、期間終了後は拒否されること（FR-006）

### 7.4 認可

- **PRE-T04**: 公開範囲 3 種 × 関係（友達/距離 2/無関係/フォロー/ブロック）の組み合わせで、
  閲覧可否・コメント可否が仕様どおりであることを検査する（MUST）。
  「距離 2 のみの閲覧者は RealMoji 可・コメント不可」を含む。

### 7.5 冪等性

- **PRE-T05**: 同一 UUID・同一内容の再送が初回結果を返し効果が重複しないことを検査する（MUST）。
- **PRE-T06**: 同一 UUID・異内容の再利用が 409 になることを検査する（MUST）。
- **PRE-T07**: 503 を返した試行が確定結果にならないことを検査する（MUST）。

### 7.6 セキュリティ境界

- **PRE-T08**: 以下を検査する（MUST）。
  - Bearer 以外の資格情報源（Cookie、query、form body）の拒否
  - CORS 許可ヘッダーの不在
  - API・認可画像の `Cache-Control: no-store` 等
  - SPA 応答の CSP/Permissions-Policy

### 7.7 エラー契約

- **PRE-T09**: `application/problem+json`、`type`/`title`/`status`/`code`/`correlationId` の存在を検査する（MUST）。
  同じ状態・入力から生じる失敗が `correlationId` 以外同一であること。

### 7.8 ページング

- **PRE-T10**: 51 件以上の一覧を複数ページ取得し、順序の単調性・非重複・1 ページ 50 件上限を検査する（MUST）。

### 7.9 静的ファイル

- **PRE-T11**: SPA アセットのハッシュを PRE-008 の正本と照合する（MUST）。不一致は失格とする。

### 7.10 セッション・Push 購読

- **PRE-T12**: 再ログイン後に旧セッションが無効化されることを検査する（MUST）。
- **PRE-T13**: 再ログイン後に旧 Push 購読へ送信されないことを検査する（MUST）。

## 8. 負荷走行フェーズ

### 8.1 エージェントモデル

- **LOAD-01**: 「1 ユーザー = 1 エージェント = 1 セッション」を厳守する（MUST）。
  同一ユーザーの並列多重ログインを行わない（MUST NOT）。

- **LOAD-02**: 負荷は固定シナリオ数で上限を作らず、選手実装が速いほど多くの負荷を出す構造にする（MUST）。
  ワーカー追加による負荷増加と、応答遅延によるワーカー離脱の両方を持つこと（MUST）。

- **LOAD-03**: 新規登録ユーザーを走行中に追加投入し、並列度を増やす（MUST）。

### 8.2 投稿期間サイクル

- **LOAD-04**: 走行の骨格を次の順序で構成する（MUST）。
  1. 管理者エージェントが各地域の次回通知時刻を仮想時間上の近い将来へ設定する
  2. 仮想時間を進めて通知時刻を到達させる
  3. 投稿期間開始（通知ファンアウト）をアプリ内通知と Push モックの受信の両方で検出する
  4. 通知を受けたユーザーが一斉に投稿する（スパイク負荷）
  5. 投稿完了後、フィード（友達/友達の友達/公開/フォロー）、投稿詳細、RealMoji 一覧、コメント一覧、通知一覧を巡回する
  6. 交流（RealMoji・コメント）、関係操作（検索・申請・承認・フォロー・ブロック）、プロフィール更新、Memories 閲覧を混在させる
  7. 仮想時間を進めて次のカレンダー日へ移行し、前回期間が Memories へ遷移したことを検証する

- **LOAD-05**: 走行時間内で手順 1〜7 を複数回繰り返す（MUST）。
  少なくとも 2 サイクル以上の投稿期間を完了することを目標とする。
  2 サイクル未完了は失格としない。完了サイクル数が少ないほどスコアが低くなる結果で反映する（D-004）。

### 8.3 検証（走行中）

- **LOAD-06**: 通知ファンアウトの完了（対象ユーザー全員へのアプリ内通知作成と Push 送信）を計測対象とする（MUST）。
  ファンアウト遅延がスコアに反映される設計にできること。

- **LOAD-07**: 走行中に意図的な再送（冪等性キーの再利用）を一定割合で混ぜ、
  負荷下でも冪等性が維持されることを検証する（MUST）。

- **LOAD-08**: 走行中に不正アクセス系のリクエストを混ぜ、権限違反が確実に拒否されることを検証する（MUST）。
  他人の通知の既読化、他人の投稿の削除、ブロック相手への操作、期間終了後の交流を含む。

- **LOAD-09**: 各リクエストにタイムアウトを設定する（MUST）。超過はエラーとして記録し、
  特定エンドポイントの遅延で走行全体が停止しないこと（MUST）。

- **LOAD-10**: 503 応答は再試行可能な結果として扱い、減点にしない（MUST NOT）。加点もしない。
  発生数は運営向けに記録する。

- **LOAD-11**: 走行中に検出した違反の扱いを違反種別ごとに定義する（MUST）。
  「即時失格」か「減点継続」かを種別ごとに明示する。

- **LOAD-11a**: 走行中の違反は以下のとおり分類する（MUST）。

  **即時失格（走行中断）**:
  - 認可違反: 他人の非公開データが閲覧可能
  - データ破壊: 投稿期間あたり 1 ユーザー複数投稿の成立、RealMoji の二重成立
  - 静的ファイル改変の検出（PRE-T11 と同一チェック）
  - 初期データの改変（投入済みデータの消失・変質）

  **減点継続**:
  - レスポンス不正: ページング順序違反、件数上限超過、必須フィールド欠落
  - 冪等性違反: 同一キー再送で異なる結果
  - エラー契約違反: RFC 9457 非準拠の応答
  - 通知重複: 同一受信者×投稿期間に複数通知
  - タイムアウト超過: 個別リクエストのタイムアウト
  - セキュリティヘッダー欠落: `Cache-Control: no-store` 等の不在

  分類は較正段階（M11）で再評価し、必要に応じて調整する。

### 8.4 全書き込み操作の冪等性キー

- **LOAD-12**: ベンチマーカーの全書き込みリクエストに UUID を付与する（MUST）。
  HTTP クライアント層で一律に組み込み、後付けの漏れを防ぐ。

## 9. 最終整合性チェック（finalcheck）

走行終了後、書き込みが停止した状態で以下を検査する（MUST）。

- **FINAL-01**: 投稿期間ごとに 1 ユーザー 1 投稿が守られていること。
- **FINAL-02**: 削除 2 回後の再投稿が成立していないこと。
- **FINAL-03**: RealMoji が投稿 × 反応者ごとに有効 1 件であること。
- **FINAL-04**: 論理通知が受信者 × 投稿期間ごとに 1 件であり、Push 送信試行が 4 回を超えていないこと。
- **FINAL-05**: 走行中に 503 を返した書き込みの痕跡（DB 行・公開画像）が残っていないこと。
- **FINAL-06**: ブロック後に両者間の関係と申請が残っていないこと。
- **FINAL-07**: 削除猶予期限が到来したアカウントの物理削除が完了していること（仮想時間で 30 日を経過させて検証する）。
- **FINAL-08**: Memories へ遷移した投稿、および付随する RealMoji とコメントが投稿者本人からのみ閲覧可能であること（FR-016, FR-021）。
- **FINAL-09**: 非同期処理（通知ファンアウト、Push 再試行、物理削除）の完了待ちに上限時間を設ける（MUST）。
  上限内に収束しない場合は明確なエラーとして記録する。

## 10. レスポンス検証

- **VALID-01**: 検証関数を合成可能な形で実装する（MUST）。
  複数のバリデータを 1 レスポンスへ適用し、複数エラーをまとめて返す。

- **VALID-02**: 「ベンチマーカーの送信順序とアプリの保存順序が一致すること」を要求してはならない（MUST NOT）。
  リクエストの処理順序はアプリの裁量である。

- **VALID-03**: 画像応答は以下を検証する（MUST）。
  - JPEG としてデコード可能
  - 寸法一致
  - メタデータ不在
  - 同一 ID の再取得でバイト一致（不変性）

- **VALID-04**: 各エラーへ機械判定可能なコードを付与し、種別ごとに集計できること（MUST）。
  選手向けメッセージにはメソッド・パス・期待値・実際値を含める。

## 11. Push 受信モックサーバ

- **PUSH-01**: ベンチマーカーに Push 受信モック HTTP サーバを内蔵する（MUST）。
  購読エンドポイントとしてアプリへ登録し、受信数・重複・試行回数を記録する。

- **PUSH-02**: モックサーバは応答を制御できること（MUST）。
  正常応答、一時失敗（5xx）、恒久失敗（404/410）を購読単位またはシナリオ単位で切り替える。

- **PUSH-03**: モックサーバの受信処理はベンチマーカー本体の負荷生成を妨げないこと（MUST）。
  別ポート・独立したワーカープールで動作する。

- **PUSH-04**: 受信した送信元・宛先・タイミングを運営向けに出力し、
  通知ファンアウトの遅延分布を較正に使用できること（MUST）。

- **PUSH-05**: 以下を検証する（MUST）。
  - 論理通知 ID の重複がないこと
  - 1 論理通知あたりの外部送信試行が 4 回を超えないこと
  - 一時失敗を返した場合に再試行されること
  - 恒久失敗を返した場合に購読が無効化され、以後送信されないこと

- **PUSH-06**: Push ペイロードの検証深度は実装時に確定する。
  最低限 VAPID ヘッダーの存在を検証する（MUST）。
  RFC 8291（`aes128gcm`）復号と RFC 8292（VAPID 署名検証）は SHOULD とする。

## 12. 内部世界モデル

- **MODEL-01**: ベンチマーカーはアプリのデータモデルに対応する内部モデルを持つ（MUST）。
  パスワードは平文保持、画像はハッシュと寸法で保持する（バイト列を保持しない）。

- **MODEL-02**: モデル集合は「ソート済みリスト」と「ID インデックス」の両方を持ち、
  期待値計算を O(1)〜O(log N) で行える（MUST）。

- **MODEL-03**: ソーシャルグラフは隣接集合として保持し、距離 2 集合の計算量を制御する（MUST）。
  走行中の関係変更を反映しつつ、期待値検証はスナップショット基準の緩い判定とする。

- **MODEL-04**: 全ての共有状態は競合状態を起こさない構造で保護する（MUST）。
  構造体単位のミューテックスまたは並行安全なコレクションを使用する。

- **MODEL-05**: 地域別カレンダー日と投稿期間の判定をベンチマーカー側で独立実装し、
  アプリの判定と突き合わせる（MUST）。

## 13. スコアリングと合否

### 13.1 スコア構造

- **SCORE-01**: スコアはスコアタグ付きカウンタの重み付き合計として算出する（MUST）。
  タグは加点対象の操作種別ごとに分ける。

- **SCORE-02**: 重みは実行時に変更可能な形で定義する（MUST）。
  較正段階で係数だけを差し替えられること。本仕様では係数の確定値を定めない。

- **SCORE-03**: 減点はエラー種別ごとの係数で定義する（MUST）。
  減点で合計が負になる場合は 0 とする。

- **SCORE-04**: 走行後にスコアタグ別カウントを出力する（MUST）。
  ただし選手向けには合計スコアのみを開示する（D-005）。
  スコアタグ別カウントと減点内訳は運営向けログにのみ出力する。

### 13.2 失格条件

- **SCORE-05**: 以下を失格（`pass: false`、スコア 0）とする（MUST）。
  - 初期化失敗またはタイムアウト
  - pretest 失敗
  - finalcheck 失敗
  - 静的ファイル改変の検出
  - 走行中断（即時失格に分類された違反の検出）

### 13.3 診断情報

- **DIAG-01**: 選手向けメッセージは重複排除し、件数上限を設けて出力する（MUST）。
  発生箇所（HTTP メソッド・パス）と期待値・実際値を含める（D-005）。

- **DIAG-02**: 運営向けログに相関識別子、スタックトレース、リクエスト/レスポンス要約を含める（MUST）。
  アプリの `correlationId` と突き合わせられるよう、ベンチマーカー側の識別子も記録する。

- **DIAG-03**: ベンチマーカー内部エラーを選手向けエラーと明確に区別し、
  運営へ通報すべきものとして分類する（MUST）。

## 14. 非機能要件

- **NFR-01**: ベンチマーカー自身が先に飽和してはならない（MUST NOT）。
  想定上位解に対して CPU・メモリ・帯域・ファイルディスクリプタに余裕を持つこと。
  較正時に「ベンチマーカー側の資源使用率」を記録する（MUST）。

- **NFR-02**: 走行用画像の展開後サイズとファイル容量の入力条件を明示的に定義する（MUST）。
  上限付近の画像は境界検証のみで使用する。

- **NFR-03**: HTTP クライアントはホストごとの接続を再利用し、接続数上限を明示的に設定する（MUST）。

- **NFR-04**: メモリ使用量は投入データ量に対して線形に収まること（MUST）。
  画像バイト列を保持し続けない。

- **NFR-05**: 同一条件（ターゲット、初期データ、乱数シード、設定）で結果が再現すること（MUST）。
  乱数は明示的なシードから導出する。暗黙の時刻依存を持たない。

- **NFR-06**: フレーク率を測定可能にする（MUST）。
  同一条件の反復実行でスコア分散と失敗率を出力できること。

## 15. 再現性・較正

- **CAL-01**: 負荷条件、初期データ、仮想時間進行、乱数シード、タイムアウト、検査内容、
  採点式、実行環境を明示的に管理し、実行結果に記録する（MUST）。

- **CAL-02**: 較正で必要な計測を出力する（MUST）。
  スコアタグ別カウント、エンドポイント別レイテンシ分布（p50/p90/p99/max）、
  エラー種別集計、通知ファンアウト遅延、走行中の並列度推移。

- **CAL-03**: ボトルネックの単独・累積解消状態で同一条件の実行を繰り返せるよう、
  設定の切り替えを引数で完結させる（MUST）。

- **CAL-04**: ベンチマーカー・初期実装・初期データセット・想定解のバージョンを追跡可能にし、
  組み合わせの互換性を記録する（MUST）。

## 16. 運用・ポータル連携

- **OPS-01**: スーパーバイザから与えられる対象アドレスと全ノードアドレスを受け取り、

- **OPS-02**: 結果報告用ファイルディスクリプタまたは結果ファイルへ機械可読な結果を書き出す（MUST）。

- **OPS-03**: `SIGTERM` 受信時に速やかに結果を確定させる（MUST）。
  強制停止はスーパーバイザに委ねる。

- **OPS-04**: 選手環境のリブート後・初期化直後のいずれからでも実行できること（MUST）。
