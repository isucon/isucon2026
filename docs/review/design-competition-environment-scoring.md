## 1. 結論

スコアの単位を「投稿ゲートを通過したユーザー」にする。通知を受け（または登録し）、投稿が受理され、
解錠されたフィードを取得できたユーザーを、ウィンドウごとに 1 通過として数える。通過後の閲覧と交流は
小さい重みの従指標とし、上限が通過数に従属する形にする。減点は用いず、失格は観測窓ごとのエラー率とタイムアウト率で
SLO として判定する。

理由は次の 3 点である。

- 出題映像が「成功」として描くのは、投稿が通ってフィードが開く瞬間であり、「失敗」は回り続ける
  読み込みマークである。スコアの単位をこの瞬間に置けば、参加者への説明が「グランプリに参加できた
  人の数」で済む。
- 投稿ゲート（FR-012: 自分が投稿するまで他人の投稿は見られない）があるため、閲覧の負荷は通過数に
  従属する。閲覧系イベントを数える方式で起きる「読み取りだけを速くして稼ぐ」構造が、アプリの仕様
  そのものによって塞がれている。
- 走行中の新規ユーザーの流入とリージョンごとのウィンドウで通過が連続的に発生し、全世界ウィンドウが
  1 回でもスコアが階段状にならない。

## 2. 前提

本提案は次を前提にする。いずれも本レビューの他の提案か、出題映像の筋書きに由来する。

| 前提 | 出所 |
|---|---|
| 負荷は実時間 60 秒、仮想時計なし。日付は管理者が与えるラベル | P-101、D-008 |
| ウィンドウはリージョンごとに実時間スケジュールで開き、ずらして 3 回ずつ | P-102 |
| 加えて、全リージョン同時に開く「全世界ウィンドウ」を走行の終盤に 1 回置く | 出題映像（CHAIR GRAND PRIX）、§5.3 |
| エージェントは同時に 1 リクエスト、思考時間なしのクローズドループ | P-102、LOAD-01 |
| ユーザー数はラチェット式レベルで走行中に増える。追加分は走行中の新規登録 | P-102、LOAD-03 |
| 性能不足はまずレベルの凍結で扱い、観測窓のエラー率が SLO を超えたときだけ失格にする。固定件数の閾値（D-009）は用いない | P-102、P-109、§6 |
| 参加者には `pass` と合計点のみを開示する | D-005 |

出題映像の筋書きと本レビューの判断基準（本文 §2）との対応は次のとおり。日常の通知はリージョン内の
同時（映像の第 2 幕は「対象: 日本」）、グランプリだけが全世界同時（第 3 幕以降）と読む。

- 「社長が全世界対応を指示し、当日に負荷が来る」が、本文 §2 の「8 時間後に負荷がやってくる」に
  対応する。ルーターとリージョンサーバーは映像で説明しない。P-105 のとおり、稼働中の設定として
  参加者に渡す。
- 「海外の著名人が 2 枚撮りし、各国でダウンロードが猛回転する」が、走行中の新規登録による流入に
  対応する。成長は外生的で予測不能、というのが映像の主張なので、流入の速さは参加者の実装が
  捌けたぶんだけ増える（ラチェット）と説明する。
- 「読み込みマークを睨みつける利用者」が、通過できなかったユーザーに対応する。

## 3. スコアの単位: ゲート通過

### 3.1 定義

1 ユーザーが 1 ウィンドウで次の手順をすべて成功させたとき、そのウィンドウで 1 通過と数える。

| 手順 | 既存ユーザー | 走行中に登録したユーザー |
|---|---|---|
| 1 | 自分のリージョンのウィンドウの通知をアプリ内通知で受け取る | 登録し、ログインする（通知は届かない: FR-041） |
| 2 | 投稿が受理される（画像、キャプション、公開範囲） | 同左 |
| 3 | 解錠された現在フィード（友達）を 1 ページ取得できる | 同左 |

- 通過は「ユーザー × ウィンドウ」で一意。同じユーザーが同じウィンドウで二重に通過することはない
  （FR-005 により投稿は 1 件しか成立しない）。
- 全世界ウィンドウは別のウィンドウなので、同じユーザーが日次のウィンドウと全世界ウィンドウの両方で
  通過できる。
- 手順 1 の通知確認は、通知が届く前に投稿を試みてよい実装（ウィンドウ開始の検出をフィードや
  `current` で行う）を排除しないため、通知の到達は通過の条件にせず、通知ファンアウトの検証
  （LOAD-06、P-111）とレベル判定の信号（on-time 比率）に使う。ただし手順 1 で通知を待つ
  エージェントと待たないエージェントの比率はベンチが固定する。
- 手順 3 は「投稿したのに他人の投稿が見えない」「投稿していないのに見える」を検出する場所でも
  ある。後者は正しさの違反であり、通過ではなく失格に計上する（§6）。

### 3.2 何を測っているか

通過数は「そのウィンドウで何人を捌けたか」である。クローズドループなので、1 ウィンドウあたりの
通過数はレベル（そのウィンドウ開始時点のユーザー数）で上限が決まり、その上限に届くかどうかは
スパイク（投稿、画像サニタイズ、通知ファンアウト、フィード解錠）を時間内に処理できるかで決まる。

したがってスコアは次の 2 つの積に近い形になる。

- レベルがどこまで上がったか。定常状態でのエラー率、読み取り p99、直前のスパイクの on-time 比率で
  決まる（P-102 のラチェット）。
- 各スパイクでレベルどおりの人数を通せたか。スパイクの処理能力で決まる。

「速いが捌けない」実装はレベルが上がっても通過が伸びず、「捌けるが遅い」実装はレベルが上がらない。
どちらも上位には来ない。

### 3.3 投稿ゲートが読み取り偏重を防ぐ理由

閲覧系イベント（フィード、画像取得、通知一覧、Memories）を数える方式では、閲覧は書き込みと違って
1 ユーザーあたりの回数に天井がなく、キャッシュで桁違いに速くできるため、閲覧の秒間処理数がスコア
になる。本レビューの P-109 が防ぎたい「インメモリ単一サーバーの勝利」がそのまま最適解になる。

投稿ゲートがあると、閲覧できるのはそのウィンドウで通過したユーザーだけになる。閲覧イベント数の
上限は「通過ユーザー数 × 残り時間 ÷ 往復時間」であり、閲覧の速さは通過数に掛かる係数としてしか
効かない。閲覧だけを速くしても、通過数が少なければ伸びない。これは本提案が閲覧系イベントを従指標
として数えてよい根拠でもある（§4.2）。

## 4. スコア式

```
score = Σ_windows Σ_users pass(u, w) × W_pass
      + Σ 通過後イベント × w_event
```

減点項は持たない（§6）。合計が負になることはない。

### 4.1 主指標: 通過

| イベント | 重み（暫定） | 備考 |
|---|---|---|
| ゲート通過（リージョンのウィンドウ、既存ユーザー） | 100 | 通知 → 投稿 → フィード |
| ゲート通過（リージョンのウィンドウ、走行中に登録したユーザー） | 100 | 登録 → 投稿 → フィード。登録自体は加点しない |
| ゲート通過（全世界ウィンドウ） | 100 | 同じ重み。§9 の較正で引き上げる余地を残す |

同じ重みにする理由: 「グランプリに参加できた人の数」という説明を単純に保つため。全世界ウィンドウは
レベルが上がった状態で来るので、重みを変えなくても自然に配点が大きい。

### 4.2 従指標: 通過後の活動

| イベント | 重み（暫定） | 上限 |
|---|---|---|
| フィード 1 ページ取得（友達、友達の友達、公開、フォロー） | 1 | クローズドループで往復時間に従属 |
| 投稿画像の取得 | 1 | フィードに載った投稿の画像。P-108 の画像 GET 検証を兼ねる |
| RealMoji の送信 | 5 | 1 ユーザー 1 ウィンドウあたり 3 件まで |
| コメントの送信 | 3 | 同上 |
| 友達申請と承認 | 各 2 | 流入ユーザーあたり k 件（§5.2） |
| 認定公開アカウントのフォロー | 1 | 流入ユーザーあたり数件 |
| 通知一覧、Memories の取得 | 1 | 1 ユーザー 1 ウィンドウあたり数回 |

- 書き込み系（RealMoji、コメント、申請、承認）は 1 ユーザーあたりの回数を固定するので、合計は
  通過数に比例する。
- 閲覧系は回数を固定せず、クローズドループの速さに任せる。§3.3 のとおり上限は通過数に従属する。
- 従指標の合計が主指標を上回らないよう、重みは §9 の比率で較正する。

### 4.3 on-time の扱い

通過は on-time（ウィンドウ開始から N 秒以内、P-101 の `onTimeSeconds`）でなくても数える。遅延投稿は
仕様どおり受理されるので、遅れは正しさの違反ではない。on-time 比率はレベル判定の信号として使い
（P-102）、スコアには直接入れない。

上位の解像度が足りない場合の代替は §11 に挙げる。

## 5. 負荷モデルとの関係

### 5.1 通過が連続的に発生する仕組み

スコアが階段状になるのは、通過がスパイクのときにしか起きず、スパイクの回数が少ない場合である。
本提案では次の 2 つで通過を走行中の連続イベントにする。

- **リージョンごとのウィンドウ。** 3 リージョンが 20 秒周期で 7 秒ずつずれて開くので、常に
  どこかのリージョンがスパイク中である（P-102）。
- **走行中の流入。** 新規ユーザーが走行中ずっと登録し、登録直後に投稿して通過する。FR-041 は開始後に
  登録したユーザーの現在期間への投稿を許可しているので、仕様変更は不要。流入の速さはラチェットの
  レベルで決まる。

流入したユーザーは次のウィンドウでは既存ユーザーとして通知を受けるので、後のスパイクほど規模が
大きくなる。全世界ウィンドウは走行中に到達したレベルで受けることになる。

### 5.2 流入ユーザーの 2 種類

映像の「各国でダウンロードされる」を、友達グラフの伸び方が異なる 2 種類の流入で表す。比率はレベル表
の項目にする。

| 種類 | 登録直後の動作 | 負荷が当たる経路 |
|---|---|---|
| 完全な新規 | 認定公開アカウントを数件フォローする | フォローフィード、認定アカウント投稿のファンアウト（P-111） |
| 友達つながり | 既存ユーザーに友達申請を k 件送る。既存ユーザー側のエージェントが承認する | 友達フィード、友達の友達の判定（FR-014、FR-015） |

友達つながりの申請先は、既存ユーザーの友達数に比例した重みで選ぶ（優先的選択）。

- 走行が進むほど友達の多いユーザーが育ち、その投稿は友達の友達まで含めて閲覧者が増える。距離 2 の
  判定が重い経路として自然に現れる。
- 完全にランダムだと友達数が均一になり、距離 2 の集合が小さくまとまって重い経路に当たらない。
- 申請先がリージョンをまたぐ割合はレベルとともに上げ、リージョン間のフィード参照をレベルに応じて
  増やす。
- 一般ユーザー同士は一方向フォローできない（FR-010）ので、申請と承認の両方をベンチが行う。承認は
  受信者だけが行える、相互申請の競合で友達関係が 1 件だけ成立する、といった SC-005 の検証が負荷下で
  回る。
- 承認直後にその友達の投稿がフィードに現れることを確認すれば、書き込み直後の読み取り整合性の検証に
  なる。

### 5.3 全世界ウィンドウ

出題映像の CHAIR GRAND PRIX に対応する、全リージョン同時に開くウィンドウ。アプリ側にはウィンドウの
スコープ（リージョン限定か全世界か）を追加する。仕様への影響は補助資料に別提案として起こす。

- 通知ファンアウトが全ユーザー同時、3 台が同時に叩かれる、リージョンをまたぐ友達の友達フィードが
  一斉に開く。「世界同時トラフィックに備えろ」の対象がここに集約される。
- リージョンごとのスパイクでは、リージョン内で完結する実装が自分のスパイクを自分のサーバーで捌ける。
  全世界ウィンドウはその局所性が通用しない瞬間として来る。両方を残すことで、局所化と全体の処理能力の
  両方が要る。
- 走行の終盤（40〜45 秒付近）に 1 回置く。終盤ほどレベルが上がった状態で受けられ、残りの時間で通過後の
  閲覧まで数えられる。リージョンのウィンドウと重なるかどうかは固定の時間割で決め、走行ごとに変えない。
- 全世界ウィンドウで「遅くなる」（投稿が遅れて on-time 比率が下がる、p99 が SLO を超える）だけなら
  レベルの凍結と通過の伸び悩みで反映され、失格にはならない。「壊れる」（タイムアウトや 5xx が観測窓の
  エラー率 SLO を超える）と失格になる（§6）。全世界スパイクは全ユーザーが同時に投稿するので、壊れる
  側に落ちた実装は実質的にここで失格になる。

時間割の例（暫定、`onTimeSeconds` = 5 秒）:

| 時刻（秒） | 0 | 7 | 14 | 20 | 27 | 34 | 40 | 45 | 47 | 54 |
|---|---|---|---|---|---|---|---|---|---|---|
| asia | 開 | | | 開 | | | 開 | | | |
| europe | | 開 | | | 開 | | | | 開 | |
| america | | | 開 | | | 開 | | | | 開 |
| 全世界 | | | | | | | | 開 | | |

### 5.4 レベル判定の信号

P-102 のとおり。本提案で変わる点はない。

- 定常状態の観測窓（5 秒）でエラー率、リージョンごとの読み取り p99、直前のスパイクの on-time 比率を
  見て昇格する。条件を満たさなければ凍結、降格はしない。
- 昇格で増えるのは流入の速さ（次の観測窓で登録するユーザー数）である。

## 6. 正しさとの分離

スコアは処理能力だけを表し、正しさと可用性は失格で扱う。失格の判定は固定件数（D-009 の 100 件）では
なく、観測窓ごとの率で SLO として定義する。

### 6.1 失格条件

| 事象 | 扱い |
|---|---|
| 投稿していないユーザーが他人の投稿を取得できた | 失格（可視性の違反、1 件で） |
| 公開範囲、ブロック、距離 2 の条件に反する投稿が見えた | 失格（1 件で） |
| 同じ冪等性キーで投稿が 2 件成立した | 失格（FR-026、1 件で） |
| 観測窓のエラー率またはタイムアウト率が失格閾値を超えた | 失格（走行を打ち切る） |
| initialize の失敗と時間超過、pretest の失敗 | 失格（SCORE-05、変更なし） |

正しさの違反は 1 件で失格にする。可用性は率で判定する。

### 6.2 エラー率 SLO の定義

- **観測窓。** ラチェットの判定と同じ 5 秒。走行開始から 5 秒刻みの固定区間とし、走行ごとに変えない。
- **分母。** その観測窓に完了（成功、エラー、タイムアウトのいずれか）した操作数。操作は再試行を含めて
  1 件と数える。再試行を 1 回ずつ数えると、503 を返すほど分母が膨らんでエラー率が薄まり、負荷制限を
  するほど失格しにくくなる逆転が起きる。
- **分子。** 最終的にエラーで終わった操作数。5xx（再試行対象の 503 を除く）、4xx のうちベンチが期待して
  いないもの、接続エラー、タイムアウト、再試行を使い切った 503 が該当する。再試行の途中で受けた 503 は
  最終的に成功すれば分子にも分母の追加分にもならない。
- **最小標本数。** 分母が一定数未満の観測窓は判定しない。走行序盤や凍結直後の小さな観測窓で数件の
  エラーが率を跳ね上げるのを避ける。
- **閾値は 2 段。** 凍結閾値（例: 1%）を超えた観測窓では昇格しない。失格閾値（例: 10%）を超えた観測窓が
  1 つでもあれば走行を打ち切って失格にする。
- **固定件数を使わない理由。** レベルが上がるほど 1 スパイクの投稿数が増えるので、固定件数では上位ほど
  失格しやすくなる。率にすれば規模に依存しない。

数値は較正事項で、§11 に挙げる。

### 6.3 事象ごとの扱い

| 事象 | スコア | エラー率 | レベル判定 |
|---|---|---|---|
| 通知が届かない、遅い | 通過には影響しない | 数えない | on-time 比率に効く |
| リクエストのタイムアウト | 加点しない。エージェントは次のリクエストへ進む | 分子に数える | 効く |
| 再試行で成功した 503 | 成功として加点する | 操作 1 件が成功として分母に入る | 503 比率が閾値を超えた観測窓では昇格しない |
| 再試行を使い切った 503 | 加点しない | 操作 1 件が分子に入る。失格閾値を超えれば失格 | 効く |
| 期待していない 4xx、5xx、接続エラー | 加点しない | 分子に数える | 効く |

### 6.4 503 と再試行

意図的に 503 を素早く返してベンチの再試行に回す負荷制限は、正当な手法として認める。ただし通過を
増やす手段にはならず、次の理由で上限がある。

- 503 のリクエストは処理されていないので通過はゼロのまま。エージェントはクローズドループなので、
  再試行中は次の操作に進めない。得られるのはスパイクを時間方向に引き延ばす効果だけで、通過数は
  実際に処理できた件数で決まる。
- 再試行は回数とバックオフをベンチが固定する。バックオフはジッター付きの指数バックオフにする。回数と
  間隔（基準、係数、上限）は較正事項で、本提案では決めない（§11）。目安として基準 200 ms、係数 2、上限
  2 秒、full jitter、最大 4 回なら最悪で合計約 3 秒になる。使い切った 503 はエラー率の分子に入る。
- `Retry-After` ヘッダは上限付きで尊重する。ヘッダがあれば、その値とベンチの上限（バックオフの上限と
  同じ値）の小さいほうを待ってから再送する。上限を超える指示は上限に丸める。再試行の回数はヘッダの
  有無にかかわらず同じ。アプリが再送の時期を指示できる正当なレバーになるが、待てる幅はベンチの再試行
  予算の中に収まるので、予算を延ばす手段にはならない。ISUCON 12 予選が 429 で `Retry-After` を尊重した
  前例がある。現行の 300 ms 線形バックオフ（ジッターなし）は、全世界スパイクで全エージェントが同時に
  503 を受けると同じ時刻に再送が揃い、ベンチ側が再試行の嵐を作ってしまう。ジッターで再送を散らすのは
  実際のクライアント SDK の挙動でもあり、負荷制限を採った実装が「散らされた再送」を受ける形になる。
- 再試行の対象はすべてのエンドポイントに揃える。現行は投稿と RealMoji の 2 経路だけだが、限定する
  理由は操作単位のエラー率（§6.2）と再試行予算の上限で消えている。実際のクライアントは 503 を
  エンドポイントで区別せずに再送するので現実とも整合する。書き込み系は FR-026 の冪等性キーを付けて
  再送するので、コメント、申請、承認、フォロー、登録のすべてで再送時の重複が負荷下で検証される。
  未認証スコープ（登録）の冪等性も同様に検証できる。
- on-time と読み取り p99 は再試行込みの end-to-end で測る。503 で遅らせた分がそのままレベル判定に効く。
- 再試行は画像を毎回送り直すので、注入レイテンシと帯域の下では 1 回の 503 がリージョン間リンクの
  浪費になる。
- 観測窓内の 503 の割合が閾値を超えたら、エラー率が凍結閾値以下でも昇格しない。再試行内に収まって
  いても「捌けていない」信号として扱う。

再試行の対象を「503 かつ仕様に定めたエラーコード」に限ることはしない。レスポンス本体はアプリが自由に
書けるので効果がない。仕様とマニュアルでは「503 はすべてのエンドポイントで再試行可能」と一律に定める。

P-112 の初期実装はサニタイザの並列度 2 で塞がると 503 `image_sanitizer_unavailable` を返す。P-101 の
較正（`onTimeSeconds` 5 秒で同時投稿 100〜200 人で折れる）はこの再試行込みの見積りである。

### 6.5 減点を用いない理由

- 減点があると、参加者は「何が減点されたか」を知る必要があるが、D-005 で内訳は開示しない。減点なしなら
  合計点だけで説明が閉じる。
- 正しさの違反は減点ではなく失格にするほうが、P-108 の検証項目の位置づけと一致する。
- 現行実装の「エラー 1 件につき 10 点」は、エラーが多い走行ほど通過も少ないので二重に効く。

`spec-bench.md` SCORE-03（減点はエラー種別ごとの係数）は「係数は 0 でもよい」に緩め、較正で必要になった
場合に限って係数を入れる。

### 6.6 重複送信

映像の「50 代以上の利用者」は、読み込みマークを見ながら何度もタップする行動としてエージェントに
持たせる。タイムアウト後に同じ冪等性キーで再送するエージェントを一定比率で混ぜ、負荷下で重複が
成立しないことを検証する。重複が成立すれば失格、成立しなければ通過は 1 件のまま。

### 7.1 過去回との比較

`docs/research/isucon-manuals/` にある 7 回分のマニュアルから、スコアの単位、減点、失格条件を抜き出した。

| 回 | スコアの単位 | 重み | 減点 | 失格の閾値 | タイムアウト |
|---|---|---|---|---|---|
| 10 予選 isuumo | イス購入数 + 資料請求数 | 均一 | 1 件 50 点 | 10 件で失格、負の点で失格 | 減点なし（CSV 入稿のみ失格） |
| 11 予選 isucondition | コンディション閲覧とグラフ閲覧 | 種別ごと、50 件単位、初期 1,000 点 | 1 件 1 点 | 100 件で失格 | 10 件で 1 点、失格なし |
| 11 本選 isucholar | 課題提出 3 点、お知らせ一覧 1 点 | 2 段階 | 1 件 50 点 | 100 件超で失格 | 100 件で 100 点、失格なし |
| 12 予選 isuports | エンドポイントごとに 1 点か 10 点 | 2 段階 | 通常 1%、Critical 10% の比率減点 | 減点で 0 点確定の時点で打ち切り | 減点扱い |
| 12 本選 isuconquest | エンドポイントごとに 1〜3 点 | 3 段階 | 1 件 15 点（タイムアウト含む） | 50 件超で計測終了 | 減点扱い |
| 13 isupipe | 投げ銭の合計金額 | 金額そのもの | なし | 打ち切りなし。整合性と最終チェックで失格 | 20 秒 |
| 14 isuride | 移動距離 + ライド完了数 × 5 | 距離と件数の複合 | なし | Critical 1 件、または警告 200 件で失格 | 10 秒、通知は 60 秒 |

傾向:

- 単位は 2 世代に分かれる。10〜12 回は「リクエスト成功数の重み付き和」に減点を組み合わせた。13 回と
  14 回は「アプリのビジネス量」（投げ銭額、輸送距離）そのものを点にし、減点を廃して失格条件だけを
  残した。
- 減点をやめた 13 回以降は、正しさを Critical と警告に分け、Critical は 1 件で、警告は件数で失格に
  する。14 回の「警告 200 件」は現行の D-009（100 件）と同じ固定件数方式で、率で判定した回はない。
  12 予選の比率減点（エラー数 × 1%）は率に近いが、分母がスコアであってリクエスト数ではない。
- タイムアウトは 11 回以降ずっと「減点か無視」で、単独で失格にした回はない。
- 走行時間はすべて 60 秒。走行後の整合性チェック（finalcheck）は 11 本選以降ほぼ毎回ある。
- 負荷の増え方はマニュアルに明記されていない。公開情報からの記憶では、11 予選は ISU の追加、12 予選は
  テナントの追加、13 回は視聴者の増加、14 回は椅子の投入数が、エラーなく捌けている間に増える形で、
  いずれもラチェットに近い。9 予選はキャンペーン値を参加者が設定して負荷を選ぶ方式で、参加者が負荷を
  決める唯一の例（マニュアルはリポジトリにないので要確認）。

本提案との位置関係:

- 「ビジネス量を単位にし、減点なし、正しさは Critical で 1 件失格」は 13 回と 14 回の延長線上にあり、
  前例がある。
- 14 回の「距離 + 完了数 × 5」は主指標と従指標の複合で、本提案の「通過 + 通過後の活動」に最も近い。
- 可用性を固定件数ではなく観測窓の率で判定する点（§6.2）だけが前例のない部分である。マニュアルでは
  14 回の「警告 200 件」との違いを、レベルが上がるほど上位が不利になる問題として説明する。

## 8. 参加者への開示

D-005 のとおり `pass` と合計点のみを開示する。マニュアルには次を書く。

- スコアの単位は「投稿ゲートを通過できたユーザー数」であること。通過したユーザーの閲覧と交流も加点
  されるが、通過に比べて小さいこと。
- 走行中にユーザーが増え続けること。増え方は実装が捌けるかどうかで決まること。
- 走行の終盤に全リージョン同時のウィンドウが 1 回開くこと。
- 正しさの違反は 1 件で失格であること。エラーとタイムアウトは減点ではなく、観測窓ごとの率が閾値を
  超えると打ち切りになること。503 はすべてのエンドポイントで固定回数まで再試行されること。`Retry-After` は上限付きで尊重されること。

書かないもの: 重みの値、レベル表、レベル判定と失格の閾値の値、時間割の秒数、流入の 2 種類の比率。

## 9. 較正の目安

数値はすべて暫定で、画像サイズ、サニタイザの並列度、注入レイテンシが決まってから較正する。

- **主従の比率。** 上位チームの想定スコアで通過が 6 割以上を占めるよう、従指標の重みを置く。
  従指標が過半になれば、閲覧の速さがスコアを決める構造に戻る。
- **全世界ウィンドウの配点。** 同じ重みで走行中に到達したレベルに任せる。全世界ウィンドウで崩れる
  実装と崩れない実装の差が上位で弁別できなければ、重みを 1.5〜2 倍に上げる。
- **初期実装が折れる位置。** P-101 の見積り（`onTimeSeconds` 5 秒で同時投稿 100〜200 人）を出発点に、
  ラチェットの初期レベルを通り上位で折れる位置に置く。
- **上限。** レベル表は最強チームの想定到達点より上まで用意する（本文 §2）。通過数の理論上限は
  Σ_windows レベル(w) であり、レベル表を伸ばせば上限も伸びる。
- **流入の比率。** 完全な新規と友達つながりを初期レベルで半々、後のレベルで友達つながりを増やす。
  友達つながりの k は 3〜5 件から。

## 11. 未決事項

  タイムアウト値は「遅い」と「壊れた」の境界を決めるので、`onTimeSeconds` と合わせて較正する。
- 観測窓内の 503 比率の閾値（昇格を止める水準）。

  耐えられる幅」を決めるので、`onTimeSeconds`、観測窓の長さ、失格閾値と合わせて調整する。
- 全世界ウィンドウの回数と時刻。1 回を終盤に置く案で進めるが、2 回にして「予行」と「本番」に分ける

  採るなら減衰の形を公開する。
- 離脱モデル（通過できなかったユーザーが以後のウィンドウに参加しない）を入れるか。序盤の障害が

  変わる。

- グランプリの名前が示す投票やランキングを機能にするか。本提案では見送る。
