## 1. ナラティブと問題のテーマ

### 1.1 ナラティブ

この問題の設計判断で最も大事なのは、次のナラティブである。

> 前任者が各リージョンにサーバーを 1 台ずつ置き、すべてを東京のデータベースに向けて去った。
> CEO は誰も理解していないマネージドエッジルーターを契約した。8 時間後に負荷がやってくる。

このナラティブに従った実装やアプリケーションの設計は受け入れられる。それにフィットしない
前提は違和感が出る。以降の所見と提案は、この基準で評価している。ナラティブから直接導かれる
ものは次のとおり。

- **前任者が各リージョンに 1 台ずつ置いた** ので、アプリケーションは 3 台すべてで動いている。
  1 台にしか置けない仕組み（ローカルディスクの画像、プロセスメモリ上の状態）は、前任者が
  そうしなかったはずだという意味で不自然になる。
- **すべてを東京のデータベースに向けた** ので、初期状態は中央 DB 1 つ、リージョン間の
  レイテンシを毎回踏む構成である。これが遅い理由であり、参加者が最初に見つける問題である。
- **誰も理解していないマネージドエッジルーター** なので、ルーターは参加者の管理外にあり、
  ドキュメントは簡素で、挙動は自分で調べるしかない。ルーティングルールを触れるのは、契約者
  として管理 UI を持っているからである。
- **8 時間後に負荷がやってくる** ので、参加者は限られた時間で構成を理解し、直せるところから
  直す。これは ISUCON の競技時間そのものである。

### 1.1.1 ナラティブの補強案: GDPR

ナラティブだけでは説明しにくい仕様（リージョン外からのアクセス拒否、リージョン移行、削除
猶予とパージ）に、ひとつの理由を与える補強案として GDPR を使うことを提案する。

> この会社は日本発のサービスで、DB は東京にある。ヨーロッパのユーザーが増えてきたころ、
> 法務が「EU 在住ユーザーにサービスを提供する以上 GDPR の適用を受ける」と言い出し、
> **データ所在地ポリシー** を定めた。「ユーザーのデータは、そのユーザーが所属するリージョン
> のエンドポイントからしか提供しない。所属リージョンが変わったら、その時点から旧リージョン
> では提供しない。退会したら猶予期間後に確実に消す」。EU 向けに作ったこのポリシーは、
> 例外管理が面倒だという理由で全リージョンに一律で適用された。
>
> 前任者はこのポリシーに従って `europe` と `america` にサーバーを置き、リクエスト元の
> リージョンと所属リージョンが違えば拒否するチェックを実装した。ポリシーが求めたのは
> 「どのエンドポイントから提供するか」であって DB の物理的な場所ではなかったので、DB は
> 東京のまま「次のフェーズでやる」ことになり、そのまま前任者は去った。CEO がマネージド
> エッジルーターを契約したのは、ベンダーが「GDPR 対応のジオルーティング」として売り込んで
> きたからである。ルーターがリクエスト元のリージョンをヘッダで付けてくれるのは、その機能
> である。

この補強で説明がつくもの:

- `europe` / `america` にサーバーがある理由（P-104）と、ルーターが `client_region` を
  付ける理由（P-103）。
- `client_region` 不一致の拒否（P-106）。前任者がポリシーどおりに実装した機能になる。
- リージョン移行（P-107）。ユーザーが引っ越して在住地が変わると所属リージョンを変えなければ
  ならず、変えた瞬間から旧リージョンで提供してはならない。「その時点から」を監査ログで示す
  必要がある、という理屈で同期カットオーバーにも一応の理由がつく。
- 退会の 30 日猶予と `purge_due_at` によるパージ（既存仕様）。忘れられる権利への対応として
  自然に読める。
- 拒否ステータスの候補として **451 Unavailable For Legal Reasons** が使える。法的理由で提供
  できないという意味そのものなので、ナラティブとしての座りは 403 や 421 より良い。RFC 7725
  の本来の用途（法的な差し止め要求）からは外れるが、参加者に「これはコンプライアンス起因の
  拒否だ」と伝える効果がある。

運営側の注意: 現実の GDPR はデータの域内保存を義務づけていない。日本は十分性認定を受けており、
EU から日本へのデータ移転自体は適法である。したがってこの筋書きは「GDPR がそう求めている」
のではなく「法務がそう解釈してポリシーにした」という体裁にする必要がある。企業が GDPR 対応と
称して EU データレジデンシーを導入するのは実際によくある行動なので、参加者に違和感は与えない
と考える。マニュアルには GDPR の法解釈を書かず、「社内のデータ所在地ポリシー」として書く。

### 1.2 問題のテーマ（レビュアーの理解）

ナラティブから、この問題のテーマは **リージョン** であると理解している。ユーザーは 3 つのリージョンのいずれか
に属する。参加者に与えられるサーバーは各リージョンに 1 台ずつ配置され、リージョン間には
ネットワークレイテンシが存在する。参加者はこれを自ら発見し、リージョン間のやりとり（他リージョン
の友人、公開フィード、リージョン移行）の正しさを保ちつつ、すべてのリージョンのユーザーに対して
サービスを高速化することが期待される。

以下の所見と提案はすべてこのテーマを前提にしている。テーマ自体の理解が違っていれば、提案の
多くは前提から崩れるので、まずそこを確認してほしい。

### 1.3 検証可能性の原則

ベンチは外形しか観測できない。運営も走行後に DB を検査できない。初期状態の DB がそのまま
使われている保証がなく、参加者はストレージを丸ごと差し替えてよいからである。したがって
サーバー内部の仕事のうち応答に現れないもの（パスワードハッシュのコスト、サニタイザの隔離、
冪等性ストレージの実体）は、原理的に検証できない。レスポンスタイムも判別材料にならない。
`sleep` で偽装でき、偽装した側の方がスループットで得をする。

ここから次の原則を置く。

- 外から観測できない制約は、スコアの分母に置かない。置くと「守った方が損」になり、追試での
  失格という重い処分でしか対処できなくなる。
- 観測できない制約は、マニュアルの禁止事項として書き、上位チームのソースコード提出と追試で
  担保する。これは従来の ISUCON と同じ方式である（ISUCON13 の bcrypt コスト変更禁止など）。
- 制約を観測可能な形に変えられるなら、そちらを優先する。ただし検証できるのは出力の性質で
  あって処理量ではない。画像なら「メタデータがなく画素が保たれている」ことは取得した画像で
  検証できるが、再エンコードしたかどうかは検証できず、メタデータの除去だけでも検査は満たせる。
  on-time の締切秒数は、応答の `onTime` と遅延投稿の検査で検証できる。

P-108 の画像処理検証、P-109、P-110 はこの原則に基づく。

## 2. 現状に関する所見（2026-09-05）

### 2.1 アプリケーション

- コードは単一サーバー構成として書かれている。画像は API ホストのローカルファイルシステムに
  保存され、そこから配信される。仮想時計は API プロセスのメモリ上にあり、worker だけが
  データベースからオフセットを読み戻す。プロセスがどのリージョンで動いているかに依存する
  コードはどこにもない。ナラティブ（3 台に配置済み）とは少しずれる。前任者が 3 台に
  置いたなら、ローカルディスクの画像やプロセスメモリ上の時計では動いていなかったはず、
  という見方になる。
- 仮想時計そのものはナラティブに乗せにくい。現実のサービスには「時間を進める API」がなく、
  ベンチの都合で入れたものに見えやすい。
- リージョンは通知グループとして、および `local_date` を導出する際の固定 UTC オフセットと
  してのみ使われている。
- データベースに置かれているプロセス間状態（セッション、冪等性レコード、投稿ウィンドウ、
  通知、ジョブ）は、すでにホストをまたいで動作する。この点は問題ない。

### 2.2 ベンチマーカー

ベンチは開発途上であり、検証項目が揃っていないことは認識されている。以下は 2026-09-05 時点の
現状の記録で、欠けている項目の指摘そのものが目的ではなく、P-108 の優先順位と §1.3 の原則の
根拠として残す。

- スコアは `サイクル数 x 固定点数` である。1 サイクルは約 7 秒で、そのうち約 5.5〜6.5 秒は
  ベンチ側の固定待ち時間（スケジュール先行 3 秒、worker ポーリング最大 1 秒、ウィンドウ
  ポーリング 0.5 秒、オフセット同期スリープ 2 秒）である。無限に速いアプリケーションでも
  60 秒で約 10〜11 サイクルにしかならない。アプリケーション性能がスコアを動かせるのは
  最大でも約 30% である。ここが一番効くところだと見ている。
- アプリケーション側の処理時間の中では、画像サニタイザのサブプロセス（並列度 2、1 サイクル
  あたり約 24 回の exec）が支配的である。
- 各ユーザーが投稿直後、他のユーザーが投稿する前にフィードを取得するため、リアクションが
  失われる。アプリケーションが速いほど失われる量が増える。速くすると損をする形になって
  いるので、シナリオの順序は直したい。
- 現時点で呼ばないもの: 画像 GET、friends / friends-of-friends / following フィード、
  投稿の GET/PATCH/DELETE、コメントおよび RealMoji の一覧、リレーションシップ、push。
  `Idempotency-Key` の再利用、レスポンスヘッダの検査、順序やカーソルの
  検査も未実装で、リージョンは `asia` しか使わず、通知とメモリーの検査は `users[0]` に
  対してしか行わない。これらは整備の対象であり、P-108 に優先順位を付けて列挙した。
- その結果、今日の時点では「安全性」に関わる仕組み（OpenAPI バリデーション、サニタイザの
  隔離、セキュリティヘッダ、冪等性ストレージ、可視性ルール）を削除してもベンチが通る。
  これは整備状況によるものでアプリケーションの性質ではなく、整備で解消する。ただし
  bcrypt コストのように **整備しても外形検証できない** ものは別で、こちらは検証項目の追加では
  解決しない（§1.3、P-110）。

## 3. 提案

以下は所見を踏まえたレビュアーの提案である。番号は P-101 から振る（`spec-bench.md` の
D-xxx は採用済みの決定を指すため、区別している）。

### P-101 実時間のみにし、仮想時計を廃止する

提案内容:

- アプリケーションは実時間で動作する。`POST /api/v1/initialize` は `base_time` を返さなく
  し、`POST /api/v1/virtual-time/advance` は削除する。
- **カレンダー上の日付は時計から導出しない。** 管理者用スケジュール API はウィンドウに対して
  明示的な `local_date` ラベルを受け取る。不変条件は「リージョンと日付の組は一意」「ラベルは
  同一リージョンの直前のウィンドウより後」の 2 つだけとする。`posting_windows.utc_offset_minutes`
  と導出日付の CHECK 制約は削除する。メモリーはこのラベルを使って日付ごとのグルーピングを
  維持する。
- リージョンごとの UTC オフセットはナラティブ（「各リージョンは現地時間で毎日の通知を
  受け取る」）の中には残し、それがウィンドウをリージョン間でずらす理由になる。
  アプリケーションがそれから何かを計算することはない。
- **時間内投稿（on-time）の締切はウィンドウごとのパラメータにする。** 管理者の予約 API に
  `onTimeSeconds` を持たせ、省略時は仕様どおり 120 秒とする。ベンチは短い値（5 秒から較正）
  を明示して渡す。これにより時間圧縮が必要な唯一の理由がなくなる。
- 60 秒の実行中に経過し得ない期間（24 時間の冪等性 TTL、30 日の削除猶予）は、時間を進める
  のではなく、すでに期限切れになったレコードをシードして検証する。
- 参加者が手動で試せるように、初期データに過去のウィンドウと Memories を含め、「今すぐこの
  リージョンのウィンドウを開く」スクリプトか管理画面を用意する。日付がラベルになるので、
  翌日への遷移は仮想時計より簡単になる。

「1 日 1 回」は時計なしで表現できる。現在も投稿ウィンドウは管理者の予約からしか生まれず、時計は
予約時刻から `local_date` を導出するためにしか使われていない。ウィンドウの終了も「同じリージョンの
次のウィンドウ開始」で、時計には依存しない。日付を管理者が与えるラベルにすれば、上の 2 つの
不変条件で「各リージョンで 1 日に最大 1 回」がそのまま残る。

`onTimeSeconds` について:

- FR-004 の「通知後 2 分」は製品の既定値として物語に残る。参加者が Web 画面で手動で試すときも
  時間内投稿を体験できる（5 秒固定では人間には投稿できない）。
- 値は応答の `onTime` と遅延時間で外形検証できるので、規約ではなくベンチで担保できる（§1.3）。
  ベンチは一部のエージェントに意図的に N 秒を超えてから投稿させ、遅延投稿の記録が正しいことを
  検証する。良い実装ほど遅延投稿が自然発生しなくなるので、この検査は意図的に作る必要がある。
- ベンチが渡す N の較正: 時間内判定は `starts_at + N` で `starts_at` は予約時刻そのものなので、
  worker の検出遅れ（既定 1 秒）、ベンチのウィンドウ検出（0.5 秒）、リージョン間往復込みの
  投稿リクエスト（0.3〜0.5 秒）、503 の再試行（線形 300 ms × 4 回で最大 3 秒）がすべて N に
  含まれる。再試行を除いた床が約 2 秒なので、床の 2〜3 倍で 5 秒が下限側の目安。3 秒を切ると
  503 を 1 回受けただけで時間外になり、「503 は減点しない」と噛み合わない。上限はウィンドウ
  周期 20 秒（P-102）の半分の 10 秒で、それを超えると時間内比率がほぼ 100% になり指標の
  弁別力が消える。5 秒で初期実装（サニタイザ並列度 2）が折れるのは同時投稿 100〜200 人程度で、
  ラチェットの初期レベルは通り上位で折れる位置になる。画像サイズと帯域上限が決まったら
  再較正する。

ナラティブとの整合: 現実のサービスは実時間で動く。仮想時計を消すことで、アプリケーションは
「前任者が作った普通のサービス」に近づく。日付をラベルにするのも、運営者がスケジュールを
登録するときに日付を指定するという普通の管理操作である。

理由:

- 現在の設計（「アプリの時計は 1 つ、ジャンプは DB 経由で伝播、ベンチは伝播待ちでスリープ」）は
  複数の API ホストの構成と相性が悪く、ベンチの固定待ち時間がスコアの上限を決めてしまう。
- 参考実装の他言語移植とも相性が悪い。Go の単一 API プロセスではメモリ上のオフセットを参照
  すれば済むが、PHP-FPM、Unicorn / Puma のクラスタ、Starman のようなプリフォーク型では advance
  を受けたワーカープロセスしか更新されず、リクエストごとに DB からオフセットを読むか、共有
  メモリで同期するかを言語ごとに選ぶことになる。同期方式の差がそのまま参考実装間の性能差に
  なる。
- 過去の ISUCON では、時間を純粋にベンチ側で扱う（ISUCON11 予選、リクエストデータに載せた
  30000 倍の線形仮想時間）、initialize 時に注入されるスケジュールとして扱う（ISUCON10 本選
  xsuportal）、リクエストごとのヘッダで扱う（ISUCON12 本選 `x-isu-date`）のいずれかであった。
  アプリケーション内部に可変の時計を持ったものはない。

### P-102 スコアを「固定の実時間内に処理したイベント数」にする

提案内容:

- 負荷は 60 秒間かける（変更なし）。スコアは過去のすべての ISUCON と同様、完了したイベント
  の重み付き件数とする。サイクル数のカウントは廃止する。
- ウィンドウは実行中に実時間のスケジュールで開き、リージョンごとにずらす（例: 3 リージョン
  を周期 20 秒、7 秒ずつオフセットで開く。すべてのリージョンが 3 回開き、常にどこかの
  リージョンが投稿スパイクの中にある）。
- 負荷はクローズドループかつ継続的にする。エージェントは自分のリージョンのウィンドウが
  開いたら投稿し、その後は実行終了までフィードの閲覧、画像の取得、リアクション、コメント、
  通知とメモリーの閲覧、検索、リレーションシップの管理を続ける。**エージェントは同時に
  1 リクエスト、思考時間なし** とし、LOAD-01 に追記する。1 エージェントの毎秒イベント数は
  往復時間の逆数で頭打ちになり、リージョン内で応答する実装と `asia` 一極集中の差が海外
  エージェント数に比例して開く（P-109）。
- **ラチェット式レベル。** エラー率とレイテンシが予算内に収まっている間、エージェント数を
  増やす。各ウィンドウのスパイク（投稿、通知のファンアウト、push の試行）は現在のエージェント
  数に比例させる。スパイクが失敗した場合（on-time 比率の低下、エラー）は、実行を失敗させる
  のではなくレベルを凍結する。ハード失敗は正しさの違反にのみ用いる。
- **レベルはリージョンごと** とし、レベルアップの基準にはリージョンごとの読み取り p99 SLO と
  直前のスパイクの on-time 比率を含める（P-109 参照）。全操作を混ぜた p99 は使わない。
- **海外ユーザーの割合はレベルとともに増やす。** 初期のレベルではほぼ `asia` のユーザー
  のみを追加する。後のレベルでは `europe` と `america` のユーザーの割合を増やしていく。
  レベルと構成比のテーブルは運営側の非公開情報とし、マニュアルには海外ユーザーが増える
  ことだけを記載する。
- **追加ユーザーは走行中の新規登録で参加させる。** P-110 で認証が発行キーになれば登録は
  キー生成と SHA-256 と INSERT 2 件で済むので、LOAD-03 どおり新規登録で参加させてよい。
  登録そのものを加点イベントにでき、ユーザー名の一意性と未認証スコープの冪等性も負荷下で
  検証できる。ただし新規登録ユーザーは友達も過去投稿も持たないので、そのままでは公開
  フィードに負荷が偏り、距離 2 の友達判定や Memories のような重い経路に当たらない。初期
  データには関係グラフと過去投稿を持つユーザーを用意して定常負荷の主体にし、レベルアップの
  追加分は新規登録と、初期データのユーザーのログイン参加を混ぜる。（bcrypt を残す場合は
  登録とログインの CPU コストがレベルアップ時のスパイク計測を汚すので、初期データに
  セッション済みのユーザープールを持つ回避策が必要になる。§5 参照。）
- **新規ユーザーは認定公開アカウントをフォローする。** 新規登録したエージェントは、初期
  データにいる少数の認定公開アカウント（リージョンをまたいで数人）を登録直後にフォロー
  する。レベルが上がるほどフォロワー数が増え、認定アカウントが投稿するたびに P-111 の
  投稿起点の通知のファンアウトが大きくなる（フォローしたこと自体は通知しない）。日次通知の
  ファンアウトが「リージョンのユーザー数」に比例するのに対し、こちらは「特定アカウントの
  フォロワー数」に比例し、フォロワーはリージョンをまたぐ。認定アカウントはベンチが操作する
  エージェントで、各ウィンドウで投稿する。
- on-time 比率（ウィンドウ開始から N 秒以内の投稿）をスパイク処理能力の指標にする。遅延した
  投稿も仕様どおり受理されるので、これはスコアのシグナルであってエラーではない。
- 移行完了（P-107）は低頻度（定常状態のイベントの数パーセント）のスコア対象イベントとし、
  後のレベルで増やす。

ラチェットが必須である理由: 実時間でウィンドウ周期を固定すると、サイクル数は壁時計で決まり、
投稿は「1 ユーザー 1 ウィンドウ 1 件」なのでユーザー数 × ウィンドウ数で上限が決まる。クローズド
ループは閲覧・交流をアプリの速さに応じて伸ばすが、スパイク（投稿、通知ファンアウト、push）は
ユーザー数でしか伸びない。重みは投稿系が主、閲覧系が従になるよう、レベル表の上限を踏まえて
較正する。

ラチェットの状態遷移:

- **観測期間。** リージョンごとに 5 秒の観測窓で判定する。20 秒周期では各リージョンのスパイクは
  走行中に 3 回しか来ないので、スパイクごとの昇格では上位の伸びしろが作れない。昇格は定常
  状態の観測窓で行い、スパイクの規模はウィンドウが開いた時点のレベルに従う。
- **昇格条件。** 直前の観測窓でエラー率が閾値以下、読み取りの p99 が SLO 以下、かつそのリージョン
  の直前のスパイクの on-time 比率が閾値以上なら 1 段昇格する。昇格幅はレベル表に従う（リージョン
  ごとの追加エージェント数と構成比）。
- **凍結と再開。** 条件を満たさない観測窓があれば昇格を止め、レベルは維持する（降格はしない）。
  連続する 2 つの観測窓で条件を満たせば再開する。正しさの違反だけがハード失敗になる。
- **タイムアウト。** エージェントのリクエストタイムアウトはエラーとして数え、そのリクエストは
  イベントに数えない。タイムアウトの連続でエージェントが離脱することはなく、次のリクエストへ
  進む。
- **初回スパイク前の昇格。** そのリージョンの最初のスパイクが来るまでは on-time 比率が
  存在しないので、エラー率と読み取り p99 だけで判定する。最初のスパイク以降は 3 条件で判定する。
- **リージョン別レベルと他リージョンのユーザー追加の関係。** レベル表はリージョンごとに独立
  した表（レベル → そのリージョンのエージェント数）で、あるリージョンの昇格はそのリージョンの
  エージェント数だけを増やす。海外ユーザーが後から増える構成は、`europe` と `america` の昇格を
  `asia` のレベルが所定の段に達してから開始することで作る。開始後は各リージョンが独立に
  昇格・凍結する。
- **速い実装が早く過負荷に進んで低得点にならないか。** 過負荷では競合とタイムアウトで全体の
  成功処理量も下がり得るし、降格しないのでその状態に留まり得る。昇格幅、観測窓、凍結条件で
  これを避けられるかは較正事項とし、避けられなければ 1 段戻す降格を入れる。

ナラティブとの整合: 「8 時間後に負荷がやってくる」のがこの負荷である。海外ユーザーが後の
レベルで増えるのは、海外展開の負荷が後から乗ってくるという説明で足りる。負荷モデルはベンチ
側の話なので、アプリケーションに不自然な仕組みを要求しない。

現状の実装との距離: 開発途上のベンチは `benchUserRegion = "asia"` 固定、ユーザー数は起動時の
`-users`（既定 8）で固定、走行中の増減なし。LOAD-02 / LOAD-03 はこれから実装する段階で、
リージョン構成比の考え方は本文書にしかない。採用時はレベル表の形式（総ユーザー数とリージョン
構成比、運営の非公開情報）とレベル判定の信号（エラー率、リージョンごとの p99、on-time 比率）を
先に決め、`prepareUsers` / `runCycle` を書き換える。

### P-103 環境: 3 台のリージョンサーバーと管理されたルーター

提案内容:

- 参加者にはリージョンごとに 1 台、計 3 台のサーバーを与える。名前は配置上の事実
  （ホスト名やコンソール）であり、アプリケーションの設定ではない。
- 参加者の管理外にある **ルーター** がベンチのトラフィックをすべて受ける。参加者はその実装を
  変更できないが、管理 UI でルーティングルールを編集できる。ただし **実行前のみ**。ルールは
  実行開始時に読み込まれ、その実行中は固定される。適用されたルールセット（またはそのハッシュ）
  は実行結果に記録する。
- すべてのリクエストには、ベンチのユーザーごとのリージョンに基づいてルーターが設定する
  `client_region` ヘッダ（名前は要決定。例: `X-ISUReal-Region`）を付ける。ルールは
  `client_region`、メソッド、パスプレフィックスでマッチし、重み付きの upstream を 1 つ
  以上選択する。
- **レイテンシの注入** は参加者が取り除けない場所で行う。すなわち、ルーターからサーバーへの
  区間で（クライアントリージョン、サーバーリージョン）ごとに、およびサーバー間ネットワーク
  で行う。参加者のサーバーから計測可能でなければならない（サーバー間の `ping`、
  `ss -ti` / tcpdump によるルーター接続の TCP RTT）。クライアントからルーターへの区間に
  注入するとサーバーから見えなくなるため、そこには注入しない。
- **注入の経路。** 同一 AZ にあるサーバー同士が直接通信できると注入を迂回できるので、リージョン
  サーバーはそれぞれ別のサブネットに置き、サーバー間の経路を運営管理のゲートウェイに固定する
  （直接経路はセキュリティグループで塞ぐ）。ゲートウェイが（送信元リージョン、宛先リージョン）
  ごとに netem を適用する。ルーターからサーバーへの upstream 接続はクライアントリージョンごとに
  分け、同じサーバーへの接続でもクライアントリージョンに応じた遅延が保たれるようにする。
  Push モックにもリージョンごとのアドレスを持たせ、同じゲートウェイを経由させる。購読の
  endpoint はユーザーのリージョンのモックを指すので、`asia` の worker から海外ユーザーへの
  push には地域間遅延が乗り、海外の worker から送れば乗らない。これが worker をリージョンへ
  移す利点になる。
- レイテンシはエミュレートする。競技環境は同一リージョン・同一 AZ の EC2 で構成するため、
  実際のクラウドリージョンは使わない。ルーターとサーバー間、サーバー間の区間に netem
  （`tc qdisc`）で（クライアントリージョン、サーバーリージョン）の組ごとに遅延を注入する。
  物理的には近接しているので注入値は運営が決める決定的な値になり、較正と再現が容易になる。
  注入はサーバー側の NIC ではなくルーター側とサーバー間ネットワークで行い、参加者が外せない
  位置に置く。
- *未決*: レイテンシに加えたリージョン間帯域の上限（画像のローカリティが重要になる。現実的）。
  設ける場合は同じ仕組み（`tc` の tbf / htb）で入れられる。
- ルーターがボトルネックになってはならない（ROLE-1 がルーターにも適用される）。注入遅延下
  でのルーターの処理能力は、ベンチ自体と同様に負荷テストする必要がある。
- 実行前チェック: ルールが参照するすべての upstream が到達可能で `/health/ready` であること
  を負荷開始前に確認する。そうでなければ負荷をかける前に失敗させる。

ナラティブとの整合: ルーターは「CEO が契約したマネージドサービス」なので、参加者が実装を
触れないこと、管理 UI でルールだけ変えられること、マニュアルが簡素なことはすべて自然である。
レイテンシはリージョン間に実在するものなので、サーバーから計測できなければならない。
クライアントとルーターの間にだけ注入するのは、この世界に存在しない遅延を足すことになり、
ナラティブに反する。

### P-104 初期デプロイ状態

提案内容:

- アプリケーションプロセスは 3 台すべてのサーバーで動かす。PostgreSQL と worker は `asia`
  サーバーだけで動かす。すべてのサーバーの `ISUREAL_DATABASE_URL` は `asia` ホストを指す。
- 3 台は同一バイナリと共通の設定で起動し、ホストごとに違うのは起動するプロセスだけとする。
  DB 参照先のほか、**揃っていないと壊れる設定** がある: `ISUREAL_CURSOR_HMAC_KEY`（カーソルは
  HMAC 署名なので別鍵のホストでは `invalid_cursor`）、VAPID の鍵 3 つ（購読は公開鍵に紐づく）、
  `ISUREAL_PUBLIC_ORIGIN`。セッション、冪等性、通知、push 試行は DB にあり、プロセス内に
  共有状態はない。現行コードからの変更は画像の DB 化と仮想時計の廃止（P-101）だけで済む。
- 初期のルータールール: `client_region -> 同一リージョンのサーバー`。管理者リクエストと
  `/initialize` はルールが送る先に届く。他ホストへの伝播は、例年どおり参加者の責任とする。
- 初期実装はこのトポロジーで **正しく** 動かなければならない。したがって:
  - 初期実装では画像はローカルディスクではなくデータベース（bytea）に保存する。遅い
    （画像リクエストごとにリージョン間取得が発生する）が、どのホストからでも正しい。
  - アプリケーションはホストごとのリージョン設定を持たない。リージョンは `client_region`
    のチェック（P-106）にのみ現れる。
  - 仮想時計はない（P-101）。
  - サニタイザのサブプロセスは残す。ホストローカルであり、どこでも動く。
  - `push-sender` バイナリを全ホストの `/usr/local/bin` に置く。worker は試行 1 件ごとに
    exec で呼ぶ（P-112）。
- 各サーバーの nginx は「前任者」が残したデフォルトのアクセスログフォーマットのままにする。
  リクエスト時間もヘッダも記録されず、すべてのリクエストがルーターのアドレスから来ている
  ように見える。有用なロギングを追加するのは参加者の仕事である。

従来型との比較: P-103 のレイテンシ注入を入れる時点で 3 台は同じものではなくなるので、実際の
選択肢は「初期状態で前任者がソフトウェアをどう配置していたか」である。

- A（本提案）: アプリは 3 台で稼働、DB と worker は `asia`、ルーターは同一リージョンへ。
- B（従来型）: 3 台は同一イメージだが稼働は `asia` だけ、ルーターは全部 `asia` へ、残り 2 台は
  遊休。
- A は物語に忠実で、初期実装に複数ホストでの正しさ（bytea 画像、プロセス内状態なし）を要求し、
  最初の一手として「ルーターを理解して全部 `asia` へ送る」という発見ステップを置く。B は現行
  コードのまま移植でき導入体験も従来どおりだが、「海外サーバーがあるのに使われていなかった」
  理由を別に要し、テーマが後半まで現れない。
- A の初期状態はルール変更 1 回で B に化けるので、3 台配置が意味を持つのは「気づくまで」と
  「海外ユーザーが増えて再び分散したくなる後半」の 2 回である。較正でステージ 0 の「全部
  `asia` へ」と A の初期状態の差を測っておく。
- 以上から A を採る。

現行実装（P-112 適用前）の海外ホストの DB 往復数。SQL 1 文、`BEGIN` / `COMMIT`、`SAVEPOINT` /
`RELEASE` を各 1 往復として数えた値:

| エンドポイント | 往復 |
|---|---|
| フィード、通知一覧、現在ウィンドウ | 2 |
| 投稿 1 件の取得 | 3 |
| 画像取得 | 3〜5（bytea 化で +1） |
| 投稿作成 | 16（認証 1、冪等性 5、投稿トランザクション 9、再取得 1） |
| RealMoji | 18 |
| コメント | 約 16 |
| ログイン | 約 13 |

リージョン間 RTT 100 ms なら投稿作成は約 1.6 秒。往復数より効くのは接続プールの占有で、冪等性
トランザクションの開始から `COMMIT` まで 1 本の接続を握るため、pgx 既定プール（CPU 数と 4 の
大きい方）では海外ホストは毎秒 2〜3 件しか投稿を通せない。CPU は遊んだまま、プール待ちで
詰まる。これが「最初の一手は全部 `asia` へ」になる理由である。

P-112 を適用した初期実装では、冪等性のミドルウェアと入れ子トランザクションとユーザー行ロックが
なくなるので、投稿作成は 9 往復前後（認証 1、冪等性キーの検索と INSERT 2、状態の SELECT と
画像・投稿の INSERT と状態の UPDATE 4、応答保存 1、`BEGIN` / `COMMIT` 1 組）まで減る見込み
である。それでも往復は逐次なので RTT 100 ms で約 1 秒かかり、海外ホストが往復時間で頭打ちに
なる構造は変わらない。数値は実装を直した時点で測り直し、較正の材料にする。

ナラティブとの整合: この初期状態は §1.1 のナラティブをそのまま構成に落としたものである。
画像を DB に置くのは「3 台に置いた前任者が、どのホストからでも配信できるようにした」結果
であり、遅いが筋は通る。nginx のログがデフォルトのままなのも、前任者が去った現場として自然
である。逆に、ホストごとにリージョンを設定する環境変数のようなものを初期実装に入れると、
「前任者はリージョンを意識して作っていた」ことになり、問題の発見を先取りしてしまう。

### P-105 参加者に伝えること

通常のレギュレーション以外に伝えるのは 3 つだけにする。

1. **計測可能なレイテンシ。** 何もドキュメント化しない。`ping` と `ss` で見える。
2. **稼働中の設定。** 各サーバーの環境ファイル、管理 UI の現在のルータールール、そして
   ルーターのみを説明する簡素なルーターマニュアル。マニュアルにはルール構文、`client_region`
   の値とそのヘッダが upstream に転送されること、ルール変更が次の実行から有効になることだけ
   を記載する。
3. **push の送り方。** push は Web Push（RFC 8030 / 8291 / 8292）で送ること、`push-sender`
   コマンドが各サーバーにあること、自分の実装で送ってもよいこと。使い方には触れない
   （P-112）。

提供しないもの: レイテンシ表、SLO 表、レベル/構成比の表、リージョンごとのスコア内訳。ベンチは
`pass` と合計スコアだけを報告する（D-005 は維持）。

道具のハードルについて: 3 台の観測結果を LLM に集められるか（ssh を配る、ログとメトリクスを
集める）は、それ自体を弁別点として残す。これができない参加者が層 1 で止まるのは許容する。
したがって、リージョンごとの SLO 達成有無をベンチ結果に返す、ルーター UI にルールごとの
リクエスト数や応答時間を出す、nginx のログを最初から整えておく、といった観測を楽にする
緩和は行わない。例年どおりの環境整備（3 台間の鍵なし ssh、リージョン入りのホスト名）だけは
用意する。これがないと弁別点が「鍵をどう配るか」の作業にずれる。

ナラティブとの整合: 「誰も理解していない」ルーターなので、参加者に渡せるのは契約時に付いて
きたマニュアルと管理 UI だけである。レイテンシ表や SLO 表を配るのは、社内にそれを知っている
人がいることになり、ナラティブと矛盾する。

発見可能性の受け入れテスト案: サーバーへのアクセス、ルーター UI、ルーターマニュアルだけを
持つ誰か（人間または LLM エージェント）が、仕様を読まずに「リージョンホストが 3 台、中央 DB が
1 つ、ルーターはリージョンで振り分け、リージョン間は約 100 ms」と結論できなければならない。

### P-106 `client_region` をアクセスルールにする

提案内容:

- 認証済みリクエストのうち、`client_region` がプリンシパルのリージョンと異なるものは拒否
  する。ステータスは *未決*: 固有のコードを持つ 403 か、421 Misdirected Request か、
  §1.1.1 の筋書きに乗せるなら 451 Unavailable For Legal Reasons か。
- これにより「データは旧リージョンから取得できてはならない」が HTTP 上で観測可能になる。
  それ自体は物理的なデータ配置を強制しない。強制するのはレイテンシと SLO である。
- リージョン間のやりとり（`asia` の閲覧者が `europe` の作者の投稿を読む）は、通常の可視性
  ルールのもとで引き続き許可する。このチェックはリクエスト元に関するものであり、データの
  所有者に関するものではない。
- 例外は移行操作（P-107）の冪等リプレイだけとする。移行の成功応答を失ったクライアントが同じ
  `Idempotency-Key` で旧リージョンから再送したとき、地域の拒否を先に適用すると永久に結果を
  受け取れない。移行操作に限り、冪等性の判定を地域の判定より先に行い、旧新どちらのリージョン
  からの再送にも保存した応答を返す。それ以外の操作は地域の判定が先で、旧リージョンからの
  再送は拒否する（新リージョンから同じキーで再送すれば保存した応答が返る）。
- チェックは `client_region` ヘッダとユーザーの所属の一致だけを見て、処理したサーバーの場所は
  見ない（P-104 でアプリはホストごとのリージョン設定を持たない）。したがって **全リクエストを
  `asia` で処理する構成はこのルールに反しない。** マニュアルには「ポリシーはエンドポイントの
  話であり、処理サーバーの場所は問わない」と明記し、参加者が規約違反を疑って手を止めない
  ようにする。この構成を抑制するのは規則ではなく計測（P-109 の SLO とレイテンシ）である。

ナラティブとの整合: **この提案は元のナラティブだけでは乗らない。** 「自分のリージョン以外
から来たリクエストを拒否する」ことに、現実のサービスとしての理由がないと、ベンチの都合で
作ったルールに見える。§1.1.1 の GDPR 由来のデータ所在地ポリシーを採用すれば、このチェックは
前任者がポリシーどおりに実装した機能になり、P-107 のリージョン移行にも同じ理由が使える。
仕様とマニュアルには「社内のデータ所在地ポリシー」としてこの理由を書くべきである。ポリシーの
「エンドポイント」はユーザーが接続するルーターのリージョンエッジであり、裏でどのサーバーが
処理するかは含まない（DB が東京のままで法務が納得した、という筋書きと同じ理屈）。現実の
GDPR でも東京での処理は適法なので、全部 `asia` で処理する構成は物語上も問題ない。

### P-107 同期的なリージョン移行

提案内容:

- `POST /api/v1/me/region-migration`（名前は要決定）は呼び出し元を別のリージョンへ移し、
  新しいリージョンとともに 200 を返す。現在の `pending_region` の仕組み（ウィンドウ終了時に
  適用）を置き換え、後者は削除する。
- **移行の成功応答を受信した後に開始したリクエスト** について、以下すべてが成立していなければ
  ならない:
  - そのユーザーの旧 `client_region` によるリクエストは拒否される（P-106）。
  - 新 `client_region` によるリクエストからは、ユーザーの完全なデータが見える。メモリー、
    通知、リレーションシップ、プロフィール画像、コメントと RealMoji の履歴、および既存の
    セッショントークン（再ログイン不要）。
- **移行と重なったリクエスト**（成功応答の受信前に開始したもの）は、成功しても拒否されても
  よい。移行前に送った要求の成功応答がネットワークで遅れて移行応答より後に届くことは防げない
  からである。ただし成功した書き込みは新リージョンで見えなければならない（書き込みの消失
  なし）。
- **再送の規則。** 移行操作の冪等リプレイは旧新どちらのリージョンからでも同じ結果を返す
  （P-106 の例外）。それ以外の操作を旧リージョンから再送すると拒否され、新リージョンから
  同じ `Idempotency-Key` で再送すれば同じ結果が返る。
- 投稿は、それが行われた投稿ウィンドウに留まる。新リージョンの現在のウィンドウが開いていれば、
  ユーザーはそこに投稿してよい（既存の FR-042 のセマンティクス）。
- サーバー間トラフィックはベンチからは観測しない。中央ディレクトリを切り替え、履歴を旧
  リージョンから遅延的に取得する設計も、観測可能なルールが成立する限り有効な解とする。
- ベンチのプローブ案: 事前にスナップショットを取る。移行中に旧リージョンへ読み書きを同時に
  大量に送り、各リクエストの開始時刻と応答受信時刻を記録する。成功応答の受信後に開始した
  旧リージョンのリクエストだけを拒否の検査対象にし、重なったものは成功・拒否のどちらも許容
  する。旧リージョンで成功した書き込みが新リージョンに現れることを検証する。移行操作を旧
  リージョンから同じキーで再送して同じ結果が返ることを検証する。

ナラティブとの整合: ユーザーが引っ越したので所属リージョンを変える、という操作は自然であり、
§1.1.1 のデータ所在地ポリシーがあれば「移行後は旧リージョンから提供してはならない」も同じ
理由で説明できる。同期にする点は本質的には競技の都合だが、「所属変更の時点を監査ログで
示せなければならない」という理屈で一応の説明はつく。

同期にする理由: サービスとしてはステータスを持つ非同期の方が現実的だが、競技としては同期的な
カットオーバーこそが面白い部分である。中央 DB の実装は UPDATE 1 つで通過する。シャーディング
した実装はアトミックな切り替え、処理中リクエストのドレイン、書き込み消失の解決が必要になり、
これが意図した非対称性である。

### P-108 ベンチに追加すべきチェック

欠けた場合に設計をどれだけ壊すかの順に並べる。

1. **画像 GET**: アップロードされたすべての画像を取得し、デコードでき画素が元画像と近似
   一致すること（9 参照）、メタデータが除去されていることを検証する。マルチホスト構成で
   最初に壊れる箇所である。
2. **フィードと可視性**: friends / friends-of-friends / following フィード、ブロック、投稿
   ごとの可視性を、リージョンをまたぐユーザーとリレーションシップで検証する。想定解法の
   ステージ 3 を検証する。
3. **`client_region` の拒否と移行プローブ**（P-106、P-107）。
4. **通知** がすべてのリージョン・多数のユーザーに配信されること。on-time 比率を計測する。
5. **冪等性のリプレイ**: 同じキーでの再送。同一ウィンドウ内の重複投稿は 409 を返す。
   削除 / 再投稿 / 削除 / 再投稿拒否のシーケンス。
6. **セッションの置き換え**: 新しいログインが古いトークンを無効化する。
7. **シードした期限切れ**: 期限切れの冪等性レコードはリプレイされない。`purge_due_at` を
   過ぎた `deletion_pending` ユーザーをシードしておき、実行中にパージされることを確認する。
8. レスポンスヘッダ（`Cache-Control: no-store` など）は *未決*: 検証するか、マニュアルで
   対象外と宣言する。

9. **画像の検証**（§1.3）: EXIF 入りの大きめ JPEG を投稿し、取得した画像に EXIF がなく、
   寸法が元画像と一致し、画素が元画像と近似一致することを検証する。メタデータの除去だけで
   画素を触らない実装は画素が完全一致し、再エンコードする実装は近似一致になる。どちらも
   合格とする。バイト列の完全一致は要求しない。処理量は検証できないので、CPU 負荷を計測に
   乗せる目的では使わない。
10. **on-time 締切の検証**（P-101）: `onTimeSeconds` 省略時は 120 秒、指定時はその値で
    `onTime` と遅延時間が判定されること。意図的な遅延投稿で遅延の記録を検証する。
11. **投稿起点の通知**（P-111）: 認定公開アカウントの投稿後、全リージョンのフォロワーに
    アプリ内通知が 1 件だけ届き、push 購読者には push が届くこと。ブロック関係にある
    フォロワーには届かないこと。通知を開くと当該投稿へ遷移すること。到達までの時間を
    リージョンごとに計測する。
12. **push の重複**（P-112）: 外部送信の試行、論理通知、利用者への表示を分けて数える。
    違反とするのは正常系の重複だけである。すなわち、モックが 2xx を正常に返した送信（応答を
    遅延も切断もしていないもの）について、同じ論理通知 ID を再度受信した場合。モックが意図的
    に 503 を返した送信への再送は期待どおりの再試行で、重複に数えない（規定の回数と間隔で
    再送されることを別途検証する）。**結果不明の障害系では重複を許す。** モックは「2xx を返す
    前に切断する」「応答を遅延させて送信側をタイムアウトさせる」ケースを意図的に作り、これらへの
    再送で同じ ID を再受信しても違反にしない。P-112 が結果不明を `transient` として再試行する
    よう要求している以上、これを違反にすると正しい実装が失格になる。エミュレートした
    ネットワークでは自然なパケットロスは無視できるので、モックが意図的に作らなかった結果不明は
    想定しない。アプリ内通知は（ユーザー、対象）ごとに 1 件であることを一覧で検証する。
    worker を複数にした実装が claim を直していないと、正常系の重複で落ちる。

### P-109 「高速なインメモリ単一サーバー」の勝利を防ぐ

DB を分散させないまま「海外サーバーに処理を逃がさず `asia` 1 台オンメモリで処理し切る」構成が
最速になる可能性がある。単一サーバーの弱点は「CPU が 1 台分」「海外ユーザーへの往復が必ず
リージョン間 RTT を踏む」「リージョン間帯域を全部使う」の 3 つで、CPU 効率では打ち破れない
レバーとして、DB に触らずこのどれかを計測に効かせるものを強い順に提案する。

1. **クローズドループ × 注入レイテンシ。** エージェントは同時に 1 リクエスト、思考時間なし
   （P-102）なので、1 エージェントの毎秒イベント数は往復時間の逆数で頭打ちになる。`europe`
   エージェントを `asia` で処理すると往復約 100 ms で毎秒約 10 イベント、`europe` サーバーが
   リージョン内キャッシュで返せば数 ms で毎秒数百イベント。サーバー側処理が短いほど差が
   開くので、`asia` を極めるほど「海外をリージョン内で返す」側の伸びしろが大きい。海外比率が
   上がるレベルでは、一極集中はこの差を海外エージェント全員分払う。これが最大のレバーで、
   SLO 門（下記 5）がなくてもスコアで効く。
2. **リージョン間帯域の上限**（未決、P-103）。閲覧トラフィックはバイト数で見るとほぼ画像
   なので、海外ユーザーへの画像配信を `asia` から出す構成は帯域で詰まる。CPU が余っていても
   帯域で止まる。ルーターから計測できる制約なので物語にも乗る。
3. **一貫性ルール: リージョン内では read-your-writes、リージョン間では有界の陳腐化を許容。**
   「自分の投稿は自リージョンですぐ見える」「他リージョンの投稿は数秒遅れてよい」を検査項目に
   する。リージョンごとのキャッシュやレプリカを許可する根拠になり、1 と 2 を正当化する。
   どこで処理するかは制限しない（全リクエストを `asia` で処理する構成は P-106 のとおり許される）。
4. **投稿スパイクをリージョンで受ける。** 時間内判定は受理時刻なので、海外サーバーが画像を
   リージョン内で受理し、メタデータの書き込みだけを `asia` の DB に投げれば海外の on-time
   比率が上がる。DB は 1 つのままで、投稿の受理だけリージョンに寄せる。
5. **レベルアップのためのリージョンごとの SLO。** 読み取りリクエストの p99（注入レイテンシを
   含め、ベンチ側で計測）が、リージョン間 RTT より十分低く、同一リージョンの通常処理より
   十分高い閾値（例: ローカル 2 ms、リージョン間 100 ms に対して 50 ms）を下回り、かつ直前の
   スパイクの on-time 比率が閾値以上のときだけレベルを上げる。読み取りと書き込みを分けるのは、
   全操作を混ぜた p99 だと、100 ms 以上かかる遠隔書き込みが 1% を超えた時点で読み取りを
   ローカル化しても p99 が 50 ms を切れず、リードレプリカの段階を阻害するからである。逆に
   高速な GET が増えるだけで遅い書き込みが p99 から消えるので、書き込みは on-time 比率で
   別に見る。`asia` の単一サーバーでは `europe` や `america` の読み取り p99 が RTT を下回らず、
   レベルを上げられない。後のレベルはほとんどが海外ユーザーなので、単一サーバーの上限は
   「asia の全部とベースレベルの海外分」になる。1〜4 が「スコアの伸び」で効くのに対し、
   これは「レベルが上がらない」で効く。

画像処理はレバーにしない。メタデータの除去だけで検査（P-108 の 9）を満たせるので、再エン
コードによる CPU 負荷を強制する根拠がなく、軽い処理で妥当な結果を返すのは ISUCON として正当な
改善である。較正では軽量化した構成も対象にし、分散の利点はレイテンシ、帯域、負荷モデルで
確認する。

組み合わせの勘所: 1 と 2 は読み取りのキャッシュ、4 は投稿の受理で、それぞれ DB を分散せずに
海外サーバーへ仕事を渡せる。DB が 1 つのままなのは弱点ではなく「DB 以外をリージョンに
寄せる」設計問題として成立する。1 台オンメモリを完全に封じる必要はなく、序盤で `asia` 一極集中が
最速なのは意図どおりで、海外比率が上がる後半で逆転するように較正する。逆転するレベルを
「人間のチームがステージ 1 に到達する点」より下に置く。

ナラティブとの整合: いずれもベンチ側の計測ルールか、リージョン間に実在する制約（レイテンシ、
帯域）の延長であり、アプリケーションに不自然な仕組みを要求しない。一貫性ルールは「海外の
ユーザーが少し古いフィードを見るのは許容するが、自分の投稿がすぐ見えないのは許容しない」と
いう普通のサービス要件として書ける。

レバーとして機能しないと考えるもの: データ量（構成上 1 台のディスクに収まる）、スパイクの
大きさ（インメモリで処理できる）、正しさのルール（中央 DB なら自明に通過する）、bcrypt の
ような外形検証できない CPU コスト（§1.3、P-110）、画像処理の CPU（メタデータ除去だけで検査を
満たせる）。

なぜ単一サーバーを封じることが最優先か: 1 台の CPU 効率を上げる作業（インデックス、クエリ
書き換え、キャッシュ、ミドルウェア除去、N+1 解消）は LLM エージェントが最も得意な領域で、
1 つのシェルで完結し、結果がすぐ返る。1 台で勝てる問題は LLM に最適化された競技になる。
3 リージョンが要求する作業（複数ホストにまたがる運用、タイミング依存の正しさ、実験コストの
高い意思決定、内訳のないスコアからの推定、やらないことを決める判断）は現時点の LLM が
苦手とする種類のもので、人間のチームにも難しいので公平性の問題はない。ただしこの差は
恒久的ではなく「今年の競技」を守るものである。試し解き（§5）を本番直前に行い、その結果で
レベル表を最終調整する。

キャリブレーションの目標を言い換えると、「LLM が層 1 を極めた 1 台構成の上限」を「人間の
チームがステージ 1 に到達したスコア」より下に置く。同時に、上位で頭打ちにならないよう、
レベル表は最強チームの想定到達点より上まで用意する。競技の主眼は上位の弁別であり、レベル表
は上に余裕を持たせる方向で誤る方がよい。

### P-110 認証をサーバー発行キーにし、bcrypt を廃止する

提案内容:

- 自己登録はユーザー名、表示名、リージョンを受け取り、サーバーが乱数キー（32 バイトを
  base64url）を生成して応答で一度だけ返す。保存は SHA-256 ハッシュのみ。ログインはユーザー名
  とキーで行い、ハッシュを定数時間比較する。管理者も同じ方式にし、初期データに管理者キーを
  含める。キーの再発行は競技の範囲では行わない。
- 登録応答を失った場合の再取得は冪等リプレイで行う。登録は `Idempotency-Key` 付きで、同じ
  キーでの再送には冪等性レコードに保存した応答（キーを含む）を 24 時間返す。キーの保存要件は
  「`users` にはハッシュしか持たない」とし、冪等性レコードが応答を 24 時間保持することを
  明示的な例外として仕様に書く。24 時間を過ぎて応答を失ったアカウントは復旧しない。
- 仕様から「コスト係数 12 の bcrypt」と、それに付随するパスワード長・文字種の規則、
  72 バイト制限、未知ユーザーへのダミー比較を削除する。安全性要件は「平文を保存しない。
  正しいキーの照合だけが成立する」に書き換える。
- [`design-competition-environment-tuning.md`](design-competition-environment-tuning.md) §1.6 から「bcrypt コスト引き下げ」を削除する。

理由:

- **検証できない制約である。** bcrypt のコストは外形観測できず、運営も DB を検査できない
  （§1.3）。仕様が MUST で固定している一方で参考資料は引き下げを定番の調整に挙げていて
  食い違っており、許せば全チームが最初の 1 時間でコストを下げて終わる（実力差を生まない）、禁止すれば
  唯一の対策が台数追加という固定の CPU コストになる。
- **レベルアップ時のログインコスト。** コスト 12 は 1 回 200〜300 ms の CPU で、セッションは
  無期限・ユーザーごと 1 件なので、負荷が集中するのは「レベルアップでユーザーを追加する
  瞬間」だけになる。4 コアで毎秒 15 件程度しかログインできず、100 人追加で 7 秒近く CPU が
  飽和し、スパイク処理能力ではなく bcrypt でレベルが凍結する。
- **ランダムキーにコストは不要である。** bcrypt のコストは人間が選ぶ低エントロピーな
  パスワードを守るためのもので、128 ビット以上の乱数には SHA-256 で十分。これは妥協では
  なく正しい設計であり、セッショントークンの保存方式（`HashSessionToken`、SHA-256）と
  揃うだけ。速いハッシュが正解なので下げる誘惑もなく、追試の項目からも外せる。
- 単一サーバー対策は P-109 のレイテンシと SLO で果たすので、bcrypt をそのレバーにする
  必然性はない。

ナラティブとの整合: BeReal 本家は電話番号と SMS ワンタイムコードでパスワードを持たない。
「端末に保存する発行キーでログインする」はパスワードレスの流れとして自然で、Web クライアント
はすでに IndexedDB にセッショントークンを保存しているので実装上も無理がない。失うものは
isucari 以来の「bcrypt が CPU ボトルネック」という定番の題材だが、レバーにしないと決めた
以上、実質的な損失はない。

変更範囲: 仕様の自己登録とログインの FR、Key Entities の User、安全性要件、Clarifications の
パスワード関連 3 項目。OpenAPI の登録リクエストと応答、ログインリクエスト。`service/auth.go`
の bcrypt を乱数生成と SHA-256 に置換、`domain.ValidatePassword` の削除、seed の固定ユーザーの
キー。フロントエンドの登録画面（キーの表示と保存の導線）とログインフォーム。ベンチは登録
応答からキーを取り込み、初期データのユーザーはキー一覧で参加、pretest の「誤パスワードで
401」はキー不一致に置換。

### P-111 認定公開アカウントの投稿をフォロワーへ通知する

提案内容:

- 通知種別を追加する。認定公開アカウントが投稿すると、ファンアウトを実行した時点の有効な
  フォロワー（ブロック関係にない、アクティブなユーザー）ごとにアプリ内通知を 1 件作成し、push 購読があれば
  日次通知と同じ仕組み（論理通知 ID、最大 3 回の再試行、恒久失敗で購読無効化）で push を
  送る。重複防止の単位は（フォロワー、投稿）。通知を開くと当該投稿へ遷移し、既読になる。
- 通知の対象は公開範囲が「公開」の投稿だけとする。認定公開アカウントも友達限定で投稿できる
  が、フォロワーが閲覧できるのは公開投稿だけなので、それ以外は通知しない。内容を含まない
  通知を閲覧できない人に送ることもしない。
- 対象者の判定（フォロワーである、ブロック関係にない、アクティブである、投稿が公開である）は
  ファンアウトを実行する時点で 1 回だけ行う。初期実装ではファンアウトが投稿トランザクション内
  なので投稿時点と同じだが、非同期化した実装では実行時点の状態で判定してよい。投稿から実行
  までの間のフォローや解除は、届いても届かなくてもよい。ベンチは投稿の前に確定したフォロワー
  集合だけを検査対象にし、投稿と重なったフォロー操作は検査対象にしない。判定後の公開範囲の
  変更、ブロック、フォロー解除、投稿の削除があっても、作成済みの通知は取り消さない。開いたときに投稿が見えなければ、削除済みと
  同じく「見られない」で終わる（単純化）。
- push の配信先は購読の endpoint が指すリージョンのモックで、経路の遅延は P-103 に従う。
- 対象は認定公開アカウントの投稿だけとし、友達の投稿は通知しない。友達は日次通知で同時に
  投稿する前提なので、通知する意味が薄い。「フォローされた」「友達申請が来た」といった関係
  操作の通知も追加しない。ファンアウトを生むのは投稿起点の通知だけである。
- 現行の `notifications` テーブルは投稿ウィンドウの通知しか表せない（`posting_window_id`
  必須、ユーザーとウィンドウで一意）ので、種別と対象投稿を持てる形に変える。

ナラティブとの整合: BeReal 本家にも友達の投稿や遅刻投稿を知らせる通知があり、「フォローして
いる有名人が投稿したら知らせる」は SNS として普通の機能である。認定公開アカウント（RealPeople /
RealBrands 相当）を導入している以上、フォローに何の効果もない方が不自然だった。前任者が
「フォロー機能に通知を付けた」だけの話で、追加の物語は要らない。

競技上の意味:

- **グラフの次数に比例するファンアウト。** 日次通知のファンアウトはリージョンのユーザー数に
  比例し、ラチェットで一様に増える。投稿起点の通知は特定アカウントのフォロワー数に比例し、
  新規ユーザーが登録直後に認定アカウントをフォローする（P-102）ので、レベルが上がる
  ほど 1 投稿あたりの通知件数が増える。いわゆる有名人問題で、書き込み時ファンアウトの
  バルク化、非同期化、push 送信の並列化が効く。初期実装の worker は push を直列に送る
  （`worker/push_delivery.go`）ので、ここが最初に詰まる。
- **リージョンをまたぐファンアウト。** フォロワーは全リージョンにいるので、`asia` の認定
  アカウントの投稿が `europe` と `america` のフォロワーへの通知になる。P-104 の初期状態では
  worker が `asia` にしかなく、海外フォロワーへの通知と push は東京から出る。リージョン
  ごとの通知到達時間を計測すれば（P-108 の 11）、通知のファンアウトをリージョンごとの
  worker に分ける動機になり、ステージ 2〜3 の題材が一つ増える。
- **投稿スパイクと重なる。** 認定アカウントも日次通知を受けて同じウィンドウで投稿するので、
  投稿起点の通知のファンアウトは投稿スパイクの最中に発生する。on-time 比率と通知到達時間の
  両方に効く。

変更範囲: 仕様に通知種別（投稿ウィンドウ、フォロワー投稿）と、認定アカウントの投稿時の通知
作成・push・重複防止・遷移先の FR を追加。`notifications` に種別と `post_id` を追加し、一意制約を
種別ごとに分ける。`Open` の遷移先に投稿を追加。OpenAPI の通知一覧に種別と投稿 ID を追加。
投稿作成（`postgres/posts.go` の `Create`）またはその後段でフォロワーへのファンアウトを行う
（初期実装は投稿トランザクション内で 1 件ずつ INSERT してよい。遅いが正しい）。ベンチは
認定アカウントのエージェントと、新規ユーザーの登録直後のフォローを追加する。

### P-112 初期実装を素朴にし、移植しやすくする

現在の Go 実装はプロダクトとしては妥当な設計である。層が分かれ、並行性制御（ソート順の行
ロック、`FOR UPDATE SKIP LOCKED`、部分ユニークインデックス、世代管理付きの冪等性）と安全機構
（OpenAPI 検証、HMAC 署名カーソル、隔離されたサニタイザ）がそろい、`go test` と契約テストも
通る。ISUCON の初期実装としては出来が良すぎる。「並行性をあまり知らないジュニアが書いた普通の
サービス」に寄せ、同時に Go 以外の言語への移植を楽にする。

方針: **不変条件は DB の制約で守り、並行性の作法はアプリから外す。** 初期実装は低負荷では
正しく動き、負荷が上がると壊れ方が「データ破損」ではなく「エラー」（制約違反の 500、デッド
ロック、二重送信）として現れる。参加者はログから原因を見つけて直せ、ベンチは正しさの検査を
保てる。言語間で実装差が出やすい処理は、サニタイザと同じ発想で共有バイナリか DB 側に寄せる。
サニタイザが別プロセスなのは複数言語で提供するための意図的な設計なので、そのまま残す。

#### 並行性制御の差し替え

| 箇所 | 現在 | 素朴版 | 負荷で起きること | DB で守るもの |
|---|---|---|---|---|
| 投稿作成 | ユーザー行を `FOR UPDATE`、状態行を `ON CONFLICT` | `SELECT` で投稿済みか見てから `INSERT` | 再送やタイムアウト後の再試行で二重投稿を試み、制約違反の 500 | `posts` に（投稿者、ウィンドウ）で有効な行は 1 件という部分ユニーク制約を追加して守る（現在は状態行とロックで守っている） |
| RealMoji、コメント | 2 ユーザーをソート順にロック | ロックなし、または取得順にロック | 相互にリアクションするとデッドロックで片方が 500 | 「投稿と反応者で有効な RealMoji は 1 件」のユニーク制約 |
| ログイン | 部分ユニークインデックスと置き換えトランザクション | `UPDATE active=false` してから `INSERT`、トランザクションなし | 同一ユーザーの並行ログインで片方が 500 | 部分ユニークインデックスは残す |
| worker のキュー | `FOR UPDATE SKIP LOCKED` で claim | `SELECT status='pending'` してから `UPDATE` | worker を 2 台にすると同じ通知を二重処理し、成功済みの push を再送する | 通知の（ユーザー、期間）ユニーク制約。成功済み push の再送は Push モックで検出（P-108 の 12） |
| 通知ファンアウト | 1 トランザクションで全員分 | トランザクションなしのループ | 途中で失敗すると半分だけ通知され、再実行で制約違反 | ユニーク制約で二重は防ぐ |
| 冪等性 | 世代管理付きレコードでハンドラ全体をトランザクションに包み、応答をキャプチャ | キー行を先に `INSERT` してから処理し、処理と応答の保存を同じトランザクションで行う。世代管理と応答キャプチャのミドルウェアはやめる | 同じキーの並行送信は片方がキーの `INSERT` で制約違反（409 か 500） | （スコープ、操作、キー）のユニーク制約。「処理してからキーを保存」にはしない。自然キーのないコメントが二重に確定し、保存時の制約違反では副作用を取り消せないため |
| カーソル | HMAC 署名 | `(時刻, ID)` を base64 にしただけ | 何も起きない | なし。ホスト間で鍵を揃える必要も消える |

残すもの: DB 制約、ユーザー名の正規化、トークンのハッシュ保存、可視性ルールの SQL、
サニタイザの別プロセス、業務更新と冪等性記録の原子性。これらを抜くとデータが壊れるか仕様に
反するかで、参加者が直しようがなくなる。操作ごとに「高負荷時のエラー」で済むか「データ破損」に
なるかを確認し、破損になる操作（自然キーのないコメント、RealMoji の置換）にはトランザクションを
残す。

#### 移植性のための変更

1. **Web Push の送信を `push-sender` コマンドにする。** RFC 8291 の aes128gcm と ES256 の JWT は
   言語によってライブラリの成熟度が大きく違い（Perl はほぼ皆無）、Go のソースを配ると Go だけ
   コピーで済んで他言語は移植になる。そこで全言語が同じ条件になるよう、Go で書いたバイナリを
   ソースなしで各サーバーに置き、どの言語の参考実装も同じ呼び方をする。仕様が Web Push
   （RFC 8030 / 8291 / 8292）であることは明示し、自分の言語でアプリに組み込み直すのは自由と
   する。詳細は下の「`push-sender` の仕様」。
2. **initialize のリセットとシードを共有スクリプトにする。** 現在は Go の `migrate.Reset` と
   `seed.Minimal` をハンドラから呼んでいる。歴代 ISUCON どおり `init.sh` を exec して DB ダンプを
   復元する形にし、マイグレーションとシードは言語非依存の SQL とスクリプトに寄せる。
3. **Unicode の正規化を DB に寄せる。** 表示名の検索キーは NFC と Default Case Folding で作って
   いるが、case folding の実装は言語で違う（Python `casefold`、Perl `fc`、PHP `MB_CASE_FOLD`、
   JS には相当物がない）。Postgres の生成列で `lower(normalize(display_name, NFC))` を持たせ、
   仕様の「Default Case Folding」は「NFC と lower」に緩める。
4. **文字数の上限を DB の CHECK 制約にする。** コードポイント数の上限は JS で UTF-16 単位を
   数えてしまう典型的な落とし穴。`char_length` はコードポイントを数えるので、CHECK 制約に
   しておけば移植で揺れない。アプリ側の検証は 400 を返すための補助にとどめる。
5. **タイムスタンプの精度を固定する。** 現在は RFC 3339 のナノ秒で出しているが、Ruby と PHP は
   マイクロ秒、JS はミリ秒、Postgres もマイクロ秒。契約をマイクロ秒に固定し、カーソルは DB の
   値をそのまま運ぶ。
6. **OpenAPI 検証ミドルウェアを外す。** バリデータは言語ごとに厳密さが違い、同じ 400 を返す
   のは困難。手書きの検証にし、契約の検証はベンチの pretest で担保する。
7. **ネストしたトランザクションと冪等性の応答キャプチャをやめる。** context 経由の暗黙の
   `SAVEPOINT` は pgx 固有の書き方で、PHP の PDO や Perl の DBI には入れ子トランザクションが
   ない。上の表の平坦な形にする。
8. **worker を単一ループにする。** 現在は 1 プロセス内で 5 つの goroutine が回る。PHP や Perl
   では別プロセスか cron になり移植ごとに構造が変わるので、1 つのループが順に各ジョブを処理
   する形か、ジョブごとに独立したコマンドにする。仮想時計が消えれば時計同期はなくなる。
9. **サニタイザの同時実行制限をアプリから出す。** 「空きスロットがなければ 503」のセマフォは
   アプリ側にあり、PHP-FPM のようにプロセスが分かれる環境では効かない。制限をやめるか、
   サニタイザ側でロックファイルなどで制限し、アプリは呼ぶだけにする。
10. **契約テストを黒箱にする。** `backend/tests` は Go のルーターをプロセス内で起動している。
    移植の検証には URL を指定して HTTP で叩く形が要る。ベンチの pretest をその役に兼ねる。
11. **相関 ID とログの構造化を要求しない。** ベンチは検査しないので、参考実装の要件から外す。

#### `push-sender` の仕様

原則は「入力 1 行につき結果 1 行を必ず stdout に返す。ツール自身の異常だけを終了コードと stderr で
表す」。配信結果とツールの故障を別のチャネルに分け、呼び出し側の状態機械を単純にする。

- **使い方は 1 つだけ。** stdin から 1 行 JSON（endpoint、p256dh、auth、ペイロード、TTL、
  任意の `id`）を読むたびに送信して結果を 1 行返し、stdin が閉じられたら終了する。モードの
  切り替えはない。
- **参考実装は 1 件ごとに起動する。** worker は試行行 1 件につき `push-sender` を起動し、
  1 行書いて stdin を閉じ、結果行を読む。毎回新しいプロセスなので push エンドポイントへの
  接続も毎回張り直す（Push モックは平文 HTTP なので TCP の接続確立。本物の push サービスなら
  TLS ハンドシェイクも乗る）。P-111 のフォロワー通知で 1 投稿あたり数百〜数千件の push が出る
  上位レベルでは、これが worker の支配的なコストになる。
- **閉じなければ常駐になる。** stdin を閉じずに行を流し込み続ければ、1 プロセスが順に処理して
  行ごとに結果を返し、fork と接続確立のコストが消える。`--help` には「stdin を閉じるまで行を
  読み続ける」という読み方が書いてあるだけで、マニュアルには「`--help` を読め」とも書かない。
  気づいた人への報酬は十分大きい。送信は 1 件ずつ順次で、内部で並列化しない。並列化したければ
  複数プロセスを立てる。これで push 並列化のレバー（P-109）が参加者側に残る。
- **結果行。** 入力 1 行に対して常に JSON を 1 行返す。
  `{"seq":12,"id":"a1b2","result":"transient","status":429,"error":"rate_limited","retryAfter":30}`
  - `seq`: 入力の行番号。`id` を付け忘れても対応づけられる。
  - `id`: 入力の `id` をそのまま返す。省略時は null。
  - `result`: `delivered`、`transient`、`permanent`、`invalid` の 4 値。
  - `status`: HTTP ステータス。接続エラーやタイムアウトは null。
  - `error`: 機械可読な分類（`timeout`、`connection`、`rate_limited`、`gone`、`bad_request`、
    `invalid_input` など）。
  - `retryAfter`: 429 や 503 で `Retry-After` があれば秒数。
- **分類の規則。** 2xx は `delivered`。404 と 410 は `permanent`。400 と 413 も `permanent`
  （ペイロードやエンドポイントの誤り）。429 と 5xx と接続エラーとタイムアウトは `transient`。
  JSON として読めない行や必須項目が欠けた行は `invalid`。ツールは内部で再試行しない。1 入力は
  必ず 1 回の送信試行になり、再試行の回数と間隔はアプリの責任とする。これで push の二重送信
  検出（P-108 の 12）の意味が保たれる。
- **入力が壊れていた場合。** `invalid` の結果行を返して処理を続ける。`id` が読めなければ null
  だが `seq` は必ず入る。1 行のために落とすと、呼び出し側は後続の行の結果を失い、どこまで
  送られたか分からなくなる。
- **ツール自身の異常。** 起動時の設定不備（VAPID 鍵がない、形式が不正）は stdin を読む前に
  終了コード 1 で落ち、理由を stderr に出す。実行中の致命的な異常も終了コード 1 で終了し、
  stdout は EOF になる。呼び出し側の規則として「結果行を受け取れないまま子プロセスが終了
  したら、未応答の入力はすべて `transient` として扱う」と定める。送信済みかどうか分からない
  ので再試行になり二重送信の可能性が残るが、これは Web Push の性質上避けられず、通知側は
  論理通知 ID で重複排除する設計になっている。stderr は診断ログ専用で結果は書かない。stdin
  が EOF になったら処理中の行を完了させて結果を flush し、終了コード 0 で終わる。SIGTERM も
  同じ。
- **終了コード。** ツール異常の有無だけを表す。stdin の EOF で終われば 0、設定不備や内部
  エラーで終われば 1。配信結果は結果行だけで表し、終了コードには反映しない。
- **呼び出し側が踏みやすい罠。** 1 行読んで送信して結果を書く逐次処理なので、常駐させた
  ときに
  結果を読まずに大量の行を書き込むとパイプのバッファ（64 KB 程度）が埋まって双方が止まる。
  stdin への書き込みと stdout の読み取りを別のスレッドで行うか、N 行書いて N 行読む必要が
  ある。`--help` にはこの注意を書く。常駐化に気づいた人が次に踏む問題で、直せるかどうかも
  弁別点になる。
- **設定と配布。** VAPID の秘密鍵と subject は環境変数で受ける。Push モックは平文 HTTP なので
  `http://` の endpoint を許可する。タイムアウトの既定値は 10 秒程度で `--timeout` で変えら
  れる。競技環境のアーキテクチャ向けのバイナリだけを全ホストの `/usr/local/bin` に置く
  （P-104）。ツール自体がボトルネックにならないよう、常駐させた状態で秒間数千件を捌けることを
  運営側で負荷試験する。
- **`--help` に載せる範囲。** 「stdin から行を読み、行ごとに結果を返し、EOF で終了する」という
  読み方、入出力の行形式、`result` の 4 値と分類規則、`retryAfter`、終了コード、SIGTERM の
  扱い、パイプの注意、`--timeout`。性能の目安は書かない。
- **マニュアルに書くこと。** 「push は Web Push で送る」「`push-sender` コマンドが各サーバーに
  ある」「自分の実装で送ってもよい」の 3 点だけ。使い方には触れない。

ナラティブとの整合: 前任者は push 送信を社内ツールとして切り出していて、そのツールの
リポジトリだけ引き継がれていない。バイナリは各サーバーに残っていて、使い方は `--help` にしか
書かれていない。ソースがないのも、起動しっぱなしにできることに誰も気づいていないのも、
その状況として自然である。

#### 構造の平坦化（未決）

5 層構造とインターフェース注入は、歴代の参考実装（ハンドラに SQL 直書き、DB ハンドルは
グローバル）と質感が違い、他言語の実装者が構造を再設計する負担になる。1 パッケージにハンドラを
並べて SQL を直書きする形に平坦化すれば、読みやすさと移植のしやすさが上がる。約 8,000 行の
書き直しになるので、並行性の差し替えとは分けて判断し、やるなら仕様変更（P-101、P-110、P-111）と
同時に行う。

#### ベンチ側で必要になること

- 初期実装は基準レベルではエラーなしで通る。素朴版のエラーは負荷が上がってから出るものに限る
  ように較正する。エラー 100 件で打ち切りの閾値も見直す。
- 壊れ方を診断可能にする。ベンチのエラーメッセージにエンドポイントと期待値・実際値を出す
  （DIAG-01）のに加え、アプリのログにデッドロックや制約違反がそのまま出る状態を保つ。
- 成功済み push の再送を Push モックで検出し、正しさの違反として扱う。障害時の正しい再試行とは
  分けて数える（P-108 の 12）。

ナラティブとの整合: 前任者が 1 人で作ったサービスに並行性の穴があるのは自然で、それが
「8 時間後の負荷」で初めて露見する、という筋書きそのものである。移植性のための変更は
参考実装の作り方の話で、物語には現れない。

競技上の意味: デッドロックや制約違反は負荷をかけて初めて出るので、コードを読んで直すだけの
作業では見つからない。ログを見て再現して直す手順が要る。worker の claim が素朴だと、リージョン
ごとに worker を分けた瞬間に成功済みの push を再送してしまうので、ステージ 2〜3 で必ず踏む「分散したら
正しさを自分で担保する」という題意どおりの罠になる。

## 4. 想定される改善ステージ

提案どおりの環境と負荷モデルにした場合に、参加者がたどると想定する改善の段階。各段階の
具体的な手法とコード上の該当箇所は[`design-competition-environment-tuning.md`](design-competition-environment-tuning.md)にまとめた。

| ステージ | 重要になる時期 | 参加者がやるべきこと | 動くもの |
|---|---|---|---|
| 0. 単一ホストのチューニング | 最初から。asia が支配的 | インデックス。距離 2 の友人クエリの書き換え。負荷で現れる並行性の不具合の修正（ロック順序、冪等性の競合、worker の claim）。3 段階の画像認可の統合。メタデータ除去の軽量化。プールサイズ。通知ファンアウトのバルク化。`push-sender` の常駐化 | asia のスループットと on-time 比率 |
| 1. リージョン内リード | 海外ユーザーが現れたとき | フィード、画像、プロフィール、セッション検索のためのリージョンごとのリードレプリカまたはキャッシュ。画像のローカリティ。ルータールール | 海外のスループット。SLO の達成 |
| 2. リージョン内ライトとスパイク | 3 つのずらしたスパイク | ユーザー / 投稿 / ウィンドウ / 通知をリージョンでシャーディング。ファンアウトと worker をリージョンごとに実行。投稿トランザクションをリージョン内に閉じる | リージョンごとの on-time 比率、通知レイテンシ |
| 3. リージョン間のやりとり | シャーディング後 | 他リージョンの友人、公開フィード、ブロック、シャードをまたぐリクエストを内部 API、非同期レプリケーション、またはキャッシュで扱う | リージョン間リードのレイテンシ。正しさのチェック |
| 4. 同期移行 | 後のレベル | アトミックなディレクトリ切り替え、処理中リクエストのドレイン、書き込み消失なし、履歴の移動または取得、冪等なリトライ | 移行レイテンシ。同時プローブ |

ステージ 0 は通常の ISUCON である。ステージ 2 と 3 は一緒に解かなければならない。ステージ 4
はシャーディングした実装にとってのみ難しい。

ルータールールの想定される使い方: リージョンから同一リージョンのサーバーへ（デフォルト）。
管理者と `/initialize` を 1 ホストに固定する。画像 GET を所有リージョンへ向ける（ルーターは
ユーザー ID を見られないため、URL にリージョンを埋め込む必要がある）。海外の負荷が小さい間は
一時的にすべてを `asia` へ送る。

## 5. 未決事項

提案の中でレビュアーが決めきれていない点。採用時に判断が必要。

- 注入する遅延の値と、注入をルーター側で行うかサーバー間ネットワークで行うかの実装（P-103）。
- リージョン間帯域の上限: 設けるか否か、およびその値。エミュレートなので `tc` で入れられる。
- on-time の締め切り N の初期値。5 秒から始め、3〜10 秒の範囲で較正する（根拠は P-101）。
  `onTimeSeconds` 省略時の既定値を 120 秒にするか。
- P-110 の採否。採らない場合は、bcrypt を負荷経路から外す代替（初期データにセッション済み
  ユーザープールを持ち、登録とログインを低頻度イベントにする）、コスト 10 への引き下げ、
  変更禁止の追試項目化が必要になる。
- 画像処理検証（P-108 の 9）の画素近似一致の閾値と、ベンチが使う画像サイズ（現在は 64×64 の
  極小 JPEG）。
- レベル表の形式（総ユーザー数とリージョン構成比）と、レベル判定の信号（エラー率、リージョン
  ごとの p99、on-time 比率）。
- P-111 の規模。認定公開アカウントの人数とリージョン配置、新規ユーザー 1 人あたりのフォロー数、
  投稿起点の通知の到達時間の許容値。友達の投稿にも通知を出すかは、日次通知と重なるので
  当面は出さない。
- P-112 の構造の平坦化をやるか。やるなら仕様変更と同時に。素朴版で基準レベルがエラーなしで
  通ることの較正と、エラー打ち切り閾値の見直し。
- `client_region` 不一致時の拒否ステータス: コード付きの 403 か、421 か、451 か。
- §1.1.1 の GDPR 補強を採用するか。採用する場合、マニュアルでの書き方（法解釈ではなく
  社内ポリシーとして書く）。
- レベルごとの移行イベント頻度。実行の後半に大量移行イベントを含めるか。
- リージョン間リードの陳腐化許容量。
- ベンチが 3 つの観測点（リージョンごとに 1 つ）を持つか、1 つの観測点でルーターがリージョン
  ごとの遅延を注入するか。後者の方が単純で決定的である。
- レスポンスヘッダを検証するか、対象外と宣言するか。
- キャリブレーションに「LLM による試し解き」ステップを入れる: 新しいエージェントにサーバー
  アクセス、ルーター UI、ルーターマニュアルだけを与え、トポロジーを発見できるかを見る。
  加えて「1 台にエージェントを置いただけで他は何も教えない」条件でも走らせ、層 1 だけの
  スコア上限を実測する。レベル表の海外ユーザー比率はこの上限の上に置く。
- レベル表の上限。最強チームが層 3 まで到達しても頭打ちにならないレベル数と海外比率。

本文書の数値のうち「無限に速いアプリでもスコアは約 30% しか伸びない」「5 秒の on-time で初期
実装が折れるのは同時投稿 100〜200 人」「LLM と人間のチームの到達差」は、現行実装の静的な読みと
推定に基づく仮説であり、変更後の実装での負荷試験と試し解きで検証する。
