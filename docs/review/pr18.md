# 第 1 部: PR #18 へのレビュー

## CI の失敗
1. frontend-unit-contract-build: `frontend/vite.config.ts` から Service Worker のビルドエントリを削除したが、CI は `test -f dist/service-worker.js` を実行したまま。SW が不要なら CI のステップと残骸(`src/service-worker/push.ts`、`src/app/serviceWorker.ts`、`tests/unit/push-dedup.test.ts`)も削除する。
2. Playwright E2E: portal-mock の `tests/e2e/settings.spec.ts` が失敗(element not found)。portal-mock の UI 変更の影響と思われる。原因は未調査。

## bench: リダイレクトを追わない
- `bench/internal/client/client.go:46` の `http.Client` は既定でリダイレクトを追う。アプリが 307/308 で別ホストへ誘導すると、bench がルーター以外の経路を通り得る。
- Go は同一ホストやサブドメインへのリダイレクトでは `Authorization` を引き継ぐので、ヘッダが落ちることには頼れない。
- 修正: `CheckRedirect` で `http.ErrUseLastResponse` を返す(通知用クライアントもこれをコピーしているので 1 か所で済む)。テスト「307 はエラーになり、リダイレクト先にアクセスしない」を追加する。

## PR 説明との不一致
- PR 説明では地域外からは地域変更のみ可能とあるが、`PATCH /api/me`(displayName/bio も変更可)と `PUT/DELETE /api/me/profile-image` に `RegionMiddleware` がない(`webapp/go/server.go`)。

## 設計(docs/review との対比)
### 地域判定は `X-Country-Code` で行う
- 現状はサーバー設定の `ISUREAL_REGION` とユーザーの地域を比較している(`webapp/go/region.go:16`)。
- bench はどのサーバーで処理されたかを検知できない(レスポンスは参加者が自由に作れる)。ルールは bench が制御できるリクエスト元(bench が付ける `X-Country-Code`)とユーザーの地域で定義する必要がある。
- 提案: `ISUREAL_REGION` を廃止し、コードで `X-Country-Code` から地域を求めて(JP/KR/CN/AU=asia、GB/DE/FR=europe、US/CA/MX=america、ルーターと同じ対応)`users.region` と比較する。ルーターはこのヘッダを upstream にそのまま渡している。
  - 3 台が同一バイナリ・同一設定になる(レビュー P-104)。
  - bench で検証できる(地域の合わない国コードで送って 403 を期待する)。
  - 他サーバーへ転送してもヘッダを引き継げば正しく動く。代償は地域間の遅延で、ルール違反ではない(P-106)。

### ルーターの振り分け固定は問題ない
- PR #18(`9810a86`、`510d106`)で、main の `mainServer` と地域の変更機能がなくなり、国コード → 地域のサーバー(app1=AP、app2=EU、app3=US)に固定された。変更できるのは `defaultCountry` のみ。
- 「GDPR 対応マネージドルーター」(法務の社内ポリシー「ユーザーのデータは所属リージョンのエンドポイントからしか提供しない」のために契約した)という筋書きなら、固定は自然で分かりやすい。1 台に集約するにはサーバー間転送しかなく、攻略の選択肢がアプリ側に集まる。
- レビュー P-103/P-105 の「管理 UI でルールを変更」「ルール構文のマニュアル」は不要。参加者には国と地域の対応表を渡せばよい。
- `defaultCountry` は bench が常にヘッダを付けるので実質効かない。参加者に触らせるか運営側に閉じるかを決める。

### その他
- `onTimeSeconds` の既定値が 24 時間(`admin_posting_window_api.go:36-39`、提案は 120 秒)。bench も値を送らないので on-time 比率が意味を持たない。
- P-110 の細部: シークレットキーが UUID(提案は 32 バイトの base64url)、比較が定数時間でない、管理者は固定パスワードの SHA-256 のまま。
- 一意性を DB 制約ではなくロックで守っている(username、token_hash、posts)。`[作問]` コメントのとおり意図的(P-112 とは逆方向)。`[作問]` コメントは配布前に除去する。

## 初期データは必須(メモリに乗り切らない量)
- 現状は initialize 後の DB がほぼ空(`001-schema.sql` で全テーブルを作り直し、`002-seed.sql` は admin 1 件のみ)。60 秒程度のベンチで溜まるデータだけでは、オンメモリ戦略が有利になりすぎる。
- 対応:
  - `webapp/datagen/internal/dataset` で、サーバーの RAM を超える偏りのある履歴を生成する(ユーザー、bytea の画像付き投稿、関係、コメント/RealMoji、通知、過去の投稿ウィンドウ)。
  - bulk INSERT の seed は巨大になるので、DB イメージやダンプを配布し、init は直近の差分だけを戻す方式を検討する(レビュー detune §3.2、topology-alt §8)。
  - bench の pretest は public フィードが空であることを期待している(`bench/internal/scenario/scenario.go:171-173`)ので直す。初期データの履歴も読む・交流するようにする。
- `001-schema.sql` の DROP 対象に残る不要なテーブル(`worker_jobs`、`idempotency_records`、`app_settings`)を整理する。

## インデックス: 初期状態は index shotgun にする(detune A-8)
- 現状は主キーと UNIQUE 制約以外にインデックスがほぼない(`token_hash`、`username`、`posts` の各列など)。メモリに乗り切らない初期データがあるのに、稼働してきたサービスで重要な検索にインデックスがないのは不自然。
- 方針: 重要な検索にもインデックスを張ったうえで、冗長なインデックスを大量に付けておく(**index shotgun**)。
  - 例: notifications に 10 本以上、重複・包含関係にある複合インデックス、使われない単一列インデックス、キャプションや表示名への trigram GIN。
  - 効果: INSERT のたびに全 btree の更新と WAL が増える(通知のファンアウト、投稿、RealMoji、コメント)。
  - 多いことはスキーマを見れば分かるが、どれを消してよいかは `pg_stat_user_indexes` や `EXPLAIN` を見ないと決められず、誤って消すと読み取りが遅くなる。歴代 ISUCON に「多すぎる」はなかった。
  - 筋書き: 「遅いと言われるたびに足した」「AI の提案を全部入れた」。前任者の AGENTS.md に「インデックスは削除しない」(detune §5.3)。
- 「インデックスを貼っていない」旨の `[作問]` コメントと、アプリ側のロックによる一意性保証の方針もあわせて見直す。インデックスは初期データ入りで配布する DB イメージに含める。

## 画像サニタイザ(別プロセス)は残したい
- 現状は削除され、投稿・RealMoji・プロフィール画像のバイト列をそのまま `image/jpeg` として保存している(デコード、形式検証、EXIF 除去、サイズ上限なし)。
- 次の改善要素になるので残したい:
  - 初期実装は全体をデコード・再エンコードしているが、EXIF 除去だけで済むことに気づけるか。
  - 再圧縮で帯域(地域間 200Mbps)を節約するか、CPU を節約して原寸で流すかのトレードオフ。
  - サブプロセスの起動コストと同時実行数の制限(P-112、tuning §1.3)。
- bench 側で必要なこと: 画像の検証をバイト完全一致から、寸法・画素の近似一致・メタデータ除去の確認に変える(P-108)。送る画像を EXIF 入りでそれなりの大きさの JPEG にする(現状は EXIF なしの 64x64)。

## 接続先はルーター提供の managed DNS で引かせる(detune B-1)
- push の廃止で外向き通信は DB 接続のみになり、その接続先も IP 直書き(`ISUREAL_DB_HOST`、compose、provisioning)なので、現状は DNS をまったく引いていない。
- 接続先をホスト名(例: `db1.<domain>`)にし、各サーバーの resolver をルーター提供の DNS(detune §4: dnsmasq、hashlimit によるレート制限)に向ける。Go の resolver はキャッシュしないので、プール既定値(idle 2)による再接続のたびに DNS を引いてレート制限に当たる(A-1 と B-1 の相乗)。
- 筋書き: 「前任者が DB の移設に備えて接続先を名前にした」「マネージドルーターに DNS も付いてきた」。
- 必要な作業: ルーターへの DNS 実装(PR 説明でも未着手)、provisioning / compose / `init.sh` / datagen の接続先と resolver 設定の変更。

## ルーター(Envoy)を同時接続のボトルネックにしない
- bench は投稿ウィンドウを開く前に全ユーザー分の通知 SSE 接続を張って待つので、同時接続数はユーザー数に比例する。
- ルーターは参加者が触れないので、ボトルネックになってはいけない。現在の Envoy bootstrap には circuit breaker の設定がなく、既定値(クラスタあたり 1024)になる。最大レベルの同時接続数を見積もり、circuit breaker、接続上限、ファイルディスクリプタ上限、VM のスペックを設定・検証する。

# 第 2 部: 追加の提案

## 画像 URL を署名付きにする(新規の出題要素)
現状は画像の取得に `Authorization` ヘッダが必要で、ブラウザの `<img src>` では表示できない(フロントエンドは `AuthenticatedImage.tsx` で fetch → blob → object URL にしている)。

### 仕様
- 画像 URL は **投稿者の鍵で署名した共有リンク** にし、`GET /api/images/:imageId` は署名だけで許可する(ヘッダ不要)。
- 鍵の元は `users.secret_key_hash`(= `sha256(secretKey)`)。ログアウトしても共有リンクは有効なまま。bench は登録時のシークレットキーから署名を再計算し、アカウントの持ち主が署名したことを検証できる(アルゴリズムの差し替えも防げる。補助資料 §1.3)。
- URL には投稿者、発行時点の投稿者の地域、`exp`、`sig` を含める(地域を固定するので、投稿者が地域を移っても検証できる)。
- 無効化は URL の有効期限に頼らない。`exp` は共有リンクとして十分長くし、投稿者の退会と投稿の削除から N 秒以内に全地域で 403 にする。N 秒はサーバー側で状態をキャッシュしてよい陳腐化の許容範囲。
- これは現状より仕様を緩める(現在は毎回 DB で確認し、DB が 1 台なので即座に反映される)。仕様書に「退会・削除から N 秒までは取得できてもよい」と明記する。

### 他の地域へ届ける経路: P-111 の通知
- 認定公開アカウントが投稿すると、フォロワー全員へ投稿者の署名付き画像 URL を通知する(P-111 を実装する)。筋書きは「受け取る人ごとに署名し直すと高くつくので、前任者が投稿時に作者の署名で 1 回だけ作った」。
- フォロワーは地域をまたぐので、各地域のサーバーが他の地域の投稿者の鍵と状態を扱うことになる。通知が投稿ウィンドウとユーザーから計算できなくなる効果もある。
- 通知はいつ届くか分からないので、現在の SSE(1 件返したら閉じる)を複数件受け取れる形にするか、通知一覧の API を用意する。

### 仕込みと改善の段階
- 初期実装は、署名を検証したうえで投稿者・投稿・閲覧権限を毎回 DB で確認し直す(即座に無効になる状態)。
- 署名アルゴリズムがなぜか重い: SigV4 の鍵派生(HMAC 4 回)を数万回ストレッチする仕様にし、ドキュメントに「セキュリティのため」と書く。派生鍵は(投稿者、日付、地域)単位でキャッシュできるのに毎回計算する。アルゴリズムは 1 つに固定し、重さはウォームアップ程度に抑える(弁別の本命は配信経路)。
- 改善の段階:
  1. 派生鍵をキャッシュする。
  2. 閲覧権限の再確認を省く(署名が正しければ発行時点で確認済み)。
  3. 他の地域の投稿者の鍵、アカウントと投稿の状態を地域ごとにキャッシュし、退会と削除を N 秒以内に全地域へ反映する(有効期限付きキャッシュか地域間の無効化通知か。P-109 の有界陳腐化)。投稿の削除は頻繁なので整合性の要素として効く。
  4. 画像そのものを地域ごとにキャッシュし、nginx から返す(画像は asia の DB にあり、EU/US は取得のたびに往復 200ms・200Mbps を払う。tuning §2.2)。

### bench で確かめること
- 発行された署名が `sha256(secretKey)` から再計算した値と一致すること。
- 他の地域のフォロワーが通知のリンクで画像を取得できること。
- 改ざん・期限切れのリンクが 403 になること。
- 投稿の削除・投稿者の退会から N 秒後に全地域で 403 になること(N 秒以内の 403 は許容)。

### その他
- ストレッチ回数は言語間(PHP/Ruby/Perl など)で初期スコアが揃うよう較正する。
- `exp` を切りのよい時刻に丸めるかで、ブラウザのキャッシュの効きやすさを調整できる。

## ログイン攻撃の検知(バイナリのみの worker と daemon、新規の出題要素)
### 背景
- PR #18 で常駐 worker がなくなり、1 プロセスのコードを読めば全体を理解できるので、簡単になりすぎるおそれがある。
- システム全体(プロセス、ログ、リージョン、DB)を把握しないと改善できない要素を足したい。

### 筋書き
- 「ログイン攻撃が相次いだので、前任者がセキュリティ製品を導入した」。ベンダー製品なので **バイナリのみ** 配布する。
- 製品は DB を知らない。検知時に呼ぶ外部コマンド(hook)を前任者がシェルスクリプトで書き、`psql` で DB を更新している。
- 当日マニュアルには書かない。拒否時のステータスコードと閾値は、製品のログと `-h`(`--help`)で知る。

### 構成要素
各アプリサーバーに次の 2 つが常駐する。

1. **guard-worker(ユーザー単位の soft ban)**
   - アプリが journald に出すログからログイン失敗をサーバーごとに集計し、閾値を超えたら検知した内容を環境変数に入れて hook を呼ぶ。
   - journald は `journalctl` をサブプロセスで起動して読む(cgo 不要で静的リンクのバイナリを配れる)。
     ```sh
     journalctl -u "$GUARD_WORKER_JOURNAL_UNIT" -f -o json --all \
       --cursor-file=/var/lib/isureal-guard/journal.cursor
     ```
     - `--cursor-file` で再起動後も続きから読む。`--all` がないと 4096 バイトを超えるフィールドが `null` になる。
     - `MESSAGE` は UTF-8 でないとバイト配列になるので両方受け付ける。実行ユーザーは `systemd-journal` グループに入れる。
   - nginx の **製品専用のアクセスログ** も読み、IP ごとの URL、最終アクセス時刻、ウィンドウ内のアクセス数をローカルの SQLite に書き続ける。専用ログはメインとは別ファイルなので、メインのログを alp 用に JSON にするなどの定番作業で bench は落ちない。
     ```nginx
     log_format guard '...';                              # 製品のマニュアルどおりの形式
     access_log /var/log/nginx/access.log main;           # 参加者が自由に変えてよい
     access_log /var/log/isureal-guard/access.log guard;  # セキュリティ製品用。変更しないこと
     ```
2. **guard-daemon(IP 単位の hard ban)**
   - nginx の `auth_request` の委譲先。`X-Original-URI`(`proxy_set_header X-Original-URI $request_uri;`)とルーターが付ける `X-Real-IP` を受け取り、ログイン API へのアクセスなら SQLite を読んで、失敗が閾値を超えた IP を拒否する。
3. **hook スクリプト(前任者作、参加者が読めて変えられる)**
   - worker は hook を 1 件ずつ同期的に実行し、終了を待つ(`GUARD_WORKER_HOOK_TIMEOUT` で打ち切り)。失敗(非 0 終了)は stderr とともにログに出し、再試行しない。
   - hook に渡す環境変数: `GUARD_DETECTED_USERNAME`、`GUARD_DETECTED_FAIL_COUNT`、`GUARD_DETECTED_WINDOW`、`GUARD_DETECTED_BAN_UNTIL`(RFC 3339)、`GUARD_DETECTED_AT`。
     ```sh
     #!/bin/sh
     # /etc/isureal-guard/hooks/ban-user.sh(guard-worker が検知時に呼ぶ)
     psql "host=db1.<domain> dbname=isureal user=isureal" -v ON_ERROR_STOP=1 \
       -v username="$GUARD_DETECTED_USERNAME" -v until="$GUARD_DETECTED_BAN_UNTIL" <<'SQL'
     UPDATE users SET banned_until = :'until' WHERE username = :'username';
     SQL
     ```
   - フラグは DB(asia)にあり、アプリはセッション検証とログインで確認するので、**全リージョンで拒否** される。

### 迷彩: admin API でも soft ban できる
- `PUT /api/admin/users/:userId/ban`(解除は `DELETE`)を足す。既存の `/api/admin/users/:userId/certification` と同じ形。bench も少しだけ叩く。
- hook と同じフラグを書く。例: `users.banned_until`(hook は `GUARD_DETECTED_BAN_UNTIL`、admin API は `infinity`、アプリは `banned_until > now()` で拒否)。
- 解除(`DELETE`)は worker による ban も消す(誤検知を運営が手で解除する運用として自然)。
- アプリのコードを grep するとフラグを書く箇所が admin API に見つかるので、「フラグは API 経由でだけ更新される」ように見える。実際は hook の `psql` が DB へ直接書く別経路がある。
- 罠: ban 状態をアプリ内にキャッシュし、admin API でだけ無効化すると、worker による ban が反映されず bench が失敗する(「soft ban の反映が遅すぎます」)。製品のログ、`pg_stat_activity`(`application_name` が `psql`)、DB のログ、unit の環境変数から hook にたどり着く必要がある。

### 設定(systemd の環境変数)
- 設定ファイルは持たず、すべて unit の `Environment=` で渡す。参加者は `systemctl cat` で読み、`systemctl edit` の drop-in で変える。起動時に実際の値をすべてログに出す。
- `-h` / `--help` で、環境変数の一覧と既定値、拒否時のステータスコード、hook に渡す環境変数を表示する。
- 名前は製品のものと分かるよう `GUARD_` で始め、片方だけが使う値は `GUARD_WORKER_` / `GUARD_DAEMON_` にする。hook に渡す値は `GUARD_DETECTED_` にする。

| 変数 | 使う側 | 内容 | 変えてよいか |
|---|---|---|---|
| `GUARD_USER_FAIL_THRESHOLD` / `_WINDOW` / `_BAN_DURATION` | worker | soft ban の閾値、集計期間、継続時間 | 不可(仕様) |
| `GUARD_IP_FAIL_THRESHOLD` / `_WINDOW` / `_BAN_DURATION` | worker、daemon | hard ban の閾値、集計期間、継続時間 | 不可(仕様) |
| `GUARD_SQLITE_PATH` / `GUARD_SQLITE_JOURNAL_MODE` | worker、daemon | SQLite のパスと journal mode(初期値 `DELETE`) | 可 |
| `GUARD_WORKER_JOURNAL_UNIT` / `GUARD_WORKER_ACCESS_LOG` | worker | 読むアプリの unit、製品用アクセスログのパス | 可 |
| `GUARD_WORKER_BATCH_SIZE` / `GUARD_WORKER_FLUSH_INTERVAL` | worker | SQLite へ書くバッチの大きさと間隔 | 可 |
| `GUARD_WORKER_ON_USER_DETECTED` / `GUARD_WORKER_HOOK_TIMEOUT` | worker | soft ban 検知時に呼ぶコマンドとタイムアウト | 可 |
| `GUARD_DAEMON_LISTEN` / `GUARD_DAEMON_PROTECTED_URI` | daemon | `auth_request` の委譲先、判定する URI | 可 |

- 仕様の値も環境変数で変えられるが、bench が挙動で検査する(上げれば ban が発動せず、下げれば誤検知になる)ので別途の検出は不要。

### 仕込み(初期状態の非効率)
- **ログの出し過ぎ**: 後述の「アプリのログの出し過ぎ」を参照。ログイン失敗の行は debug レベルで出ているので、ログレベルを info に上げたり、journald のレート制限を超えたりすると ban が効かなくなる(「soft ban の反映が遅すぎます」)。
- **hook のコスト**: 検知 1 件ごとに `psql` のプロセスを起動し、asia の DB へ新しく接続する。接続先の名前解決(ルーター DNS のレート制限、B-1)、EU/US からは TCP と認証で往復 200ms を数回払う。hook は直列に実行されるので、攻撃が重なると待ち行列が伸びて N 秒を超える。
- **アプリとのロック競合**: フラグを `users` に置くので、ログインの `SELECT ... FOR UPDATE`、登録とウィンドウ開始の `LOCK TABLE users` の間は hook の UPDATE が待たされ、後続の hook も詰まる。
- **SQLite**: アクセスログ 1 行ごとに書き込んで fsync する。WAL でないので daemon の読み取りとぶつかり、`SQLITE_BUSY` のとき daemon は拒否側に倒れる(fail closed)。
- **nginx のログ**: 製品用とメインの 2 本を毎リクエスト書く。`location` に `access_log` を書くと server レベルの設定が継承されず製品用のログが止まるが、nginx でよくある落とし穴の範囲とする。
- **auth_request の範囲**: 全リクエストにかけているが、daemon が判定するのはログイン API だけ。

### 改善の例
- `auth_request` と製品用のログを、ログイン API の `location` に限定する。
- アプリのログをログイン失敗の行だけにする(後述の「アプリのログの出し過ぎ」)。
- hook を書き換える: 近くのアプリに HTTP で通知してアプリの接続プールで更新する、アプリ内のキャッシュも同時に更新する、など。
- SQLite を tmpfs に置く、`GUARD_SQLITE_JOURNAL_MODE=WAL` にする、バッチの大きさと間隔を調整する(nginx の `flush=` も含め、大きくすると検知が遅れて N 秒を超えうる)。
- soft ban のフラグを `users` から分け、アプリ側の確認をキャッシュする。無効化は admin API と hook の両方の経路に対応させる(有効期限付きにするなど)。
- 製品を止めてアプリに組み込む(解法として認める。後述)。ログ、SQLite、hook、`auth_request` の往復が不要になる。

### bench で確かめること
- soft ban: 同じユーザーへログイン失敗を送り、閾値を超えてから N 秒以内に全リージョンで拒否されること。製品はサーバーごとに数えるので、1 ユーザーへの失敗は 1 つの国から送る。
- hard ban: 同じ IP からの失敗が閾値を超えたら、N 秒以内にその IP からのログインが拒否されること。仮想 IP ごとに国を固定して送る。
- admin API: ban したユーザーが N 秒以内に全リージョンで拒否され、解除後は N 秒以内に使えるようになること(呼ぶ頻度は低くし、迷彩にとどめる)。
- 誤検知: 正規ユーザーや、閾値未満の IP とユーザーが拒否されないこと。
- 判定はステータスコードのみで、拒否した経路(nginx かアプリか)は問わない。N 秒より早い拒否は許容する(P-109 の有界陳腐化)。
- 失敗は bench のログ(ポータルで参加者に見える)に、理由と N 秒を含めて出す(例: 「soft ban の反映が遅すぎます(N 秒経過)」)。

### 決めること・必要な作業
- **ルーターが `X-Real-IP` を付ける**: 現在は `x-country-code` しか渡していない(`router/internal/xds/routes.go`)。bench は 1 台から送るので、`X-Country-Code` と同様に bench が指定した仮想 IP をルーターが `X-Real-IP` として付ける。
- **ユーザーの単位**: ログインは `username` と `secretKey` なので username 単位で数える。無効な Bearer トークンを対象にするかは要検討(ユーザーを特定できない)。
- **レギュレーション(決定)**: 製品をアプリ内の処理に置き換えるのは解法として認める。同じ条件で同じステータスコードを返せばよい。条件(閾値、集計期間、ban の継続時間)とステータスコードは、製品のログと `--help` に出す(マニュアルには書かない)。許容時間 N 秒もマニュアルには書かず、bench のログ(参加者がポータルで見られるもの)に理由付きで出す。
- **製品の実装**: 言語別実装とは別に Go で作ってバイナリだけ置く。アプリが出すログの形式は全言語で揃える。
- **気づける手がかり**: worker は解析できない行を `unrecognized log format: N lines` のように目立つ形で出す。unit 名やログの出力先が変わったときのために、「N 秒間ログイン失敗の行を読んでいない」旨の警告も出す。hook の実行時間と終了コードもログに出す。
- **provisioning**: 旧 `isureal-worker.service` を置き換え、guard-worker と guard-daemon の unit(`GUARD_*` を含む)、hook スクリプトと `psql`(postgresql-client)、`.pgpass`、nginx の `auth_request` と製品用 `access_log`、SQLite とログの配置を入れる。
- 関連: P-114(常駐の集計サービス)、B-1(ルーター DNS)、B-2(リクエストのメタデータログ)、B-14(auditd)。

## アプリのログの出し過ぎ(新規の出題要素)
### 仕込み
- アプリが何でもかんでもログに出す。リクエストログ、実行した SQL と引数、セッション検証の結果、レスポンスの件数など、1 リクエストで数行を stdout 経由で journald に書く。
- ログの出力はログレベルで制御する(例: `ISUREAL_LOG_LEVEL`)。既定値は `debug` で、上記のほとんどは debug レベル。
- ログイン失敗の行も debug レベルで出ている。セキュリティ製品は「debug で運用している」前提で後から導入され、この行に依存している。
- 筋書き: 「障害調査のたびに前任者がログを足し、debug のまま運用していた。その後、そのログを読むセキュリティ製品を入れた」。

### 効果
- journald の書き込みと保存で CPU とディスクを食う。
- journald が詰まると stdout への書き込みがブロックし、アプリのレイテンシになる。
- journald のレート制限を超えると行が捨てられる。既定は unit ごとに 30 秒 10000 件で、journal の空き容量に応じて最大 6 倍(空き 64GB 以下なら 5 倍、毎秒約 1700 件)。
- ログイン攻撃の検知と組み合わさる:
  - guard-worker の `journalctl` が全行を JSON に変換するので、子プロセスの CPU も増える(worker 本体ではないので `top` を見ないと気づかない)。
  - レート制限でログイン失敗の行が落ちると ban が効かなくなり、bench が失敗する。負荷が上がる(= スコアが伸びる)と突然起きるので、原因がアプリの改善ではなくログにあると気づく必要がある。

### 改善の例
- 罠: 定番の対処として `ISUREAL_LOG_LEVEL=info` に切り替えると、ログイン失敗の行も出なくなり、ban が効かなくなる(bench は「soft ban の反映が遅すぎます」で失敗する)。
- 不要なログを消す、またはログイン失敗の行を info 以上で出すようにアプリを直してからレベルを上げる。製品を止めてアプリに組み込むならこの依存は消える。
- レート制限は unit の `LogRateLimitIntervalSec=` / `LogRateLimitBurst=` や `journald.conf` で緩められるが、ログの量が多いままだと CPU を食い続ける。

### 決めること
- 較正: 初期状態では制限に届かず、ある程度スコアが伸びた負荷で超えるよう、1 リクエストあたりの行数を調整する。上限はディスクの空き容量で変わるので、初期データとディスクサイズを決めてから較正する。
- 全言語の実装で同じ量・同じ形式のログを出す。

## 本番(EC2)の構成
前提:
- 全インスタンスを同一リージョン・同一 AZ に置き、地域間の遅延と帯域はルーターの tc でエミュレートする。
- 参加者の AWS アカウントに CloudFormation で構築し、コストも参加者が負担する。app と db は large(2 コア)。ルーターも大きくしない。
- large の ENI 上限は 3 本なので、ルーターの ENI は 2 本(データ用 + パブリック・制御用)で成立させる。現在の検証用構成(`provisioning/aws`、サーバーごとに VPC、ルーターの ENI 5 本、`c8in.4xlarge`)はコスト面から本番では使えない。

### 1. ネットワーク構成
```
VPC (チームごと)
├─ app1 subnet ─┐  ルートテーブル:
├─ app2 subnet ─┤    他の 3 サーバーのサブネット → router data ENI
├─ app3 subnet ─┤    0.0.0.0/0 → IGW(外向き通信のみ)
├─ db1  subnet ─┘
├─ router data subnet   ← local ルートのみ
├─ router public subnet ← EIP。Portal との接続と bench の入口
└─ eice subnet          ← EC2 Instance Connect Endpoint(ルーターを経由させない)
```
- サーバー間の通信はサブネットのルートテーブルでルーターのデータ用 ENI に送られ、ルーターは同じ ENI から宛先へ折り返す(VPC 内のミドルボックスルーティング)。転送先は OS ではなく VPC が決めるので、参加者が経路を変えても迂回できない。同一サブネット内には効かないので、サーバーごとにサブネットを分ける。
- ルーターは NAT しない。

### 2. ルーターの変更
現在の実装は「サーバーごとに別インターフェース」前提なので変更が必要。
- tc(`router/internal/netcontrol/tc.go`): データ用 ENI の egress に HTB を 1 つ置き、送信元・宛先 IP の組でクラスを分ける(地域間: netem 片道 100ms・200Mbps、app1 ↔ db1: 0ms・1Gbps)。Envoy → アプリ(送信元がルーター)は既定クラスで遅延なし。
- netem の `limit` を指定する。既定の 1000 パケットでは地域間経路(200Mbps × 片道 100ms ≒ 2.5MB、約 1700 パケット)があふれて 200Mbps まで出ない。
- nftables: 同じデータ用 ENI で折り返す転送(送信元・宛先ともサーバーのサブネット)を許可する形に変える。
- `send_redirects=0`(同一インターフェースへの転送で ICMP リダイレクトを出さない)。source/dest check は無効。
- `provisioning/aws`(topology.ts、index.ts、network.ts)をサブネット単位に変え、compose / Vagrant も同じ折り返し構成に揃える。

### 3. 迂回経路を塞ぐ
- サーバーのセキュリティグループは、他サーバーのサブネット、ルーター、EIC Endpoint からの着信のみ許可し、インターネットからは一切受けない。パブリック IP 経由のサーバー間接続(ssh ポートフォワードでの遅延回避など)もこれで塞がる。
- サーバーからルーターのパブリックな入口を拒否する。開いていると `app1.<domain>` に `X-Country-Code: JP` を付けて Envoy 経由で送れば、同一リージョン扱いで遅延なしのサーバー間通信になる。サーバーのサブネットの NACL でルーターの EIP とパブリック用サブネットを拒否する(どちらも固定なので静的なルールで済む)。
- IPv6 は付けない。
- VPC 提供の DNS(`169.254.169.253`)に切り替えればルーター DNS のレート制限を回避できるが、`/etc/hosts` に書く解法も許される想定なので塞がなくてよい。扱いは決めておく。
- 参加者の AWS 認証情報をサーバーに置けば、SSM や EIC Endpoint のトンネルでルーターを迂回できる。外部 VPS の中継と同様に、レギュレーション(走行中に競技環境外のリソースを経由しない)で禁止する。

### 4. ルーターの性能
- ネットワーク最適化型(c6in / c7gn / c8in など)の large から始め、足りなければ xlarge。バーストではなくベースライン帯域と PPS で選ぶ。
- 1 本の ENI をサーバー間転送(地域間 200Mbps × 10 方向、app1 ↔ db1 1Gbps)と Envoy → アプリで分け合う前提で見積もる。
- Envoy、tc、conntrack が 2 コアに載るので、SSE の同時接続が多い状態で負荷試験する(`nf_conntrack_max`、Envoy の接続上限、ファイルディスクリプタ上限)。

### 5. AWS の既定クォータ
緩和申請を前提にせず既定値に収める([Amazon VPC quotas](https://docs.aws.amazon.com/vpc/latest/userguide/amazon-vpc-limits.html))。
- VPC は 1 リージョン 5 個(1 チーム 1 VPC なので既存が 4 個までなら構築できる)。
- Elastic IP は 1 リージョン 5 個。上限による構築失敗はありがちなので、EIP はルーターの 1 個だけにし、サーバーは自動割り当てのパブリック IPv4 を使う。サーバーのパブリック IP は外向き通信(パッケージ取得、agent → ポータル、SSM)専用なので、アドレスが変わっても追従は不要。
- NACL、サブネット、セキュリティグループのルール数は既定値に収まる。

### 6. サーバーへのログイン
- ssh をインターネットに直接開けない。SSM Session Manager と EC2 Instance Connect Endpoint(EIC)の両方を用意する。どちらも追加コストはほぼなく、CloudFormation だけで構築できる。ポータルにはインスタンス ID を表示する。
  ```
  # SSM(AWS CLI + session-manager-plugin)
  Host isucon-app1
    HostName i-xxxxxxxx
    ProxyCommand aws ssm start-session --target %h --document-name AWS-StartSSHSession --parameters portNumber=%p

  # EIC Endpoint(AWS CLI v2)
  Host isucon-app1-eice
    HostName i-xxxxxxxx
    ProxyCommand aws ec2-instance-connect open-tunnel --instance-id %h
  ```
- 制約が違うので両方用意して使い分けられるようにする:
  | | SSM | EIC Endpoint |
  |---|---|---|
  | サーバー側 | ssm-agent、外向き HTTPS、名前解決 | sshd のみ |
  | 同時接続数 | EIC ほど厳しくないはず(要確認) | エンドポイントあたり 20(緩和不可、チームで共有) |
  | 接続時間 | 設定次第 | 既定 1 時間 |
- SSM: インスタンスのロールに `AmazonSSMManagedInstanceCore`。パブリック IP から出るので VPC エンドポイント(時間課金)は不要。ルーター DNS のレート制限で SSM が止まらないよう、`*.amazonaws.com` はレート制限の対象外にするか VPC の DNS へ転送する。
- EIC Endpoint: VPC に 1 つ(1 VPC 1 個・1 アカウント 5 個まで、緩和不可)。専用サブネットに置き、ルーターを経由させない。同時接続数 20 は VS Code のリモート接続や LLM エージェントで届きうるので、`ControlMaster` による多重化を案内する。
- サーバー間の ssh(デプロイの rsync など)は private IP でルーターを経由し、地域間の遅延がかかる(意図どおり)。
- 復旧手段は用意しない。ログイン経路は通常の運用では壊れないので、壊して入れなくなったら CloudFormation で構築し直すよう案内する。
