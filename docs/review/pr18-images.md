## 現状の実装(39bb251)
- `GET /api/images/:imageId?exp=&sig=` は署名だけで認可する。セッションと地域のミドルウェアはなく、全地域で配信する。フロントエンドは `<img src>` で参照する。
- 署名は、画像の持ち主の `secret_key_hash` を鍵にした HMAC-SHA256 を 1000 回連鎖させたもの。持ち主は、投稿なら投稿者、RealMoji ならリアクションした人、プロフィールなら本人。有効期限は 24 時間。
- 処理の順は「期限 → 鍵の取得 → HMAC → 生死の確認」。失敗はすべて 403 `image_forbidden`、`Cache-Control: no-store`。
- 無効化は毎回の生死の確認で行う。削除、差し替え、退会で全地域から即座に 403 になる。
- 閲覧者ごとの認可(ブロック、公開範囲)は見ない。配布済みの URL は期限まで有効。
- 元の決定([pr18.md](pr18.md))との差: 24 時間の期限がある(決定は「期限に頼らない」)、URL に地域がない、鍵導出が 1000 回(決定は数万回)。

## 画像を DB から追い出す方法
ルーターは国→地域で固定なので、画像を各サーバーのローカルに置くと、他の地域の利用者に配れない。

| 方式 | 得失 |
|---|---|
| A. 書き込み時に全台へ複製 | 読み込みは常にローカル。書き込みのたびに地域間リンクを 2 本通り、ディスクは 3 倍 |
| B. ローカルになければ持ち主から取る(nginx の `try_files` → `proxy_pass` ＋ `proxy_cache`。持ち主は画像 ID に埋め込む) | 書き込みはローカル。地域をまたぐのは見られた画像の初回だけ |
| C. 1 か所に集約(1 台か NFS) | DB の負荷は減るが、地域間の遅延は残る |
| D. DB に残して各台でキャッシュ | B と同じ効果で、初期データ(約 16 GB)の移行が要らない |

どの方式でも鍵の取得と生死の確認は asia の DB へ行く。配信を nginx に任せ(`X-Accel-Redirect`)、判定をキャッシュして初めてローカリティが効く。

## キャッシュの分け方
画像は不変(差し替えは新しい ID)で、削除は一方向(復活しない)。

| 判定 | キー | 寿命 |
|---|---|---|
| 中身 | imageID | 無期限 |
| 死んでいる | imageID | 無期限 |
| 生きている | imageID | 5 秒未満(削除の猶予時間) |
| 署名の正否 | (imageID, exp, sig) | 無期限(期限は毎回比べる) |

- 5 秒ごとに取り直すのは生死の判定だけで、本体は取り直さない(nginx なら query を外した `proxy_cache_key` ＋ `auth_request`)。
- 処理の順を「期限 → 生死 → 署名 → 中身」にすると、削除済み画像で HMAC を計算しない。
- 403 を URL 単位でキャッシュしてはいけない(不正な URL で汚染される)。キャッシュするのは imageID 単位の「死んでいる」判定。
- 生死の確認をさらに安くするには、持ち主への軽い問い合わせ、削除時の push による無効化(届かないときの安全策が要る)、生死の列だけの論理レプリケーションがある。

## 現状の bench(587af67)の画像アクセス
- 利用者は自分の地域のサーバーにだけ届く。投稿直後に自分の画像を取得し、閲覧では見えた投稿の画像を 1 枚取得する。思い出を見返す利用者は履歴全体から一様に古い画像を取得する。
- 友達関係はほぼ地域内なので、他の地域への画像配信は少ない。
- 削除済み画像への要求は、閲覧と削除が競合したときしか起きない。
- 走行中の投稿画像と RealMoji 画像はそれぞれ 1 種類(64×64 と 32×32)。
- プロフィール画像、退会、認定アカウントの走行中の投稿は扱わない。

## bench の画像を一意にする
同じバイト列だと、中身のハッシュによる重複排除で走行中の画像がほぼゼロコストになる。64×64 では帯域の工夫も効かない。

### 生成方法: ベース画像 ＋ 決定的な変換 ＋ 文字
フロントエンドで見て不自然でないこと、JPEG の品質とサイズの関係が実際の写真に近いことを狙う。

- ベース画像は約 200 枚の写真(AI 生成でもよい)。
- seed から、ベース画像の選択、切り出しの位置と拡大率、左右反転、色のわずかな変化、隅のインセット(BeReal の「インカメラ」)を決める。撮影日時やユーザー名を Go fonts(BSD)でスタンプする。
- 一意性は画素で作る(COM や APP セグメントは EXIF 除去(P-108)で崩れる)。変種どうしの差は判定の許容誤差より十分大きくする(切り出し位置をずらすなど全画素が変わる変換を必ず入れる)。そうしないと、別の変種を返しても判定を通ってしまう。bench の自己テストで確かめる。
- 初期データの画像も同じ生成器で作る(`dataset.renderJPEG` を置き換える)。

### 変種の事前生成と見積もり
bench を軽くするため、変種を事前に作り、走行中は読んで送るだけにする。

- 1 回の走行の上限(既定のラチェットで asia が毎日 Buzz した場合): 投稿 約 3 万、RealMoji 最大 約 9 万。較正までは上位チームで投稿 5,000〜10,000 と見ておく。
- 容量(品質 90 の概算): 投稿 640×640 が約 120 KB、480×480 が約 70 KB、RealMoji 160×160 が約 10 KB。各 3 万枚で、640 なら約 4 GB、480 なら約 2.5 GB。
- bench ホスト上のデータファイル(1 ファイル＋インデックス)から `pread` で読む。インデックスには SHA-256 と近似一致用の特徴量を事前に計算して持たせる。
- 使い切ったら先頭に戻る(最上位チームで少し重複排除が効く程度は許容する)。
- 前回の再圧縮結果を使い回されないよう、プールは 1 回分の 2〜3 倍(5〜10 GB)にし、走行ごとの seed で使う範囲と順番を変える。
- サイズはラチェットの較正後に確定する。

## 画像の同一性の判定(近似一致)
完全一致にすると、再エンコードで品質を下げてサイズを減らす作戦が取れない。CPU と帯域のトレードオフを題材にするため、近似一致にする(P-108)。

1. SHA-256 が一致すれば、デコードせずに合格。
2. `image/jpeg` でデコードでき、寸法が完全一致すること(縮小は認めない)。
3. 輝度(Y)の PSNR が全体で閾値以上(例: 35 dB)、かつブロック(例: 16×16)ごとの最小値も閾値以上(一部の塗りつぶし対策)。
4. 比較にはインデックスの特徴量(8×8 ブロックの平均と分散)を使う。分散の比で極端なぼかしも検出できる。負荷走行中はサンプリングし、事前検証では全数を検証する。

トレードオフを成り立たせる条件:
- bench は品質 90〜95 で送り、閾値は「品質 70〜80 への再圧縮なら通る」位置に較正して公開する。
- 再圧縮は 1 回、配信は何度も起きるので、放っておけば常に再圧縮が得になる。CPU が効く場面として、通知直後の投稿の集中(同期の再圧縮はゲート通過に直撃する)、投稿直後の自分の画像の取得、初期データ(約 16 GB)の再圧縮の時間を使う。地域間の帯域上限を入れると、帯域側の価値がはっきりする。

## 認定公開アカウントの通知と即削除
現状、認定アカウントの投稿通知はない(`bench/spec-bench.md` §12 の未実装)。P-111 を入れると次の負荷が作れる。

- **地域をまたぐファンアウト**: 認定アカウントはほぼ asia にいて、フォロワーは全地域にいる。同じ画像に一斉に要求が来るので、B のキャッシュと同時取得の集約(`proxy_cache_lock`)が効く。通知の書き込みのファンアウトも題材になる。
- **投稿してすぐ削除する**(誤投稿): 削除済み画像への要求が大量に走る。確認の順番と「死んでいる」判定のキャッシュが効き、他の地域のキャッシュを 5 秒以内に無効にできるかも試される。

## 拡散された URL への外部アクセス
署名付き URL は共有リンクなので、一度拡散されると、アプリ以外からもセッションなしで、どの国からでも長期間要求が届く。削除後も届く。

- 古い画像のロングテールが全地域に届くので、長期間保持するキャッシュと nginx だけで完結する配信が効く。削除済み画像への要求も恒常的になる。
- bench は開いたループ(一定レート)で送り、レートを人気(フォロワー数、レベル、Buzz)と連動させる。
- 加点はしない。判定は、生きていれば中身が一致、削除から 5 秒を過ぎていれば 403、期限切れなら 403。
- 署名を改ざんした要求は DoS に近くなるので、入れないかごく少量にする。

## `Cache-Control` を仕様で許可する
`no-store` をやめ、一定期間のキャッシュを仕様で許可する。bench が途中のキャッシュを模擬して、有効期間内の同じ URL への要求を省けば、適切なヘッダーが報われる。ただし、共有キャッシュは削除後も `max-age` の間は画像を出し続け、5 秒ルールと衝突する。

| 方式 | 効果 | 削除との整合 |
|---|---|---|
| ① `max-age` の上限＝5 秒 | 通知直後の一斉アクセスをまとめられる | 成り立つ |
| ② 上限を長くする | ロングテールも減る | 共有キャッシュ経由では最大 N 秒見えうると明記する |
| ③ `no-cache` ＋ `ETag` | 要求は減らないが、304 で本体の転送を省ける | 成り立つ |

案: ① ＋ ③。期限が切れたら ETag(画像 ID)で再検証し、生きていれば 304 を返す。`public` でよい。

## 未決事項
- URL の有効期限: 24 時間だと、拡散から 1 日たった要求は安い 403 で終わる。期限を長くするか、bench が期限内の URL だけを送るか。
- URL に地域を固定するか。鍵導出の回数。
- 削除された投稿の通知を取り消すか。フォロワーと外部の要求が、削除から何秒後に取りに行くか。
- 削除済み画像の 403 と外部の要求を、読み取りの p99 と地域の観測窓に数えるか。
- P-111 の規模(認定アカウントの人数と配置、フォロー数、即削除の確率、通知の許容時間)。削除済み画像の比率は、問題の重心がずれない程度に抑える。
- `Cache-Control` の上限を超えたときの扱い(失格か、丸めるか)。bench が模擬するキャッシュの種類。
- GDPR 補強案を採る場合に、他の地域の利用者の画像を複製・キャッシュしてよいか。
- 地域間の帯域上限を入れるか。
- ベース画像の入手元と、RealMoji とプロフィール画像に何を使うか(人物の実写は肖像権の扱いが要る)。
- 近似一致の閾値と、投稿画像のサイズ。
