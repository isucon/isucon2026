## 1. 結論

現状の実装とベンチマーカーの組み合わせは、このままだと ISUCON の問題として成り立ちにくい、
というのがレビュアーの見立てである。理由は次のとおりで、いずれも開発途上のいま方向を揃えて
おきたい話として挙げている。

- スコアがアプリケーション性能でほとんど動かない。1 サイクル約 7 秒のうち 5.5〜6.5 秒が
  ベンチ側の固定待ちで、無限に速いアプリケーションでもスコアは約 30% しか伸びない。
- ベンチは開発途上で、検証項目が揃っていないことは認識済みである。現時点では安全性に
  関わる仕組み（OpenAPI 検証、サニタイザ隔離、冪等性、可視性ルール）を消しても通るが、
  これは整備で解消する。本文書の論点は、整備するときに何を必須にするか（P-108）である。
- テーマである「リージョン」が、アプリケーションにもベンチにもまだ現れていない。
  ベンチは `asia` しか使わず、アプリはどのリージョンで動くかに依存しない。
- 仮想時計が複数 API ホストの構成と両立せず、ベンチの固定待ちの原因にもなっている。
  プリフォーク型の言語（PHP、Ruby、Perl）では参考実装の移植時に同期方式が言語ごとに変わり、
  参考実装間の性能差になる。
- 一方で、ベンチを整備しても検証できない制約がある。仕様が MUST にしている bcrypt コストは
  外形観測できず、運営は走行後に DB を検査できないので、追試でしか担保できない。整備で
  解消する項目とは分けて扱いたい（補助資料 §1.3、P-110）。

負荷モデルと競技環境を見直し、開発途上のベンチに載せる検証項目をこの段階で決めておきたい。
§3 がその提案である。

## 2. 判断基準: ナラティブ

すべての提案は次のナラティブに照らして評価している。

> 前任者が各リージョンにサーバーを 1 台ずつ置き、すべてを東京のデータベースに向けて去った。
> CEO は誰も理解していないマネージドエッジルーターを契約した。8 時間後に負荷がやってくる。

このナラティブに従った実装やアプリケーションの設計は受け入れられる。フィットしない前提
（現実のサービスに存在しない仕組み、ベンチの都合でしか説明できないルール）は参加者に違和感
を与えるので、避けるか、ナラティブ側に理由を用意する。

**競技の主眼**: ISUCON は 1 位を競う競技である。問題は上位の強いチームを弁別できることを
最優先にし、低スキルの参加者の体験は設計の主眼にしない。中位の参加者が LLM で多少改善できる
ことは想定するが、それも主眼ではない。この前提から次が導かれる。

- 1 台の CPU 効率で勝てる問題は、LLM が最も得意な領域（インデックス、クエリ書き換え、
  キャッシュ、ミドルウェア除去）で決まる。3 リージョンを維持する最大の理由はこれである。
  リージョンを捨てた案や通知グループとしてだけ残す案は、勝ち筋が 1 台チューニングに収束する
  ので採らない。
- 3 台を LLM の観測対象にできるか（ssh を配る、3 台のログとメトリクスを集める）は弁別点と
  して残す。この道具のハードルは下げない。ベンチ結果は `pass` と合計点のみ（D-005 維持）、
  nginx はデフォルトのまま、ルーター UI にダッシュボードは付けない。3 台間の鍵なし ssh と
  リージョン入りのホスト名は例年どおりの環境整備として用意する。
- キャリブレーションの目標は「LLM が 1 台チューニングを極めた構成の上限を、人間のチームが
  ステージ 1 に到達したスコアより下に置く」こと、および「上位に頭打ちを作らない」こと。
  レベル表は最強チームの想定到達点より上まで用意する。

**補強案（GDPR）**: 法務が GDPR 対応として「ユーザーのデータは所属リージョンのエンドポイント
からしか提供しない」という社内データ所在地ポリシーを定め、全リージョンに一律適用した、と
いう筋書きを足す。海外サーバーの存在、リージョン不一致の拒否、リージョン移行、退会後の
パージに一つの理由が付き、ルーターは「GDPR 対応ジオルーティング」として契約したことになる。
現実の GDPR は域内保存を義務づけていないので、マニュアルには法解釈ではなく社内ポリシーとして
書く。詳細は補助資料 §1.1.1。

## 4. 想定される改善ステージ

0. 単一ホストのチューニング（通常の ISUCON）。
1. リージョンごとのリードレプリカやキャッシュ、画像のローカリティ、ルータールール。
2. リージョンごとのシャーディングとファンアウト。ステージ 3 と一緒に解く必要がある。
3. リージョン間のやりとり（他リージョンの友人、公開フィード、ブロック）。
4. 同期移行。シャーディングした実装にとってのみ難しい。

番号は補助資料 §4 と参考資料の層（層 1 = ステージ 0、層 2 = ステージ 1、層 3 = ステージ 2〜4）
に対応する。

各ステージで参加者が具体的に何をするかは[参考資料: チューニング手法](design-competition-environment-tuning.md)。

## 5. 主な未決事項

- リージョン間帯域の上限を設けるか。エミュレートなので `tc` で入れられる。
  （レイテンシは同一リージョン・同一 AZ の EC2 上で netem によりエミュレートすると決定。
  補助資料 P-103。）
- on-time 締切 N の初期値（5 秒から、3〜10 秒で較正）と `onTimeSeconds` 省略時の既定値。
- P-110 の採否。採らない場合の代替（セッション済みユーザープール、コスト 10、追試項目化）。
- レベル表の形式（総ユーザー数とリージョン構成比）と、レベル判定の信号。
- P-111 の規模（認定アカウントの人数と配置、新規ユーザーあたりのフォロー数、通知到達時間の許容値）。
- P-112 の構造の平坦化（5 層をハンドラに SQL 直書きへ）をやるか。約 8,000 行の書き直し。
- `client_region` 不一致の拒否ステータス（403 / 421 / 451）と、GDPR 補強の採否。
- ベンチの観測点を 3 つ持つか、1 つでルーターに遅延を注入させるか。
- レスポンスヘッダを検証するか、対象外と宣言するか。

全リストは補助資料 §5。採用時に変更が必要な仕様・データモデル・OpenAPI・実装の一覧は
補助資料 §6。
