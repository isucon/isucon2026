# ISUReal レビュー 別案: 東京の DB を独立させた 4 台構成

**レビュアー**: fujiwara

**位置づけ**: [`design-competition-environment.md`](design-competition-environment.md)（要点）と同
[`-appendix.md`](design-competition-environment-appendix.md)（補助資料）の P-104（初期デプロイ状態）に
対する別案。決定事項ではない。採用する場合は P-103、P-104、P-105 と参考資料の「3 台」の記述を

## 1. 動機: 3 台それぞれをリージョン単位でオンメモリにする解法

P-109 のレバー（注入レイテンシ、リージョンごとの SLO、帯域）はすべて「リージョン内で応答して
いるか」を見る。したがって「各リージョンの 1 台を、DB を使わずオンメモリで完結させる」構成は
すべてのレバーを満たす最上位の解法になる。必要な書き換え（保存層の全面置き換え、初期データの
ローダー、メタデータの相互複製、投稿起点の通知の転送、同期移行、ディレクトリ）は大きいが、
LLM のコーディング力を前提にすると 8 時間で現実的な選択肢になる。

この解法は P-104 の 3 台構成（asia のホストにアプリと DB が同居）では、DB 併用のどの設計よりも
処理能力で上回る。1 リージョン 1 台なので、DB 併用側に「状態を共有したままアプリを横に増やす」
余地がなく、対抗手段がない。

## 2. 別案の構成

| リージョン | ホスト | 初期状態で動くもの |
|---|---|---|
| asia | `app-asia` | アプリ、nginx |
| asia | `db-asia` | PostgreSQL（既定値のまま）、`pg_dump` の timer |
| europe | `app-europe` | アプリ、nginx |
| america | `app-america` | アプリ、nginx |

- 全アプリの `ISUREAL_DATABASE_URL` は `db-asia` を指す。ルーターの初期ルールは変更なし
  （`client_region -> 同一リージョンのアプリ`）。`db-asia` は upstream に入っていない。
- ホスト名が役割を語るので、P-105 の「稼働中の設定を見れば分かる」がそのまま成立する。
- `db-asia` にアプリを載せるか、画像配信を寄せるかは参加者の判断。
- 4 台のスペックは揃えなくてよい。「DB だけ必要があるので強い」も「必要がないので弱い」も
  ごく自然な構成で、全チーム同じなら公平性の問題はない。`db-asia` のスペックは、DB 併用の
  横展開とオンメモリのどちらを有利にするかを決める較正のつまみになる（§4）。

## 3. なぜ対抗策になるか

| 観点 | 3 リージョンオンメモリ | DB 併用（ローカル DB + プロセス内キャッシュ） |
|---|---|---|
| asia の状態のある経路 | 1 プロセスに閉じる。2 台目を使うには asia 内でさらにシャーディングが要り、フィードが asia 内のシャードをまたぐ | `db-asia` にもアプリを載せ、DB を共有したまま asia を 2 台に広げられる。ルーターの重み付き upstream で割る |
| 2 台目の使い道 | 状態のない仕事（画像配信とサムネイル、サニタイズ、`push-sender`）を寄せる | 同上に加えて、状態のある経路も広げられる |
| クラッシュ | asia の最大シャードが落ちると走行が正しさで終わる | 再起動で戻る |
| 1 リクエストの処理時間 | 数十〜数百 µs | ローカル DB で数往復。チューニング後は DB の割合が 3〜5 割 |

asia はユーザーの大半を占め、ラチェットで最も多くのエージェントが乗るので、最上位レベルで最初に
飽和するのは asia である。そこで「2 台のアプリ + 共有 DB」が「1 台オンメモリ」と同等以上の
総処理量になれば、2 つの最上位解法が並び立つ。地域をまたぐ複製、投稿起点の通知、同期移行という
難所はどちらにも共通で、弁別の主戦場は変わらない。

## 4. 成立条件（較正）

- 最上位レベルで asia の負荷が 1 台のオンメモリの処理能力を超えるところまでレベル表を伸ばす。
  閉ループでは 1 エージェントの処理量は往復時間で頭打ちだが、エージェント数が増えれば総量は
  サーバー能力に当たる。ここまで伸ばさなければ、両者の差は 1 エージェントあたりの処理時間の差
  （1.5〜2 倍程度）に戻り、オンメモリが有利のままになる。
- チューニング後の DB 往復のオーバーヘッドが小さいこと（接続の使い回し、プリペアド、往復数の
  削減、プロセス内キャッシュ）。これは参考資料の層 1〜2 の作業そのもの。
- `db-asia` のスペック。大きくすれば「DB を共有して asia を 2 台に広げる」が有利になり、小さく
  すれば DB が先に飽和してオンメモリが有利になる。どちらの最上位解法をどれだけ報いるかを、この
  1 台のスペックで調整できる。

## 5. ナラティブとの整合

「前任者が各リージョンにサーバーを 1 台ずつ置き、すべてを東京のデータベースに向けて去った」は、
DB が独立した 1 台である方が素直に読める。前任者が各地域に置いたのはアプリで、DB は最初から東京の
別の箱、という説明で GDPR 補強（「DB は東京のまま次のフェーズへ」）とも一致する。アプリのホストに
DB を同居させていたのは例年の「3 台同一」の慣習で、物語上の必然はない。

## 6. 副作用と決めること

- 初期状態で asia が 2 台になるので、「全部 asia へ」の単一リージョン戦略も少し強くなる。海外の
  SLO とレイテンシのレバーで抑える構造は同じだが、較正の前提が変わる。
- チームあたり 4 台になり、環境コストが増える。`db-asia` のスペックは物語に合わせて決めてよく
  （前任者が DB だけ大きくした、あるいは小さいまま）、それがそのまま較正の前提になる。
- asia のアプリから DB への往復も Unix ソケットではなく網越しになり、数百 µs 増える。「往復を
  減らす」動機が asia にも乗り、海外との差は程度の問題になる。
- detune の置き場所: `db-asia` に `pg_dump` の timer と肥大した通知テーブル、アプリホストに
  ログ設定と nginx の gzip、`AGENTS.md` はリポジトリ。
- 採用時の書き換え: P-103（「3 台のリージョンサーバー」を「アプリ 3 台 + DB 1 台」に）、P-104、
  P-105（ホスト名）、参考資料と detune の「3 台」の記述、ルーターの upstream 定義。
