# ISUReal レビュー 参考資料: 初期実装に意図的に残す遅さ

**レビュアー**: fujiwara
**日付**: 2026-09-06
**位置づけ**: [`design-competition-environment.md`](design-competition-environment.md)（要点）と同 [`-appendix.md`](design-competition-environment-appendix.md)（補助資料）の
参考資料。P-112（初期実装を素朴にする）の前提で、初期状態にさらに残す遅さ（detune）の候補を
整理したもの。決定事項ではない。提案に含まれているもの（exec ごとの `push-sender`、bytea 画像、
毎リクエストの認証クエリ、直列の push 配信、worker の 1 秒ポーリングとバッチ 50、並行性制御の
欠如、Memories の `to_char` 検索）は除く。

---

## 1. 選定の基準

- ジュニアが自然に書く、または前任者が残しそうな形であること。
- 全言語の参考実装で同じに再現でき、特定の言語だけ有利・不利にならないこと。
- 正しさを壊さないこと。直すと壊れる方向の遅さは入れない。
- 基準レベル（`asia` のみ、少数ユーザー）はエラーなしで通ること。
- できれば地域テーマ（東京の DB、地域間レイテンシ、帯域）に効くこと。
- ディスク使用量が単調増加する仕込みは入れない。気づきにくい割に、埋まった時点で全滅するので
  弁別ではなく運になる。ログとダンプは上限付きのローテーションで固定サイズにし、WAL の保持を
  増やすもの（放置されたレプリケーションスロット、失敗する `archive_command`）は採らない。
- ルーターやゲートウェイ側の遅さは参加者が直せないので入れない。特定言語だけ不利になるもの
  （GC 設定、ランタイム固有のバッファリング）も入れない。
- OS と nginx は既定値に近く保つ。あえて変な設定が入っていると不自然になる。入れるのは、前任者が
  気を利かせたつもりで理解が浅かった設定（Brotli 最高圧縮）だけとし、既定値が足を引っ張るもの
  （systemd の `LimitNOFILE` 既定、ソケットのバックログ、エフェメラルポートの範囲）はそのまま残す。

## 2. LLM に直させるときの段階

「どこを見れば分かるか」で 4 段階に分かれる。段階が上がるほど道具、観測、判断が要り、弁別力が
上がる。段階 1 だけの項目は上位チームが監査で全部見つけるので弁別にならず、数を絞る。

| 段階 | 必要な作業 | 弁別力 |
|---|---|---|
| 1. 監査 | ssh で入って設定ファイル、systemd の unit と timer を読む | ほぼなし。「監査を思いつくか」だけ |
| 2. 負荷下の観測 | ベンチを走らせながらログとメトリクスを集め、症状から原因へたどる。結果は `pass` と合計点だけなので仮説ごとに A/B 走行を重ねる | 主役 |
| 3. 仕様と製品の判断 | 仕様を読んで機能を足す、セキュリティを下げる判断をする | agent は躊躇しやすい |
| 4. 多ホストへの適用 | 3 台に配り、走行中に再起動せず、再起動後も残す（追試で戻ると失格）。resolved や netplan で ssh を失わない | 事故が起きやすい |

段階 1 の項目を段階 2 に上げる工夫: 定期ジョブは cron ではなく systemd timer にし、実行ユーザーは
競技用の `isucon` とは別の前任者のサービスユーザー（例: `isureal-ops`）にする。`crontab -l` では
出ず、`systemctl list-timers` か `ps` で見る必要がある。PostgreSQL は既定値のままなので隠す必要が
なく、既定値が合わない理由を負荷下で理解する作業自体が段階 2 になる（§3.1）。

## 3. 候補一覧

A はアプリのコードを読めば分かるもの、B は環境・データ・負荷を観測しないと分からないもの。

### A. コードを読めば分かる（段階 1）

| 案 | 内容 | 効き | 備考 |
|---|---|---|---|
| A-1 | リクエストごとに DB へ接続する（プールなし） | 接続確立は 3 往復前後。海外ホストで処理前に約 300 ms | PHP / Perl の素朴な実装は本来こう動く。全言語を揃える |
| A-2 | 認証のたびに `login_sessions.last_used_at` を UPDATE | 全リクエストが書き込みになり、読みを地域に寄せても東京への往復が残る | API には出さないので外しても検査は通る。ステージ 1 の入口の罠 |
| A-3 | フィードの N+1（投稿者プロフィールを別クエリ） | 50 件で 50 往復 | 件数や自分の RealMoji まで別にすると海外ホストで 20 秒になるので 1 種類に絞る |
| A-4 | 画像 GET のたびに SHA-256 を再計算 | バイト数に比例した CPU | 「配信前の整合性確認」 |
| A-5 | 未読通知数を全応答に含める（`COUNT(*)`） | 通知はユーザー数 × ウィンドウ数で増える | 部分インデックスがないと顕著 |
| A-6 | 友達の友達をアプリ側で計算 | 友達ごとに一覧を引き、巨大な `= ANY(...)` | 直し方が明快 |
| A-7 | 投稿トランザクション内で 1 件ずつファンアウト | 認定アカウントの投稿応答がフォロワー数に比例 | P-111 に記載済み |
| A-8 | インデックスの張りすぎ（index shotgun） | 通知と push 試行に 10 本以上、重複する複合索引、キャプションと表示名に trigram の GIN。ファンアウトと投稿の INSERT が索引本数分の btree 更新になり、WAL も増えて B-13 と相乗 | 数が多いことはスキーマで分かる（段階 1）が、どれを消してよいかは `pg_stat_user_indexes` と `EXPLAIN` を見ないと決められず、誤って消すと読み取りが遅くなる（段階 2）。歴代は「足りない」だけで「多すぎる」はなかった。「遅いと言われるたびに足した」「AI が提案した索引を全部入れた」 |
| A-9 | エクスポートをメモリ上で組み立て、JPEG を deflate する（P-113） | 数百 MB をプロセスが抱え、同時数人で OOM に近づく。圧縮できない JPEG に CPU を使う | 直し方はストリーミング書き出しと store（無圧縮）。ジュニアの ZIP ライブラリの使い方として典型 |
| A-10 | RealMoji の顔写真とプロフィール画像を JSON に base64 で埋め込む | 投稿詳細やフィードの応答が数百 KB になり、帯域上限に直撃する | 「毎回画像を GET しないために埋め込んだ」という動機は自然（条件付き GET を知らない）。直し方は URL に戻して A-11 を直すこと |
| A-11 | 画像にも `Cache-Control: no-store` を付け、`ETag` を出さない | 同じ画像を毎回全量転送する | 前任者が安全ヘッダを全 API に一律で付けた結果。画像は内容が変わらないので `ETag` と private キャッシュを許してよい。過去の ISUCON にも出ている通常の運用設定で、ベンチ側が条件付き GET を正しく扱うことが前提（§7） |

採用候補: A-1、A-2、A-3、A-8、A-9、A-10、A-11。

### 3.1 PostgreSQL: 既定値のままで足を引っ張るもの

設定はすべて既定値のままにし、既定値の想定（1 ユーザーの開発機、HDD、小さな行）と競技の負荷の形
（bytea 画像の一斉書き込み、3 台からの接続、1 件ずつの INSERT、複雑な結合）が食い違う箇所を狙う。
参加者の作業は「設定を直す」ではなく「なぜ既定値が合わないかを理解する」になる。

| 項目 | 既定値 | なぜ足を引っ張るか | 気づき方 |
|---|---|---|---|
| TOAST の圧縮 | `default_toast_compression = pglz`、bytea は STORAGE EXTENDED | 圧縮できない JPEG を INSERT のたびに圧縮しようとする | プロファイル。`SET STORAGE EXTERNAL` で直る |
| TLS | Ubuntu のパッケージは `ssl = on`（snakeoil 証明書）、libpq は `sslmode=prefer` | 何も設定しなくても DB 接続が TLS になり、A-1 と地域間 RTT に相乗 | `pg_stat_ssl`、接続時間。`sslmode=disable` か接続の使い回し |
| 接続の仕組み | 接続ごとに backend を fork。プーラーは同梱されない | A-1 の毎回接続が fork のコストになる | `pg_stat_activity` の backend_start |
| `max_connections` | 100 | 3 台がプールを広げて RTT と戦い始めると当たる | `too many connections` |
| チェックポイント | `max_wal_size = 1GB`、`checkpoint_timeout = 5min` | 投稿スパイクの bytea 書き込みで WAL が一気に増え、ウィンドウごとにチェックポイントが走る | ログの警告、`pg_stat_bgwriter` |
| 同期コミット | `synchronous_commit = on` | ファンアウトの 1 件ずつの INSERT が毎回 WAL の fsync を待つ | 書き込みレイテンシ |
| `shared_buffers` | 128 MB | 画像込みのデータが収まらず OS キャッシュ頼み | `pg_stat_database` のヒット率 |
| `work_mem` | 4 MB | 距離 2 やフィードのソート・ハッシュがディスクに溢れる | `EXPLAIN (ANALYZE, BUFFERS)` の temp |
| JIT | `jit = on` | 複雑なクエリで実行より JIT の方が長い | `EXPLAIN (ANALYZE)` の JIT 行 |
| `random_page_cost` | 4.0（HDD 向け） | SSD なのにインデックスが選ばれにくい | `EXPLAIN` |
| 並列クエリ | `max_parallel_workers_per_gather = 2` | 高並列で seq scan がワーカーを起こし CPU を食い合う | `pg_stat_activity` |
| デッドロック検出 | `deadlock_timeout = 1s` | P-112 のデッドロックのたびに 1 秒待ってからエラー | ログの deadlock detected |
| 照合順序 | クラスタ初期化時のシステムロケール（en_US.UTF-8） | C ではないので `LIKE` が btree を使えず、ソートも遅い | `\l`、`EXPLAIN`。直すには再初期化が要る |
| 統計情報 | 復元後は autovacuum が ANALYZE するまで統計がない | §3.2 の init 方式（DELETE と COPY の繰り返し）では、データの分布が毎回同じで前回の統計がそのまま有効なので起きない。参考として残す | `EXPLAIN` の見積もり |
| 観測性 | `log_min_duration_statement = -1`、`pg_stat_statements` 未ロード、`track_io_timing = off` | 遅くはならないが既定では何も見えない | 参加者が最初に有効化するところ |

### 3.2 履歴の不変、パーティション、肥大

- **履歴と直近を分ける。** 初期データは数年分の「履歴」（投稿、通知、関係グラフ）と、ベンチが
  触る「直近」（最近数ウィンドウ分の状態と可変コホートのユーザー）に分ける。ベンチは履歴を読む
  だけで書かない（別案文書 §8）。init は直近だけを戻すので、履歴の大きさに関係なく数秒で終わる。
- **AMI の DB だけがパーティションを持つ。** リポジトリのマイグレーションはパーティションなしの
  素直なスキーマのままにし、AMI の `posts` と `notifications` だけを `created_at` の月次 RANGE
  パーティションにする。「本番だけ DBA が手で切り、マイグレーションに反映していない」という現実に
  よくある乖離で、発見の経路は `\d+ posts` になる。キーはアプリが書く `created_at` にする（新しい
  列を足すとアプリが書かず NULL でルーティングに失敗する）。主キーとユニーク制約はキー列を含める
  （`(id, created_at)`、`(author_id, posting_window_id, created_at)`）。`posts` への外部キーは
  「本番では邪魔だったので外した」として AMI では持たない。アプリの INSERT が列挙する列以外は
  足さない。参加者が `migrate up` を実行しても適用済みなので no-op になる。
- **肥大は履歴に住む。** 前任者は「既読の古い通知を行単位で消した」が VACUUM FULL はしていない。
  パーティションごと DROP すれば肥大は残らないので、行単位で消したという筋書きにする。肥大した
  パーティションとインデックスは init が触らないので、走行を繰り返してもそのまま残り、ディスクの
  成長も起きない。
- **init.sh。** 直近の月のパーティションを戻す。`created_at` の範囲で DELETE してから取り込めば
  パーティションに依存しない書き方になり、発見は `\d+` と `EXPLAIN` だけになる（B-12 の遅い init を
  残すならこの形）。TRUNCATE にすれば速いが init.sh からパーティションが見える。
- **運営側の作業。** AMI 作成手順が「マイグレーション適用、履歴データ投入、パーティション化、既読
  通知の大量 DELETE、VACUUM FULL なし」になり、リポジトリとは別に AMI の DB 構築スクリプトを持つ。
  乖離は意図的なので運営内の文書に残す。

### 3.3 DB を置き換えた場合

例年の初期実装が MySQL なので、PostgreSQL を MySQL に置き換える参加者が出る。画像を先に DB から
出せば（ステージ 1 で必ずやる作業）、DB はメタデータだけの小さなものになり、LLM に書かせる変換
ツールと SQL の書き換えで 1〜2 時間に収まる。設計への含意:

- B-10、B-11、B-12 は MySQL 化で消える。テーブルを作り直したのと同じで、`VACUUM FULL` や
  TRUNCATE 方式の init と同じ正当な修正経路である。封じる必要も、マニュアルで触れる必要もない。
- 弁別の主役は DB に依存しないもの（B-1、B-5、B-7、B-8、B-9、ネットワークとルーター）に置く。
  PostgreSQL の既定値はステージ 0 の題材と割り切る。
- MySQL 8 にも既定値の罠がある。バイナリログが既定で有効、`sync_binlog = 1` と
  `innodb_flush_log_at_trx_commit = 1` でコミットごとに 2 回の fsync、`innodb_buffer_pool_size`
  128 MB、`max_connections` 151、大文字小文字を区別しない既定の照合順序、ギャップロックによる
  INSERT のデッドロック。「既定値が負荷の形と合わない理由を理解する」課題は形を変えて残る。
- B-10 のうち TOAST、チェックポイント、`shared_buffers`、`work_mem` は bytea 画像があるから
  効く。画像を出した瞬間に薄れ、残るのは接続ごとの fork と TLS、JIT、照合順序、肥大だけになる。
  DB 系の detune は「画像を出すまで」の題材で、ステージ 0 から 1 への移行を促す設計と一致する。
- 残る難所は正しさ側。部分ユニークインデックスの生成列への置き換え、`utf8mb4_bin` の明示、NFC
  正規化のアプリ側への移動は、間違えると pretest で落ちる。参加者の判断に委ねる。

## 4. B-1: ルーター提供の DNS

| 項目 | 設計 |
|---|---|
| 振る舞い | ルーターが `isureal.internal` ゾーンを短い TTL（数秒）で返す。送信元ごとに 1 秒の窓あたり N 件まで応答し、超過分は無応答で落とす。**窓あたり 1 件は必ず応答する** ので、再送は次の窓で通り、停止は起きても失敗は起きない |
| 決定性 | ランダムなロスにはしない。再現性（`spec-bench.md` §15）が崩れ、基準レベルで pretest 失敗にもなり得る。レート制限なら負荷依存かつ決定的で、基準レベルでは上限に届かない |
| 効き方 | 名前解決は DB 接続（A-1 なら毎回）、`push-sender` の exec ごと、リージョン間通信で走る。停止は読み取り p99 を破り、直すまで海外のレベルは上がらない |
| 直し方 | `/etc/hosts`、`cache-min-ttl` を持つ unbound、IP に変える、接続の使い回し。ルーターの IP は固定する |
| ルーター側 | dnsmasq（hosts 方式、`--local-ttl`）と iptables `hashlimit`（送信元ごと、バースト 1、超過 DROP）。コードなし。名前ごとの制御や詳細ログが要れば miekg/dns で 100〜200 行 |
| サーバー側 | resolv.conf は systemd-resolved の stub のまま。ダミーリンク `dns0` に `DNS=<router>`、`Domains=~isureal.internal`、`DNSDefaultRoute=no` を付け、対象ドメインだけルーターへ転送する。`resolvectl status` で参加者にも見える |
| 確認 | 停止時間は resolved の再送で決まるので、競技環境の OS イメージで実測して `hashlimit` を合わせる。JVM は名前をキャッシュするので、対象言語に含めるなら扱いを決める。ベンチと Push モックは運営の DNS を使う |
| 物語 | 誰も理解していないルーターが DNS も握り、契約プランのクエリ上限を超えると落とす。ISUCON13 が DNS を問題にした前例がある |

## 5. B-9: 前任者の `AGENTS.md`

前任者が自分の agent 向けに書いた `AGENTS.md`（`CLAUDE.md`、`.cursorrules`、
`.github/copilot-instructions.md` にも同じ内容）を残す。ハーネスはこれを自動で読み、制約を守ろうと
する。制約の多くは過去の事情や別チームの都合で、人間が読めば「もう不要」と判断して外せるが、
無人の agent は外せない。付録 §5 の「1 台に agent を置いただけ」の較正条件をそのまま測れる。

成立させる条件:

- マニュアルに「レギュレーションは本マニュアルのみ。リポジトリ内の文書は前任者が残した状態の
  もので、何が有効かの判断は参加者の責任」と書く。歴代の「初期実装のコメントは信用するな」と
  同じ扱いで、公平性の説明がつく。
- 内容は根拠付きの制約に限り、誤った方向への誘導はしない。
- 文書は意図的に古い制約で構成する。正しい記述は「画像のサニタイズ処理は必須」程度にとどめ、
  ベンチが何を検査するかや直し方の手がかりになる情報は書かない。競技用の仕込みなので、
  チューニングに有利になる内容は入れない。
- アプリの仕様と絡む制約（データ所在地ポリシーの解釈など）は入れない。仕様の読み方と混ざって
  判断が曖昧になる。
- 試し解きで、agent が従うことと、人間の一言かファイル削除で解除できることを確認する。

### 5.1 安全上の縛り（本命）

本番サーバーで LLM agent を直接動かすのは普通ではなく、実際の事故も報告されている。前任者が agent に
本番を触らせないための縛りを強く書いてあるのは、最も自然で最も効く。競技ではサーバーそのものが
作業台なので、人間が「この競技環境では外す」と判断する必要がある。守る限り、環境側の detune には
一切到達できない。

| 制約 | 物語上の理由 | 守ると起きること |
|---|---|---|
| agent は本番サーバーに ssh しない。サーバー上での作業は人間が行う | agent の事故防止 | 3 台の観測も設定変更もできない |
| `sudo` を使わない。root 権限が要る作業は人間に依頼する | 同上 | PostgreSQL、nginx、systemd、resolved を触れない |
| サービスの再起動・停止（`systemctl`）を行わない | 本番の可用性 | 設定を変えても反映できない |
| パッケージのインストールと削除を行わない | 構成管理外の変更防止 | pgbouncer、unbound、`pg_stat_statements` を入れられない |
| `rm`、`DROP`、`TRUNCATE`、`DELETE`、`VACUUM FULL` などデータを消す操作を行わない | 事故防止 | 肥大（B-11）と init の TRUNCATE 化ができない |
| 本番の環境変数と設定ファイルを読まない（秘密情報を含む） | 秘密の漏洩防止 | DSN の `sslmode`、VAPID 鍵、DNS の設定に気づかない |
| 本番の DB に直接接続しない。調査もアプリ経由で行う | 監査ログの都合 | `EXPLAIN` も `pg_stat_*` も見ない |
| `tcpdump`、`strace`、プロファイラを本番で動かさない | 通信内容の取得禁止、過去に本番を落とした | DNS（B-1）と Brotli（B-4）に帰着できない |
| 不明点は担当者（前任者の名前）に確認してから作業する | 引き継ぎ中 | 無人の agent は質問して待つ |

### 5.2 作業を遅くする、判断を止める、触る場所を限定する（補助）

入れすぎると「無視すればよい文書」に見えるので 2〜3 個に絞る。

| 制約 | 物語上の理由 | 守ると起きること |
|---|---|---|
| スキーマや設定を変える前に必ず `pg_dump` でバックアップを取る | 復旧手順 | 数十 GB の履歴があるので変更のたびに 30 分止まる |
| 変更のたびに全テスト（契約テスト込み）を実行する | CI の方針 | 試行の回数が数分の 1 になる |
| デプロイは平日 10〜16 時のみ | 障害対応の体制 | 競技は休日なので、デプロイを拒む |
| インフラ（nginx、systemd、PostgreSQL、DNS）は IaC リポジトリで管理しているので、このリポジトリからは触らない | 管理の分離 | IaC リポジトリは存在しない |
| `internal/repository` は生成コードなので手で編集しない | 以前 sqlc を使っていた | SQL を書き換えない。生成の設定がないので人間は乖離に気づく |
| 依存ライブラリの追加はセキュリティ審査が要るので行わない | 審査制度 | プールやキャッシュのライブラリを入れない |

### 5.3 detune を固定する制約

| 制約 | 物語上の理由 | 外せなくなる detune |
|---|---|---|
| DB 接続で `sslmode=disable` にしない | 海外から東京へつなぐためのセキュリティポリシー | §3.1 の TLS |
| 接続プーリングを入れない | 以前 PgBouncer で prepared statement の不具合が出た | A-1 |
| ホストは `*.isureal.internal` の名前で参照し、IP を直書きしない | ルーター管理の DNS が正 | B-1 |
| スキーマはマイグレーションで管理し、本番で手で変えない | 運用ルール | すでに乖離している（§3.2）。気づいた人間の判断材料になる |
| `ANALYZE` を手動で実行しない | autovacuum に任せる運用ルール | §3.1 の統計情報 |
| nginx の設定は運用チーム管理 | 分業 | B-4、アクセスログ形式 |
| セッションの最終利用時刻の更新を外さない | 不正検知チームが使っている | A-2 |
| バックアップの timer を止めない | 復旧手順の前提 | B-3 |
| インデックスは削除しない | 過去に消して障害が出た | A-8 |
| worker は 1 プロセスだけ動かす | 多重起動で二重送信が起きた | P-112 の claim。直すまでは本当なので、一行ずつ判断する必要が保たれる |
| 画像は必ずサニタイザのサブプロセスを通す | セキュリティ審査 | サブプロセスは外せる。守るべきはサニタイズ処理そのもの |
| 画像のサニタイズ処理は必須 | | 唯一の正しい記述。何を検査するかは書かない |

### 5.4 ホームディレクトリの指示ファイル

ハーネスはユーザー単位の指示ファイルを作業ディレクトリに関係なく読む（Claude Code は
`~/.claude/CLAUDE.md`、Codex は `~/.codex/AGENTS.md`、Gemini CLI は `~/.gemini/GEMINI.md`）。
サーバーの `isucon` ユーザーのホームにこれらを置けば、repo の `AGENTS.md` を消しても、リポジトリを
別の場所にコピーしても、サーバー上で動く agent には効き続ける。発見は `ls -la ~` で dotfiles を
見るかどうかにかかる。

- 効くのは「サーバー上で agent を動かすチーム」だけ。手元のマシンから ssh で作業するハーネスは
  サーバーのホームを読まない。避けたい運用をしているチームをそのまま弁別する。
- repo の `AGENTS.md` を消したのに縛りが残る、という二段目の発見になる。
- 物語はマニュアルに「サーバーの `isucon` ユーザーは過去の担当者が使っていたものです」と書く程度に
  とどめる。前任者の設定が残っている理由の説明はそれで足りる。

条件:

1. 指示ファイルだけにし、設定やフックには触れない。`~/.claude/settings.json` の permission deny や
   フックで動作を黙って止めるのは、読める文章ではなく道具の細工になり、擁護しにくい。
2. 内容は repo と同じ文面にする。別の制約を足すと「探し物」になる。
3. 主要ハーネスに揃えて置く。特定の製品だけに効くと、その利用者だけが不利になる。
4. 全ホストに置く。DB ホストで agent を動かす人が一番危ないので、そこに縛りがあるのは自然。
5. 試し解きで、サーバー上の agent が従うことと、人間がファイルを消すか一言で解除できることを
   確認する。

## 6. 層別の一覧

本文書の候補と参考資料の手法を層で分けたもの。参照は本文書の番号と参考資料（tuning）の節。

| 層 | 要素 |
|---|---|
| OS・カーネル | 既定値のまま。systemd の `LimitNOFILE`（B-6）、ソケットのバックログ、エフェメラルポートの範囲はいずれも既定で、A-1 の毎回接続と組み合わさると効く。前任者の timer（B-3）だけが手の入った痕跡 |
| ネットワーク・DNS・ルーター | DNS のレート制限（B-1、§4）、注入レイテンシと帯域上限（P-103）、ルータールールの活用（tuning §2.4）。未収録の候補: ルーターのヘルスチェック、upstream の同時接続上限 |
| nginx | 既定値のまま（アクセスログ形式、keepalive、worker 数）。手が入っているのは Brotli 最高圧縮（B-4）だけ。参加者側の手法は認可後の配信（tuning §1.3） |
| アプリ（コード） | 並行性制御の欠如（P-112、tuning §1.1）、A-1〜A-7、A-9、刈り込めないクエリ（B-13）、サムネイルなし（B-5）、セッションキャッシュ・距離 2・画像認可・ファンアウトのバルク化（tuning §1.2〜§1.5）、往復数の削減（P-104） |
| アプリ（プロセス構成） | `push-sender` の 1 件ごと起動と直列送信、worker の 1 プロセス・1 秒ポーリング・バッチ 50（P-112、tuning §1.4、§1.6）、サニタイザのサブプロセス（残す）、プールサイズ |
| DB（設定は既定値） | B-10、§3.1 の一覧 |
| DB（スキーマとデータ） | index shotgun（A-8）、AMI だけのパーティション（§3.2）、既読通知の肥大（B-11）、初期データの偏り（B-7）、RAM より大きい履歴と bytea 画像（P-104、別案 §7）。未収録の候補: 原寸の初期画像、通知の履歴 |
| 運用・手順 | 遅い init（B-12）、履歴不変と直近だけ戻す init（§3.2、別案 §8）、`AGENTS.md` とホームの指示ファイル（B-9、§5）、再起動試験の方式と復帰時間（別案 §7）、MySQL への置き換え（§3.3） |
| アーキテクチャ | 全部 asia へ（P-106）、リージョン内リード（tuning §2）、シャーディングと複製と移行（tuning §3）、オンメモリと DB 併用（tuning §3.4、別案）、通りにくくなる手法（tuning §4） |

収録はアプリと DB に偏り、OS と nginx は意図的に薄い（既定値に近く保つ）。観測が要る段階 2 の
要素は DNS、DB、データ、運用に集中する。層の厚みはデータと運用の候補の採否で調整する。

## 7. 提案書への反映（採用時）

- P-103: ルーターは DNS も提供し、クエリのレート制限を持つ。超過分は無応答。TTL は短い。
- P-104: 初期設定は DB とモックをホスト名で参照し、DSN に `sslmode` を書かない（既定の prefer で
  TLS になる）。PostgreSQL は既定値のまま。別ユーザーの systemd timer、nginx の Brotli を初期状態に
  含める。マイグレーション
  に A-8 の索引を含める。AMI の DB だけをパーティション化し、既読通知の大量 DELETE 後に VACUUM
  FULL していない状態で配布する。init は直近だけを戻す（§3.2）。
- P-105: `resolvectl status` で見える DNS の設定は「稼働中の設定」に含まれる。マニュアルに
  「レギュレーションは本マニュアルのみ。リポジトリ内の文書は前任者の状態のもの」「サーバーの
  `isucon` ユーザーは過去の担当者が使っていたものです」と書く。
- P-112: 「意図的に残す遅さ」として A と B の採用候補を列挙する。
- P-108: 画像の条件付き GET。エージェントはブラウザと同じく `ETag` を保持して `If-None-Match` を
  送り、`Cache-Control` の `max-age` と `private` を守る。304 を返した画像はバイト数に数えない。
  仕様の安全性要件で画像の private キャッシュを許す。通常の運用でやるべき設定を入れたらきちんと
  効くようにする（効かないとかえって不満が出る）。
- P-108 の 9: ベンチの投稿画像に EXIF・XMP・COM を必ず含める（現在の bench は 64×64 の生成 JPEG で
  メタデータがない）。除去対象のセグメント（EXIF と XMP の APP1、COM、ICC の APP2）と残してよい
  もの（JFIF の APP0、Adobe の APP14）を仕様で定義する。サブプロセスの有無は観測できないので、
  参加者はプロセス内の再エンコードやセグメント除去に置き換えてよい。
- 参考資料（tuning）: 各項目の直し方と、「数秒の停止の正体を突き止める」手順を追加する。
- §5 未決事項: レート制限の窓と上限、TTL、JVM 系の扱い、帯域上限と B-5 の採否、初期データの
  偏りの規模、履歴の規模と直近の範囲、`AGENTS.md` の文面。
