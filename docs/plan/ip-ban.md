# IP BAN

作成日: 2026-10-17。

## 目的

AI の利用を前提とする（[指針](../philosophy.md)）。ただし、問題をダウンロードしてローカルだけで解ける形にはしない。
AI を使ってサーバーを調べ、設定のミスを探すのは想定どおりの解き方とする。

高速化は AI が簡単にこなすので、サーバーの状況から利用者の振る舞い（シナリオ）を推定し、それに合わせて最適化することを
問題の着地点にする。IP BAN はその入口になる要素とする。

## 決定事項

| # | 内容 |
|---|---|
| D-1 | アプリには IP アドレスを BAN する機能がある |
| D-2 | BAN しないこと、BAN しすぎることでは失格にしない。何を BAN するかを推測するゲームにしないため |
| D-3 | 正常なユーザーを BAN すると悪評が立つ。bench のログに出す |
| D-4 | 初期状態では、同じ IP から 10 秒に 10 回ログインに失敗すると 2 分間（走行の間ずっと）BAN される。初期スコアに大きく効く |
| D-5 | 初期状態の BAN はアプリではなく外部の監視プログラムが行う。webapp とは別のディレクトリのサービスにする。ソースだけで完結すると、ダウンロードしてローカルだけで解けてしまうため |
| D-6 | BAN した IP への応答は `403 {"error":"ip_banned"}` に固定する。参加者が独自に拒否する場合も同じ応答を返す |

## 構成

```
bench ──X-Country-Code, X-Client-IP──▶ Router(Envoy) ──X-Client-IP──▶ nginx ──▶ app
                                                                    │
                                                         監視プログラム（ログを読み BAN を反映）
```

- Router: bench が `X-Client-IP` で宣言した仮想 IP をそのまま渡し、ヘッダーがなければ接続元の IP を入れる。値の検証や
  偽装の対策はしない。bench が宣言する値なので偽装されても困らず、Envoy の CPU を使うと問題の負荷に影響するため。
  `X-Real-IP` は使わない。nginx でよくある `proxy_set_header X-Real-IP $remote_addr;` で
  上書きされず、言語やフレームワークごとの `X-Real-IP` / `X-Forwarded-For` の扱いの違いも受けないため。
- app: すべての API で `X-Client-IP`（なければ接続元）を `ip_bans` と照合し、BAN 中なら `403 {"error":"ip_banned"}` を返す（D-6）。
  `ip_bans` は、前回の読み込みから 200ms 以上たっていれば、そのときのリクエストの処理中に読み直す。他の言語へ移しやすいよう、
  バックグラウンドの処理は使わない。`/api/initialize` で空にする。
- 監視プログラム（`isureal-guard`、ソースは `guard/`）: サーバーには `/opt/isureal-guard/src` にソース（`_test.go` を除く）、
  `/opt/isureal-guard/bin` にバイナリを置き、`isureal-guard.service` で動かす（app の役割のとき user-data が有効にする）。`journalctl --unit isureal-go.service --follow --output json`
  でアクションログを読み、`"action":"login","status":401` を IP ごとに数える。ジャーナルの時刻で 10 秒以内に 10 回なら、`ip_bans` に
  DB の時刻から 2 分後を期限として書く（すでに BAN があれば遅い方の期限を残す）。DB の接続先はアプリと同じ `env.sh` の
  `ISUREAL_DB_*` を使い、`application_name=isureal-guard` で接続する。閾値などは unit の `GUARD_*` で渡し、`-h` で一覧を出す。
  `put_profile_image` の 400 で `abuse=invalid_image` は 5 秒で 2 回、`get_image` の 403 で `abuse=invalid_signature` は 5 秒で 3 回でも BAN する。全言語のアプリがJPEG復号失敗と署名照合失敗に `abuse` を付ける。Go版はストリーミング判定の実験が復号前に大きな画像を拒否する場合も記録する。
  journalctl の出力を読む流れの中で BAN を順に書くので、DB への書き込みが遅いと検知も遅れる。
- bench: 全ユーザーに仮想 IP を割り当てる。IP は走行ごとに無作為に選び、攻撃者と正常ユーザーで範囲を分けない。

## PR #18 のレビュー案との違い

[pr18.md「ログイン攻撃の検知」](../review/pr18.md) からの変更点。

- 判定: PR 案は BAN の遅れと誤検知を失格にしていた。本案は失格にせず悪評にする（D-2、D-3）。
- 対象: PR 案はユーザー単位（soft ban）と IP 単位（hard ban）の 2 つ。本案は IP のみ。
- 同じ点: 判定はソースのない外部プログラムが行う。Router がクライアントの IP をヘッダーで渡す（PR 案の `X-Real-IP` から `X-Client-IP` に変更）。

## 競技として成り立たせる条件

- bench は BAN の応答（D-6）をエラー率に数えない。既存の失格条件（5 秒間のエラー率 10%）と D-2 がぶつからないようにする。
- bench の検証（事前検証、初期データの検証、走行後の整合性チェック）は走行ごとの新しい IP から送る。誤ログインを送った IP は使い回さない。
- 攻撃の量は、初期アプリで BAN しなくても失格しない範囲にする。
- 「監視を止める」も「全部 BAN する」も最適にならないよう較正する。重い正常ユーザー（Memories を見返すユーザーなど）を BAN して得をしないようにする。
- IP を走行ごとに変え、前の走行の BAN を持ち越さない。

## 検討中: BAN しないとスコアが下がる仕組み

悪意のあるユーザーのリクエストは得点にならない。そのうえで、次の 2 つの経路でスコアを下げる。

| 経路 | 内容 | 効き方 |
|---|---|---|
| 1. 資源を奪う | 重い処理（画像の取得、検索、Memories など）を叩き、正常ユーザーの応答を遅くする | 正常ユーザーの p99 が上がり、口コミとバズが止まる。今のスコアは速さがほぼ効かず段差になるので、効き方も段差になる |
| 2. 正常ユーザーに害を与える | 乗っ取り、プロフィールの書き換え、スパムのコメントや友達申請 | 悪評が立つ。誤 BAN と同じ仕組み（D-3）で、件数に応じて決まった量だけ効く |

- ラチェットの健全判定は正常ユーザーのリクエストだけで行う。
- 経路 1 だけだと、効き方がラチェットの段差しだいで較正しにくい。ラチェットを目標追従の成長に見直せば、容量に比例して効く。
- 経路 2 は速さに依存しないので、較正しやすく走行ごとのばらつきも小さい。
- ログイン失敗の処理は軽いので、総当たりは経路 1 ではほとんど効かない。攻撃者が漏えいした認証情報を持っていて、
  一部が成功すると乗っ取りになる（経路 2）設定にすれば、BAN が遅れるほど被害が増える。

## 検討中: 負荷が増えると悪意のあるユーザーが現れる

サービスが大きくなる（ラチェットのレベルが上がる）と悪意のあるユーザーが現れ、参加者はそれを推定して BAN する。

過剰な推測にしないための条件:

- 現実のサービスでも使われる見分け方であること。
- サーバーで観測できる情報（アクセスログ、DB）だけで見分けられること。
- 結果が bench のログ（悪評、攻撃の量）で分かること。

候補:

| 候補 | 振る舞い | 見分ける手がかり |
|---|---|---|
| A. あり得ない移動 | 乗っ取ったアカウントに、本人のリージョンと別の国からログインする | 同じアカウントへの、離れた国からの短時間のアクセス。登録リージョンと接続国の不一致 |
| B. 分散した総当たり | 多数の IP から、IP ごとには初期ルール未満の頻度でログインに失敗する | 失敗が少数の IP 帯（/24 など）に集中する。存在しないユーザー名が多い |
| C. スクレイパー | 投稿、画像、プロフィールを大量に読み、投稿しない | 関係のないユーザーへのアクセスの多さ |

A と B は地理・ネットワーク上のまとまりで見分ける設定になる。A は既存の「地域外からはログインとプロフィール更新だけ許可」と
つながり、乗っ取り後にできることがプロフィールの書き換えに限られる。

## アプリのログ

監視プログラムが BAN に使うのはログイン失敗の行だけにする。ただしアプリは、すべての API（42 個）で処理の結果を
1 リクエスト 1 行で出す。負荷が上がるとログの量も増え、journald の負荷やレート制限が問題になる。

### 形式

1 リクエストにつき JSON のオブジェクトを 1 行、標準出力に書く。systemd 経由で journald に入る。

```json
{"level":"info","action":"login","status":401,"ip":"203.0.113.7","user_id":null,"username":"alice"}
{"level":"info","action":"create_post","status":201,"ip":"198.51.100.3","user_id":"0b6c2f9e-..."}
{"level":"debug","action":"get_feed","status":200,"ip":"198.51.100.3","user_id":"0b6c2f9e-..."}
```

| キー | 型 | 値 |
|---|---|---|
| `level` | 文字列 | `debug` / `info` / `error` |
| `action` | 文字列か null | ハンドラーの名前を snake_case にしたもの（例: `createPostHandler` → `create_post`）。一覧は `webapp/go/action_log.go`。ルートに当たらないときは null |
| `status` | 数値 | 返した HTTP ステータス |
| `ip` | 文字列 | `X-Client-IP`（なければ接続元） |
| `user_id` | 文字列か null | ログイン中のユーザーの ID。未ログインは null |
| `username` | 文字列か null | `login` と `register` だけに付ける。送られたユーザー名。規則（`^[a-z0-9_.-]{1,64}$`）に合わなければ null |

- そろえるのは、1 リクエスト 1 行であることと、上のキーと型だけにする。キーの順番、空白、時刻などほかのキーは
  言語ごとの標準的なロガーに任せる。監視プログラムは JSON として読み、知らないキーは無視する。
- 今の Echo の RequestLogger は消す。1 リクエストで 2 行目を出すことになり、行数が言語ごとにそろわないため。

### ログレベル

- 読み取り（GET）は `debug`、それ以外は `info`、5xx は `error`。`ISUREAL_LOG_LEVEL`（既定は `debug`）より低いレベルの行は出さない。
- ログイン失敗は `info` なので、レベルを `info` に上げても監視プログラムが使う行は残る。
- 量は、初期状態では journald のレート制限に届かず、スコアが伸びた負荷で超えるよう較正する。
  - 確認済み（2026-10-17、systemd を動かすコンテナ、journal は空き 3.6GB の tmpfs）: 30 秒あたり約 37,500 行で制限がかかり、
    超えた分はログイン失敗の行も捨てられて BAN されなかった。期間が明けると journal に
    `Suppressed N messages from isureal-go.service` が出る。上限は journal の空き容量で変わるので、本番の AMI で測り直す。
