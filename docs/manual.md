## スケジュール

時刻は日本標準時（JST）です。
競技日と競技時間は公開済みレギュレーションに従います。

| 日時 | 内容 | 状態 |
|---|---|---|
| 2026年10月31日 10:00 | 競技開始 | 公開済み |
| 同日 17:00 | 他チームのリーダーボード更新停止 | 提案 |
| 同日 18:00 | 競技終了 | 公開済み |
| 競技終了後 | 追試 | 実施予定、詳細は要確定 |
| 別途告知 | 結果発表、競技環境の操作解禁 | 要確定 |

リーダーボードの更新停止後も、自チームのベンチマーク結果は確認できる運用を提案します。

## ポータルと連絡手段

ポータルの入口は<https://portal.isucon.net/>です。
参加登録したアカウントでログインし、当日案内する競技ページを使用してください。
ベンチマークの実行と結果確認、サーバー情報の確認、質問とサポート依頼、リーダーボードの閲覧に使用します。

競技中の質問は原則としてポータルから送信してください。
問題全体に関係する回答は全チームに公開し、チーム固有の障害などは個別に回答します。
質問の内容によっては、高速化の解法に関係するため回答できないことがあります。

全体アナウンスと、主催者からの個別の呼びかけにはDiscordを使用します。
競技中はポータルとDiscordを確認できる状態を維持してください。
ポータル自体に接続できない場合の連絡先は、競技開始前に別途案内します。

## 競技環境

現行の構成は、アプリケーションサーバー3台、DBサーバー1台、運営管理のルーター1台です。
選手がアプリケーションの実行に利用するサーバーと、運営が管理するルーターを区別してください。

| サーバー | 固定リージョン | 初期状態の役割 |
|---|---|---|
| app1 | asia | nginx、Goアプリケーション |
| app2 | europe | nginx、Goアプリケーション |
| app3 | america | nginx、Goアプリケーション |
| db1 | asia | 共有PostgreSQL 16 |
| ルーター | 対象外 | 国別の転送、通信遅延と帯域制限 |

初期状態でapp1〜app3のすべてを使用します。
ベンチマーク対象として、任意の1台だけを選ぶ構成ではありません。
サーバーのリージョンは変更できません。
ルーターへのログインや設定変更は禁止です。

> 要確認：db1を選手が操作できる範囲、各サーバーのCPU、メモリ、ディスク、AWSインスタンスタイプ、本番AMIと環境構築テンプレートを確定してください。
> この草案では、チューニング用サーバーをapp1〜app3とdb1の4台とする案で記載しています。

### 環境の構築と接続

各チームが用意したAWSアカウントに、当日指定するAMIと構築手順で環境を作成します。

1. ポータルで配布される自チーム用の構築情報を確認します。
2. 指定された手順で環境を作成し、ポータルのサーバー情報と一致することを確認します。
3. 案内された接続先へ、`isucon`ユーザーでSSH接続します。
4. アプリケーションをブラウザで開き、変更前にベンチマークを1回実行します。

> 要確認：テンプレートの入手先、AWSリージョン、SSHの鍵と接続経路、環境確認の操作、再構築の手順を、配布環境で検証して追記してください。
> 復旧や再構築で保存済みデータが失われる場合があるため、コードと設定は各チームで管理してください。

## 参考実装と操作

参考実装は次の7言語です。
初期状態では各appサーバーでGo実装が動作します。

| 言語 | ソースコード | systemd unit |
|---|---|---|
| Go | `/home/isucon/webapp/go` | `isureal-go.service` |
| Ruby | `/home/isucon/webapp/ruby` | `isureal-ruby.service` |
| Rust | `/home/isucon/webapp/rust` | `isureal-rust.service` |
| Python | `/home/isucon/webapp/python` | `isureal-python.service` |
| PHP | `/home/isucon/webapp/php` | `isureal-php.service`（php-fpm） |
| Perl | `/home/isucon/webapp/perl` | `isureal-perl.service` |
| Node.js | `/home/isucon/webapp/nodejs` | `isureal-nodejs.service` |

> TODO（最終チェック）：最終配布物で全言語の配置と切替手順を確認してください。

各参考実装はポート8080で待ち受けます。
appサーバーのnginxはポート80で静的ファイルを配信し、`/api/`をアプリケーションへ転送します。
ルーターの待受ポート8080と、各サーバー内の待受ポートを混同しないでください。

Ruby実装へ切り替える場合は、app1〜app3のそれぞれで次を実行します。
Rust、Python、Perl、Node.jsへ切り替える場合は、2行目のサービス名を表にある対応するサービス名に変更します。

```sh
sudo systemctl disable --now isureal-go.service
sudo systemctl enable --now isureal-ruby.service
```

PHP実装では、nginxが`127.0.0.1:8080`で受けたリクエストをFastCGIでphp-fpmへ渡します。
GoからPHPへ切り替える場合は、app1〜app3のそれぞれで次を実行します。

```sh
sudo systemctl disable --now isureal-go.service
sudo ln -s /etc/nginx/sites-available/isureal-php.conf /etc/nginx/sites-enabled/isureal-php.conf
sudo systemctl reload nginx
sudo systemctl enable --now isureal-php.service
```

Go実装のビルドと再起動は、対象のappサーバーで次のように行います。

```sh
cd /home/isucon/webapp/go
make
sudo systemctl restart isureal-go.service
sudo systemctl status isureal-go.service
```

環境設定は`/home/isucon/env.sh`、静的ファイルは`/home/isucon/webapp/public`にあります。
ログは、例えば`sudo journalctl -u isureal-go.service`で確認できます。
独自の実装へ切り替えた場合も、再起動後に自動で起動し、必要な機能が利用できる状態にしてください。

## ベンチマーク

ポータルから自チームの環境に対して実行を要求します。
ベンチマークは初期化を行うため、手動で登録したデータや前回の走行で追加されたデータは保持されません。

> 提案：同じチームで待機中または実行中のジョブがある間は、追加の実行要求を受け付けません。
> 受付状態の表示名、競技終了時の待機ジョブの扱いは、ポータルの実装と照合して確定してください。

### 実行の流れ

1. `POST /api/initialize`を実行します。
2. 基本機能と初期データを検証し、負荷走行用の利用者を準備します。
3. 負荷走行を行います。
4. 走行で作成した投稿や友達関係などの整合性を確認します。

> TODO（最終チェック）：初期化と各検証の制限時間、負荷走行の長さを、本番ベンチマーカーの設定と照合して記載してください。

初期化では、変更したデータ構造やキャッシュを含めて、全リージョンで整合した初期状態へ戻してください。
初期データの履歴と画像も取得できる状態を保ち、独自に追加したキャッシュや複製先も初期化してください。
参考実装は、前回の走行で増えた画像を月ごとのパーティションの`TRUNCATE`で削除します。
初期化の仕組みを変更した場合も、最終チェックで確定する制限時間内に初期化を完了してください。
初期化に成功した場合は、実装言語を空でない`language`に設定して返します。

```json
{"language":"go"}
```

`lang`というフィールド名ではありません。
初期化または検証に失敗した走行はFAILとなり、その走行のスコアは0点です。
走行のFAILと、規則違反によるチームの失格を区別します。

### 負荷の内容

ベンチマーカーは、各リージョンの投稿期間を順に開きます。
投稿期間の日付を進めますが、サーバーの時計は変更しません。

> TODO（最終チェック）：投稿期間を開く間隔、リージョン間の開始時刻の差、再現する日数を確定して記載してください。

通知を受けた利用者は投稿し、友達のフィードを読み、その後に画像の取得、RealMoji、コメントなどを行います。
過去のMemoriesを読む利用者も並行してアクセスします。

アプリケーションの応答が良好なリージョンでは、利用者が段階的に増えます。
余裕がある場合は、話題になったことを想定して、多数の利用者が流入します。
書き込みと読み取りの両方が正しく完了することが必要です。

### スコア計算

スコアは、検証に成功した活動の件数に配点を掛けた合計です。
現行実装にはエラー件数に応じた直接の減点はありません。
FAILの条件を満たした場合は合計を採用せず、0点になります。

採点対象は、投稿後の友達フィードの検証通過、フィードと画像の取得、RealMoji、コメント、通知、Memories、友達申請と承認、フォローです。
HTTPリクエストの成功数と採点件数は同じではありません。
初期検証のリクエストなど、採点しない操作もあります。

> TODO（最終チェック）：各活動の配点と、利用者ごとまたは投稿期間ごとの加点上限を、本番ベンチマーカーと照合して記載してください。

### FAILの条件と許容される遅延

次のような場合は、その走行をFAILとします。

- 初期化のタイムアウト、空の`language`、事前検証や最終検証の失敗。
- 閲覧権限のない投稿の返却や、権限のない交流操作の受理。
- 初期データの履歴や画像が期待値と一致しないこと。
- 投稿の削除から許容される猶予時間を過ぎても、その画像を取得できること。
- 観測期間のエラー率が上限を超えること。

エラー率は、観測期間ごとに全リージョンの操作を合算して判定します。

> TODO（最終チェック）：観測期間、判定対象となる最小操作数、エラー率の上限、標本抽出率を確定して記載してください。

利用者数の増加判定はリージョン別に行うため、このFAIL判定とは別です。
一部の重い検証は標本抽出し、見つけた失敗を抽出率の逆数で重み付けしてエラー率に含めます。
画面に表示されたエラーメッセージの行数だけでは、失敗率を計算できません。

書き込み成功後の読み取りには、原則として即時の反映を要求します。
画像削除の猶予時間は、アプリケーションマニュアルと本番ベンチマーカーを照合して最終チェック時に確定します。
ベンチマーカーが検査しない機能も、アプリケーションの仕様を保ってください。

ベンチマーカーはHTTPリダイレクトを追いません。
`503`は再試行しますが、再試行することはエラー率の判定や応答時間の計測から除外することを意味しません。

## 変更できる範囲

公開済みレギュレーションの範囲で、サーバー内のソフトウェア、DBスキーマ、インデックス、保存方式、アプリケーションの実装を変更できます。
他の言語での再実装やキャッシュの追加も可能です。
仕様上の応答、初期化、データの永続化、再起動後の動作を維持してください。

> 提案：app1〜app3でのDBやキャッシュの追加を許可します。
> db1への別用途のプロセスの配置を含めた役割変更の範囲は要確定です。
> いずれの場合も固定リージョン、公開先、ルーター経由の通信を維持します。

次の外部仕様は維持してください。

- URI、HTTPメソッド、HTTPステータス、JSONやHTMLの構造と意味。
- JavaScript、CSS、画像など配布された静的ファイルの内容。
- 認証、閲覧制限、公開範囲、削除、画像署名の検証結果。
- 初期データ、初期化処理、ブラウザからの利用。

管理者アカウントを削除したり、固定の応答でデータの整合性検証を回避したりすることはできません。
ベンチマーカーだけを識別して、本来の機能と異なる結果を返す実装は認めません。

## 禁止事項

公開済みレギュレーションの禁止事項に加え、ISURealの通信制約を適用します。

- ルーターを迂回するサーバー間通信や、ベンチマーカーとの通信。
- 外部サーバー、外部ストレージ、マネージドDB、CDNなどへ競技中のリクエスト処理やデータ配信を委譲すること。
- サーバーのリージョン、通信遅延、帯域制限を変更または回避すること。
- 運営管理のルーター、ベンチマーカー、他チームの環境への不正なアクセス。
- 環境確認や追試を妨げる変更、運営用アカウントやSSH公開鍵の削除。
- 競技終了前の非公開の問題内容や解法の公開、チーム外の人物との問題に関する相談や結託。
- 主催者が競技や他チームを妨害すると判断する行為。

監視、テスト、開発には手元のPCや外部サービスを利用できます。
公開済みレギュレーションは、開発でのAIによるコード分析や生成も認めています。
これらの許可は、ベンチマーク対象の処理を外部へ委譲することや、競技情報を他チームに公開することを認めるものではありません。

> 要確認：環境確認プログラム、ログ監視サービス、ネットワーク設定のうち、変更禁止とするファイルとサービスの一覧を確定してください。
> 過去大会のパスを転載せず、2026の配布物から一覧を作成します。

## 最終スコアと競技終了

**この節の採点対象の選び方は提案です。**
競技終了までに受け付けたベンチマークのうち、受付順で最後のジョブの結果を最終スコアとします。
最後のジョブがFAILの場合は、過去の成功結果へ戻さず、最終スコアなしとします。
終了時に待機中または実行中のジョブは、その後に完了した結果を採用する案です。
運営側の障害で完了できなかった場合の再実行は、主催者が全チームに条件を告知して判断します。

> 要確認：この受付順の定義、待機ジョブの処理、同点時の順位、賞の条件はポータルと運営方針に合わせて確定してください。
> ISUCON11予選の「終了後の測定値」や、過去の最高スコアとは異なる案です。

競技終了時には、構成する全サーバーを起動した状態にしてください。
競技終了後は、自動デプロイや予約した更新を含めて環境の変更を止め、主催者の操作解禁まで接続や操作を行わないでください。
この終了後の操作制限も、当日の正式な案内に含めることを提案します。

## 追試

公開済みレギュレーションに従い、競技終了後に再起動を含む追試を行います。
再起動の順番は保証しません。
再起動後に正常動作し、書き込んだデータを保持していることが必要です。

追試の具体的な手順として、次を提案します。

1. 登録された競技環境、固定配置、通信経路、変更禁止事項を確認します。
2. app1〜app3とdb1を再起動します。ルーターの再起動の有無とタイミングは運営側で決定します。
3. 自動復旧を確認し、同じ環境にベンチマークを実行します。
4. ベンチマーク後に再度再起動し、初期化を挟まずに、直前に書き込んだデータを取得できることを確認します。
5. ブラウザで表示と操作を確認します。

> 要確認：スコア再現率、再試行回数、自動復旧の待ち時間、ブラウザ確認の対象範囲を確定してください。
> 過去大会の75%や85%という基準は、この草案では採用していません。

規則違反や追試不合格の場合の失格は、公開した判定基準に従って主催者が判断します。
環境を削除してよい時刻は別途案内します。
結果発表と環境操作の解禁を同じものとみなさないでください。
