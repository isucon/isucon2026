# ISUCON 2026 擬似地理分散アーキテクチャ

## 1. 背景 — なぜこの構成なのか

**競技に「地理的分散」というテーマを組み込みたい。**

Webサービスが世界中のユーザーを相手にするとき、リージョン間の遅延と帯域は避けられない制約になる。どこにデータを置き、どこからアセットを配り、どのユーザーをどのサーバーで受けるか — こうした設計判断はパフォーマンスに直結する、現実的で面白い問題である。

一方で、**実際に複数の地域にベンチマーカーやサーバーを物理的に配置するのは運用上難しい**。コスト、調達、ネットワークの安定性、いずれも競技環境として現実的ではない。

そこで、**擬似的に地理的分散を実現するコンポーネントとして router を導入する**。router がリージョン間の遅延と帯域制限を人工的に再現することで、単一のデータセンター内に閉じた環境でありながら、参加者からは世界に分散したインフラを扱っているように見える。

---

## 2. 構成要素

| 要素 | 台数 | 役割 | 参加者のログイン |
|---|---|---|---|
| app1 / app2 / app3 | 3台(同一性能) | アプリケーション・インフラの改善対象 | 可 |
| db1 | 1台(アプリと同一性能) | AP 固定の共有 PostgreSQL 16 | 可 |
| router | 1台 | 遅延・帯域制御 + HTTPリバースプロキシ | **不可(ルール違反、BAN有)** |
| ベンチマーカー | — | ポータルから実行。リクエストは router 宛(`app.<team>...`)に送られる | — |

ベンチマーカーは常に router を経由してサーバーへ到達する。したがって、すべての通信に地理的制約が適用される。

---

## 3. 地理的制約のモデル

### 3.1 リージョン

isureal には **US / AP / EU** の3リージョンが存在する。配置は app1=AP、app2=EU、app3=US、db1=AP に固定し、参加者は変更できない。

### 3.2 帯域と遅延

| 通信種別 | 帯域 | 追加遅延 |
|---|---|---|
| 同一リージョンのクライアントからの通信 | 1Gbps | 0ms |
| 異なるリージョンのクライアントからの通信 | リージョンごとに200Mbps | HTTP応答時間に100ms |
| 異なるリージョンのサーバー同士の通信 | それぞれ200Mbps | RTT 100ms（片道50ms） |

異なるリージョン間の値は既定値である。router は AP↔EU、EU↔US、AP↔US のリージョンペアごとに帯域と遅延を設定できる。

**ポイント:**

- クライアント↔サーバーだけでなく、**サーバー間通信にも同じ制約がかかる**。app1↔db1 は同一リージョン（1Gbps / 追加遅延0ms）。app2・app3 から共有 db1 への DB 接続を含め、異なるリージョン間には 200Mbps / RTT 100ms が乗る。
- 逆に、**クライアントと同じ国のサーバーからレスポンスやアセットを返せば制限を受けない**。アセット配信をどこから行うかは重要な判断ポイントになる。

### 3.3 「リージョン」と「国」の対応

2つの概念が登場するので区別が必要。

| 概念 | 誰のものか | どこで表現されるか |
|---|---|---|
| **region** | サーバー / アプリケーション上のユーザーが選ぶもの | DBに保存される |
| **country** | クライアントが実際にいる場所 | HTTPヘッダー(`X-Country-Code`)で送られる |

---

## 4. router の挙動

router は2つの役割を兼ねる。

1. **遅延・帯域制御つきルーター** — パケットはすべて router を通過する
2. **HTTPリバースプロキシ** — ホスト名とクライアントの国でサーバーへ振り分ける

### 4.1 国の判定

- クライアントの **`X-Country-Code` ヘッダー**を見て、遅延・帯域制御の対象国を判定する。
- ヘッダーが存在しない場合は、ポータルで設定した**デフォルトの国**が使われる。
- `X-Country-Code` は制御に使われるだけでなく、**アプリケーションにもそのまま渡される**。アプリケーション側でクライアントの国を参照できる。

### 4.2 ホスト名によるルーティング

| ホスト名パターン | 振り分け先 |
|---|---|
| `app.team<Number>-<random-hash>.isucon2026.westens.tokyo` | クライアントの国と同じリージョンのサーバーへ自動振り分け |
| `app1-3.team<Number>-<random-hash>.isucon2026.westens.tokyo` | 指定した**個別のサーバー**へ直接 |

メインサーバーは設けず、初回設定から3台すべてを使用する。JP/KR/CN/AU は app1 (AP)、GB/DE/FR は
app2 (EU)、US/CA/MX は app3 (US) へ送る。ベンチマークのターゲットは共通の `app` ホスト名とする。

---

## 5. アプリケーション上のユーザーと国

競技環境のネットワーク制約とは別に、**アプリケーションのユーザー自身も「国」を持つ**。

- ユーザーの国は HTTP ヘッダーに載って渡される。
- **ユーザーと同じ国のサーバーから返せば、遅延・帯域の制限を受けない。** 同じ国からアセットを配信できれば速い。
- **ユーザーは任意のタイミングで国を移動できる。** 移動した場合、ログインセッションも移動先へ引き継がれる必要がある。
- 最初から全3リージョンでリクエストを受けられる構成とする。国が変われば同じ `app` ホスト名でも接続先サーバーが変わる。

---

## 6. ポータルからの設定

参加者がポータルから設定できる項目:

- クライアント接続時の**デフォルトの国**(`X-Country-Code` が無いときの向き先)

### 制約

- **ベンチマーク実行中は設定を変更できない**(完了まで固定)。
