# ISUReal アプリケーションマニュアル

## アプリケーションの概要

ISURealは、日常の写真を共有するソーシャルネットワーキングサービスです。利用者は1日に1度訪れる投稿期間中に写真を投稿し、友達と共有します。コメントの投稿や、自身の顔写真を使ったリアクション機能による交流が可能です。

## 3リージョンモデル

本システムは、世界各地からの利用を想定した地理的分散モデルを採用しています。サービス全体を構成する区分は、asia、europe、americaの3リージョンです。アプリケーションの機能やネットワーク構造は、この地域区分に基づきます。

利用者はアカウント登録時に、所属先としていずれか1つのリージョンを選択します。日々の投稿通知や締め切り時間は、リージョンごとに独立した設定です。また、利用者は原則として自身が所属するリージョンからのみサービスを利用できます。このアクセス制限は、社内のデータ所在地ポリシーを遵守するための制約です。

競技環境では、各リージョンにアプリケーションサーバーが1台ずつ配置されています。一方、データベースサーバーの配置先はasiaリージョンのみです。異なるリージョン間の通信には、ネットワーク遅延と帯域制限が適用されます。

## 競技環境の構成

チームごとに次の 5 台が用意されます。

| サーバー | リージョン | 役割（初期状態） |
|---|---|---|
| app1 | asia | アプリケーション（nginx、`isureal-go.service`） |
| app2 | europe | アプリケーション（nginx、`isureal-go.service`） |
| app3 | america | アプリケーション（nginx、`isureal-go.service`） |
| db1 | asia | PostgreSQL 16 |
| ルーター | - | 運営が管理する。選手はログインできない |

- 従来と異なり、初期状態で app1～app3の全てが利用されています。ルーターは対応するリージョンのサーバーにリクエストを転送します。
- サーバーのリージョンは固定で、変更できません。

### 参考実装

参考実装は次の 4 つです。初期状態では Go 実装が動いています。

| 言語 | ソースコード | systemd unit |
|---|---|---|
| Go | `/home/isucon/webapp/go` | `isureal-go.service` |
| Ruby | `/home/isucon/webapp/ruby` | `isureal-ruby.service` |
| Rust | `/home/isucon/webapp/rust` | `isureal-rust.service` |
| Python | `/home/isucon/webapp/python` | `isureal-python.service` |

どれも `:8080` で待ち受けるので、同時に動かすことはできません。たとえば Ruby 実装に切り替えるには、各 app サーバーで次を実行します。Rust や Python の実装に切り替えるときは、`isureal-ruby.service` をそれぞれ `isureal-rust.service`、`isureal-python.service` に読み替えてください。

```sh
sudo systemctl disable --now isureal-go.service
sudo systemctl enable --now isureal-ruby.service
```

### ルーター

ルーターは、データ所在地ポリシーに対応するために導入したマネージドのルーターです。運営が管理しており、
設定の変更やログインは禁止です。

利用者（ベンチマーカーを含む）からのリクエストは、すべてルーターを通ります。ルーターはリクエストの
`X-Country-Code` ヘッダの国から、次の表のリージョンのサーバーへリクエストを転送します。

| 国（`X-Country-Code`） | 転送先 |
|---|---|
| JP、KR、CN、AU | app1（asia） |
| GB、DE、FR | app2（europe） |
| US、CA、MX | app3（america） |

- `X-Country-Code` は転送先のサーバーにもそのまま渡されます。
- 表にない国、空の値、小文字、複数の値を指定したリクエストは、ルーターが400を返します。

サーバー間の通信もすべてルーターを経由します。ルーターは、異なるリージョンにあるサーバー間の通信に遅延と
帯域の制限を加えます。

サーバー間でのルーターを迂回するような通信は禁止されています。

### アプリケーションの URL

| URL | 転送先 |
|---|---|
| `http://app.<チームのドメイン>:8080/` | 国に応じたリージョンのサーバー（ベンチマーカーはここにアクセスする） |
| `http://app1.<チームのドメイン>:8080/` など | 指定したサーバー（動作確認用） |

参加者のアプリケーションの動作確認のためにHTTPSでもアクセス可能となっていますが、ベンチマーク時にはhttpプロトコルが利用されます。

## データ所在地ポリシー

社内のデータ所在地ポリシーにより、利用者は自分が所属するリージョンからしかサービスを使えません。
所属と違うリージョンからのリクエストは、ログイン、ログアウト、プロフィールの変更（所属リージョンの変更を含む）
を除いて拒否します（403）。この動作は変えてはいけません。

### 管理者アカウント

| ユーザー名 | パスワード |
|---|---|
| `admin` | `password1234` |

ベンチマーカーはこのアカウントで投稿期間を開きます。変更しないでください。

## ベンチマーカーについて

### 負荷走行の流れ

1. 初期化処理（`POST /api/initialize`）。30 秒以内に応答しなければ失格です。
2. 動作と初期データの検証。
3. 負荷走行（60 秒）。
4. 負荷走行後の整合性の検証。

どこかで失敗した場合、その時点で負荷走行は失敗（fail）となり、スコアは 0 点です。

## 禁止事項

当日マニュアルの禁止事項に加え、次を禁止します。

- ルーターを経由しないで、サーバー間やベンチマーカーとの通信を行うこと。
  競技環境の外のリソース（外部のサーバー、AWS の機能など）を経由した通信も含みます。

## 追試

競技終了後、運営が全サーバーを再起動し、負荷走行を行います。再起動後も、負荷走行で書き込んだデータが
取得できなければなりません。

## `POST /api/initialize` の応答

`POST /api/initialize` の応答には、利用した言語を返してください。参考実装はそのようになっています。

```json
{
  "language": "実装言語"
}
```

`language` が空の場合、初期化処理は失敗とみなされます。
