# ポータルの Discord 連携機能と検証手順

調査日：2026-10-17。
対象は、この作業ツリーの Go 版ポータルと、旧 `isucon/isucon2026-portal` の Django 実装です。
Go 版の常駐 bot は、ソースコメント上では ISUCON14 の `bin/isuxportal-discord-bot` を移植元としています。
以下では現在のコードの動作と、dev での実機確認結果を区別します。
この文書の作成時には、bot の起動や Discord への投稿は行っていません。

## 環境情報の参照先

環境固有の URL、Application ID、サーバー ID、ロール ID、検証アカウント、DB 名、実機試験の記録は [非公開の環境別資料](https://github.com/isucon/isucon2026-private/blob/main/docs/research/portal-discord.md) で管理します。
非公開資料の追加は [isucon2026-private PR #2](https://github.com/isucon/isucon2026-private/pull/2) を参照してください。
この文書の `<TEAM_ID>` などは実値に置き換えるためのプレースホルダーです。
実値や認証情報をこのリポジトリへ転記しないでください。
登録情報の変換規則と戻し方は [登録情報の移行手順](../../portal/docs/registration-migration.md) を参照してください。

## 機能を担当するプロセス

| 担当           | 機能                                                                                            | 常駐 bot の起動 |
| -------------- | ----------------------------------------------------------------------------------------------- | --------------- |
| portal         | OAuth、登録済み選手との照合、再連携、参加状態の表示、運営 API                                   | 不要            |
| worker         | Discord REST API による所属確認、参加者ロール同期、ニックネーム変更、アナウンス送信、Slack 通知 | 不要            |
| bot            | Discord Gateway のイベント受信、リアクション応答、テキストコマンド、サポートチャンネル運用      | 必要            |
| フロントエンド | Discord widget、連携ボタン、未参加表示                                                          | 不要            |

**所属確認**は Discord にいるかを読み、ポータルの DB に保存する処理です。
**ロール同期**はポータルの登録状態を基準に Discord のロールを変更する処理です。
所属確認が成功しても、参加者ロールが付与されたことは意味しません。

Bot トークンは Secrets Manager に保存し、worker と `enableBot=true` の bot にだけ注入します。
portal、notifyloop、migrate、停止設定の bot のタスク定義には注入しません。
OAuth client secret と Bot トークンは別の認証情報です。

## OAuth ログインとアカウント連携

### 認証の入口と callback

| 用途                           | Go 版の URL / 動作                                                                        |
| ------------------------------ | ----------------------------------------------------------------------------------------- |
| Discord 認証開始               | `GET /session/new/discord` → `/auth/discord`                                              |
| 通常の callback                | `/auth/discord/callback`                                                                  |
| 旧 Django と同じ callback パス | `/auth/discord/complete/`。末尾の `/` が必要                                              |
| callback の選択                | `ISUXPORTAL_DISCORD_CALLBACK_PATH`。既定は通常の callback、環境別の選択は非公開資料を参照 |
| OAuth scope                    | `identify`                                                                                |
| 取得内容                       | `/users/@me` から ID、ユーザー名、discriminator、アバター                                 |
| 戻り先                         | `back_to` によるポータル内の戻り先。マイページの再連携ボタンは `/registration` に戻る     |

両 callback パスを受け付けます。
トークン交換時の `redirect_uri` は実際に受信した callback パスを使います。
OAuth の state をセッションと照合し、使用済み state の再使用を拒否します。
互換性の対象は callback のパスであり、旧 Django のログインセッションや認証途中の state を Go に引き継ぐ機能ではありません。
ドメインを変える場合は、Discord Application に登録された redirect URI も別途確認してください。

Discord ID は連携先の識別子として使います。
ユーザー名だけでは照合しません。
discriminator が `0` または空ならユーザー名だけを表示し、それ以外は `username#discriminator` の形式にします。
OAuth のアクセストークンとアバター URL はセッションに保持します。
認証開始 URL は `Discordbot` / `Slackbot` の User-Agent に 404 を返し、リンクプレビューから認証を開始しないようにしています。
Go 版には旧版の refresh token を使う定期更新処理はありません。

### callback 後の分岐

| 条件                                                      | 動作                                                                               |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Discord ID が登録済み選手に一致                           | その選手としてログインし、Discord 表示名を更新。失格チームの場合はマイページへ戻る |
| Discord ID が未登録で、現在のセッションに有効な選手がいる | 現在の選手の Discord ID と表示名を付け替える                                       |
| Discord ID が未登録で、選手として未ログイン               | OAuth 情報をセッションに保持して参加登録画面へ進む                                 |

付け替え時は、旧 Discord ID の参加者ロールを外すジョブ、所属確認ジョブ、変更内容の Slack 通知を登録します。
新しい Discord ID への参加者ロール付与は、この分岐では登録していません。
所属確認ジョブの登録は DB の ID 更新より先なので、worker との実行順序も再連携試験の確認対象です。
別の既存選手に紐付く Discord アカウントで認証すると、その選手でのログイン分岐になります。

新規チーム作成と招待参加では GitHub、Discord 両方の OAuth 情報を要求し、Discord ID の重複を拒否します。
登録済み選手は GitHub 数値 ID でも照合できるため、移行後の GitHub 再ログインで Discord の再認証は不要です。
新規登録処理自体には、参加者ロール付与のジョブ登録はありません。

参照：[認証処理](../../portal/internal/handler/auth.go)、[登録処理](../../portal/internal/handler/registration.go)、[callback テスト](../../portal/tests/integration/discord_callback_test.go)。

## サーバー所属の確認と表示

### 個人の所属確認

worker は Bot トークンで `GET /guilds/{server_id}/members/{discord_id}` を実行し、`contestants.is_discord_guild_member` を更新します。
取得成功なら true、404 なら false にします。
それ以外の API エラーでは更新せず、ジョブをエラーにします。
Bot トークン未設定時の実装は「見つからない」として扱うため、未設定のまま確認すると false になります。

個人の確認が登録される契機は次のとおりです。

- 登録済み選手の GitHub 再ログイン。
- Discord アカウントの付け替え。
- 常駐 bot が受け取るサーバー参加イベント。
- `#readme` の 🪑 リアクション。

既存 ID に一致する Discord ログインの分岐には、所属確認ジョブの登録はありません。
サーバー退出イベントを受けて即時に false にするハンドラーもありません。
表示値は最後に確認した結果なので、Discord 上の最新状態と一時的に異なる場合があります。

### 全員の所属確認と運営向け機能

| 機能                      | 入口                                                           | 動作                                                                                                               |
| ------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 全員の所属再取得          | 運営認証付き `GET /admin/sync_all_discord_stats`               | `sync_discord_member_state_of_all_contestants` を登録。サーバーのメンバー一覧をページング取得し、DB の全選手と照合 |
| 未参加者の一覧            | `GET /api/admin/unprepared_stats/discord_stats`                | 表示対象の有効なチームから、保存済みの所属状態が false の選手を返す。画面を開くだけでは Discord API を再照会しない |
| 運営による ID 修正        | 運営のチーム編集画面                                           | Discord ID と表示名を DB に保存。OAuth 確認やロール同期は伴わない                                                  |
| 開発用の Discord 情報設定 | 運営の `/admin/impersonate`、`POST /admin/impersonate/discord` | セッションの Discord ID と表示名を設定またはクリア。実 OAuth の検証にはならない                                    |
| テスト用 OAuth            | 開発用 fake OAuth routes                                       | 実 Discord を使わず callback の分岐をテスト。実接続の成功とは区別する                                              |

全員確認は参加状態だけを更新し、参加者ロールを一括で追加または削除する処理ではありません。
スケジューラーから定期的に全員確認を登録する処理は、現在の Go 実装では確認できません。

マイページには GitHub 名、Discord 名、所属結果と再連携ボタンがあります。
競技ページの `/contestant/discord` とマイページには Discord widget を埋め込んでいます。
widget の表示は Discord 側の公開設定にも依存し、ポータルの所属確認結果とは独立しています。
マイページの「準備が整っています」という見出しは、現在の実装では Discord 所属を条件に切り替えていないため、個別の参加表示を確認してください。

参照：[worker の所属確認](../../portal/internal/job/jobs.go)、[運営 API](../../portal/internal/handler/admin_api.go)、[運営用ページ](../../portal/internal/handler/pages.go)、[マイページ](../../portal/frontend/app/javascript/RegistrationStatus.tsx)、[Discord ページ](../../portal/frontend/app/javascript/contestant/ContestantDiscordPage.tsx)。

## 参加者ロールとニックネームの同期

`maintain_discord_contestant_roles` は、対象の Discord メンバーが現在持つロールと、ポータルから求めた参加者ロールの有無を比較します。
管理対象は `ISUXPORTAL_DISCORD_CONTESTANT_ROLE_ID` の1種類です。

| 同期時の条件                                     | 変更                                                         |
| ------------------------------------------------ | ------------------------------------------------------------ |
| 対象選手のチームが存在し、辞退も失格もしていない | 参加者ロールがなければ付与                                   |
| 対象選手のチームが無効                           | 参加者ロールがあれば削除                                     |
| `force_discord_id` だけを指定                    | その ID の参加者ロールを削除。辞退や旧アカウントの掃除に使う |
| Discord メンバーが見つからない                   | 警告を記録して終了。サーバーへ自動参加させない               |
| その他のロール                                   | 変更しない                                                   |

参加者ロールを新規付与し、チームが非表示ではない場合だけ、ニックネームを `選手名 (チーム名)` に設定します。
最大32文字で切り詰めます。
参加者ロールが既に付いている場合は、名前変更後でもこの処理でニックネームを再設定しません。
ロール追加後にニックネーム変更が失敗すると部分適用になり、次回は「新規付与」の条件に入らない可能性があります。

| 同期の契機                    | 対象                                                         |
| ----------------------------- | ------------------------------------------------------------ |
| サーバー参加、`#readme` の 🪑 | Discord ID に一致する登録済み選手                            |
| 選手の辞退                    | 削除対象の選手。代表者の辞退では処理対象となるチームメンバー |
| Discord アカウントの付け替え  | 旧 Discord ID のロール削除                                   |

失格や名前編集を行っただけで、この同期が直ちに実行される構成ではありません。
チーム全員への定期ロール同期、現地参加ロール同期、チーム専用ロールの自動作成はありません。
サポート用ロールは、後述する別の処理で管理します。

参照：[MaintainDiscordContestantRoles](../../portal/internal/job/jobs.go)、[辞退処理](../../portal/internal/handler/registration.go)。

## 常駐 bot のイベントとコマンド

bot は設定されたサーバー ID のイベントだけを処理します。
メッセージコマンドは `.` で始まる通常の投稿で、大文字小文字を区別します。
Slash Command の登録や `/ping` は実装されていません。
メッセージの投稿者が Bot の場合は無視します。

| 操作                     | 実行できる人 / 場所                              | 動作と副作用                                                                               |
| ------------------------ | ------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| `.ping`                  | 対象サーバー内の、bot が読めるチャンネルの利用者 | 同じチャンネルへ `Pong, <username>` と返信                                                 |
| サーバーへ参加           | 登録済み Discord ID の選手                       | 参加者ロール同期と所属確認を worker に登録。未登録 ID には何もしない                       |
| 🪑 を付ける              | 名前が `readme` のチャンネルのメッセージ         | 登録済み選手ならロール同期と所属確認を登録。利用者の 🪑 を取り除き、bot 自身が 🪑 を付ける |
| 🆘 を付ける              | 名前が `readme` のチャンネルのメッセージ         | Slack webhook に選手名と選手 ID を通知。未登録者は `_unknown_`。bot 自身も 🆘 を付ける     |
| `.supportOpen <TEAM_ID>` | 運営ロールを持つ人、設定済みサポートチャンネル   | チーム<TEAM_ID>へサポート用ロールを付与し、非公開の問い合わせを作成                        |
| `.support`               | 運営ロールを持つ人、設定済みサポートチャンネル   | 使用方法と現在の使用状態を同じチャンネルへ返信                                             |
| `.supportClose`          | 運営ロールを持つ人、設定済みサポートチャンネル   | 会話を問い合わせへ保存し、チームメンバーのサポート用ロールを削除                           |

運営判定は `ISUXPORTAL_DISCORD_ADMIN_ROLE_ID` とメンバーのロール ID の一致です。
Discord のサーバー管理者であるだけでは、このコマンドの運営判定を満たしません。
権限がない場合は `FORBIDDEN`、未設定のサポートチャンネルならエラーを返信します。

`readme` はチャンネル名で判定し、特定のメッセージ ID に限定していません。
リアクション用ハンドラーには Bot 自身のイベントを除外する条件がありません。
自身のリアクションによる再処理や通知重複は、実機試験で確認が必要です。
この文書では正常動作を確認済みとは扱っていません。

参照：[常駐 bot の全実装](../../portal/cmd/bot/main.go)。

### サポートチャンネルの運用

サポート機能は既存チャンネルのロールを付け外しします。
チャンネル自体や権限設定を新しく作成する機能はありません。
事前に、サポート用ロールを持つ人だけが対象チャンネルを閲覧できるよう、Discord 側で設定します。

1. 運営が対象チャンネルで `.supportOpen <TEAM_ID>` を投稿します。
2. bot がチームの問い合わせを作り、現在のメンバーへ、そのチャンネルに対応するロールを付与します。
3. Redis にチャンネルごとの利用チーム、開始メッセージ ID、問い合わせ ID を保存します。使用中のチャンネルを再度開くとエラーになります。
4. `.support` で使用状態を確認します。
5. `.supportClose` で開始メッセージより後の会話を取得し、発言者、日時、本文を問い合わせの回答欄に保存します。
6. 終了時点のチームメンバーからロールを外し、Redis の利用状態を空にして、終了メッセージを投稿します。

会話ログはそのチャンネルで取得できたメッセージ本文を対象にします。
添付ファイルの実体を保存する処理はありません。
途中で脱退した選手や、手動でロールを付けた人のロール削除は自動では保証されません。
終了処理のロール削除エラーは無視しているため、終了メッセージだけで権限回収の完了と判断せず、Discord 側も確認してください。
Redis を切り替える場合は、使用中のサポートチャンネルを引き継ぐ方法も別途決める必要があります。

## アナウンスと Slack 通知

| 通知                                | 契機                                                                              | 宛先と内容                                                                       |
| ----------------------------------- | --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Discord アナウンス                  | 公開対象の運営アナウンスまたは質問回答の作成、更新に伴う `clarification_response` | `ISUXPORTAL_DISCORD_CHANNEL_ID`。新規か更新か、問い合わせ ID、競技ページへの URL |
| 任意テキストの Discord 投稿         | `discord_announce` ジョブ                                                         | 同じアナウンスチャンネル。Bot の投稿 API を使用                                  |
| SOS の Slack 通知                   | `#readme` の 🆘                                                                   | `ISUXPORTAL_SLACK_WEBHOOK_URL`。選手情報または `_unknown_`                       |
| Discord アカウント変更の Slack 通知 | OAuth で未使用の別 ID へ付け替え                                                  | 選手 ID と変更前後の Discord ID、表示名                                          |

公開対象外の問い合わせ回答は、全体 Discord アナウンスの対象になりません。
Discord アナウンスには質問本文や回答本文を転載せず、ポータルへのリンクを載せます。
公開回答処理は Discord 投稿に失敗してもエラーをログに残して続行するため、ポータル上の公開成功と Discord 配信成功は別に確認します。
Bot トークンや Slack webhook が未設定の場合は、外部送信を省略する実装です。
Slack クライアントは HTTP 応答コードをエラー判定していないため、ジョブの成功だけで通知の到着を判断せず、通知先で確認します。
通知先が未確認の dev では、公開アナウンスや 🆘 の実送信テストはまだ行っていません。

参照：[通知ジョブ](../../portal/internal/job/jobs.go)、[Discord REST クライアント](../../portal/internal/external/discord.go)。

## 設定項目と起動条件

| 設定                                                                                                  | 用途                                                                                                       |
| ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `ISUXPORTAL_DISCORD_CLIENT_ID`                                                                        | OAuth Application の client ID                                                                             |
| `ISUXPORTAL_DISCORD_CLIENT_SECRET`                                                                    | OAuth client secret。Secrets Manager へ保存                                                                |
| `ISUXPORTAL_DISCORD_CALLBACK_PATH`                                                                    | 通常または旧 Django の callback パス                                                                       |
| `ISUXPORTAL_DISCORD_BOT_TOKEN`                                                                        | REST と Gateway 用の Bot トークン。Secrets Manager へ保存                                                  |
| `ISUXPORTAL_DISCORD_SERVER_ID`                                                                        | 所属確認とイベント処理の対象サーバー                                                                       |
| `ISUXPORTAL_DISCORD_CONTESTANT_ROLE_ID`                                                               | 参加者ロール                                                                                               |
| `ISUXPORTAL_DISCORD_CHANNEL_ID`                                                                       | 公開アナウンス先のチャンネル                                                                               |
| `ISUXPORTAL_DISCORD_ADMIN_ROLE_ID`                                                                    | サポートコマンドを実行できる運営ロール                                                                     |
| `ISUXPORTAL_DISCORD_SUPPORT_COMM_CHANNEL_ROLES`                                                       | `channel_id=role_id,channel_id=role_id` 形式の対応表。空白を除去する実装ではないため、余分な空白を入れない |
| `ISUXPORTAL_SLACK_WEBHOOK_URL`                                                                        | SOS とアカウント変更などの通知先。Secrets Manager へ保存                                                   |
| `ISUXPORTAL_DISCORD_AUTHORIZE_URL`、`ISUXPORTAL_DISCORD_TOKEN_URL`、`ISUXPORTAL_DISCORD_API_BASE_URL` | テストなどで接続先を差し替える設定                                                                         |
| Pulumi `secretKeys`                                                                                   | ECS に渡す秘密値のキー名。値そのものは書かない                                                             |
| Pulumi `enableBot`                                                                                    | 常駐 bot を稼働させるか。環境別資料を参照                                                                  |

サーバー、アナウンス先、参加者ロール、運営ロールには ISUCON14 由来の既定 ID が残っています。
新しい環境で bot や通知を試す前に、対象 dev の ID を明示的に設定してください。
各環境の設定状況は非公開の環境別資料を参照してください。

Gateway で要求する intents は `GuildMembers`、`GuildMessages`、`GuildMessageReactions`、`MessageContent` です。
`GuildMembers` と `MessageContent` は privileged intents のため、Discord Developer Portal 側の許可も確認します。
全メンバーを列挙する REST API も `GuildMembers` の制約を受けます。
単独メンバーの取得成功だけでは、全員取得や Gateway の起動成功は検証できません。
詳細は [Discord Gateway の公式仕様](https://docs.discord.com/developers/events/gateway#gateway-intents) を参照してください。

参加者ロールとサポート用ロールの付け外しには `MANAGE_ROLES`、他のメンバーのニックネーム変更には `MANAGE_NICKNAMES` が必要です。
Bot のロール順位も変更対象より上に配置します。
API ごとの条件は [Discord Guild API の公式仕様](https://docs.discord.com/developers/resources/guild) を参照してください。
投稿、履歴取得、リアクションの追加や利用者のリアクション削除ができるチャンネル権限も、使う機能ごとに確認します。

設定変更は Pulumi のコードまたは対象 stack に記録し、Pulumi 適用後に ecspresso で対象サービスをデプロイします。
常駐 bot を試す場合は `enableBot=true` とし、bot と worker が同じ検証用 DB、Redis、サーバー ID を参照することを確認します。
停止時も `enableBot=false` を適用して ecspresso で反映します。
秘密値の変更だけでは既存タスクへ反映されないため、該当サービスの再デプロイが必要です。

参照：[設定](../../portal/internal/config/config.go)、[Pulumi 設定](../../portal/deploy/pulumi/config.ts)、[タスク定義](../../portal/deploy/ecspresso/task.jsonnet)、[外部連携設定](../../portal/deploy/external-integrations.md)。

## 旧 Django からの移行差分

| 機能                                     | 旧 Django                                                                | 現在の Go 版                                                                   |
| ---------------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| Discord OAuth の位置付け                 | ログイン済みでチーム所属のユーザーが Discord を接続                      | 新規登録前の OAuth と、Discord ID を使う既存選手ログインにも対応               |
| OAuth scope                              | `identify guilds.join`                                                   | `identify`                                                                     |
| サーバーへの自動参加                     | OAuth 接続時に `join_discord` を実行                                     | 未移植。利用者がサーバーへ参加する                                             |
| OAuth トークンの保存と更新               | DB に access / refresh token と期限を保存し、期限が近いものを更新        | 旧トークンは移行しない。DB 上の Discord ID と Bot API で所属を確認             |
| 定期更新                                 | `updatediscord` でトークン更新とユーザー情報、ロール、ニックネームの更新 | 同等の定期処理はない。イベントや明示的な所属確認を使用                         |
| 参加者ロール                             | チームの有効状態から決定                                                 | 対象者について差分で追加、削除                                                 |
| 現地参加ロール                           | `is_local_participation` に応じて付与                                    | 未移植                                                                         |
| 他のロール                               | member PATCH に `roles` の一覧を渡す                                     | 参加者ロールだけを個別 API で操作                                              |
| ニックネーム                             | 更新処理のたびに設定。403 の場合はロール更新だけ再試行                   | 参加者ロール新規付与時だけ設定。ニックネーム失敗時の同等のフォールバックはない |
| 連携済みユーザーのチーム参加、編集、辞退 | 対象の処理から `update_discord` を呼ぶ                                   | すべての編集を自動同期する構成ではない。上記の契機に限定                       |
| 常駐 bot のコマンドとサポート            | 旧 Django の OAuth / バッチとは別系統                                    | ISUCON14 由来の Go 実装あり。今回の dev では未稼働                             |

現地参加ロール、定期的な修復、名前変更後のニックネーム追従、自動参加を旧版と同じ運用にする場合は、追加実装と実機検証が必要です。
旧版と Go 版を同じサーバーで並行運用する間は、旧 `updatediscord` もロールや名前を変更し得るため、試験結果の原因を区別してください。

旧版の参照元：

- [authentication/models.py](https://github.com/isucon/isucon2026-portal/blob/main/isucon/portal/authentication/models.py)：`join_discord`、`refresh_discord_token`、`update_discord`。
- [authentication/views.py](https://github.com/isucon/isucon2026-portal/blob/main/isucon/portal/authentication/views.py)：OAuth、参加、編集、辞退時の更新。
- [updatediscord.py](https://github.com/isucon/isucon2026-portal/blob/main/isucon/portal/authentication/management/commands/updatediscord.py)：定期実行する管理コマンド。

調査した旧版のリビジョンは非公開の環境別資料に記録しています。

## コマンドで開始する非公開スレッド（dev検証用）

`ISUXPORTAL_DISCORD_SUPPORT_THREAD_PARENT_ID` を設定すると、通常テキストチャンネルの下に相談単位の非公開スレッドを作ります。
運営が親チャンネルで `.supportOpen team_id` を実行したときだけ作成します。
clarの投稿だけではスレッドを作成しません。
Botの定期処理は、コマンドで開始した作成・終了処理の失敗を再試行するためにだけ使います。
運営アナウンスは対象外です。
環境固有値はprivate側の設定記録を参照してください。

### 開始と終了

- コマンドで指定したチームの相談記録をclarとして作成し、非公開スレッドを対応付けます。対象チームのDiscord連携済みメンバーを招待します。
- 同じチームに相談中のスレッドがあれば再利用し、重複作成しません。終了後の再実行では新しい相談とスレッドを作成します。
- `invitable=false` により、参加者から他の参加者を追加できない設定にします。
- スレッド内の `.support` で状態を確認できます。
- 運営がスレッド内で `.supportClose` を実行すると、投稿をロックし、ログ保存成功後にBot以外のスレッドメンバーを全員除外します。運営はスレッド管理権限で引き続き閲覧できます。
- 除外後のメンバー一覧を照合し、ロック・アーカイブが成功してから終了済みと記録します。
- 保存や除外に失敗した場合は終了済みにせず、Botが再試行します。管理情報はPostgreSQLに保存し、Bot再起動後も継続します。
- 終了済みスレッドへ参加者を招待し直すことはありません。以前のログは運営用に保持します。

既存の固定チャンネル方式は残ります。
固定サポートチャンネルでも非公開スレッドの親チャンネルでも、コマンドは `.supportOpen team_id` です。
親チャンネルと固定サポートチャンネルを同じIDに設定しないでください。

### 権限

| 対象 | 親チャンネルで必要な権限 |
| --- | --- |
| Bot | チャンネルを見る、履歴を読む、非公開スレッドの作成、スレッドの管理、スレッドでメッセージを送信 |
| 運営 | チャンネルを見る、履歴を読む、スレッドの管理、スレッドでメッセージを送信 |
| 参加者 | チャンネルを見る、履歴を読む、スレッドでメッセージを送信 |

参加者にはスレッドの管理権限を与えません。
スレッドの管理または管理者権限を持つ非運営メンバーの招待は拒否します。
親チャンネルが見えるだけでは、招待されていない非公開スレッドは見えません。
通常の「メッセージを送信」と「スレッドでメッセージを送信」は別の権限です。

### ログと検証

ログは `discord_support_threads` テーブルに保存し、参加者向けclarの回答欄には書き込みません。
運営ログイン後、`/admin/support_threads` から各clarの保存ログをJSONで取得できます。
未ログイン・参加者セッションからのアクセスは拒否します。
Discord上でも終了時に参加者を除外するため、終了後は運営だけが参照できます。
参加者が終了前に読んだ内容や保存したコピーの回収はできません。
添付ファイルはDiscordメッセージに含まれるメタデータとURLを保存し、ファイル本体の別ストレージへの複製は行いません。

自動テストでは、作成の重複防止、招待失敗からの再開、ログ取得・DB保存・メンバー除外の失敗、手動追加メンバーの回収、100件を超えるメッセージの取得、運営専用HTTPアクセスを検証します。
実機では、clar投稿だけでは作成されないこと、運営コマンドでの作成、対象メンバーの招待、別チームから見えないこと、終了後の参加者の閲覧拒否、運営のログ閲覧、Bot再起動後の継続を確認します。
