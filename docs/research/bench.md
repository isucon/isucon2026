# supervisor と ISUReal ベンチマーカーの結合要件

記録日: 2026-09-23。
対象は `isucon2026` の `42c0583` と、流用元 `isucon/isucon14-portal` の supervisor（`4c2b99a`）。
初回調査は上記のリビジョンを対象とする。
2026-09-24 のベンチ側実装に合わせ、以下のチェック状態を更新した。
開催日時は確定済みの値を後日設定するため、この文書では仮置きしない。

## 実行確認の結果

ローカルの隔離した Docker 環境で、実 supervisor、Go ポータル、PostgreSQL 18.6、Redis 8.2.9、ISUReal の API と worker を起動した。
今回のベンチは 2 ユーザー、1 サイクルで実行した。
既存の開発環境と登録データには接続していない。

| 条件 | 確認結果 |
|---|---|
| supervisor → dummybench → ポータル | ジョブ取得、途中報告、確定に成功。pass、3 点を保存 |
| 今回のベンチを単独実行 | pass、29 点 |
| 今回のベンチを supervisor から直接実行 | 生 IP に URL スキームがなく、初期化に失敗。終了コード 1 |
| 対象だけ URL に補正して実行 | ベンチの JSON は pass、29 点。ポータルには fail、0 点、終了コード 0 を保存 |
| 検証用アダプターで URL 補正と FD 報告を追加 | ポータルにも pass、29 点、終了コード 0 を保存 |
| 今回のベンチに `--only-post-validation` を渡す | 未対応フラグとして終了コード 2 |

URL 補正だけでは結果が伝わらない原因は、今回の CLI が結果を stdout にしか書かず、supervisor の報告用 FD に送信していないことだった。
検証用アダプターは最終結果だけを変換する一時的なプログラムで、リポジトリには取り込んでいない。
この検証は接続方式を確認するもので、通常の 60 秒走行やランキング更新を含む受け入れ試験は未実施である。
検証用コンテナは撤去済み。

## 2026-09-24 の実装と確認

今回のベンチに `internal/benchrun` を追加し、共有の生成 protobuf を使う FD 報告を組み込んだ。
IP の URL 化、対象ポートの指定、全体タイムアウト、段階ごとの途中報告、最終報告に対応した。
明示的な合計点と加点、減点を送り、supervisor 実行時の stdout は pass と score に限定する。
詳細な結果 JSON は stderr に出す。

同じ隔離環境で、実 supervisor から変更後のベンチを直接起動し、2 ユーザーの通常 60 秒負荷を実行した。
検証用アダプターを使わずに途中報告と結果確定が成功し、ポータル DB に pass、383 点、加点 383、減点 0、終了コード 0 が保存された。
この点数は今回の走行結果であり、性能の基準値ではない。
最終検証指定と全体タイムアウトでも fail、0 点、終了コード 1 の保存を確認した。

`--only-post-validation` は対象へ接続せず、未実装であることを報告して終了する。
専用の検証シナリオは未実装であり、B-6 と A-3 は未完了のままとする。
全体の制限は既定 120 秒、supervisor 側のハードタイムアウトは今回 150 秒で検証した。
本番の時間予算は別途確定する。

`go -C bench test -race ./...`、`go -C bench vet ./...`、`go -C bench build ./...` を実行した。
実 FD を子プロセスへ渡すテスト、公開出力、フレーム長の境界、書き込み失敗、負荷準備失敗、中断時の判定を含む。
実行方法は [ベンチの README](../../bench/README.md) を参照。

## 責務と通信形式

**supervisor** は、ポータルからジョブを取得し、ベンチを子プロセスとして起動し、結果の中継と実行時間の監視を行う。
採点と対象 URL の解決はベンチ側で行う。
配備と認証情報の管理は Ansible などの運用設定で行う。

```text
ポータル ← HTTP + protobuf → supervisor ← パイプ + protobuf ← ベンチ
                                 └─ 起動引数と環境変数 ─────→ ベンチ
```

**ISUXBENCH_REPORT_FD** は、supervisor が作成して子プロセスに引き継ぐパイプの書き込み側 FD 番号を格納する環境変数である。
標準出力の FD 1、標準エラーの FD 2 とは別に使用する。
環境変数だけを手動で設定しても、対応するパイプがなければ動作しない。

1 回の報告は、protobuf のバイト数を表す 2 バイトの unsigned big-endian 整数と、`BenchmarkResult` の protobuf 本体を連続して書き込む。
複数回の報告を同じパイプへ送信できる。
2 バイトで表せる長さの上限は 65,535 バイトであり、65,536 バイト以上は送信前に拒否する必要がある。
流用元 Reporter の上限チェックはこの境界を修正する必要がある。

supervisor は途中報告の `finished` を false にし、`execution` を除去してポータルへ送る。
終了時には最後に受け取った結果へ終了情報とログを追加し、確定 API へ送る。
終了コード 0 だけでは採点結果は伝わらない。

## ベンチ側の実装チェックリスト

- [x] **B-1 結果報告**: `benchrun.Reporter` 相当を取り込み、`ISUXBENCH_REPORT_FD` がある場合に protobuf を送る。単独 CLI 実行との切り替え方を決める。
- [x] **B-2 結果の対応付け**: `pass`、`score`、採点内訳、理由、実装言語、`marked_at` を `BenchmarkResult` に対応付ける。途中報告の時刻を単調に進め、最後の結果を flush してから終了する。
- [x] **B-3 スコアの契約**: 下限 0 を適用した明示的な合計点と `raw/deduction` を送る。現在のスコア下限 0 と、失敗時の 0 点が一致することをテストする。
- [x] **B-4 対象アドレス**: supervisor が追加する `--target <IP>` を競技ポート付き URL に変換する。単独実行の URL 指定も保持し、不正な入力は明示的に失敗させる。
- [ ] **B-5 複数台の情報**: 現状のベンチは `ISUXBENCH_ALL_ADDRESSES` を使用しない。複数台を検証対象とするかを決める。流用元 supervisor は 3 要素を直接参照するため、必要な台数と未設定時の挙動を合わせる。
- [ ] **B-6 最終検証**: `--only-post-validation` を実装する。初期化によるデータ消去や通常負荷を実行するかを別途定義し、通常走行と区別する。
- [x] **B-7 出力の公開範囲**: 運営向けの採点内訳と詳細エラーを stderr に移す。stdout はポータルで選手にも返るため、現在の詳細 JSON をそのまま公開しない。
- [ ] **B-8 終了時の契約**: 正常終了、採点失敗、ベンチ自身の異常で、報告内容と終了コードが整合することを確認する。FD 書き込み失敗を成功扱いしない。

## supervisor 側の実装チェックリスト

- [x] **S-1 流用元の固定**: `supervisor/` に本体と生成 protobuf、Cargo.lock、ライセンスを取り込み、取得元を完全 SHA で固定した。Docker によるテストとビルド、および ISUReal ベンチ同梱イメージの手順は [supervisor/README.md](../../supervisor/README.md) を参照。ベンチの Reporter は `bench/internal/benchrun` を使用する。
- [ ] **S-2 報告の異常系**: 不正 protobuf、長さ境界、途中で閉じた FD、報告なしでの終了をテストする。プロセス終了と FD の読み取りが競合しても最終報告を失わないことを確認する。
- [ ] **S-3 全体の時間制限**: 取り込み版の既定値は150秒に変更済み。本番の実測と確定は未完了。 初期化、事前検証、60 秒負荷、終了処理を含む時間予算を定義し、`HARD_TIMEOUT` に設定する。流用元の既定値70秒では、初期化最大 30 秒と負荷 60 秒だけでも収まらない。
- [ ] **S-4 強制終了**: ハードタイムアウト、SIGTERM、supervisor 自身の異常終了で、ベンチとその子プロセスが残らないことを確認する。ラッパーを採用する場合はプロセスグループを含めて検証する。
- [ ] **S-5 不正な成功の防止**: 途中報告が pass の後で異常終了しても、最終結果が成功として採用されないことをポータル側の判定まで確認する。
- [ ] **S-6 通信障害**: 取り込み版は全 HTTP 要求に15秒の上限を設定済み。 ポーリング、途中報告、確定報告に時間上限と失敗時の扱いを定義する。流用元の途中報告は失敗をログに残すだけなので、再送方針を決める。
- [ ] **S-7 孤児ジョブ回収**: 起動時の `cancel_owned` または別の回収手順を実装する。流用元には API クライアントがあるが、起動時の呼び出しはない。
- [ ] **S-8 所有者の範囲**: AZ 単位の振り分けと、実行プロセス単位の所有者を区別する。同じ `instance_name` の running をまとめて回収する API のため、同一 AZ の正常稼働中のジョブを巻き込まない設計にする。
- [ ] **S-9 ログの秘匿**: 取り込み版では設定とリクエストログの共有トークンおよび handle を除去済み。ログへのアクセス権限と公開範囲の結合確認は未完了。 設定と受領要求のログから共有トークンを除く。ジョブの handle も認証に使うため、出力の要否とログへのアクセス権限を確認する。

## 配備とポータル設定のチェックリスト

- [ ] **D-1 実行機**: supervisor とベンチのバイナリ、必要なランタイム、systemd unit、実行ユーザーを Ansible で配置する。現状の portal 用 Ansible には supervisor 実行機の配備を含まない。
- [ ] **D-2 通信経路**: 実行機からポータルの HTTPS と選手環境の競技ポートに到達できることを確認する。TLS 証明書の検証を有効にする。
- [ ] **D-3 ジョブ情報**: 試験用チーム、対象インスタンス、対象 IP、AZ ID を登録する。3 台分の情報の欠落も検査する。
- [ ] **D-4 秘密情報**: 共有トークンを安全に配布し、再起動後も同じ設定で接続できることを確認する。
- [ ] **D-5 運用**: 自動再起動、ログの保存期限、ディスク使用量、連続失敗、ジョブ滞留の監視を設定する。負荷生成能力と必要な実行機台数を測定する。

環境変数は以下を設定する。
表中の `TEAM_ID` などは、すべて `ISUXPORTAL_SUPERVISOR_` を接頭辞に持つ。

| 変数の末尾 | 設定内容 |
|---|---|
| `ENDPOINT_URL` | ポータルのベース URL。開発環境は `https://portal-dev.isucon.whywrite.it` |
| `TOKEN` | ポータルの `ISUXPORTAL_BENCH_TOKEN` と一致する共有トークン |
| `INSTANCE_NAME` | 現実装ではチームの `availability_zone` と一致する AZ ID。任意のホスト名ではジョブを取得できない |
| `TEAM_ID` | 結合試験では対象チームに限定。制限なしで動かす場合は未設定 |
| `HARD_TIMEOUT` | 全フェーズの時間予算から決めた秒数 |
| `LOG_DIRECTORY` | 実行ユーザーが書き込めるログ保存先 |
| `INTERVAL_AFTER_EMPTY_RECEIVE` | 空のキューを再確認する間隔の秒数 |

## 結合完了の判定

次の項目は検証用アダプターではなく、正式に配備するバイナリと設定で確認する。

- [x] **A-1 通常走行**: enqueue → 受領 → 初期化 → 事前検証 → 60 秒負荷 → 途中報告 → 確定が完了し、ベンチとポータルの pass と score が一致する。
- [ ] **A-2 表示更新**: portal worker の完了処理、best 更新、ランキングとダッシュボードの反映を確認する。
- [ ] **A-3 最終検証**: `post_validation` ジョブが専用モードで動作し、意図しない初期化を行わず、結果を確定する。
- [ ] **A-4 失敗系**: 初期化失敗、事前検証失敗、負荷中の失敗、ベンチ異常、強制終了を区別して保存し、成功スコアとして扱わない。
- [ ] **A-5 障害復旧**: ポータル断、再送、supervisor 再起動、孤児回収を実行し、ジョブが永久に running に残らない。
- [ ] **A-6 複数実行機**: 同一 AZ と異なる AZ でポーリングし、重複実行、振り分け漏れ、他の実行機のジョブ回収が発生しない。
- [ ] **A-7 公開範囲**: 選手画面と API に、共有トークン、ジョブ handle、運営向けの詳細ログが出ない。
- [ ] **A-8 再現性**: ソースのリビジョン、設定、起動コマンド、期待結果を固定した結合試験手順を保存し、再実行できる。
