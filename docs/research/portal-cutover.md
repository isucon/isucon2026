# 旧ポータルからGoポータルへの切替

この文書は、登録済みデータを保持して旧DjangoポータルからGoポータルへ切り替える手順と、移行後のデータの扱いをまとめます。
実施状況は [切替Issue](https://github.com/isucon/isucon2026/issues/44) で管理します。
接続先、リソースID、DNSの値、バックアップ保存先、環境別設定は [privateの切替記録](https://github.com/isucon/isucon2026-private/issues/4) と [private PR](https://github.com/isucon/isucon2026-private/pull/2) を参照してください。
秘密値と生の登録データはGitに保存しません。

## 登録データの変換

実装は [`registrationmigration`](../../portal/internal/registrationmigration/migration.go) と [取り込み後の照合](../../portal/internal/registrationmigration/verify.go) を参照してください。
登録情報の移行と、旧DB全体の復元用バックアップを分けて保全します。

| 対象 | Go側の扱い |
| --- | --- |
| チーム | ID、名前、代表者、辞退状態、失格状態、作成日時、更新日時を保持します。招待チームの `is_guest` は `is_hidden` に変換します。 |
| 所属のあるユーザー | ID、所属、GitHub数値ID、Discord ID、表示名、学生区分、登録情報、同意記録を移します。 |
| 未所属ユーザー | 移行元レコードとして保存します。有効な参加者には自動変換しません。 |
| 登録招待クーポン | 使用日時と対象チームを含む移行元レコードを保存します。旧コードをGoの有効な招待へは変換しません。 |
| AWSとさくらの利用料金クーポン | チームに紐付け、コードをGoのクーポン欄へまとめます。元の各項目も移行元レコードに保持します。 |
| チームへの参加方法 | Go用の招待トークンを新しく生成します。旧チームパスワードや旧登録クーポンのURLは使いません。 |
| セッション、パスワード、OAuthトークン | 復元用バックアップに保持します。Goの認証には使わず、利用者は再ログインします。 |
| アバター | 実体をコピーして照合し、Goから参照するURLへ変換します。 |
| Go固有の参加状態 | `final_participation=true` とします。チームの学生判定は、メンバーが存在し全員学生であることから導出します。 |
| 参加者の作成日時と更新日時 | インポーターは所属チームの日時を使います。旧ユーザーの `date_joined` は復元用バックアップに保持します。 |

旧ポータルの**登録招待クーポン**は、スポンサーなどの招待チーム向けに発行するコードです。
通常の募集期間やチーム数上限を超えてチームを作成でき、使用後は同じコードでそのチームに参加できます。
利用料金のクーポンとは用途が異なります。
移行済みの招待チームとメンバーはGoでも保持されますが、旧登録コードによる追加登録はできません。

問い合わせ、競技サーバー、ジョブ、スコア、envcheck結果などは、登録インポーターの対象外です。
旧側に存在する場合は全件バックアップに加えて、各データをGoの稼働用テーブルへ移す方法を個別に検証してください。
対象が空かどうかは、最終取得時の件数で確認します。

## 最終同期

1. 新側のDB全体を保全し、復元用スナップショットが利用可能になるまで待ちます。新側だけに作成したテストチーム、同意記録、サポートログ、ジョブも対象です。
2. 旧Webの書き込みとDiscord更新cronを停止します。停止方法と復帰方法を記録し、全アプリホストで停止を確認します。ホストを停止する場合もディスクとDBを保持します。
3. 停止後の旧DB全テーブルを整合性のあるトランザクションで取得し、非公開の保存先へ暗号化保存します。全ファイルを読み戻して照合します。
4. 登録移行用スナップショットを生成し、前回の検証済みインポート元と全件比較します。アバターの参照と実体も確認します。
5. 登録差分がなければ、現DBを保持して追加インポートを省略できます。稼働中のGo側でもID、所属、移行元レコード、新側だけのデータの保持を確認します。
6. 差分があれば新旧双方の変更とID衝突を調べ、移行方法を検証します。旧側だけのスナップショットで新DBを置き換えると、新側だけのデータが失われます。

既存インポーターは空のDBへの取り込みを前提とします。
`Verify` は全体の行数も検査するため、新側だけのテストチームなどが追加されたDBでは、そのまま実行しても行数が一致しません。
照合を通すために新側データを削除せず、追加分を区別した確認を行います。

## DNS切替と通常稼働

DNSの変更前に、旧レコードの種別、値、設定TTL、AAAAの有無を保存します。
リゾルバが返す残存TTLと、設定されているTTLを区別してください。
DNSの変更は担当者の判断で行います。

外部DNSからALBへ向ける場合、サブドメインにはCNAME、またはプロバイダーが対応するALIASを使います。
ALBの解決IPを固定Aレコードとして登録しません。
CNAMEを使う場合、同じ名前のAレコードと共存させません。
ALIASではCNAME応答がなくても正常なので、管理API上の転送先とA/AAAAの解決結果を確認します。

権威DNS、外部リゾルバ、通常のHTTPS接続を確認します。
切替後も利用者側に旧レコードのキャッシュが残るため、旧側の書き込み停止を維持します。
切替前の接続先上書きによるHTTPS検証と、公開DNS経由の検証は区別して記録します。

新側への到達を確認してから、Pulumiの `standby=false` と `environment.ISUXPORTAL_ADMIN_ONLY="0"` を適用します。
環境変数全体を置き換えず、既存のOAuth設定などを保持します。
プレビューで対象差分を確認し、無関係なDB変更などを同時に適用しません。
Pulumiが生成した配布設定を使い、ecspressoで各サービスを反映します。
`notifyloop` は公開URLへアクセスするため、DNS切替確認後に起動します。

通常稼働ではポータル2タスク、Workerとnotifyloop各1タスクです。
Botは `enableBot=true` の場合に1タスクで稼働します。
タスクの起動だけでなく、デプロイ完了、ALBヘルス、ログ、公開画面、実OAuth、チーム所属、必要な保存操作を確認します。
envcheckのテンプレート静的検証と、実起動、SSH、結果callbackの確認は別の検証です。

## 切り戻し

切り戻し時は新側を管理者限定にし、`standby=true`、`enableBot=false`、`enableBotInStandby=false` を設定してecspressoで反映します。
`standby` だけでは先行起動中のBotは止まりません。
管理者限定でもchecker認証のenvcheck callbackなどは受け付けるため、全書き込みを止める場合は入口の遮断またはportalタスクの停止も必要です。
新旧DB、ログ、キュー、サポート履歴を保全し、RedisのflushやDB削除は行いません。

新側の変更が保全済みのテストデータだけなら、旧側にそのデータがないことを確認したうえで、保存済みDNS設定へ戻して旧側を再開します。
旧ホストの起動はWebとcronの再開を伴う可能性があるため、新側の書き込みと背景処理を先に止めます。

新側に参加者の業務更新がある場合、または変更範囲が不明な場合は、逆移行の判断が必要です。
Goから旧Djangoへ戻す逆移行ツールは未実装です。
データを失わず復旧できると判断するまでは旧側の受付を再開せず、Go側の修復も検討します。

イメージだけを戻す場合も、現在のDBスキーマとの互換性を確認します。
古いDBへの接続変更やスナップショット復元は、その後の書き込みを失うため、別途差分保全が必要です。
